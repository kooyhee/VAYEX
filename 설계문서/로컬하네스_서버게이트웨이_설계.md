# 로컬 하네스 · 서버 게이트웨이 2평면 설계

> **문서 지위.** 이것은 설계 문서다. 이 문서가 정의한 엔드포인트·정책·원장·스케줄러 가운데 **동작이 확인된 것은 스텁 업스트림을 대상으로 한 `gateway/` 기능 시험(148개 통과) 범위뿐**이며, 실제 공급자·실제 Ollama 모델을 붙인 실행과 독립 보안 재검토는 끝나지 않았다. 그 통과는 "정책 코드가 스텁에서 의도대로 동작한다"는 뜻이고 보안 수용이 아니다. 검증은 13장의 표로만 한다.
>
> **시연 형태.** 심사에 제출되는 것은 사전 녹화 영상이다(0.5). 시연 시점에 서버는 필요하지 않다. **시연의 필수 조건은 랩톱 평면 하나이며, 서버 평면은 시연의 구성 요소가 아니다** — 설계와 부분 구현 상태다(13.0.1). 서버가 만든 이미지·영상은 녹화 전에 생성된 산출물로만 등장하고, 서버에서 찍은 화면을 넣는다면 "사전 촬영 footage"로 라벨한다.

## 0. 문서의 지위, 전제, 장 매핑

### 0.1 왜 이 문장을 먼저 쓰는가

이 프로젝트는 한 번 "임베디드 게이트웨이"를 제품의 구성 요소로 주장했다가 철회했다. 철회 기록은 `40_AI보고서/공학작품경진대회_작품개발보고서_수정본_v2.md:457` 에 남아 있다 — "자체 제작한 런타임도, 자체 게이트웨이도 없으며, 그렇게 주장하지 않는다". 같은 문서 `:72` 는 "별도의 게이트웨이를 자체 제작하지 않았고"라고 적는다.

그 철회의 이유는 게이트웨이라는 발상이 틀렸다는 것이 아니라, **주장이 증거보다 앞섰다**는 것이다. 따라서 이 문서는 게이트웨이를 다시 설계하되 다음 규율을 스스로에게 건다.

- 이 문서는 어떤 코드의 존재도 함의하지 않는다. "설계한다", "정의한다"만 쓴다.
- 게이트웨이가 실제로 서고 그 앞에서 요청이 처리되는 것을 관측하기 전까지, 제품 문서는 게이트웨이를 기능으로 열거하지 않는다.
- 검증되지 않은 것은 **성격에 따라** 표 B(서버 필요 — 서버에서 관측·측정하면 증명된다) 또는 표 C(실제 키 필요 — 제공자 계약·실호출이 있어야 증명된다)로 보낸다. 두 표를 섞지 않는다: 서버 GPU·모델·지연·용량 측정치는 표 B, 제공자 정책·단가·지연은 표 C다. **모든 미검증 항목을 표 C로 보내지 않는다** — 그러면 서버에서 측정 가능한 것이 영원히 미검증으로 남고, 표 B가 존재할 이유가 사라진다. 두 표의 항목 모두 제품 주장에 쓰지 않는다.
- 영상에 나왔다는 사실은 어떤 주장도 승격시키지 않는다(13.0의 다섯 상태).

### 0.3 범위 변경: 서버는 중계자가 아니라 모델 호스트다

초기 구상에서 서버는 요청을 받아 외부 제공자에게 넘기는 중계자였다. 지금은 다르다. 서버 평면은 네 가지를 직접 실행하거나 직접 연결하며, 그중 첫째는 **이미 설치되어 있다**.

1. 서버 자체 GPU의 LLM — Ollama 0.21.0이 `127.0.0.1:11434`에서 OpenAI 호환 표면을 제공한다. 새로 설치할 것이 없다.
2. 이미지 생성 모델 — **없다.** 4장은 설치 대상의 계약을 설계하며, 설치 전까지 이 기능은 존재하지 않는다.
3. 영상 생성 모델 — **없다.** 같은 이유로 4장에 계약만 있다.
4. 외부 프록시 업스트림 — OpenRouter, A6API 등.

그래서 게이트웨이는 **두 종류의 업스트림을 가진 라우터**다: 자체 호스팅 모델과 외부 프록시. 둘 다 같은 OpenAI 호환 표면으로 주소 지정되고, allowlist가 각 모델 ID가 어느 종류인지 기록한다. 이 변경은 2.5, 3.8, 4장, 5장, 6장, 10장에 반영되어 있다.

한 가지를 처음부터 분명히 한다. **Ollama가 있다는 사실과 게이트웨이가 있다는 사실은 다르다.** Ollama는 우리 게이트웨이도 아니고 우리 정책의 집행자도 아니다. 그것은 이 호스트에서 이미 돌고 있는 별개 소프트웨어이며, 우리 설계는 그것을 `server_local` 업스트림 하나로 취급한다.

### 0.5 시연의 형태 — 사전 녹화 영상

심사에 제출되는 것은 **사전에 녹화한 영상**이다. 심사장에서 서버를 가동하지 않는다. 이 사실이 문서의 무게 중심을 변경한다.

| 함의 | 결과 |
| --- | --- |
| 시연 시점의 서버 가용성 | 무관하다. 서버가 꺼져 있어도 영상은 재생된다 |
| 시연 시점의 네트워크 | 무관하다. 터널이 없어도 된다 |
| 시연 시점의 지연 리스크 | 사라진다. 5장의 스왑 지연은 영상에서 문제가 되지 않는다 |
| 무엇이 시연되는가 | **녹화 시점에 랩톱에서 실제로 동작했던 것**만. 녹화 후에 만들어진 것은 영상에 없다 |
| 무엇이 증명되어야 하는가 | 랩톱 평면 전부. 서버 평면은 증명 대상이 아니다 — 시연의 구성 요소가 아니다(13.0.1) |
| 시연의 필수 조건 | 랩톱 한 대. 서버·터널·게이트웨이가 없어도 영상은 성립한다 |
| 서버 평면의 지위 | **설계 + 부분 구현.** 영상은 서버의 실시간 동작에 의존하지 않는다 |
| 서버가 만드는 산출물 | 녹화 전에 생성되어 삽입된다(0.5.2, 4.7). 녹화 중 생성 장면은 넣지 않는다 |

여기서 새 위험이 생긴다. **녹화물은 무엇이든 주장할 수 있다.** 실시간 시연은 실패하면 실패가 보이지만, 영상은 실패를 편집으로 지울 수 있고 없는 동작을 자막으로 만들 수 있다. 영상 기반 시연은 라이브 지연 리스크를 제거하지만, 그 대가로 **내레이션 리스크**를 만든다 — 영상은 화면과 자막과 해설로 무엇이든 말할 수 있고, 반박당하지 않는다. 이 위험을 규율로 막는다.

#### 0.5.1 영상 주장의 증거 기준

**규칙 V-1. 영상에 등장하는 모든 화면은 스크립트로 재현 가능한 실행에서 나온 것이어야 한다.** 그 실행의 명령과 출력은 영상과 함께 보관하며, 영상의 주장은 보고서의 주장과 **동일한 증거 기준**을 통과해야 한다. 영상에 나온 문장이라고 해서 표 A·B·C의 분류를 면제받지 않는다.

구체적으로:

| 요건 | 내용 |
| --- | --- |
| 실행 스크립트 | 영상의 각 장면은 스크립트 파일 하나로 재현된다. 손으로 타이핑한 우연한 성공을 쓰지 않는다 |
| 실행 로그 | 스크립트의 명령과 표준출력·표준에러를 그대로 보관한다. 편집하지 않는다 |
| 테이크 표시 | 실패한 테이크와 성공한 테이크를 모두 남긴다. 실패를 지우는 것은 편집이지 증거 조작은 아니지만, **성공만 남기고 "항상 된다"고 말하면 조작이다** |
| 자막의 출처 | 영상 자막과 **내레이션**의 각 주장은 이 문서의 어느 장에 근거가 있는지 대응시킨다. 대응이 없는 자막·해설은 쓰지 않는다 |
| 내레이션 금지 | 화면에 없는 동작을 말로 보태지 않는다. 해설이 화면보다 앞서면 그 해설은 주장이고, 주장은 표 A·B·C의 증거 기준을 통과해야 한다 |
| 서버 footage 표시 | 화면이 랩톱이 아니라 서버에서 찍힌 것이면 영상에 그 사실을 표시한다. 표시 없는 서버 장면은 랩톱 장면으로 오해된다 |

이 규칙이 없으면 영상은 이 프로젝트가 이미 한 번 실패한 방식(주장이 증거보다 앞섬)을 가장 빠르게 반복하는 통로가 된다.

#### 0.5.2 서버 산출물이 영상에 등장하는 방식

이미지·영상 생성 결과는 영상에 나올 수 있다. 단 **녹화 전에 생성된 산출물**로서만 등장하며, 녹화 중에 실시간으로 생성되지 않는다. 그 이유는 정직성이다 — 모델이 설치되어 있지 않은 상태에서(4.0) "생성하는 장면"을 연출하면 그 장면은 거짓이 된다.

출처 기록 방식은 4.7에 정의한다. 요약하면 각 산출물마다 생성 시각·모델 ID·파라미터·명령을 남기고, 영상에서는 그 기록이 있는 산출물만 쓴다. 이렇게 삽입된 산출물의 상태는 **시연 등장**이 아니라 **사전 생성 산출물**이다(13.0). 영상은 결과만 보여 주고 생성 과정을 보여 주지 않으므로, 그 산출물로 "생성 기능이 시연되었다"고 말하지 않는다.

## 1. 왜 나누는가

### 1.1 로컬 앱이 구조적으로 줄 수 없는 것

로컬 앱의 설정 파일은 **사용자가 소유한 파일**이다. 로컬 앱이 무엇을 금지해도, 그 금지는 사용자가 편집하거나 우회할 수 있는 코드 안에 있다. 이것은 구현 품질의 문제가 아니라 소유권의 문제다.

서버는 그 파일을 소유하지 않는다. 서버가 거부하면 요청은 실제로 일어나지 않는다. 다음 다섯 가지는 이 차이에서만 나온다.

| 얻는 것 | 로컬 앱에서 왜 안 되는가 | 서버에서 왜 되는가 |
| --- | --- | --- |
| 안정적인 프로바이더 경계 | 프로바이더별 분기·재시도·오류 해석이 클라이언트 버전마다 흩어진다. 클라이언트를 수정하면 경계가 바뀐다 | 경계가 한 프로세스에 있고, 클라이언트는 OpenAI 호환 한 가지 표면만 본다 |
| 키 보관 분리 | 클라이언트가 키를 들면 그 키는 사용자 디스크·메모리·백업에 남는다 | 키가 서버에만 있고 클라이언트는 게이트웨이 토큰만 갖는다 |
| 한 곳의 쿼터·비용 회계 | 사용자별 상한을 클라이언트에서 강제할 수 없다. 사용자가 지우면 끝이다 | 원장과 상한이 서버에 있고, 초과 시 업스트림 접촉 전에 거부된다 |
| 서명된 프리셋 배포 | 프리셋이 JSON 파일이면 사용자가 편집한다. "개발자가 고정한 프리셋"이 성립하지 않는다 | 서명 검증을 통과한 것만 적용되고, 실패 시 적용 자체가 거부된다 |
| 무시할 수 없는 라우트 정책 | 클라이언트가 `zdr_cloud`를 선언하고 실제로는 아무 데나 보낼 수 있다 | 게이트웨이가 요청마다 정책을 다시 계산하고, 금지면 업스트림에 닿기 전에 403을 낸다 |

### 1.2 서버가 모델 호스트가 되면서 추가로 얻는 것

- **모델 선택이 우리 것이 된다.** 27B급 모델은 이 랩톱(7.77 GiB 사용 가능)에서 포그라운드 코더로 쓰기 어렵다(0.2의 산술). 서버(31.36 GiB)에서는 가능하다. 노트북에서 어려운 능력이 서버에서 가능해진다는 것이 이 변경의 실질이다. "어떤 양자화로도 불가"라고 쓰지 않는다 — 그 주장은 모든 양자화를 열거해야 성립하고, 이 문서는 하나의 구성을 계산했을 뿐이다(6.1).
- **이미지·영상 생성이 설계 범위에 들어온다.** 노트북 8 GB에서는 논외인 작업군이다. 서버 GPU에서만 성립한다. **단, 이 글을 쓰는 시점에 그 모델들은 설치되어 있지 않다**(4.0). "생성한다"가 아니라 "생성하도록 설계한다"다.
- **프록시의 정책을 우리가 판정할 수 있다.** OpenRouter와 A6API를 클라이언트가 직접 호출하면 클라이언트마다 키·정책·과금이 흩어진다. 게이트웨이를 거치면 "이 모델은 어느 라우트에서 허용되는가"를 한 곳에서 정한다.
- **자체 호스팅 모델은 제3자 노출이 구조적으로 0이다.** 프롬프트가 우리 호스트를 떠나지 않는다. 단, 이는 "제3자에게 안 간다"는 뜻이고 "아무 데도 안 간다"는 뜻이 아니다(1.3).

### 1.3 비용과 의무 — 정직한 쪽

서버를 두는 순간 다음이 따라온다.

1. **프롬프트가 우리 서버를 통과한다.** 자체 호스팅 모델이면 제3자에게 가지 않지만, 사용자의 노트북을 떠나 우리가 운영하는 기계에 도착한다. 그 기계의 접근 제어·보존 정책·삭제 절차·사고 통지 절차는 우리 책임이 된다.
2. **프록시 라우트에서는 프롬프트가 제3자에게 간다.** OpenRouter와 A6API는 우리 서버가 아니라 그들의 인프라다. 게이트웨이는 어느 업스트림으로 보냈는지를 응답에 남겨야 하고, 사용자는 그 사실을 알 수 있어야 한다.
3. **자격증명이 우리 서버를 통과하거나 우리 서버에 상주한다.** 모드 (b)의 BYOK에서는 사용자의 제공자 키가 게이트웨이에 도착해 복호화된다. 이때 "우리는 키를 모른다"고 주장할 수 없다(8.3).
4. **"무료"와 "완전 오프라인"이 제품 전체에 대해 성립하지 않는다.** 두 주장은 이제 랩톱 평면에만 적용된다. 클라우드 라우트는 돈이 들고(우리 GPU 전력이든 프록시 종량이든) 네트워크가 필요하다.
5. **서버가 죽으면 제품의 절반이 사라진다.** 로컬 평면은 계속 돌지만, 서버 LLM·이미지·영상은 없다.
6. **GPU가 유휴여도 비용이 나간다.** 프록시는 쓴 만큼 내지만 자체 호스팅 GPU는 가동하는 시간만큼 나간다. 이 비대칭은 5장(스케줄링)과 14장(운영)의 설계 압력이다.
7. **공개 엔드포인트가 없다.** 서버의 공인 주소는 라우터의 WAN 주소이고, 전달되는 포트는 SSH 두 개와 라우터 관리 페이지뿐이다. 그래서 모든 클라이언트 경로는 **SSH 로컬 포워드 터널**이다(2.7). 이 사실은 제품 형태를 바꾼다: "웹에 배포된 API"가 아니라 "계정을 가진 사람이 여는 통로"다.
8. **기계를 다른 사람과 공유한다.** 홈 계정이 9개이고, 감사 중에도 두 사람이 세션을 돌리고 있었다. 우리 게이트웨이는 그 기계의 유일한 사용자가 아니며, GPU·디스크·회선을 남과 나눈다. 우리 정책은 우리 프로세스가 낸 요청만 통제한다. 다른 사용자의 직접 실행은 통제하지 못한다(5.8). **그들은 우리에게 예고하지 않고 모델을 적재한다** — 그래서 우리 중재는 "지금 비어 있다"를 전제할 수 없다(5.9.4).
9. **우리에게 root가 없다.** `sungjung`은 일반 사용자이고 sudo가 없다. 따라서 인증서 자동 갱신, 시스템 서비스 등록, 커널 모듈 교체, 마운트 같은 운영 작업을 우리가 할 수 없다. 이것은 기능 목록을 줄인다(14.1).
10. **서버는 시연 시점에 필요 없다.** 영상이 사전 녹화이므로(0.5), 서버 평면의 가치는 "심사장에서 보여 주는 것"이 아니라 "녹화 시점에 실제로 돌았다는 기록"이다. 이것은 서버 평면을 **설계 + 부분 구현**으로 재분류한다 — 라이브 시연의 구성 요소가 아니므로, 서버 평면의 미완성이 시연을 막지 않는다. 반대로 그 재분류는 랩톱 평면을 시연의 **유일한 필수 조건**으로 만든다. 서버 평면에서 미완성인 부분을 랩톱 화면으로 대신 채우는 것은 금지다(12.6).

이 열 줄을 제품 문서에 쓰지 않으면서 게이트웨이를 자랑하는 것은, 앞서 철회한 주장과 같은 종류의 실수다.

### 1.4 "무료·완전 오프라인" 주장의 새 범위

| 주장 | 랩톱 평면 | 서버 평면 |
| --- | --- | --- |
| 비용 0 | 성립. 전력 외 추가 과금 없음 | 성립하지 않음 |
| 완전 오프라인 | 성립. 네트워크 없이 포그라운드 코딩 가능 | 성립하지 않음. 네트워크가 전제 |
| 데이터가 기기를 떠나지 않음 | 성립 | 성립하지 않음 |
| 제3자에게 가지 않음 | 성립 | 자체 호스팅 모델에서만 성립 |

### 2.1 랩톱 평면

| 구분 | 내용 |

| 경계 통과 | GW-1 요청/응답(터널), 제어 평면 manifest 조회 |

핵심 성질: 랩톱 평면은 **서버가 존재하지 않는 세계에서도 완결**된다. 12장이 이 성질을 항목별로 나눈다.

#### 2.1.1 메모리 계층 — SQLite FTS5 네임스페이스 격리

랩톱 평면에는 대화 세션과 별개로 **어휘 기반 메모리 계층**(`40_AI보고서/engine/memory_layer.py`)이 있다. 세션 이력은 메모리의 대체물이 아니다. 세션은 지금 열린 대화이고, 메모리는 세션을 넘어 유지되는 검색 가능한 기록이다.

| 항목 | 값 |
| --- | --- |
| 엔진 | SQLite FTS5 (전문 검색 확장) |
| 네임스페이스 격리 | **세션/네임스페이스 단위 전용 FTS5 가상 테이블 분리 (`fts_indexes` 레지스트리)** |
| 공용 색인 금지 | 공유 단일 `chunks_fts`는 BM25 어휘 통계와 문서 순위가 네임스페이스 간 혼입되므로 배제 |
| 저장 위치 | 랩톱 로컬 파일(프로젝트 로컬 `.sqlite`/`.db`) |
| 검색 방식 | 어휘 검색(keyword/BM25 계열, `sanitize_fts5_query` 살균 적용). 임베딩·벡터 검색이 아니다 |
| 네트워크 | **쓰지 않는다.** 인덱스 구축·질의 모두 로컬 파일 I/O |
| 서버 의존 | **없다.** 게이트웨이·터널과 무관하게 동작한다 |
| 쓰기 시점 | 세션 진행 중 또는 세션 종료 후 로컬 배치 |
| 읽기 시점 | 새 세션의 컨텍스트 구성, 사용자 질의에 대한 과거 근거 검색 |

세 가지를 명확히 한다.

1. **네임스페이스 격리가 구조적으로 보장된다.** FTS5 색인은 프로젝트/세션 네임스페이스별로 전용 가상 테이블(`chunks_fts_<hash>`)로 분리 생성된다. 하나의 공용 FTS5 테이블에 여러 사용자의 프로젝트 문서를 섞어 넣으면 BM25 문서 빈도(IDF) 통계가 오염되어 검색 순위가 왜곡되고 다른 세션의 메모리가 섞여 인출될 위험이 있다. 따라서 레거시 공용 색인은 즉시 제거(`_drop_legacy_shared_index`)하고 네임스페이스별 격리 색인만 운용한다.
2. **네트워크가 없다는 것은 주장이 아니라 구조다.** FTS5는 파일 기반 인덱스이므로 서버 왕복이 없다. 터널이 끊겨도 메모리 조회는 계속된다.
3. **어휘 검색이지 의미 검색이 아니다.** 동의어·의역·언어 간 매칭은 보장하지 않는다. 이것을 "의미 기억"이라고 부르면 과장이다. 서버의 `qwen3-embedding:0.6b`(A-2)는 별개의 자원이고, 랩톱 메모리는 그것에 의존하지 않는다.
4. **메모리 인덱스는 경계를 넘지 않는다.** B-2(세션 비전이)의 연장이다. 게이트웨이는 이 인덱스를 받지 않고, 받을 필요도 없다. 검색된 내용이 프롬프트의 일부로 클라우드로 갈 때는 사용자가 그 요청을 보낸 것이므로 보통의 프롬프트와 같은 규칙을 따른다(10장).

메모리 계층이 없으면 세션이 끝날 때 사용자가 넣은 근거가 사라진다. 그것이 이 층을 2장의 실행 구성 요소로 올리는 이유다 — 부속 기능이 아니라 평면의 구성 요소다.

#### 2.1.2 로컬 GUI와 의사결정 모델 계층 (oh-my-pi-gui 영감)

랩톱 평면의 사용자 경험과 하네스 제어는 과거의 무거운 독점 DSH 의존성 대신 **oh-my-pi 및 오픈소스 생태계 GUI(`https://nornzach.github.io/oh-my-pi-gui/`, `github.com/{unkeyn,nornzach}/oh-my-pi-gui`)에 영감을 받은 경량 웹 인터페이스**(`40_AI보고서/app/`)로 구현 및 연계된다.

- **GUI 아키텍처:** Node.js/Bun 기반의 정적 HTTP 서빙 + WebSocket(`/ws`) + omp stdio NDJSON 브리지 구조로, 하네스의 TUI 제어 프로토콜을 브라우저 UI로 시각화한다.
- **턴별 동적 조정 모델 (TurnPlan)의 지위 (설계 단계):**
  - 매 턴 실행 직전, 경량 결정 모델이 세션 상태와 기계 프로필을 검토하여 `TurnPlan`(모델 ID, 실행 트랙, 허용 도구/스킬 등)을 추천하도록 설계되었다(`40_AI보고서/설계문서/결정모델_동적조정_설계.md`).
  - **하드 정책 게이트의 권위 강제 (설계 목표):** 결정 모델이 내놓는 `TurnPlan`은 어디까지나 "조언(advisory)"에 불과하도록 설계되었다. 최종 승인 권한은 결정론적 하드 정책 게이트(`DeterministicDAGOrchestrator`, `validate_turn_plan`)에 둔다. 단, **현재 코드에는 `TurnPlan` 계열 프리미티브만 존재하고, 결정 HTTP 경로·런타임 연결·턴 원장·핀 고정은 통합되어 있지 않다.** 즉 "게이트가 실제로 모든 턴을 강제한다"는 문장은 아직 성립하지 않는다. 또한 이 계층은 쿼터 원장과 별개이며, 쿼터 원장을 턴 원장으로 부르지 않는다.
  - **상태의 솔직한 표기:** 이 동적 결정 모델(`TurnPlan`, `turn_router`, `turn_validator`) 계층은 현재 **부분 구현 + 설계** 상태이며, 코드로 통합·검증되기 전까지는 "구현 완료"로 주장하지 않는다. 시스템 문서에서는 이를 "인터페이스 정의 및 부분 구현 단계"로 엄격히 구분한다.

### 2.2 서버 평면

| 구분 | 내용 |
| --- | --- |
| 실행되는 것 | 게이트웨이 프로세스(부분 구현). **현재 코드가 실제로 하는 일은 요청 검증(자체 Bearer·identity), 자체 라우트 판정, 업스트림 전달, `/api/ps` 관측 수준이며, 쿼터 원장 강제·GPU 중재·생성 작업 큐·manifest 배포는 설계 상태다**(13.0.2). 업스트림으로서 Ollama 0.21.0(`127.0.0.1:11434`)과 외부 프록시(OpenRouter, A6API 등). 이미지·영상 모델은 설치 후에만 실행된다 |
| 보유 상태 | 사용자·토큰·쿼터 원장, 업스트림 자격증명(모드 a: 팀 키 / 모드 b: 암호화된 사용자 키), 생성 작업 상태와 산출물, GPU 상주·중재 상태, 업스트림 메타데이터(allowlist), 폐기(revocation) 목록. **프롬프트 본문은 기본 보관하지 않는다**(8.3) |
| 절대 하지 않는 것 | (1) 정책이 금지한 요청을 클라이언트가 원한다는 이유로 수락하지 않는다. (2) 본문·키를 로그에 남기지 않는다. (3) **어떤 경우에도 한 요청을 두 번째 업스트림으로 보내지 않는다.** 선택된 업스트림의 실패는 그 요청의 실패다 — 폴백 필드도, 예외 조항도, `fallback_used` 표시도 두지 않는다(2.6, 10.5). (4) 사용량 미상인 요청을 0으로 기록하지 않는다. (5) 랩톱의 존재를 전제로 동작하지 않는다. (6) **다른 사용자의 프로세스를 죽이거나 그들의 GPU 점유를 되돌린다고 주장하지 않는다** — 우리는 우리가 낸 작업만 중재한다(5.8). (7) root 권한이 필요한 운영을 전제하지 않는다 |
| 경계 통과 | GW-1 응답, 원장 갱신, 생성 작업 상태, manifest |
| 전제 조건 | 이 평면은 **터널이 열려 있을 때만** 클라이언트에게 도달한다. 터널은 서버가 아니라 클라이언트가 연다. 게이트웨이는 터널의 존재를 알 수 없고, 알 필요도 없다(2.7) |

### 2.3 경계는 하나다: GW-1

두 평면 사이의 모든 트래픽은 **하나의 계약**을 쓴다. 이름을 `GW-1`로 고정한다.

- 하나의 계약, 두 네임스페이스: 데이터 평면 `/v1/*`, 제어 평면 `/ctl/v1/*`.
- 하나의 인증: `Authorization: Bearer <token>`.
- 하나의 오류 봉투: OpenAI 형식 `{"error":{"message","type","code","param"}}` + 게이트웨이 코드.
- 하나의 버전 헤더: `X-GW-Contract: gw1`. 서버는 N-1 계약까지 수용한다(`P_CONTRACT_SUPPORT_DEPTH`).
- 하나의 주소: **클라이언트는 게이트웨이를 `http://127.0.0.1:<로컬 포트>`로 본다.** 이 루프백 주소는 SSH 로컬 포워드 터널의 클라이언트 쪽 끝이다(2.7). 서버 쪽에서 게이트웨이는 `127.0.0.1:<게이트웨이 포트>`에만 바인딩한다.

전송 규칙을 정확히 쓴다. 이전 판의 "HTTPS만"은 **이 서버에서 성립하지 않는다.** 공인 인터페이스에 443이 열려 있지 않고, 인증서를 발급·갱신할 root도 없다. 따라서 구간별로 나눠 적는다.

| 구간 | 전송 | 암호화 주체 |
| --- | --- | --- |
| 랩톱 앱 ↔ 랩톱의 ssh 클라이언트 | 평문 HTTP, `127.0.0.1` | 없음(같은 기계의 루프백) |
| 랩톱 ssh ↔ 서버 sshd | SSH | SSH 세션 암호 |
| 서버 sshd ↔ 게이트웨이 | 평문 HTTP, `127.0.0.1` | 없음(같은 기계의 루프백) |

즉 전송 보호는 **SSH가 담당**하며, 게이트웨이는 TLS를 종단하지 않는다. `P_REQUIRE_LOOPBACK_BIND`가 true이면 게이트웨이는 루프백이 아닌 주소에 바인딩하려 할 때 기동을 거부한다. 이 거부가 없으면 실수로 `0.0.0.0`에 바인딩되어 같은 서브넷의 다른 사용자에게 그대로 노출된다.

경계 계약의 불변식 여섯 개:

| ID | 불변식 | 깨졌을 때 |
| --- | --- | --- |
| B-1 | 랩톱과 서버 사이의 모든 트래픽은 GW-1을 쓰고 **터널을 통해서만** 지난다. stdio NDJSON은 랩톱 내부이므로 경계가 아니다 | 계약 밖 채널이 생기면 정책·쿼터·감사가 우회된다 |
| B-2 | 대화 세션과 **FTS5 메모리 인덱스**는 랩톱 소유다. 게이트웨이는 요청 단위로 상태가 없고 세션·인덱스를 저장하지 않는다 | 서버가 세션을 들면 보존·삭제 의무가 대화 전체로 확대되고, 메모리 인덱스를 들면 랩톱의 오프라인 성질이 서버 의존으로 바뀐다 |
| B-3 | 서버 비밀(업스트림 키)은 클라이언트로 내려가지 않는다. 클라이언트 비밀(모드 b 키)은 서버 저장 시 암호화된다 | 한 번 내려간 키는 회수할 수 없다 |
| B-4 | 클라이언트는 서버 정책을 느슨하게 만들 수 없다. 더 엄격하게 만드는 것만 가능하다 | 정책이 클라이언트 설정 파일로 격하된다 |
| B-5 | 서버 실패는 로컬 평면의 기능을 바꾸지 않는다 | 제품의 절반이 원격 의존이 된다 |
| B-6 | 게이트웨이는 루프백에만 바인딩한다. 도달 가능성은 터널이 만든다. 게이트웨이는 터널의 존재를 전제하지 않는다 | 게이트웨이가 스스로를 공개 서비스로 착각하면 인증서·방화벽·노출 면적이 전부 따라온다 |

### 2.4 넘지 않는 것

경계를 넘는 것은 **요청 한 건**과 **정책·카탈로그 스냅샷**뿐이다. 넘지 않는 것: 파일 시스템, 셸, 세션 이력, **FTS5 메모리 인덱스**, 원시 GPU 접근과 제어(장치 핸들, 온도·전력·사용률 원시 판독, VRAM 직접 예약, 타 프로세스 제어), 모델 파일, 사용자 디스크. 그래서 "서버가 내 파일을 본다"는 서술은 이 설계에서 사실이 아니다. 서버가 보는 것은 요청 본문이고, 그 본문에는 사용자가 넣은 코드 조각이 들어 있을 수 있다 — 이 구분을 흐리지 않는다.

**문서화된 상태 메타데이터는 예외적으로 넘는다.** `X-GW-GPU-State`, `X-GW-Queue-Position`, `gw.gpu.external_occupancy` 같은 **계약에 정의된 상태 값**은 경계를 넘는다. 그것은 GPU에 대한 접근이 아니라 이 요청이 얼마나 기다릴지에 대한 답이다. 원시 판독과 제어를 금지하는 것과 상태를 알려 주는 것은 다르며, 이 둘을 구분하지 않으면 클라이언트가 대기 이유를 알 수 없게 된다(5.5).

### 2.5 업스트림 분류

세 클래스다. 모든 모델 ID는 정확히 하나의 업스트림 레코드로 해석된다.

| 클래스 | 운영 주체 | 무엇인가 | 인증 | 실재하는 예 |
| --- | --- | --- | --- | --- |
| `server_local` | 우리(호스트) | 서버 GPU에 상주하는 모델을 OpenAI 호환으로 서빙 | 내부 전용(게이트웨이 → 호스트 루프백) | **Ollama 0.21.0 `127.0.0.1:11434`** (설치·가동 확인). 이미지·영상 모델은 **미설치** |
| `proxy` | 제3자(중계) | 여러 제공자를 중계하는 프록시 엔드포인트 | 제공자별 키 | OpenRouter, A6API |
| `direct` | 제3자(원 제공자) | 제공자 자신의 엔드포인트를 직접 호출 | 제공자별 키 | 제공자 자체 API |

`server_local`의 실체를 정확히 적는다. 그것은 우리가 새로 배포한 추론 스택이 아니라 **이미 돌고 있는 Ollama**다. 게이트웨이가 그 앞에 서서 allowlist·정책·쿼터를 씌우는 것이 이 설계의 몫이고, 모델 적재와 추론 자체는 Ollama의 몫이다. 이 구분을 지키지 않으면 "우리가 추론 서버를 만들었다"는, 앞서 철회한 종류의 주장이 된다.

업스트림 레코드는 다음 필드를 갖는다. 전부 설계 필드이며 값은 릴리스 카탈로그가 확정한다.

```json
{
  "upstream_id": "<string, 안정 식별자>",
  "class": "server_local | proxy | direct",
  "family": "chat | image | video",
  "base_url": "<string>",
  "auth_mode": "none | bearer | header_key",
  "model_ids": ["<카탈로그 모델 ID와 동일 문자열>"],
  "privacy": {
    "zero_data_retention": true,
    "training_opt_out": true,
    "retention_evidence": "<근거 포인터 또는 null>"
  },
  "cost": {
    "currency": "<ISO 4217>",
    "input_per_million": 0,
    "output_per_million": 0,
    "cache_read_per_million": 0,
    "image_unit": 0,
    "video_second": 0
  },
  "limits": { "max_context": 0, "max_output": 0, "rate": "<string>" },
  "residency": {
    "gpu_family": "<string|null>",
    "arbiter_group": "llm | image | video",
    "peak_vram_gib": 0,
    "vram_measured": "measured | estimated | unknown"
  }
}
```

규칙 다섯 개.

1. `class`는 형식적 표기가 아니다. `server_local`은 데이터가 우리 호스트를 떠나지 않는다는 뜻이고, `proxy`·`direct`는 떠난다는 뜻이다. `server_local`이라도 **랩톱은 떠난다**(1.3).
2. `zero_data_retention`·`training_opt_out`은 **업스트림 단위가 아니라 모델 단위**로 기록한다. 같은 프록시가 모델에 따라 다른 보존 정책을 갖기 때문이다.
3. `retention_evidence`가 `null`이면 그 모델은 `zdr_cloud`에서 **기본 제외**한다. 근거 없는 ZDR 표시를 신뢰하지 않는다(10.3).
4. `cost`의 0은 "무료"가 아니라 "미확정"일 수 있다. 원장은 0과 미확정을 구분해 기록한다(9.5).
5. `arbiter_group`은 GPU 중재 단위다. 같은 그룹의 모델들은 동시에 상주할 수 있지만(Ollama가 알아서 관리한다), 서로 다른 그룹은 중재자가 순차화한다(5.8). `vram_measured`가 `unknown`인 모델은 중재자가 **보수적으로** 취급한다 — 여유가 있다고 가정하지 않는다.

### 2.6 모델 ID 해석 규칙

- allowlist는 모델 ID 하나를 업스트림 하나로 해석한다. **1:1**이다. 예외는 없다.
- 같은 모델 ID가 두 업스트림에 나타나면 manifest가 무효다(fail closed). "첫 번째 것을 쓴다"는 규칙을 두지 않는다.
- **폴백 체인은 없다.** 업스트림 레코드에 폴백 필드를 두지 않으며, 게이트웨이는 선택된 업스트림이 실패하면 **그 요청을 실패로 끝낸다.** 다른 업스트림으로 대신 보내지 않는다.
- 왜 예외를 두지 않는가. "정책 조건을 통과하는 폴백"이라도 폴백은 폴백이다. 게이트웨이가 같은 프롬프트를 다른 곳으로 보내는 순간, 사용자가 고른 모델·업스트림·클래스가 바뀌고 그 사실은 응답이 도착한 뒤에야 드러난다. `fallback_used`를 표시하는 것으로는 부족하다 — 표시는 사후 통보이고, 사용자는 사전에 선택하지 않았다.
- 회복 탄력성이 필요하면 **클라이언트가 다른 모델 ID를 명시적으로 고른다.** 그것은 대체가 아니라 선택이며, 라우트·allowlist·쿼터 판정을 처음부터 다시 거친다. 게이트웨이가 대신 골라 주는 경로는 만들지 않는다.
- 이 규칙은 `local_only`의 "조용한 대체 금지"(12.4)와 같은 원리다. 경로를 바꾸는 결정은 사용자에게 있어야 한다.

### 2.7 경계의 전송: 터널이 유일한 길이다

#### 2.7.1 측정된 도달성

| 사실 | 값 | 귀결 |
| --- | --- | --- |
| 공인 주소 | `220.68.175.38`은 **라우터의 WAN 주소**이고 호스트의 인터페이스가 아니다 | 이 주소로 호스트에 직접 닿는 경로는 없다 |
| 호스트 주소 | `192.168.0.21` (NAT 뒤) | 랩톱에서 직접 라우팅되지 않는다 |
| 포워딩된 포트 | `2025`(이 상자의 sshd), `2024`(다른 sshd), `80`(라우터 관리 페이지) | 모델·게이트웨이 포트는 하나도 열려 있지 않다 |
| 스윕 결과 | 36포트 스윕에서 `22, 443, 3000, 7860, 8000, 8080, 8888, 11434, 9090, 1111` 및 나머지 후보 전부 closed 또는 filtered | 관측 시점 기준 `http://220.68.175.38:8000` 형태의 직접 호출은 성립하지 않는다. 라우터 설정이 바뀌면 달라질 수 있으므로 이 설계는 공인 접속을 전제하지 않는다 |
| 역방향 게시 | `GatewayPorts no` | 서버가 스스로 포트를 열어 바깥에 게시할 수 없다 |
| Tailscale | 노드 `100.70.58.53`으로 가입되어 있다 | 대안 경로가 존재한다(2.7.5) |

따라서 **클라이언트에서 게이트웨이로 가는 모든 경로는 SSH 로컬 포워드 터널이거나 Tailscale이다.** 제3의 경로는 이 서버에 없다. 사용자 노트북이 `http://220.68.175.38:8000`을 호출하는 설계는 존재할 수 없다.

#### 2.7.2 기본 경로: SSH direct-tcpip 터널 (게이트웨이 전용 노출)

문서화하는 기본값은 **비밀번호 인증만으로 되는 SSH direct-tcpip 로컬 포워드 경로**다. Tailscale은 계정이 필요하므로 기본값이 될 수 없다(2.7.5).

**터널의 엄격한 포워딩 원칙:**
SSH direct-tcpip 포워드는 **오직 게이트웨이 서비스 포트 하나만 클라이언트에 노출**해야 한다. 예시 게이트웨이(출하 예제 구성)는 `8000`에서 수신하고, 일반 기본값·스텁 구성은 `8787`을 쓴다. 두 값은 서로 다른 설정이며, 문서의 예시 명령은 출하 예제 구성의 `8000`을 기준으로 적는다.
- **업스트림 직접 노출 금지:** Ollama(`127.0.0.1:11434`)나 이미지/영상 추론 백엔드 포트를 클라이언트 쪽으로 직접 포워딩(`ssh -L 11434:127.0.0.1:11434`)하는 행위는 **절대 금지**된다.
- **이유:** 업스트림을 직접 포워딩하면 클라이언트가 게이트웨이의 allowlist·정책 판정·쿼터 원장·인증·로그 리댁션을 완전히 우회하여 백엔드를 호출할 수 있게 되기 때문이다. 게이트웨이가 루프백에만 격리되어 존재하는 유일한 관문이어야 한다. 이 원칙은 **현재 코드가 강제하는 범위와 별개로** 문서의 기본값이다(게이트웨이의 실제 강제 범위는 13.0.2에 적는다).

랩톱에서 여는 명령의 형태는 다음과 같다. 로컬 포트는 설계 파라미터 `P_TUNNEL_LOCAL_PORT`이며 아래 값은 예시다. 원격 포트 `8000`은 출하 예제 게이트웨이의 수신 포트다.

```
ssh -N -L 127.0.0.1:4318:127.0.0.1:8000 sungjung@220.68.175.38 -p 2025
```

| 요소 | 값 | 이유 |
| --- | --- | --- |
| 로컬 바인드 주소 | `127.0.0.1` | `0.0.0.0`이나 `*`로 열면 같은 카페 Wi-Fi의 다른 기기가 사용자의 인증된 터널을 그대로 쓸 수 있다. 이것은 편의가 아니라 사고다 |
| 로컬 포트 | `P_TUNNEL_LOCAL_PORT` (예시 4318) | `40_AI보고서/app/`이 4317을 이미 쓰므로 충돌을 피한다 |
| 원격 끝 | `127.0.0.1:8000` | 출하 예제 게이트웨이의 수신 포트. 게이트웨이가 루프백에만 바인딩하므로 원격 끝도 루프백이어야 한다 |
| 원격 포트(스텁·일반 기본값) | `127.0.0.1:8787` | 스텁 및 일반 기본 구성의 수신 포트. **출하 예제와 다른 설정이므로 두 값을 섞어 쓰지 않는다** |
| 서버 포트 | `2025` | 유일하게 열린 sshd |
| 인증 | SSH 비밀번호 또는 SSH 키 | 계정 발급만 받으면 되는 경로 |

랩톱 하네스는 이 터널의 로컬 끝을 가리킨다. **하네스가 보는 주소는 원격 서버가 아니라 자체 기계의 루프백이다.**

```yaml
providers:
  campus-gateway:
    baseUrl: "http://127.0.0.1:4318/v1"
    api: openai-completions
    auth: apiKey
    apiKey: "<GW_TOKEN>"
```

이 구성의 성질 세 가지.

1. `baseUrl`이 `http://`인 것은 결함이 아니다. 그 구간은 같은 기계의 루프백이고, 실제 구간 보호는 SSH가 한다(2.3).
2. 게이트웨이 입장에서 요청은 sshd가 전달한 로컬 연결로 보인다. 게이트웨이는 **그 요청이 터널에서 왔는지 같은 호스트의 프로세스에서 왔는지 구분할 수 없다.** 따라서 "터널 전용"을 게이트웨이가 강제한다고 주장하지 않는다. 강제할 수 있는 것은 루프백 바인딩(B-6)뿐이다.
3. 터널은 클라이언트마다 하나다. 동시 포워드 수 상한은 sshd 설정에 달려 있고 이번 감사에서 측정하지 않았다 — 사용자 수에 비례해 늘어나는 미확인 항목이다(부록 B).

#### 2.7.3 터널이 스트림 도중 끊기면

이것은 이 배포 형태에서 **가장 자주 일어날 장애**이며, 답을 고정한다.

| 단계 | 무슨 일이 일어나는가 |
| --- | --- |
| SSH 세션 종료 | 랩톱 쪽 로컬 소켓이 닫힌다 |
| 클라이언트가 보는 것 | SSE 스트림이 `[DONE]` 없이 끝난다. 3.4의 규칙에 따라 **완료된 응답이 아니다** |
| 클라이언트 표시 | 부분 응답은 유지하되 "중단됨"으로 표시한다. 완료로 승격하지 않는다 |
| 게이트웨이가 보는 것 | 업스트림 응답을 쓰려는 순간 쓰기 실패. 그 시점에 업스트림 연결을 닫는다 |
| 원장 | 그때까지 업스트림이 보고한 토큰이 있으면 `partial`, 없으면 `unknown`. **0으로 기록하지 않는다**(9.5) |
| 자동 재시도 | 금지. 터널 단절은 요청 실패가 아니라 전송 실패이며, 재시도하면 같은 프롬프트를 두 번 과금한다 |
| 사용자 선택 | 재시도 버튼. 재시도는 새 요청이고 `X-GW-Request-Id`도 새로 발급된다 |

영상 작업은 예외적으로 **끊겨도 살아남는다.** 작업은 서버 측 상태이므로, 터널이 끊겨도 `running`은 계속되고 클라이언트는 재접속 후 `GET /v1/videos/{job_id}`로 재부착한다. 이 성질이 비동기 계약을 정당화하는 두 번째 이유다(4.1).

터널 유지를 위한 파라미터를 둔다. `P_SSH_ALIVE_INTERVAL_S`와 `P_SSH_ALIVE_COUNT_MAX`로 클라이언트가 죽은 터널을 조기에 감지하고, 감지 후 재연결은 지수 백오프로 `P_TUNNEL_RECONNECT_MAX_S`까지 물러난다. 이 값들이 없으면 반쯤 죽은 터널이 살아 있는 것처럼 보여, 사용자는 응답을 기다리다 아무것도 못 받는다.

#### 2.7.4 터널이 없을 때의 제품 상태

랩톱이 터널을 열지 않았거나 터널이 끊긴 동안이 **이 설계의 기본 상태**다. 서버는 살아 있지만 도달 불가이고, 클라이언트는 그것을 구분할 수 없다.

| 상태 | 클라이언트 표시 | 로컬 평면 |
| --- | --- | --- |
| 터널 미개설 | "서버 미연결" | 정상 |
| 터널 개설·게이트웨이 미기동 | "서버 연결 실패(게이트웨이 없음)" | 정상 |
| 터널 개설·게이트웨이 기동 | 정상 | 정상 |

첫 두 줄을 구분해 표시하는 이유: 사용자가 SSH는 붙었는데 게이트웨이가 없다는 사실을 알아야, 다음 행동(운영자에게 문의)이 정해진다.

#### 2.7.5 Tailscale은 대안이지 요구가 아니다

| 항목 | SSH 터널 (기본) | Tailscale (대안) |
| --- | --- | --- |
| 전제 | 계정 발급 + 비밀번호 또는 SSH 키 | **Tailscale 계정** + 클라이언트 설치 + 테넌트 승인 |
| 주소 | `http://127.0.0.1:<로컬 포트>` | `http://100.70.58.53:<게이트웨이 포트>` |
| 게이트웨이 바인딩 | 루프백만 | **루프백만으로는 부족하다.** tailnet 인터페이스에 바인딩해야 한다 |
| B-6과의 관계 | 그대로 성립 | 완화가 필요하다(아래) |
| 서버 측 추가 권한 | 없음 | 없음(노드는 이미 가입됨) |
| 비밀번호만 가진 사용자 | 가능 | **불가** |

판정: **기본값은 SSH 터널이다.** Tailscale은 이미 가입된 노드가 있다는 이유로 편의상 쓸 수 있지만, 계정이라는 추가 요건을 사용자에게 요구하므로 문서의 기본 경로가 될 수 없다. "비밀번호만으로 되는 길"을 지우고 계정을 전제하는 순간, 그 문서는 이 환경의 절반에게 틀린 문서가 된다.

Tailscale 경로를 쓰려면 설계상 결정이 하나 필요하다. 게이트웨이는 루프백에만 바인딩하므로(B-6), tailnet 주소로 접속하려면 tailnet 인터페이스에 바인딩해야 한다. 그때 B-6은 "tailnet 내부로 한정"으로 완화되며, 이것은 **고지된 예외**다. 예외를 쓰지 않으려면 Tailscale에서도 SSH 터널을 겹쳐 쓰면 된다 — 경로는 늘지만 불변식은 유지된다.

### 3.2 요청 형태

`POST /v1/chat/completions`의 본문은 OpenAI chat completions와 같다. 게이트웨이가 각 필드를 어떻게 다루는지 명시한다.

| 필드 | 처리 |
| --- | --- |
| `model` | allowlist 조회 키. 없으면 `404 gw_model_not_allowed`. 업스트림 접촉 없음 |
| `messages` | 통과. 게이트웨이는 본문을 수정하지 않는다(리댁션은 로그에만, 3.7) |
| `stream` | `true`면 SSE(3.4) |
| `stream_options.include_usage` | 지원. 스트리밍에서도 최종 usage 청크를 보낸다 |
| `max_tokens` / `max_completion_tokens` | 통과. 동시에 쿼터 예약액 계산의 상한이 된다(9.2) |
| `temperature`, `top_p`, `stop`, `seed` | 통과. 단 **프리셋이 고정한 파라미터는 서버가 덮어쓴다**(3.2.1) |
| `tools`, `tool_choice` | 통과. 단 서버 자체 LLM의 tool-calling 지원 여부는 서버 스택 확정 시 검증 대상(부록 B) |
| `response_format` | 통과. `json_schema` 지원 여부는 업스트림별 능력 플래그로 판정 |
| 그 외 확장 필드 | 거부하지 않되 업스트림에 전달하지 않는다. `400`을 내지 않는 이유는 omp가 보내는 부가 필드로 대화가 끊기지 않게 하기 위함이다 |

#### 3.2.1 프리셋 파라미터와 클라이언트 파라미터가 충돌할 때

7.5는 "서버의 프리셋이 우선한다"고 주장한다. 그 주장이 성립하려면 요청 단계에서 무엇을 하는지 정해야 한다. 두 가지 중 하나를 고르고 섞지 않는다.

| 전략 | 동작 | 클라이언트가 보는 것 | 채택 |
| --- | --- | --- | --- |
| A. 덮어쓰기 | 프리셋이 고정한 키만 서버 값으로 교체하고 업스트림으로 보낸다 | 응답 `gw.overridden_params`에 **덮어쓴 키 이름 목록**과 서버 값 | **채택** |
| B. 거부 | 충돌하면 `409 gw_preset_conflict` + 충돌 키 목록 | 요청 실패 | 미채택 |

A를 채택한다. 이유: 프리셋의 목적은 재현성이므로 서버가 값을 확정해야 하고, 동시에 사용자는 무엇이 바뀌었는지 알아야 한다. 조용한 덮어쓰기는 금지다 — `gw.overridden_params`가 비어 있으면 덮어쓴 것이 없다는 뜻이고, 값이 있으면 사용자가 요청한 것과 다르게 실행되었다는 뜻이다.

B를 미채택하는 이유: omp 같은 하네스는 매 요청에 자체 기본값을 붙인다. 그 기본값이 프리셋과 어긋날 때마다 요청을 거부하면, 대화가 기능 자체를 사용할 수 없게 된다. 거부는 안전해 보이지만 이 문맥에서는 사용 불가를 만든다.

프리셋이 고정하지 않은 키는 클라이언트 값을 그대로 통과시킨다. 즉 **덮어쓰기 범위는 프리셋이 명시한 키로 한정**된다. 이를 벗어난 전면 재작성은 하지 않는다.

요청 헤더.

| 헤더 | 의미 | 필수 |
| --- | --- | --- |
| `Authorization: Bearer <token>` | 사용자·토큰 식별 | 예 |
| `X-GW-Contract: gw1` | 계약 버전 | 예 |
| `X-GW-Route` | 클라이언트가 선언한 라우트. 서버는 이를 **하한**으로만 쓴다(10.4) | 아니오(기본값은 토큰 정책) |
| `X-GW-Request-Id` | 상관 ID. 없으면 서버가 생성 | 아니오 |
| `Idempotency-Key` | 생성 작업 중복 제출 방지 | 아니오 |

### 3.3 응답 형태

비스트리밍은 OpenAI `chat.completion` 객체에 `gw` 확장을 더한다.

```json
{
  "id": "<string>",
  "object": "chat.completion",
  "created": 0,
  "model": "<요청한 모델 ID>",
  "choices": [{ "index": 0, "message": { "role": "assistant", "content": "<string>" }, "finish_reason": "stop" }],
  "usage": { "prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0 },
  "gw": {
    "upstream_id": "<string>",
    "upstream_class": "server_local | proxy | direct",
    "route_effective": "local_only | zdr_cloud | any_cloud",
    "usage_state": "known | partial | unknown",
    "cost": { "estimated": 0, "currency": "<ISO 4217>", "state": "settled | reserved | unknown" },
    "quota": { "remaining": 0, "reserved": 0, "unknown_count": 0, "reset_at": "<ISO 8601>" }
  }
}
```

`gw` 확장은 OpenAI 클라이언트가 무시해도 동작하도록 최상위에만 둔다. `choices[].message` 안에는 아무것도 더하지 않는다.

응답 헤더: `X-GW-Upstream`, `X-GW-Upstream-Class`, `X-GW-Route-Effective`, `X-GW-Quota-Remaining`, `X-GW-Quota-Reset`, `X-GW-GPU-State`(서버 자체 모델일 때), `X-GW-Request-Id`.

### 3.4 스트리밍

- 전송: `text/event-stream`. 각 이벤트는 `data: <chat.completion.chunk JSON>` 한 줄, 종료는 `data: [DONE]`.
- 유휴 시 주석 줄(`: keep-alive`)을 보낸다. 간격은 `P_SSE_KEEPALIVE_MS`.
- `include_usage`가 있으면 마지막 청크에 `usage`를 담아 보낸다.
- **중단의 구분.** 업스트림이 스트림 도중 실패하면 게이트웨이는 `data: {"error":{...}}` 이벤트를 보내고 **`[DONE]` 없이** 연결을 닫는다. `[DONE]`의 부재가 "정상 종료가 아님"의 신호다. 이 규칙이 없으면 클라이언트는 잘린 응답을 완성된 응답으로 표시한다.
- 클라이언트가 먼저 끊으면 게이트웨이는 업스트림 연결을 닫고, 그때까지 업스트림이 보고한 토큰 수로 정산한다. 보고가 없으면 `usage_state = unknown`(9.5).
- 스트리밍 중 쿼터 초과는 사전 예약으로 이미 걸러져야 한다. 도중에 초과가 확인되면 `error` 이벤트로 `gw_quota_exhausted`를 보내고 닫는다.

### 3.5 오류 분류

> **구현된 코드와의 차이(2026-11-06 실측).** 아래 표의 `gw_*` 코드는 이 설계 문서가 정의한 이름이며, 현재 `gateway/lib/`가 실제로 내보내는 문자열과 같지 않다. 구현은 라우트를 `400 invalid_route`(인식할 수 없는 값, `error.detail.source`가 `header`/`body`), `local_only` 도착을 `400 local_only_not_served`, ZDR 조건 불충족을 `403 route_policy_violation`, allowlist 밖 모델을 `404 model_not_allowed`, 같은 요청에 경로가 충돌하면 `400 route_conflict`로 거부한다. 이 차이는 문서가 설계명을 쓰기 때문이며, 어느 쪽 이름도 "검증된 보안 수용"을 뜻하지 않는다. `gateway/` `npm test` 148개는 스텁 업스트림 대상 기능 시험이다.

| HTTP | `error.code` | 뜻 | 재시도 | 쿼터 |
| --- | --- | --- | --- | --- |
| 400 | `gw_bad_request` | 본문 형식 오류 | 불가 | 소모 없음 |
| 401 | `gw_auth_invalid` | 토큰 없음·만료·폐기 | 재인증 필요 | 소모 없음 |
| 403 | `gw_route_forbidden` | 정책이 이 요청을 금지(예: `zdr_cloud` + 비ZDR 업스트림) | 불가 | 소모 없음 |
| 403 | `gw_model_forbidden` | allowlist에 있으나 이 토큰에 허용되지 않음 | 불가 | 소모 없음 |
| 404 | `gw_model_not_allowed` | allowlist에 없음 | 불가 | 소모 없음 |
| 409 | `gw_preset_stale` | 계약·카탈로그 버전 불일치. `required_catalog_version` 반환 | manifest 갱신 후 | 소모 없음 |
| 410 | `gw_job_expired` | 작업 산출물 보존 기간 경과 | 불가 | 이미 정산됨 |
| 413 | `gw_payload_too_large` | 본문 상한 초과(`P_MAX_BODY_BYTES`) | 불가 | 소모 없음 |
| 422 | `gw_manifest_invalid` | 서명·중복 ID 등 무결성 실패(제어 평면) | 불가 | 소모 없음 |
| 429 | `gw_quota_exhausted` | 하드 캡 도달 | 리셋 후 | 소모 없음 |
| 429 | `gw_rate_limited` | 토큰·사용자 레이트 리밋 | 백오프 후 | 소모 없음 |
| 502 | `gw_upstream_error` | 업스트림 5xx·형식 오류 | 가능(정책 허용 시) | 9.2.1 |
| 503 | `gw_upstream_unavailable` | 업스트림 연결 불가 | 가능 | 9.2.1 |
| 503 | `gw_gpu_busy` | GPU가 다른 패밀리를 실행 중이거나 큐 상한 초과. `Retry-After` 동봉 | 가능 | 소모 없음(업스트림 미접촉) |
| 503 | `gw_telemetry_unavailable` | `cuMemGetInfo`·`/api/ps` 모두 실패해 적재 판정 불가 | 가능 | 소모 없음(업스트림 미접촉) |
| 504 | `gw_upstream_timeout` | 동기 상한 초과(`P_GW_SYNC_TIMEOUT_MS`) | 가능 | 9.2.1 |

원칙 둘.

1. **거부는 업스트림 접촉 전에 한다.** allowlist·라우트·쿼터 판정은 업스트림 호출 앞에서 끝난다. 거부된 요청은 비용을 만들지 않는다. 이 표에서 "소모 없음"이라고 적은 행은 모두 이 부류다 — 업스트림에 닿지 않았으므로 확실히 0이다.
2. **업스트림에 닿은 뒤의 실패는 하나의 규칙(9.2.1)을 따른다.** "소모 없음"이라고 단정하지 않는다. 업스트림이 이미 토큰을 생성했거나 과금했을 수 있기 때문이다. 위 표의 502·503·504 중 업스트림 접촉 후 발생한 것은 9.2.1로 넘긴다.

### 3.5.1 소모 없음과 미상의 경계

| 시점 | 쿼터 기록 | 이유 |
| --- | --- | --- |
| 업스트림 접촉 전 거부(400·401·403·404·409·413·422·429, 그리고 503 `gw_gpu_busy`·`gw_telemetry_unavailable`) | 0 | 업스트림이 존재조차 모른다. 확실히 0 |
| 업스트림 접촉 후 실패(502·503·504, 스트림 중단, 클라이언트 중도 이탈) | 9.2.1에 따름 | 이미 생성된 토큰이 있을 수 있다. 0으로 단정하면 총합이 틀린다 |

이 구분이 없으면 "실패는 무료"라는 인상이 생기고, 그 인상은 재시도 폭주와 원장 왜곡을 만든다.

### 3.6 `omp`를 게이트웨이에 붙이는 방법 (하네스 수정 없음)

`omp` 18.16.0은 `models.yml`의 `providers` 아래에 임의 이름의 커스텀 프로바이더를 정의할 수 있다. 필요한 것은 `baseUrl`, `api`, `auth`, `models[]`다. 게이트웨이는 `openai-completions` API로 말하므로 하네스 코드를 고칠 이유가 없다.

`baseUrl`은 **터널의 로컬 끝**을 가리킨다. 원격 주소가 아니다.

```yaml
providers:
  campus-gateway:
    baseUrl: "http://127.0.0.1:4318/v1"
    api: openai-completions
    auth: apiKey
    apiKey: "<GW_TOKEN>"
    models:
      - id: "server/qwen3-32b"
        name: "Qwen3 32B (서버 GPU)"
      - id: "server/qwen2.5-72b"
        name: "Qwen2.5 72B (서버 GPU, 부분 오프로드)"
      - id: "openrouter/<모델>"
        name: "<카탈로그 표시명>"
      - id: "a6api/deepseek-chat-v3.1"
        name: "DeepSeek V3.1 (A6API Proxy)"
```

`server/` 접두사는 예시이며, 최종 문자열은 카탈로그가 확정한다. 중요한 것은 접두사가 아니라 세 곳의 일치다(규칙 1).

설계 규칙 여섯 개.

1. **모델 ID 문자열은 세 곳에서 동일해야 한다.** 카탈로그, 게이트웨이 allowlist, `models.yml`의 `models[].id`. 매핑 표를 두지 않는다. 매핑 표는 드리프트의 온상이다.
2. **`baseUrl`은 항상 `http://127.0.0.1:<P_TUNNEL_LOCAL_PORT>/v1`이다.** 서버 WAN 주소를 쓰지 않는다(2.7.1). `https://`도 쓰지 않는다 — 그 구간은 루프백이고 TLS 종단이 없다(2.3).
3. **`auth` 리터럴에 대한 정직한 메모.** 요구사항 서술은 인증을 "bearer"로 부른다. 설치된 18.16.0의 스키마가 허용하는 리터럴은 `"apiKey" | "none" | "oauth"`이고(`40_AI보고서/.omp-runtime/node_modules/@oh-my-pi/pi-coding-agent/src/config/models-config-schema-bundle.ts:374`), 전송은 `Authorization` 헤더의 bearer 토큰이다. 즉 파일에 적히는 값은 스키마가 아는 리터럴이어야 하고, 의미는 bearer다. `bearer`라는 문자열이 그대로 수용되는지는 **미확인**이며, 확정 전까지 위 예시는 `auth: apiKey`다(부록 B).
4. **`transport: pi-native`를 쓰지 않는다.** 그 값은 `baseUrl`이 `omp auth-gateway`의 `POST /v1/pi/stream`을 가리킬 것을 전제한다(`models-config-schema-bundle.ts:405`). 우리 게이트웨이는 omp auth-gateway가 아니다. 이 경로를 쓰면 계약이 두 개가 된다.
5. **`baseUrl`의 `/v1` 처리.** 게이트웨이 표면은 `/v1`에 뿌리를 두므로 스키마의 기본 `/v1` 주입과 일치한다. 버전 경로를 더 깊게 두지 않는다.
6. **터널이 없으면 이 프로바이더는 죽은 주소다.** 하네스는 연결 실패를 그대로 받는다. 실패를 로컬 모델로 우회하지 않는다(12.4).

`auth: none` 경로는 랩톱 로컬 엔드포인트용으로 이미 동작이 확인되어 있다. 게이트웨이는 그 경로를 쓰지 않는다 — 인증 없는 표면은 쿼터·정책·감사의 전제를 없앤다.

### 3.7 게이트웨이가 더하는 것 (직접 호출과의 차이)

| 추가 | 어디서 | 직접 제공자 호출에는 없는 이유 |
| --- | --- | --- |
| 모델 allowlist 강제 | 업스트림 호출 전 | 직접 호출은 어떤 모델이든 부를 수 있다 |
| 라우트 정책 판정 | 매 요청, 서버 측 | 클라이언트 선언은 강제가 아니다 |
| 쿼터 계량·예약 | 업스트림 호출 전 + 정산 | 사용자별 상한을 둘 곳이 없다 |
| 리댁션 | 로그 기록 시점 | 로그가 각 클라이언트에 흩어진다 |
| 비용 원장 | 응답마다 | 과금·회계의 단일 지점이 없다 |
| 업스트림 클래스 노출 | 응답 `gw` | 어디로 갔는지 사용자가 알 수 없다 |
| 폐기 전파 | manifest | 이미 배포된 클라이언트 설정을 회수할 수 없다 |

리댁션의 범위를 정확히 한다. 게이트웨이는 **요청·응답 본문을 수정하지 않는다**. 리댁션은 로그에 쓰기 직전에만 적용된다(키 형태, `Authorization` 류 헤더, 알려진 토큰 패턴). 본문을 수정해 업스트림에 보내면 사용자가 쓴 코드가 조용히 바뀌고, 그것은 재현 불가능한 버그가 된다.

### 3.8 업스트림 선택

요청 처리 순서를 고정한다.

1. 토큰 인증 → 실패 시 401.
2. 모델 ID를 allowlist에서 해석 → 없으면 404. 중복 해석이면 422(카탈로그 무결성).
3. 유효 라우트 계산: `stricter(token_policy, X-GW-Route)`.
4. 라우트 조건 검사: `zdr_cloud`면 `zero_data_retention && training_opt_out && retention_evidence != null`. 불충족이면 403 `gw_route_forbidden`.
5. 쿼터 예약 → 초과면 429.
6. 업스트림 호출. `server_local`이면 GPU 중재자에 입장 요청(5.8), `proxy`/`direct`면 그대로 전달.
7. 정산·원장 기록·응답.

`server_local`은 6단계에서 GPU를 못 받을 수 있다. 그때의 응답은 503 `gw_gpu_busy`(동기) 또는 큐 대기(영상)다. 프록시 업스트림은 GPU와 무관하므로 이 대기에서 자유롭다 — 이 비대칭이 5장 설계의 출발점이다.

### 3.9 `server_local`의 실체: Ollama 0.21.0 및 모델 식별자 규율

서버 LLM은 우리가 설치하는 llama.cpp가 아니라 **이미 가동 중인 Ollama**다. 이 사실이 설계를 바꾸는 지점만 적는다.

| 항목 | 측정된 사실 | 설계상의 귀결 |
| --- | --- | --- |
| 버전·가동 | Ollama 0.21.0, 2026-09-16부터 활성 | 설치 단계가 설계에서 사라진다 |
| 바인딩 | `127.0.0.1:11434` 루프백 | 게이트웨이는 같은 호스트에서 `server_local` 업스트림으로 부른다. 외부에 노출되지 않는다 |
| 표면 | `/v1` OpenAI 호환 하위집합 | 게이트웨이가 `openai-completions`로 말할 수 있다. 단 **부분집합**이므로 능력 차이를 흡수해야 한다 |

| 블롭 저장소 | `/usr/share/ollama`, `ollama:ollama 0750`, `sungjung` 읽기 불가 | **재고 열거는 HTTP API로만 한다** |
| 모델 관리 API | `GET /api/tags`(설치된 모델), `GET /api/ps`(적재된 모델, `size_vram`·`expires_at` 포함), `keep_alive`(적재 유지 시간) | 인벤토리·적재 상태·언로드가 HTTP로 가능하다 |

#### 3.9.0 서버 1차 LLM 식별자와 외부 벤치마크에 대한 정직한 경계

서버 기본 대화 및 코딩을 담당할 1차 모델로 논의되어 온 "27B IQ3_S thinking GGUF"와 관련하여, 2026-11-06 독립 직접 HTTP 200 감사가 완료되었으며 그에 따른 정밀한 경계와 상태를 다음과 같이 규정한다.

1. **식별자 및 모델 아키텍처 (검증 완료된 메타데이터):**
   - **업스트림 모델 리포지토리:** `Qwen/Qwen3.8-27B` (리비전 `8c0b3d30f3ae96f5c7f774de704bf0ada83e422a`, 라이선스 선언 Apache 2.0).
   - **GGUF 리포지토리:** `unsloth/Qwen3.8-27B-GGUF` (리비전 `4ca720788d1e01f1bff70c033e0d0028fd02e502`).
   - **대상 파일 메타데이터:** `Qwen3.8-27B-UD-IQ3_S.gguf` (크기 12,040,883,104 bytes ≈ 11.21 GiB 가중치, LFS OID `d847e2c1e4aa276e4b7b8e9ad7628050e61e165d49ab995407bc36677a6f3864`, Hugging Face API 메타데이터 검증 완료, 독립 SHA-256 전체 바이트 해싱은 미실시).
   - **설정 파일 (`config.json`) 구조:** `model_type`은 `qwen3_5`로 기재되어 있으나, 이는 리포지토리 버전이 아니라 아키텍처 패밀리 식별자다. 세부 스펙은 64개 레이어(16 full + 48 linear), 4 KV head, 256 dim, `max_position_embeddings` 262,144 (256K)다. 즉, 백본 식별자가 Qwen3.5인지 3.8인지의 불확실성은 해소되었으며 **Qwen3.8-27B 백본 모델**임이 확인되었다.
2. **벤치마크 아티팩트 매핑의 한계 (미해결 상태 / 후보 취급):**
   - llm-bench 결과 페이지(`https://llm-bench.io/benchmarks/cmvuhnxew016n01lafi3jkl4u`)에서 스크린샷 별칭인 `Qwen3.8-27b-iq3s`와 공개 수치(64.8 T/S, 429.2 PP, 1447 TTFT, 20.0 MEM, 200,000 컨텍스트 설정, 8,192 thinking)가 확인된다.
   - 그러나 해당 벤치마크 페이지에는 **어떠한 리포지토리 링크, 원본 파일명, 해시 값도 명시되어 있지 않다.** 따라서 벤치마크에 사용된 바이너리가 Unsloth 양자화 파일과 정확히 동일한 아티팩트인지의 매핑은 **미해결(Unresolved)** 상태이며, Unsloth 파일은 가장 유력한 **후보(Candidate)**일 뿐이다.
3. **외부 벤치마크 지표의 성격 및 실측치 혼동 금지:**
   - 벤치마크의 메모리 지표(20.0 MEM)는 정의(VRAM 단독인지 시스템 RAM 포함인지 등)가 명확하지 않다.
   - 또한 RTX 4090 D24GB 기준 속도(예: 85 tok/s, 3,280 tok/s), 벤치마크 점수 등은 모두 **외부 참고 자료(External Reference)**일 뿐이며, 연구실 RTX 5090(31.36 GiB) 서버에서의 실제 성능, 실제 200K 컨텍스트 사용 가능 여부, 실제 적재 안정성은 전혀 검증되지 않았다.
   - 가중치 크기(11.21 GiB)에 임의의 여유분(예: +0.8 GiB)만을 단순 합산하여 추정 속도를 제시하거나 적재 가능성을 단정하는 표는 작성하지 않는다.
4. **서버 배치 상태 및 정책 지위:**
   - 이 모델은 **이 작업에서 설치·적재하지 않았으며, 서버 배치·가동은 확인되지 않음**.
   - 따라서 게이트웨이 카탈로그 및 하네스 정책은 이를 즉시 호출 가능한 고정 모델로 등록하지 않고, **설정 가능(Configurable / Planned Policy)** 상태로 유지한다.
5. **독립 프로세스 임대(Process Lease) 요구 — 드레인은 예약이 아니다:**
   - 공용 Ollama의 전역 `/api/ps`는 소유권 증거가 될 수 없다. 조회 결과는 `reported`이며, 우리 소유라는 증명이 아니다. 다른 사용자의 모델은 우리 것이 아니다.
   - 우리가 제안하는 **자체 프로세스 드레인·생명주기 관리 자체는 GPU를 예약하지 않는다.** 드레인은 우리 in-flight 요청을 정상 종료시키는 절차일 뿐, 카드의 여유 공간을 확보한다고 보장하지 않는다.
   - **실제 입장(admission)은 강제된 할당·리스·접근 격리 수단이 있어야 성립한다.** 이 호스트에는 cgroup GPU 제한이 없고 `/dev/nvidia0`은 전 사용자 쓰기 가능이므로, 그런 수단은 현재 **설계 대상이지 확보된 자원이 아니다**(5.8.2).
   - **포트·프로세스 분리나 컨테이너 분리는 GPU 예약이 아니다.** 같은 카드의 여유 VRAM은 여전히 공유되며, 우리 프로세스를 따로 띄웠다는 사실이 남의 적재를 막지 않는다.
   - 따라서 축출은 자체 소유 런타임에 한정하고, 입장 판정은 매번 다시 읽은 여유 바이트와 모순 검사로만 한다(5.9.4).

#### 3.9.1 파일시스템을 읽지 않는다

블롭 저장소를 읽을 수 없으므로, 그리고 읽을 수 있다 해도 그 내부 레이아웃은 Ollama의 사적 구현이므로, **인벤토리는 `GET /api/tags`로만 만든다.** `P_INVENTORY_SOURCE = "http"`가 유일한 허용값이고, 파일 경로를 훑는 구현은 설계 위반이다. 이유는 두 가지다.

1. 권한: `0750`이고 소유자가 `ollama`이므로 `sungjung`은 읽을 수 없다. 시도하면 실패하고, 실패를 "모델 없음"으로 보고하면 거짓 상태가 된다.
2. 의미: 파일이 있다는 것과 Ollama가 그 모델을 로드할 수 있다는 것은 다르다. `/api/tags`는 후자를 답한다.

같은 이유로 321.4 GB·36종이라는 수치는 감사 시점의 `/api/tags` 응답이며, 이후 변할 수 있다. 카탈로그는 이 값을 하드코딩하지 않고 조회 결과를 쓴다.

#### 3.9.2 OpenAI 호환의 부분집합을 흡수한다

Ollama의 `/v1`은 OpenAI API의 **부분집합**이다. 게이트웨이는 차이를 다음처럼 처리한다.

| 능력 | 처리 |
| --- | --- |
| `/v1/chat/completions` | 사용 |
| `stream: true` | 사용. 종료 규약은 3.4를 따른다 |
| `tools` | Ollama 모델이 지원하지 않으면 업스트림이 오류를 낸다. 게이트웨이는 이를 `gw_upstream_error`로 감싸고 **모델 능력 플래그**로 사전 차단할 수 있게 한다 |
| `response_format` | `json` 계열만 신뢰하고, `json_schema`는 능력 플래그로 판정 |
| `usage` | Ollama는 자체 카운터를 보고한다. 게이트웨이는 그 값을 `usage_state = known`의 근거로 쓰되, 없으면 `unknown`이다(9.5) |
| `keep_alive` | 게이트웨이가 명시한다. 기본 5분에 맡기지 않는다 |

`keep_alive`를 게이트웨이가 명시하는 이유는 상주 정책이 게이트웨이의 것이기 때문이다(5장). Ollama의 기본 5분 유휴 언로드는 우리 중재 정책과 무관하게 모델을 내리므로, 그대로 두면 "상주 중"이라는 우리 상태 표시가 사실과 어긋난다.

#### 3.9.3 게이트웨이와 Ollama의 책임 경계

| 책임 | 게이트웨이 | Ollama |
| --- | --- | --- |
| 모델 allowlist | 예 | 아니오 |
| 라우트 정책 | 예 | 아니오 |
| 쿼터·원장 | 예 | 아니오 |
| 모델 적재·언로드 실행 | 요청(`keep_alive`, `/api/ps` 관측) | 실제 수행 |
| GPU 메모리 배분 | 아니오(중재만) | 예(적재 시도) |
| 동시 요청 처리 | 아니오 | 예 |

마지막 두 줄이 이 설계의 정직한 한계다. **Ollama는 우리 정책을 모른다.** 게이트웨이를 거치지 않고 `127.0.0.1:11434`를 직접 부르는 프로세스(같은 호스트의 다른 사용자 포함)는 allowlist도 쿼터도 우회한다. 게이트웨이가 강제할 수 있는 것은 **게이트웨이를 통과한 요청**뿐이며, 이것을 "서버 전체의 정책"이라고 부르면 거짓이다(5.8).

## 4. 데이터 평면 — 이미지·영상 생성

### 4.0 이 장의 현재 상태 — 이미지·영상 모델은 설치되어 있지 않다

감사 시점의 Ollama 재고 36종은 전부 텍스트·임베딩 계열이다. 이미지 생성 모델도, 영상 생성 모델도 없다. 따라서 이 장은 **계약 및 아키텍처 계획 설계**이며, 다음 두 조건이 충족되기 전까지 이 기능들은 "있는 기능"이 아니다.

1. 모델이 실제로 설치되고 VRAM 요구가 측정될 것(6.2).
2. 중재자가 그 모델을 세 번째 그룹으로 인식할 것(5.8).

이 장의 엔드포인트·상태 기계·계량 규칙은 지금 확정할 수 있다. 그것들은 모델이 무엇이든 성립해야 하는 계약이기 때문이다. 반대로 품질·해상도 상한·길이 상한·적재 시간은 지금 확정할 수 없다. 이 항목들은 **제공자 키 없이 서버 GPU에서 측정하면 끝나는 문제**이므로 **표 B**에 등재한다(13.2의 실측 등급). 표 C는 제공자 정책·단가·지연 전용이다.

또 하나: 이 모델들은 Ollama로 서빙한다고 가정하지 않는다. Ollama는 현재 텍스트·임베딩만 담고 있고, 이미지·영상 추론은 별도 프로세스가 될 가능성이 크다. 게이트웨이 입장에서 차이는 없다 — 둘 다 `server_local` 업스트림이고, 게이트웨이는 그 앞에서 정책과 중재만 한다. 다만 **"Ollama가 알아서 관리하리라"는 가정은 이미지·영상에 적용되지 않는다.** 이 두 패밀리의 적재·언로드는 중재자가 직접 지시해야 한다(5.5).

#### 4.0.1 이미지 생성 백엔드 및 모델 독립 감사 사실

요청 없는 임의 설치를 배제하고 단일 최소 백엔드 후보만을 기술 규격으로 검토한 독립 감사 증거는 다음과 같다:

1. **단일 최소 백엔드 인터페이스 (`sd.cpp`):**
   - 저장소: `leejet/stable-diffusion.cpp` (리비전 `79526930040ba361c78cb42e79610cc5bfdc301e`).
   - `examples/server/routes_openai.cpp`에서 표준 OpenAI 호환 엔드포인트인 `POST /v1/images/generations`를 자체 지원함을 확인(`https://github.com/leejet/stable-diffusion.cpp/blob/79526930040ba361c78cb42e79610cc5bfdc301e/examples/server/routes_openai.cpp`). 라이선스는 MIT.
2. **FLUX.1-schnell 최소 후보 아티팩트 및 라이선스:**
   - 허브 저장소: `leejet/FLUX.1-schnell-gguf` (리비전 `c7f665ddaf9f197ff493f41fc211f5480f5f19ac`). 가중치 선언 라이선스 Apache 2.0.
   - 최소 후보 파일: `flux1-schnell-q4_0.gguf` (크기 6,884,606,880 bytes ≈ 6.4118 GiB).
   - 별도 필요 구성요소: CLIP, T5 인코더, VAE 파일이 별도로 요구되며, 각 구성요소의 출처 및 라이선스는 별도 증빙이 필요하다.
   - **타 기종 및 업스트림 벤치마크 수치 인용 금지:** 업스트림 `docs/flux.md`에 기재된 6,394.53 MB / 12,068.09 MB 수치는 `sd-cli` 기준의 **Flux-dev 벤치마크** 수치이며, `schnell`이나 `sd-server`의 수치가 아니다. 이를 우리 시스템의 VRAM 핏으로 인용하지 않는다. 또한 Q8 파일 크기(12,801,721,248 bytes)는 파일 용량일 뿐 런타임 VRAM 점유량이 아니다. Windows(7.77 GiB 가용) 환경에서의 적재 가능성은 **전혀 입증되지 않았다(NOT demonstrated)**.
3. **대안 모델(SDXL-turbo) 라이선스 사실:**
   - 공식 커뮤니티 라이선스(`https://huggingface.co/stabilityai/sdxl-turbo/blob/71153311d3dbb46851df1931d3ca6e939de83304/LICENSE.md`, 리비전 `71153311d3dbb46851df1931d3ca6e939de83304`): 상업적 이용 시 등록 및 연간 매출 한도에 따른 조건부 로열티 프리 커뮤니티 라이선스를 적용한다. 일괄 유료 멤버십 또는 비상업 전용이라는 주장은 사실이 아니다.
4. **원격 부재 증명 규율:** 로컬 파일시스템의 glob 결과만으로 원격 호스트의 소프트웨어/모델 부재를 단정하지 않는다. 인벤토리 부재 판단은 HTTP API 판독에만 의존한다.

### 4.1 왜 동기 계약으로는 안 되는가

이미지도 영상도 chat completion이 아니다. 그리고 영상은 **동기 요청 모델이 성립하지 않는 유일한 워크로드**다. 이유는 세 가지다.

1. 처리 시간이 요청 타임아웃보다 길다. HTTP 동기 응답으로 붙잡으면 프록시·로드밸런서·클라이언트가 먼저 끊는다.
2. GPU가 그동안 다른 패밀리를 못 쓴다(5장). 동기 요청은 "GPU 점유 시간"을 클라이언트 연결 수명에 묶어 버린다.
3. 실패·취소·재시도의 단위가 요청이 아니라 **작업**이다. 중간에 끊긴 영상 생성을 "요청 실패"로 기록하면 비용과 산출물의 관계가 사라진다.

그래서 이미지는 동기(짧고, 상한이 있는 대기), 영상은 비동기 작업으로 나눈다.

### 4.2 이미지

`POST /v1/images/generations` — OpenAI images 형식.

요청: `{ "model": "<카탈로그 ID>", "prompt": "<string>", "n": <int>, "size": "<WxH>", "response_format": "b64_json | url" }`

응답(성공): `{ "created": 0, "data": [ { "b64_json": "<base64>" } ] }` 또는 `{ "created": 0, "data": [ { "url": "<서명 URL>" } ] }`, 그리고 `gw` 확장(3.3과 동일 구조 + `gpu_seconds`).

동작 규칙.

- 동기 대기 상한은 `P_IMG_SYNC_WAIT_MS`. 초과하면 `503 gw_gpu_busy` + `Retry-After`. 클라이언트는 재시도하거나 사용자에게 "GPU 교체 중"을 표시한다.
- `response_format: "url"`의 URL은 게이트웨이가 서명한 단기 URL이다(유효 `P_ARTIFACT_URL_TTL_S`). 외부 공개 버킷을 만들지 않는다.
- `n`의 상한은 `P_IMG_MAX_N`. 이미지 1장이 쿼터 1단위다(`image_unit`).
- 배치 창(`P_IMG_BATCH_WINDOW_MS`) 동안 도착한 요청을 모아 한 번의 모델 적재로 처리한다. 이 창이 없으면 이미지 요청 하나마다 GPU 스왑이 일어나 채팅 지연이 붕괴한다(5.3).

### 4.3 영상 — 작업 계약

영상은 네 개의 엔드포인트로만 다룬다.

**생성.** `POST /v1/videos`

```json
{
  "model": "<카탈로그 ID>",
  "prompt": "<string>",
  "duration_s": 0,
  "resolution": "<WxH>",
  "seed": 0
}
```

`duration_s`는 **필수**이고 상한은 `P_VIDEO_MAX_DURATION_S`다. 필수인 이유는 쿼터 예약액을 제출 시점에 계산해야 하기 때문이다(4.6).

응답 `202 Accepted`:

```json
{
  "object": "video.job",
  "job_id": "<string>",
  "status": "queued",
  "model": "<카탈로그 ID>",
  "created_at": "<ISO 8601>",
  "expires_at": "<ISO 8601>",
  "queue_position": 0,
  "estimated_start_at": "<ISO 8601|null>",
  "poll_after_ms": 0,
  "gw": { "quota": { "reserved": 0, "remaining": 0, "unknown_count": 0 } }
}
```

`estimated_start_at`는 추정이며 `null`일 수 있다. 추정을 사실처럼 표시하지 않는다.

**조회.** `GET /v1/videos/{job_id}` → 상태 객체. `status`가 `succeeded`면 `output`에 산출물 메타데이터(길이, 해상도, 바이트, 서명 URL)를 담는다.

**산출물.** `GET /v1/videos/{job_id}/content` → `302` 로 서명 URL, 또는 바이트 스트림. 산출물은 `P_JOB_ARTIFACT_TTL_H` 후 삭제되고, 그 뒤에는 `410 gw_job_expired`.

**취소.** `DELETE /v1/videos/{job_id}` → `queued`면 즉시 취소. `running`이면 모델이 중간 취소를 지원할 때만 취소되고, 아니면 `409 gw_job_cancel_unsupported`와 함께 끝까지 실행된다. 취소된 작업의 쿼터는 실제 소모분만 정산한다.

**멱등성.** `Idempotency-Key`가 같은 재제출은 같은 `job_id`를 돌려준다(보존 `P_IDEMPOTENCY_TTL_S`). 재시도가 영상 두 개를 만들면 비용도 두 배다.

**목록.** `GET /v1/videos?limit=<n>` → 최근 작업. 상한 `P_JOB_LIST_MAX`.

### 4.4 상태 기계

```
queued → running → succeeded
   |         |  |
   |         |  └→ failed
   |         └→ cancelled          [조건부: cancel_supported = true]
   └→ cancelled
   (succeeded|failed|cancelled) → expired   [보존 기간 경과]
```

| 상태 | 뜻 | 클라이언트가 할 일 | 쿼터 |
| --- | --- | --- | --- |
| `queued` | GPU 대기 중. `queue_position` 유효 | `poll_after_ms` 후 조회 | 예약됨 |
| `running` | GPU 점유 중 | 폴링. 취소 가능 여부는 `cancel_supported` | 예약됨 |
| `succeeded` | 산출물 존재 | `content` 조회 | 실제값 정산 |
| `failed` | 실패. `error.code` 포함 | 재제출 여부 결정 | 9.2.1 |
| `cancelled` | 취소됨. `cancelled_from`이 `queued`인지 `running`인지 기록 | 없음 | 9.2.1 |
| `expired` | 산출물 삭제됨 | 없음(재생성 필요) | 이미 정산됨 |

**`running`에서의 취소.** `queued`에서만 취소할 수 있다고 쓰면 `cancel_supported`가 `running`에 대해 무엇을 뜻하는지 설명되지 않는다. 둘을 맞춘다.

| 전이 | 조건 | 결과 | 쿼터(9.2.1 적용) |
| --- | --- | --- | --- |
| `queued → cancelled` | 항상 가능 | GPU를 쓰지 않았으므로 즉시 종료 | 보고 없음 + 우리가 실행 주체 → 과금 없음 확인 → 전액 해제 |
| `running → cancelled` | `cancel_supported = true`일 때만 | 현재 프레임/스텝에서 정지. 부분 산출물의 보존 여부는 `partial_output` 필드로 알린다 | 실제 소모 GPU 초로 `partial` 정산, 차액 반환 |
| `running → cancelled` 요청, `cancel_supported = false` | 영상 인코더가 중간 정지를 지원하지 않는 경우 | `409 gw_job_cancel_unsupported`. 작업은 계속 실행된다 | 변화 없음. 사용자는 완료를 기다린다 |

`cancel_supported`는 **작업 단위** 필드다. 모델·해상도·길이에 따라 중간 정지가 가능한지가 달라지기 때문이다. 값이 `false`인 작업에 취소를 요청받으면 조용히 무시하지 않고 `409`로 거절한다 — 무시하면 사용자는 취소되었다고 믿고 다른 작업을 제출해 GPU를 이중으로 예약한다.

`running → cancelled`는 조건부 전이다. `cancel_supported = false`인 작업에서는 이 전이가 존재하지 않으므로, 상태 기계는 위 그림과 같이 조건 표시를 단 채로 둔다. 무조건 전이로 그리면 상태 기계가 실제 허용 범위보다 넓은 것을 약속한다.

전이는 단조롭다. `succeeded`에서 `running`으로 돌아가지 않는다. `cancelled`와 `failed`는 종결 상태이며 서로 전이하지 않는다. 서버 재시작 시 `running` 작업은 `failed`로 확정하고 사유를 `gw_upstream_error`가 아니라 `gateway_restart`로 남긴다 — 이 구분이 없으면 재시작이 업스트림 장애로 둔갑한다.

### 4.5 긴 작업을 클라이언트에 보고하는 방법

v1에는 푸시가 없다. 웹훅도, 콜백도, 인바운드 연결도 쓰지 않는다. 이유: 클라이언트가 NAT 뒤에 있고, 수신 엔드포인트를 여는 것은 랩톱 평면의 공격면을 넓힌다.

그래서 보고 수단은 **폴링 + 서버가 지시하는 간격**이다.

- 서버는 모든 작업 응답에 `poll_after_ms`를 넣는다. 클라이언트는 이 값보다 자주 폴링하지 않는다. 이 값은 작업 단계에 따라 커진다(`queued` 초기 > `running` 중반).
- 앱 UI(`40_AI보고서/app/`)는 `queue_position`, `estimated_start_at`, `progress`(있으면)를 표시하고, 없으면 표시하지 않는다. 0으로 채우지 않는다.
- `5xx` 폴링 실패는 백오프 상한 `P_POLL_BACKOFF_MAX_MS`까지 지수 백오프한다. 무한 재시도 루프를 만들지 않는다.
- 작업이 끝나면 UI는 산출물 URL을 받아 사용자에게 준다. URL 만료가 임박하면 재조회한다.

이 구조의 정직한 한계: 서버가 죽으면 클라이언트는 "작업 상태 미상"을 표시할 수밖에 없다. 그 상태를 "실패"로 단정하지 않는다(11장).

### 4.6 쿼터 계량

| 워크로드 | 계량 단위 | 예약 시점 | 정산 시점 | 미상 처리 |
| --- | --- | --- | --- | --- |
| 텍스트 | 입력·출력 토큰 | 요청 전(`max_tokens` 기반) | 응답 usage 도착 시 | usage 없으면 unknown(9.5) |
| 이미지 | 장(`image_unit`) × 해상도 계수 | 요청 전(`n` 기반) | 응답 시 | 부분 생성이면 생성 장수로 정산 |
| 영상 | 초(`video_second`) + GPU 초 | 제출 시(`duration_s` 기반) | 종료 상태에서 | 산출물 길이 미상이면 요청 길이로 확정하고 `usage_state=partial` |

영상은 제출 시점에 **최대치로 예약**한다. 예약하지 않으면 한 사용자가 긴 영상 여러 개를 동시에 제출해 원장을 음수로 만들 수 있다. 제출 후의 정산은 9.2.1의 단일 규칙을 따른다. 큐 대기 중 거부·취소는 전액 해제, GPU 실행 후 실패·취소는 실제 소모 초로 `partial` 정산이다.

### 4.7 사전 생성 산출물의 출처 기록

시연이 사전 녹화 영상이므로(0.5), 이미지·영상 산출물은 **녹화 전에 생성되어 영상에 삽입된다.** 녹화 중 실시간 생성이 아니다. 그 삽입이 정직하려면 산출물마다 출처 기록이 있어야 한다.

산출물 1건당 다음 레코드를 남긴다. 이 레코드가 없는 산출물은 영상에 쓰지 않는다.

```json
{
  "artifact_id": "<string>",
  "job_id": "<string|null, 비동기 영상인 경우>",
  "family": "image | video",
  "model_id": "<카탈로그 모델 ID>",
  "upstream_id": "<업스트림 ID>",
  "upstream_class": "server_local | proxy | direct",
  "created_at": "<ISO 8601, 서버 시각>",
  "params": { "<요청 파라미터 원문>": "<값>" },
  "command": "<재현 가능한 호출 명령 또는 스크립트 경로>",
  "run_id": "<스크립트 실행 1회의 식별자>",
  "log_path": "<그 실행의 표준출력·표준에러 경로>",
  "output_sha256": "<산출물 파일 해시>",
  "captured_on": "server | laptop",
  "video_timestamp": "<영상에서 이 산출물이 보이는 시각, mm:ss>",
  "note": "<생성 후 편집 여부 등>"
}
```

규칙 여섯 개.

1. **`command`가 없으면 영상에 쓰지 않는다.** 재현 명령이 없는 산출물은 "어떻게 나왔는지 모르는 그림"이고, 그것을 시연 자료로 쓰면 증거가 아니라 주장이 된다.
2. **`run_id`와 `log_path`가 없으면 영상에 쓰지 않는다.** 산출물이 나온 실행 1회를 가리키는 기록이 없으면, 그 산출물과 그 실행을 연결할 방법이 없다. 규칙 V-1(0.5.1)이 요구하는 "스크립트 + 실행 로그"가 산출물 수준에서 구체화된 것이 이 두 필드다.
3. **`created_at`은 녹화 시각보다 앞서야 한다.** 녹화 이후 생성된 산출물을 "녹화 중 생성"으로 제시하지 않는다.
4. **후편집을 숨기지 않는다.** 자르기·색보정·자막 삽입을 했다면 `note`에 적는다. 편집 자체는 문제가 아니다 — 편집을 "원본 생성 결과"라고 부르는 것이 문제다.
5. **`captured_on`을 영상에 표시한다.** 서버에서 생성한 산출물임을 화면에 적는다. 표시가 없으면 랩톱이 만든 것으로 오해된다. 표시 문구는 이 레코드에서 생성하며, 손으로 타이핑한 자막을 쓰지 않는다(13.5).
6. **`video_timestamp`로 영상과 레코드를 연결한다.** 레코드 묶음과 영상이 따로 존재하면 "어느 산출물이 영상 어디에 나오는지"를 사후에 아무나 주장할 수 있다. 시각을 적어 두면 대조가 가능하다.

**출처는 산출물 옆에 보관한다.** 영상 파일과 같은 디렉터리에 `artifacts/provenance.jsonl`(레코드 1줄 = 산출물 1건)을 두고, 영상과 함께 제출한다. 이 파일이 없는 영상은 이 문서의 기준으로 시연 자료가 아니다. 산출물 파일 자체는 `output_sha256`으로 대조한다 — 해시가 맞지 않는 파일은 다른 파일이다.

이 기록의 목적은 감사 대응이 아니라 **자체 규율**이다. 녹화물은 반박당하지 않으므로, 반박당하지 않는다는 사실이 곧 유혹이다. 기록은 그 유혹에 대한 유일한 방어다.

## 5. GPU 상주와 스케줄링

이 장이 이 설계의 **주요 운영 리스크**다. 한 장의 GPU 위에서 세 패밀리(LLM, 이미지, 영상)가 상주를 다투고, 그 GPU를 우리만 쓰지 않는다. 상주는 배타적이고, 교체는 명시적이며, 교체에는 비용이 있다. 이 전제를 숨기면 "게이트웨이가 이미지도 영상도 즉시 준다"는 거짓 약속이 된다.

### 5.1 측정된 GPU

| 항목 | 측정값 | 설계상의 의미 |
| --- | --- | --- |
| 카드 | RTX 5090 1장 | 카드 증설은 이 설계의 범위 밖이다. 6.4는 "이 카드로 무엇이 되는가"만 다룬다 |
| 총 VRAM | 31.36 GiB | 모든 산술의 상한. 6장이 이 값을 쓴다 |
| 감사 시점 여유 | 30.83 GiB | 감사 시점에는 거의 비어 있었다. **상시 값이 아니다** |
| Compute capability | 12.0 | CUDA-13 계열 러너가 필요하다. Ollama의 러너가 드라이버 API 13.2와 일치한다 |
| 공유 상태 | 홈 계정 9개, cgroup GPU 제한 없음, `/dev/nvidia0` 전 사용자 쓰기 가능 | 5.8의 근거 |

여유 30.83 GiB를 "우리가 쓸 수 있는 양"으로 읽지 않는다. 그것은 감사 순간의 스냅샷이고, 같은 카드에 다른 사용자의 Ollama 호출이나 학습 작업이 언제든 올라올 수 있다.

### 5.2 기본 상주

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 기본 상주 패밀리 | `chat` (Ollama) | 대화가 지연에 가장 민감하고 호출 빈도가 가장 높다. 이미 유일하게 실제로 상주 중인 패밀리다 |
| 상주 판정 주체 | 게이트웨이 중재자 | 클라이언트는 상주 상태를 결정하지 않는다 |
| 상주 확인 수단 | Ollama `GET /api/ps`의 `size_vram`·`expires_at`, `cuMemGetInfo`의 여유 바이트(5.9) | `nvidia-smi`를 쓸 수 없다 |
| 상주 상태 노출 | `X-GW-GPU-State`, `/v1/models`의 `gw.resident` | 클라이언트가 상태를 숨기지 않도록 |
| 판독값 신선도 | `P_TELEMETRY_MAX_AGE_MS`보다 오래된 판독값은 **없는 것으로 취급**한다 | 다른 사용자가 예고 없이 모델을 올리므로 마지막 판독값은 언제든 틀릴 수 있다(5.9.4) |

**상주 상태는 우리 기억이 아니라 매번 다시 읽는 관측이다.** 중재자는 "내가 마지막으로 봤을 때 chat이 상주해 있었다"를 근거로 아무 결정도 하지 않는다. 상주 판정이 필요한 모든 지점(적재, 스왑, 거부)에서 `cuMemGetInfo`와 `/api/ps`를 다시 호출하고, 두 응답이 서로 모순되면(예: `/api/ps`는 모델이 있다는데 여유가 그 크기만큼 줄지 않았다) **모순을 상태로 노출**하고 적재를 보류한다. 이 규칙이 없으면 다른 사용자의 적재 한 번에 우리 중재가 조용히 틀린 판단을 한다.

### 5.3 스왑 트리거

| 트리거 | 조건 | 결과 |
| --- | --- | --- |
| 이미지 요청 도착 | chat 상주 중, 이미지 큐에 요청 존재, 배치 창 경과 | chat 언로드(`keep_alive: 0`) → 이미지 적재 → 배치 처리 → `P_LLM_RELOAD_IDLE_S` 후 chat 복귀 |
| 영상 작업 큐 선두 | 영상 작업이 admitted 상태 | chat 언로드 → 영상 모델 적재 → 작업 실행 |
| 유휴 복귀 | 마지막 chat 요청 후 `P_LLM_RELOAD_IDLE_S` 경과, 대기 중 생성 작업 없음 | chat 재적재 |
| 상주 모델 헬스 실패 | 연속 실패 `P_RESIDENT_FAIL_THRESHOLD` | 언로드, 상태 `degraded`, 이후 교체 시도 |
| 여유 VRAM 부족 | `cuMemGetInfo`의 여유가 요청 모델의 `peak_vram_gib`보다 작다 | 적재 시도하지 않고 `503 gw_gpu_busy`. 시도했다가 OOM으로 죽는 것보다 낫다 |
| **판독값 만료** | 마지막 판독 후 `P_TELEMETRY_MAX_AGE_MS` 경과 | 결정을 내리지 않고 재판독. 재판독도 실패하면 `gw_telemetry_unavailable` |
| **외부 점유 급증** | 직전 판독 대비 여유가 `P_EXTERNAL_OCCUPANCY_WARN_GIB` 이상 줄었다 | 우리가 내리지 않은 모델이 올라온 것으로 보고 `contended`. 우리 모델을 재적재하지 않는다(5.9.4) |
| 관리자 개입 | 수동 고정(`pin`) | 자동 스왑 중단. 감사 로그에 기록 |

언로드 수단은 두 가지다. LLM은 Ollama의 `keep_alive: 0`으로 즉시 내린다(3.9.2). 이미지·영상 프로세스는 우리가 실행한 것이므로 우리가 종료한다. **Ollama에 맡기지 않는다** — Ollama는 이미지·영상 모델을 모른다.

**GPU 축출(Eviction) 및 소유권 원칙 (절대 타인 작업 불간섭):**
1. **진행 중 요청 드레인(Drain) 선행:** 우리 모델을 언로드하거나 교체하기 전에는 반드시 게이트웨이가 수신하여 실행 중인 자체 in-flight 요청들을 안전하게 완료(drain)시킨 뒤에만 축출을 시작한다. **단, 드레인은 우리 작업의 안전한 종료 절차이지 GPU 자원 예약이 아니다.** 드레인 후에도 다른 사용자의 적재가 우리 자리를 차지할 수 있다.
2. **소유권 한정 축출:** 우리가 축출(언로드/종료)할 수 있는 대상은 **오직 우리 런타임과 우리가 직접 적재한 모델뿐**이다. 소유권은 `/api/ps` 조회가 아니라 우리가 발급·추적하는 런타임 리스 기록으로 판정한다.
3. **공유 `/api/ps`는 소유권 증거가 아니다:** Ollama는 공용 서비스이므로, `GET /api/ps`에 모델이 조회된다고 해서 그것이 우리 모델이라는 보장은 전혀 없다. 그러한 조회값은 `reported`(보고됨)로만 표시하고 `owned`로 승격하지 않는다. 다른 사용자가 올린 모델을 우리 임베디드 중재자가 임의로 `keep_alive: 0`을 보내 내리거나 프로세스를 강제 종료하는 행위는 **엄격히 금지**된다.
4. **분리는 예약이 아니다:** 별도 포트·별도 프로세스·컨테이너는 장애·설정 격리를 줄이지만 **GPU 메모리를 예약하지 않는다.** "우리 프로세스니까 우리 몫이 보장된다"는 서술은 이 호스트에서 성립하지 않는다.
5. **미지 측정값은 미지로 유지:** 다른 사용자의 프로세스나 메모리 점유량을 추측하거나 조작하지 않으며, 알 수 없는 지표는 항상 `unknown`으로 처리하여 거부(503)할지언정 다른 사용자의 모델을 변경하지 않는다.
6. **원격 부재는 로컬 탐색으로 증명되지 않는다:** 로컬 글롭 결과나 로컬 파일 인벤토리로 원격 호스트의 모델·백엔드 부재를 단정하지 않는다. 부재 판단에는 원격 HTTP 판독이 필요하다.

스왑 시간은 값을 발명하지 않는다. `P_SWAP_LLM_MS`, `P_SWAP_IMAGE_MS`, `P_SWAP_VIDEO_MS`를 릴리스가 서버에서 측정해 확정한다. 그 전까지 중재자는 스왑 시간을 0으로 가정하지 않는다 — 스왑 중에는 양쪽 모두 `503 gw_gpu_busy`다.

### 5.4 영상 실행 중에 chat 요청이 오면

이것이 실제로 발생하는 최악의 조합이고, 답을 고정한다.

| 상황 | 처리 | 클라이언트가 보는 것 |
| --- | --- | --- |
| 영상 `running`, chat 상주 불가 | chat 요청은 **큐 대기**(상한 `P_CHAT_QUEUE_MAX_WAIT_MS`) | 대기 중이면 응답 지연. 상한 초과 시 `503 gw_gpu_busy` + `Retry-After` |
| 영상 `running`, 남는 VRAM에 chat이 들어감(실측으로 확인된 경우만) | chat 정상 서비스 | 정상 응답. 이 경로는 실측 전 활성화하지 않는다(6.3) |
| 영상 `queued`, chat 서비스 중 | 영상은 chat이 유휴해질 때까지 대기 | `queue_position` 유지, `estimated_start_at` 갱신 |
| 영상 `running`, 다른 영상 제출 | 큐 대기(상한 `P_QUEUE_MAX_DEPTH`) | `202` + `queue_position`, 상한 초과 시 `503 gw_gpu_busy` |
| 영상 `running`, 이미지 요청 | 큐 대기 또는 `503 gw_gpu_busy` | `Retry-After` |

영상은 **선점하지 않는다**(`P_VIDEO_PREEMPT = false`). 이유: 영상을 중간에 끊으면 그때까지 쓴 GPU 시간이 산출물 없이 소모된다. 대신 영상의 최대 길이를 제한해(`P_VIDEO_MAX_DURATION_S`) 점유 시간의 상한을 만든다. 이것이 선점 대신 쓰는 통제 수단이다.

### 5.5 클라이언트가 받는 정보

- `X-GW-GPU-State`: `llm_resident | image_resident | video_running | swapping | degraded | contended`
- `X-GW-Queue-Position`: 정수 또는 없음
- `Retry-After`: 초 단위 권고
- `gw.queue_reason`: `gpu_swap | video_running | queue_full | model_loading | external_occupancy`

`contended`와 `external_occupancy`가 이 배포 환경에서 추가된 값이다. 우리 중재자가 통제하지 않는 점유(다른 사용자의 프로세스) 때문에 대기하는 상태를, 우리 스왑 때문인 것처럼 표시하지 않기 위해서다. 앱 UI는 이 값을 그대로 표시하고, "곧 됩니다" 같은 추정 문구를 넣지 않는다. 남은 시간을 모르면 모른다고 표시한다.

### 5.6 진동 방지와 공정성

- 최소 상주 시간 `P_MIN_RESIDENCY_S`: 한 번 적재한 모델은 이 시간 동안 내리지 않는다. 없으면 chat 1건과 이미지 1건이 번갈아 스왑을 유발한다.
- 이미지 배치 창 `P_IMG_BATCH_WINDOW_MS`: 창 안의 요청을 모아 한 번의 스왑으로 처리한다.
- 큐 공정성: chat이 우선이되, 생성 작업이 `P_STARVATION_GUARD_S` 이상 대기하면 chat 유휴 시점에 강제 승격한다. 승격도 스왑을 동반하므로 chat 지연이 늘어난다 — 이 맞교환을 문서화하고 파라미터로 조정한다.
- 스왑 카운터를 메트릭으로 노출한다. 스왑이 잦으면 모델 선택을 낮추거나 대기 시간을 늘리는 신호다(6.4).

### 5.7 왜 이것이 1급 리스크인가

- 상주 교체는 **지연의 원인**이고, 지연은 사용자가 가장 먼저 알아채는 품질 저하다.
- 영상 하나가 GPU를 오래 잡으면 그 시간 동안 텍스트 서비스가 degrade된다. 텍스트가 제품의 주 사용 경로라면, 영상은 텍스트의 가용성을 담보로 얻는 기능이다.
- 교체 정책을 문서화하지 않으면, "영상도 되고 채팅도 즉시 된다"는 약속이 된다. 그 약속은 한 장의 GPU에서 성립하지 않는다.
- 게다가 우리는 그 GPU의 유일한 사용자가 아니다(5.8). 우리 정책이 아무리 정교해도 다른 사용자의 직접 호출은 우리 큐를 거치지 않는다.

### 5.8 공용 GPU 중재 — 이 설계의 첫 번째 제약

#### 5.8.1 측정된 경합 환경

| 사실 | 의미 |
| --- | --- |
| 홈 계정 9개 | 이 기계는 개인 서버가 아니라 공용 워크스테이션이다 |
| Slurm·PBS 등 배치 큐 없음 | 작업 순서를 정해 주는 시스템이 없다 |
| cgroup GPU 제한 없음 | 한 사용자가 GPU를 독점해도 커널이 막지 않는다 |
| `/dev/nvidia0` 전 사용자 쓰기 가능 | 누구나 GPU 컨텍스트를 만들 수 있다. 권한으로 격리되지 않는다 |
| 감사 중 다른 사용자 2명이 세션을 돌리고 있었다 | 경합은 가정이 아니라 관측이다 |

#### 5.8.2 우리가 할 수 있는 것과 없는 것

OS가 아무것도 주지 않으므로 중재자는 **게이트웨이 프로세스 안**에 산다. 그것이 유일하게 남은 위치다. 그 위치의 한계를 정확히 적는다.

| 할 수 있다 | 할 수 없다 |
| --- | --- |
| 우리 게이트웨이를 통과한 요청의 순서를 정한다 | 다른 사용자의 직접 호출을 막는다 |
| 우리가 실행한 생성 프로세스의 적재·종료를 지시한다 | 다른 사용자의 프로세스를 종료한다 |
| Ollama에 `keep_alive: 0`으로 우리 모델을 내리게 한다 | 남이 올린 모델을 내리게 강제한다 |
| `cuMemGetInfo`로 여유를 보고 적재를 거부한다 | VRAM을 예약하거나 격리한다 |
| 우리 큐의 대기를 `contended`로 표시한다 | 우리 통제 밖의 지연을 제거한다 |

이 표의 오른쪽 열이 이 설계의 정직한 경계다. **"게이트웨이가 GPU를 관리한다"는 문장은 틀렸다.** 맞는 문장은 "게이트웨이가 **자체 요청**의 GPU 사용을 순서화하고, 여유가 없으면 자체 요청을 거부한다"이다.

#### 5.8.3 중재 규칙

1. **단일 게이트웨이 인스턴스가 GPU 소유권을 갖는다.** 두 인스턴스가 같은 카드에 각자 스왑을 지시하면 서로의 모델을 내리며 진동한다. `P_ARBITER_SINGLETON = true`가 기본이고, 두 번째 인스턴스는 기동을 거부한다.
2. **적재 전 확인.** `cuMemGetInfo`의 여유가 대상 모델의 `peak_vram_gib`보다 작으면 적재하지 않고 `503 gw_gpu_busy` + `Retry-After`를 낸다. 31.36 GiB 카드에서 이 확인이 없으면 72B 적재 시도가 다른 사용자의 실행 중 작업을 OOM으로 밀어낸다.
3. **그룹 단위 배타.** `chat`·`image`·`video`는 서로 배타적으로 상주한다(6.3의 실측 근거). 같은 그룹 안에서는 Ollama가 관리하되, 게이트웨이는 그룹 전체의 peak를 합산해 판정한다.
4. **외부 점유는 거부 사유다.** 우리 큐가 비었는데도 여유가 부족하면 그 원인은 우리 것이 아니다. 이때는 적재를 시도하지 않고 `contended`로 응답한다. 재시도를 반복하면 다른 사용자의 작업과 경합해 양쪽이 느려진다.
5. **우선순위는 우리 요청 안에서만.** chat > image > video의 우선순위는 게이트웨이 큐 안의 순서다. 다른 사용자에 대해서는 아무 우선순위도 주장하지 않는다.
6. **다른 사용자의 작업을 종료하거나 언로드하는 행위 절대 금지.** 편의 기능으로도 만들지 않는다. 공용 Ollama의 `/api/ps`에 보이는 모델이라도 우리 게이트웨이가 실행한 것이 아니면 절대 언로드(`keep_alive: 0`)하지 않는다. 오직 자체 인스턴스가 적재하고 관리하는 모델만, 진행 중인 in-flight 요청을 완전히 드레인한 후 축출한다.

#### 5.8.4 운영자에게 남는 결정

경합은 기술로 완전히 풀리지 않는다. 남는 것은 사회적 합의다. 문서에 남길 항목 세 개.

- 큰 모델(72B) 상주는 **시간대를 정해** 실행한다. 상시 기본값으로 두지 않는다.
- 우리 게이트웨이의 존재와 사용 시간대를 다른 사용자에게 알린다. 그들이 모르면 경합은 사고로 보인다.
- GPU를 독점해야 하는 작업은 게이트웨이를 우회해 직접 실행하는 편이 서로에게 낫다. 그 경우 우리 정책·쿼터는 적용되지 않는다는 것을 양쪽이 안다.

### 5.9 텔레메트리 — `nvidia-smi` 없이

#### 5.9.1 고장 상태

| 항목 | 상태 |
| --- | --- |
| `nvidia-smi` | **사용하지 않는다.** 감사 기록상 비가용이며(커널 모듈 595.84 / 유저스페이스 595.99 불일치, NVML 오류 18), 연구실이 재부팅하지 않으므로 복구를 전제하지 않는다. 이 호스트에서 `nvidia-smi`를 전제하는 도구도 쓰지 않는다 |
| 원인 | 적재된 커널 모듈 595.84, 유저스페이스 595.99의 불일치. NVML 오류 18 |
| 이 설계가 쓰지 않는 지표 | 온도, 전력, 사용률, 프로세스별 VRAM |
| 사용하는 지표 | `libcuda`의 `cuMemGetInfo`가 **정확한 바이트**를 반환한다(총량·여유). Ollama `GET /api/ps`가 적재 목록·`size_vram`·`expires_at`을 준다 |

설계 규칙: **이 설계의 어떤 판정도 `nvidia-smi` 출력에 의존하지 않는다.** 의존하면 이 서버에서 게이트웨이가 즉시 맹목이 되고, 그 상태가 영구화된다. 텔레메트리 원천은 다음 두 개뿐이며, 이 둘로 답할 수 없는 질문은 **설계에서 질문하지 않는다.**

#### 5.9.2 두 개의 텔레메트리 원천

| 원천 | 무엇을 답하는가 | 호출 | 신뢰도 |
| --- | --- | --- | --- |
| `cuMemGetInfo` (`libcuda`) | 카드 전체 여유·총 VRAM(바이트) | 게이트웨이 프로세스에서 직접 | 높음. 프로세스별 구분은 없다 |
| Ollama `GET /api/ps` | 어떤 모델이 적재되어 있는가, `size_vram`, `expires_at` | `127.0.0.1:11434` | 높음. 단 **Ollama가 올린 모델만** 보인다 |
| 이미지·영상 프로세스 상태 | 우리가 실행한 프로세스의 생존·종료 | 프로세스 핸들 | 우리 것이므로 확실 |

두 원천을 조합해 다음을 계산한다.

```
external_occupancy = total - free - sum(ollama /api/ps size_vram) - sum(our generation peak)
```

`external_occupancy`가 `P_EXTERNAL_OCCUPANCY_WARN_GIB`를 넘으면 상태를 `contended`로 두고 새 적재를 거부한다. 이 값은 **다른 사용자가 얼마나 쓰는지의 추정**이며, 정확한 프로세스별 귀속은 `nvidia-smi`/NVML 없이 이 호스트에서 확인되지 않는다. 추정임을 `gw.gpu.external_occupancy_source = "derived"`로 표시하고, 정확한 값인 것처럼 다루지 않는다.

이 유도식의 정확한 한계를 적는다. `sum(ollama /api/ps size_vram)`은 **Ollama가 올린 모델만** 센다. 다른 사용자가 Ollama 밖에서 실행한 프로세스(직접 빌드한 추론, 학습 작업)의 VRAM은 이 식에서 `external_occupancy`로 일괄 집계되고, 프로세스 이름도 사용자도 알 수 없다. 따라서 이 값으로 "누가 쓰는가"를 답하지 않는다 — 답할 수 있는 것은 "우리 몫을 뺀 나머지가 얼마인가"뿐이다.

#### 5.9.3 재부팅은 계획에 없다 — 영구 조건으로 설계한다

`nvidia-smi`를 살리려면 root 재부팅이 필요하고, 그 재부팅은 다음을 종료시킨다.

- 다른 사용자 2명의 tmux 세션
- 세 번째 사용자의 Claude·VSCode 작업

**연구실은 재부팅하지 않는다.** 이것은 "아직 결정되지 않은 일"이 아니라 내려진 결정이며, 이 문서는 그 결정을 전제로 쓰였다. 따라서 재부팅은 **대기 중인 조치도, 가능한 개선도, 미래의 해결책도 아니다.** 커널 모듈 595.84와 유저스페이스 595.99의 불일치는 이 프로젝트의 수명 동안 고정이며, 이 경로로는 `nvidia-smi`가 복구되지 않는다. "복구되면"이라는 문장을 이 문서 어디에도 쓰지 않는다 — 그 문장은 독자에게 존재하지 않는 계획을 기다리게 한다.

확인된 관측 경로와 확인되지 않은 지표를 다음처럼 구분한다. `nvidia-smi` 비가용과 재부팅 금지는 운영 제약이지, 다른 모든 관측 수단의 불가능을 증명하는 근거는 아니다.

| 지표 | 이 호스트에서 |
| --- | --- |
| 총 VRAM / 여유 VRAM | 기존 감사 기록에서 확인 — `cuMemGetInfo` |
| 적재된 Ollama 모델 목록·크기 | 기존 감사 기록에서 확인 — `/api/ps` |
| GPU 온도 | 미확인 — 이 설계는 사용하지 않음 |
| 전력 소비 | 미확인 — 이 설계는 사용하지 않음 |
| GPU 사용률(%) | 미확인 — 이 설계는 사용하지 않음 |
| 프로세스별 VRAM 귀속 | 미확인 — 이 설계는 사용하지 않음 |

이 설계는 미확인인 네 지표 없이 성립하도록 한다. 다른 계측 경로를 모두 시험해 배제한 것은 아니며, 모니터링 기능 제공이나 복구 시점을 약속하지 않는다(13.4).

관측 제약의 설계적 귀결 네 가지.

1. **과열·전력 이상을 우리가 감지할 수 없다.** 온도를 읽을 수 없으므로 "GPU가 과열되면 중단한다" 같은 보호는 설계에 넣을 수 없다. 그것은 하드웨어와 다른 사용자의 몫이다. 우리가 할 수 있는 것은 **적재를 줄이는 것**뿐이고, 그 수단은 5.8의 중재다.
2. **사용률 기반 스케줄링이 불가능하다.** "GPU가 80% 이상이면 대기" 같은 정책은 이 호스트에서 관측 불가다. 우리가 쓸 수 있는 것은 여유 바이트와 적재 목록뿐이다.
3. **프로세스별 귀속이 불가능하므로 원장의 GPU 초는 우리 작업 기준이다.** 다른 사용자가 얼마나 썼는지는 계산되지 않는다. 이 한계를 9장의 원장과 13장의 표에 명시한다.
4. **`contended` 판정은 추정이다.** 5.9.2의 `external_occupancy`는 뺄셈으로 유도한 값이며, 실제 프로세스 목록이 아니다. 이 값을 정확한 계측처럼 제시하지 않는다.

#### 5.9.4 다른 사용자는 예고 없이 모델을 올린다

이 호스트에는 조정 메커니즘이 없다(5.8.1). 다른 사용자는 우리에게 알리지 않고 자체 Ollama 모델을 올리고 내린다. 따라서 **우리가 마지막으로 읽은 여유 VRAM은 이미 틀렸을 수 있다.** 이것은 예외 상황이 아니라 정상 동작 조건이다 — 중재자는 "직전 판독값이 여전히 유효하다"는 가정을 어디에도 두지 않는다.

규칙 다섯 개.

1. **읽은 값을 캐시하지 않는다.** 적재 직전에 `cuMemGetInfo`를 다시 호출한다. `P_TELEMETRY_MAX_AGE_MS`보다 오래된 판독값으로는 적재를 결정하지 않는다.
2. **적재는 원자적이지 않다.** 우리가 확인한 뒤 적재를 시작하는 사이에 다른 사용자가 올릴 수 있다. 그래서 적재 실패(OOM)를 **정상 경로의 하나로** 처리한다: 재시도 1회 후 `503 gw_gpu_busy` + `Retry-After`. 적재 실패를 "예상 밖 예외"로 두면 재시도 폭주가 생긴다.
3. **여유가 줄어드는 방향의 변화를 정상으로 본다.** 여유가 늘어나는 것은 다른 사용자가 내린 것이고, 줄어드는 것은 올린 것이다. 둘 다 우리 통제 밖이며, 어느 쪽도 이상 징후로 경보하지 않는다. 경보는 **우리 자신의 적재가 사라진 경우**에만 낸다.
4. **`peak_vram_gib`에 헤드룸을 둔다.** 다른 사용자의 점유를 피할 수 없으므로, 우리 모델이 카드의 전부를 차지하도록 계획하지 않는다. 72B를 Q3로 올리는 작업은 **여유가 `peak + P_LOAD_HEADROOM_GIB` 이상일 때만** 허용한다. 이 헤드룸이 없으면 우리 적재가 성공해도 다른 사용자의 다음 적재가 OOM으로 죽는다.
5. **우리 모델이 사라진 것을 감지하면 재적재하지 않고 알린다.** `/api/ps`에서 우리 모델이 사라졌는데 우리가 내린 것이 아니라면, 다른 사용자의 적재가 그 자리를 차지한 것이다. 이때 즉시 재적재를 시도하면 서로 밀어내는 진동이 시작된다. `P_RESIDENT_FAIL_THRESHOLD`만큼 기다린 뒤, 여유가 헤드룸을 포함해 확보되었을 때만 재적재한다. 그동안 요청은 `contended`로 응답한다.

## 6. 서버 사이징

가격은 쓰지 않는다. 이미 있는 카드 한 장으로 무엇이 되는지만 서술한다.

### 6.1 두 개의 산술, 두 개의 결론

| 무대 | 카드 | 사용 가능 VRAM | 결론 |
| --- | --- | --- | --- |
| 랩톱 | RTX 4060 Laptop | 7.77 GiB | 27B급(7.102 GiB + KV + 약 1.21 GiB 버퍼)은 불가. 7B급(4.36 GiB)만 성립 |
| 서버 | RTX 5090 | 31.36 GiB | 27B급은 여유. 32B급은 Q4 단독, 72B급은 Q3 또는 부분 오프로드 |

같은 산술이 카드 크기에 따라 다른 결론을 낸다. 랩톱의 "27B 불가"는 서버에서 성립하지 않는다. 이 문서에서 두 값을 섞어 쓰지 않는다.

### 6.2 31.36 GiB에서의 실측 기반 판정

아래 등급은 감사에서 확인된 카드 용량과 재고 모델 크기에서 나온 판정이며, 모델별 정확한 적재 가능 여부는 `cuMemGetInfo`로 측정해 확정한다.

| 등급 | 판정 | 근거 |
| --- | --- | --- |
| ≤24B, Q4–Q8 | **여유** | 31.36 GiB에서 가중치·KV·버퍼를 모두 담을 여지가 있다. 단, 여유의 크기는 모델·컨텍스트에 따라 달라지므로 적재 전 확인은 생략하지 않는다 |
| ~32B, Q4 단독 | **단독 가능** | `qwen3:32b` 20 GB, `qwen2.5:32b` 19 GB가 재고에 있다. Q8이나 큰 KV를 추가하면 여유가 크지 않다 |
| 72B | **Q3 또는 부분 오프로드** | `qwen2.5:72b` 47 GB는 31.36 GiB에 Q4로도 들어가지 않는다. Q3 양자화나 CPU 오프로드가 필요하고, 오프로드는 지연을 크게 늘린다 |
| 이미지 (후보 가중치) | 가중치 파일 6.4118 GiB (FLUX.1-schnell Q4_0). **가중치≠VRAM** | 4.0.1의 후보 아티팩트 메타데이터. 런타임 VRAM(인코더·VAE·활성값·버퍼 포함)은 **미측정** |
| 영상 | 세 패밀리 중 가장 크다 | 재고에 없고 요구량 미측정. `P_SRV_VIDEO_MIN_VRAM_GIB` — 측정해 확정 |

확정된 것과 미확정 것을 나눈다.

- **확정**: 카드 총량 31.36 GiB. 재고 모델의 가중치 크기(20 GB·19 GB·47 GB). 이미지 후보 가중치 파일 크기(6.4118 GiB)라는 **파일 사실**.
- **미확정**: 모델별 실제 peak VRAM(양자화·컨텍스트·동시성·KV 캐시 정책에 따라 다르다), 이미지 백엔드의 런타임 VRAM 총량(별도 CLIP·T5·VAE 포함), 영상 모델의 요구량, 스왑 지연 3종.

**이미지 적재에 대해 이 문서가 하지 않는 주장.** 이미지 백엔드의 VRAM 요구량은 **측정된 적이 없다.** 따라서 "이미지 + 32B 불가"처럼 이미지 몫을 수치로 상정한 판정은 근거가 없다. 과거 초안의 fp16 대역 추정치도 근거가 확인되지 않았으므로 이 문서의 근거로 쓰지 않는다. 업스트림 `sd.cpp`의 `docs/flux.md`에 실린 6,394.53 MB / 12,068.09 MB는 **Flux-dev를 `sd-cli`로 돌린 벤치마크**이며 `schnell`이나 `sd-server`의 수치가 아니므로 우리 적재 판정에 인용하지 않는다. Q8 파일 크기(12,801,721,248 bytes)도 **파일 용량이지 VRAM 점유가 아니다.**

따라서 이미지 패밀리의 적재 판정은 **"미측정"**이며, 실측 전에는 LLM과 배타 상주로 취급한다(6.3).

**텍스트 모델 산술의 범위를 정확히 밝힌다.** "20 GiB(32B Q4 가중치) + 이미지 몫"은 이미지 몫이 미측정이므로 성립하지 않는다. 확정된 산술은 **가중치끼리의 비교**뿐이다: 32B Q4 가중치 20 GiB와 72B Q4 가중치 47 GB는 각각 단독으로 카드에 들어가는지 여부가 갈린다(6.1). 이미지와의 조합은 측정 전 어떤 방향으로도 단정하지 않는다.

영상에 대해서는 **아무 수치도 쓰지 않는다.** 모델이 없으므로(4.0) 요구 VRAM을 모른다. "27B + 영상 동시 상주 불가"라고 쓰고 싶은 유혹이 있지만, 영상 요구량을 모르는 상태에서 그 문장은 산술이 아니라 짐작이다. 그래서 이 문서는 그 문장을 쓰지 않고, `P_SRV_VIDEO_MIN_VRAM_GIB`를 측정 항목으로 남긴다. 영상 모델이 설치되고 측정되면 그때 판정한다.

### 6.3 동시 상주 판정

| 조합 | 동시 상주 | 근거 |
| --- | --- | --- |
| LLM(≤24B) + 이미지 | **가능성 높음, 실측 필요** | 24B Q4는 대략 14–16 GiB 대, 이미지 fp16 10–16 GiB. 합이 31.36에 근접하지만 KV·버퍼까지 더하면 여유가 작다. 측정 전에는 단일 상주로 취급 |
| LLM(32B) + 이미지 | **불가** | 가중치만 20 GiB + 10–16 GiB > 31.36. KV·컨텍스트를 더하면 격차가 더 벌어진다 |
| LLM(72B) + 무엇이든 | **불가** | 47 GB 가중치 자체가 카드보다 크다. Q3·오프로드로 줄여도 이미지와 겹치지 않는다 |
| 이미지 + 영상 | 측정 전 불가로 취급 | 영상 요구량 미측정(6.2). 둘 다 대형이라는 것만 알고, 스왑으로 순차 처리한다 |
| LLM(7B) + 이미지 | **가능** | 4.36 GiB + 10–16 GiB는 31.36 안에 들어간다. 이 조합이 가장 현실적인 동시 상주다 |

**여기에 없는 조합은 판정하지 않는다.** 특히 "LLM + 영상"은 영상 요구량이 측정되기 전까지 어떤 방향으로도 쓰지 않는다. 표에 없다는 사실이 "불가"를 뜻하지 않고 "모른다"를 뜻한다.

설계 규칙: **동시 상주는 실측으로 확인된 조합에만 허용한다.** 확인 전에는 중재자가 그룹 배타로 동작한다(5.8.3). 이 보수성이 공용 기계에서 사고를 줄인다.

### 6.4 이 한 장으로 무엇이 되는가

| 구성 | 성립하는 것 | 성립하지 않는 것 |
| --- | --- | --- |
| A. 단일 카드, 그룹 배타 | LLM·이미지·영상을 순차 제공. 32B까지 단독, 24B+이미지 가능성 | 72B 상시, 생성 중 즉시 대화 |
| B. 단일 카드, LLM 전용 상주 + 생성은 시간대 분리 | 대화 응답성 유지 | 생성 기능의 상시 제공 |
| C. LLM은 프록시, GPU는 생성 전용 | 생성 처리량 | 자체 호스팅의 프라이버시 이점. 이 변경의 핵심 포기 |

권고는 A다. 카드가 한 장뿐이고 증설이 범위 밖이므로 선택지가 좁다. A에서 72B는 **상시 기본값이 아니라 계획된 작업**이며(5.8.4), 이미지·영상은 대화의 가용성을 담보로 얻는 기능이다. 이 맞교환을 숨기지 않는다.

랩톱의 산술을 서버 권고로 옮겨 적지 않는다. 랩톱에서 "27B 불가"였던 이유는 7.77 GiB였고, 서버는 31.36 GiB다. 같은 문장을 두 곳에 쓰면 한 곳은 반드시 틀린다.

### 6.5 디스크와 회선

| 자원 | 측정값 | 설계상의 의미 |
| --- | --- | --- |
| `/` 여유 | 1.1 TB | 모델·산출물·로그를 담기에 충분하다. 다만 321.4 GB의 기존 재고가 이미 이 볼륨에 있다 |
| 미마운트 NVMe | 931.5 GB, 다른 OS의 파티션 보유, 완전 미마운트 | **사용 불가로 취급한다.** 마운트에는 root가 필요하고, 남의 OS 파티션을 건드린다. 빠른 저장소가 될 수 있다는 가능성만 기록하고 설계는 그것을 전제하지 않는다 |
| 아웃바운드 | 6.5 MB/s (약 52 Mbit/s) | 다중 GB 다운로드는 **계획된 작업**이다. 아래 계산 |

회선 속도의 귀결을 산술로 적는다. 6.5 MB/s에서 20 GB 모델 하나는 약 3,200초(50분대), 47 GB 모델은 약 7,200초(2시간) 규모다. 이 시간 동안 회선은 다른 사용자와 공유된다. 따라서:

- 모델 다운로드를 게이트웨이 요청 경로에서 트리거하지 않는다. 사용자가 모델을 고르면 즉시 내려받는 설계는 이 회선에서 남의 대화 지연을 만든다.
- 설치는 운영자가 시간대를 정해 수행하고, 완료 후 allowlist에 추가한다.
- 산출물(영상) 업로드·다운로드도 같은 회선을 쓴다. 영상 1건의 전송량이 대화 수백 건과 맞먹는다는 것을 원가 계산에 넣는다(14.3).

## 7. 제어 평면 — 프리셋·카탈로그 배포

### 7.1 배포물

하나의 서명된 manifest가 다음을 담는다.

```json
{
  "contract": "gw1",
  "catalog_version": "<string>",
  "channel": "stable | canary | pinned",
  "issued_at": "<ISO 8601>",
  "expires_at": "<ISO 8601>",
  "min_client": "<semver>",
  "upstreams": [ "<2.5의 업스트림 레코드, 비밀 제외>" ],
  "models": [ { "id": "<string>", "upstream_id": "<string>", "family": "chat|image|video",
                "zero_data_retention": true, "training_opt_out": true,
                "retention_evidence": "<string|null>", "roles": ["<string>"] } ],
  "presets": [ { "id": "<string>", "role": "<string>", "model_id": "<string>",
                 "params": { "<키>": "<값>" } } ],
  "policy": { "default_route": "zdr_cloud", "denied_models": ["<id>"] },
  "revocations": [ { "kind": "model|upstream|client", "id": "<string>", "reason": "<string>" } ]
}
```

봉투는 서명을 분리한다.

```json
{ "payload": { "<위 객체>" }, "signatures": [ { "key_id": "<string>", "alg": "Ed25519", "sig": "<base64>" } ] }
```

정규화는 키 정렬 + 공백 없는 JSON으로 고정한다(`P_MANIFEST_CANON`). 정규화 규칙이 없으면 서명이 환경마다 달라진다.

### 7.2 서명과 검증

- 서명은 릴리스 파이프라인에서 만들고, 개인키는 게이트웨이에 두지 않는다. 게이트웨이는 **배포자**이지 서명자가 아니다. 서버가 침해되어도 새 프리셋을 위조할 수 없어야 한다.
- 클라이언트는 공개키 목록을 내장하고 `key_id`로 고른다. 목록은 `P_MANIFEST_KEY_COUNT`개까지 회전 여유를 둔다.
- 검증 항목: 서명 유효, `contract` 일치, `expires_at` 미경과, `min_client` 충족, 모델 ID 중복 없음, `upstream_id` 참조 무결성, `denied_models`와 `revocations`의 상호 모순 없음.

### 7.3 서명 검증 실패 시 (fail closed)

| 실패 종류 | 클라이언트 동작 | 클라우드 라우트 | 로컬 평면 |
| --- | --- | --- | --- |
| 서명 불일치 | 신규 manifest 설치 거부. 마지막 검증본 유지 | 마지막 검증본 정책으로만 허용 | 영향 없음 |
| 알 수 없는 `key_id` | 설치 거부. 사용자에게 "배포 키 미지" 표시 | 마지막 검증본 정책으로만 허용 | 영향 없음 |
| `expires_at` 경과 | 설치 거부. `preset_state = stale` | 마지막 검증본 정책으로 요청하되, 서버가 `409 gw_preset_stale`을 반환하면 차단 | 영향 없음 |
| 검증본이 하나도 없음 | 클라우드 기능 비활성 | 전면 차단 (`gw_preset_missing`) | 영향 없음 |
| `min_client` 미충족 | 설치 거부 | 차단 | 영향 없음 |
| 모델 ID 중복 | 무결성 실패로 취급, 설치 거부 | 마지막 검증본으로만 | 영향 없음 |

핵심: **서명 실패는 로컬 평면을 멈추지 않는다.** 그리고 서명 실패를 "경고 후 적용"으로 처리하지 않는다. 경고 후 적용은 서명 검증을 형식으로 만든다.

### 7.4 릴리스 채널과 버전 고정

| 채널 | 뜻 | 대상 |
| --- | --- | --- |
| `stable` | 검증된 카탈로그. 기본값 | 전체 |
| `canary` | 새 모델·프리셋 선배포. 되돌림 전제 | 운영자·초대 사용자 |
| `pinned` | 사용자가 특정 `catalog_version`을 고정 | 재현성이 필요한 사용자 |

- 클라이언트는 `catalog_version`과 `contract`를 함께 고정한다. 계약이 바뀌면 프리셋 의미도 바뀐다.
- 게이트웨이는 N-1 계약을 수용한다(`P_CONTRACT_SUPPORT_DEPTH`). 그 밖의 버전은 `409 gw_preset_stale` + `required_catalog_version`.
- 되돌림: `revocations`에 모델·업스트림을 넣어 배포하면 다음 조회에서 즉시 반영된다. 이미 받은 응답은 되돌릴 수 없고, 되돌릴 수 없는 것을 되돌린다고 쓰지 않는다.

### 7.5 서버가 강한 이유, 그리고 그 한계

서버 배포의 강점은 **"개발자가 고정한 프리셋"이 실제로 고정된다**는 것이다. JSON 파일 배포에서는 사용자가 파일을 열어 모델을 바꾸고 파라미터를 지운다. 서명 검증을 붙여도, 사용자는 검증 코드를 지우거나 프리셋 캐시를 편집할 수 있다.

한계를 정확히 말한다.

- **클라우드 요청**에서는 프리셋이 실제로 고정된다. 게이트웨이가 요청을 받아 자체적으로 파악한 프리셋과 모델로 처리하므로, 클라이언트가 무엇을 주장하든 서버의 프리셋이 적용된다.
- **로컬 요청**에서는 고정되지 않는다. 로컬 추론은 사용자 기계에서 사용자 파일로 돈다. 서명은 "무결성 확인"이지 "강제"가 아니다.
- 따라서 "프리셋은 서버가 강제한다"는 문장은 **클라우드 평면 한정**이다. 이 한정을 빼면 과장이다.

**강제의 구체적 수단을 밝힌다.** "서버의 프리셋이 우선한다"는 요청 파라미터가 어떻게 처리되는지를 정하지 않으면 근거 없는 주장이다. 3.2.1이 그 처리를 규정한다: 프리셋이 명시한 키만 서버 값으로 **덮어쓰고**, 덮어쓴 키 이름과 서버 값을 `gw.overridden_params`에 담아 응답에 싣는다. 조용한 덮어쓰기는 하지 않는다. 프리셋이 명시하지 않은 키는 클라이언트 값을 그대로 통과시킨다.

이 선택이 만드는 정확한 강제 범위는 다음과 같다.

| 파라미터 | 강제되는가 |
| --- | --- |
| 프리셋이 명시한 키(`temperature`, `top_p`, `seed` 등) | 강제됨. 클라이언트 값은 무시되고, 무시된 사실이 응답에 표시된다 |
| 프리셋이 명시하지 않은 키 | 강제되지 않음. 클라이언트 값이 그대로 전달된다 |
| 모델 ID 자체 | 강제됨. 프리셋이 모델을 고정하므로 클라이언트의 모델 주장은 무시된다 |
| `max_tokens` | 강제됨(쿼터 상한과 프리셋 상한 중 작은 값) |

즉 "프리셋이 우선한다"는 **프리셋에 적힌 것에 한해** 참이다. 프리셋에 없는 파라미터까지 서버가 결정한다고 주장하지 않는다.

### 7.6 현재 카탈로그의 무결성 결함 (설계가 수정해야 할 것)

배포되는 `40_AI보고서/packaging/customization/catalog.json`의 모델 레코드는 `id, display_name, provider, roles, context_window, zero_data_retention` 여섯 필드다. `training_opt_out`은 그 파일에 없다 — 원본 `40_AI보고서/engine/registry.py:211`의 `PrivacyPolicy`에만 있고, JSON 생성 단계에서 빠진다.

결과: **배포 파일만 읽는 클라이언트는 `zdr_cloud` 조건(`zero_data_retention && training_opt_out`)을 계산할 수 없다.** 현재 카탈로그로는 정책을 강제할 수 없고, 강제한다고 주장하면 거짓이 된다.

설계 요구: manifest의 모델 레코드는 두 플래그를 **모두** 담고, `retention_evidence`를 함께 담는다. 그리고 무결성 검사에서 "`zdr_cloud` 라우트가 활성인데 `training_opt_out`이 `null`인 모델이 있으면 manifest 무효"로 처리한다.

## 8. 키 보관 모델

두 모드를 지원한다. 둘 다 정직하게 쓴다.

### 8.1 모드 (a): 팀 보유 키 + 상한 무료 쿼터

- **구조.** 우리가 제공자 키(OpenRouter, A6API 등)를 보유하고, 사용자는 게이트웨이 토큰만 갖는다. 사용자는 제공자 계정이 없어도 쓴다.
- **"무료"의 정직한 조건.** 무료라고 부르려면 (1) 사용자별 쿼터 수치가 정의되고, (2) 게이트웨이가 그것을 강제하며, (3) 사용자가 잔여량을 볼 수 있어야 한다. 세 조건 중 하나라도 없으면 "무료"가 아니라 "우리가 비용을 부담하는 동안 열려 있는 상태"다. 후자는 제품 주장이 아니다.
- **저장.** 키는 KMS 봉투 암호화로 저장하고, 복호화는 요청 처리 프로세스의 메모리에서만 한다. 회전 주기는 `P_KEY_ROTATE_DAYS`.
- **절대 로그 금지.** 업스트림 `Authorization` 헤더, 키의 접두·접미 일부, 키가 포함된 오류 본문, 요청 본문 전체. 로그에 남길 수 있는 것은 `key_id`(식별자)와 `upstream_id`뿐이다.
- **침해 시 노출.** 우리 제공자 키 → 공격자가 우리 계정으로 과금한다. 노출 범위는 그 키가 접근할 수 있는 모델 전체다.
- **프롬프트 노출에 대해 정확히 쓴다.** "보관하지 않으므로 노출되지 않는다"는 틀린 문장이다. 게이트웨이는 프롬프트 본문을 **처리한다** — 복호화·전달·리댁션을 하려면 평문이 메모리에 있어야 한다. 따라서 **실행 중인 게이트웨이가 침해되면 처리 중인 평문이 노출된다.** 로그가 0줄이어도 마찬가지다. 비보관이 줄여 주는 것은 **과거분의 노출**이지 **처리 중 노출**이 아니다. 이 구분을 흐리면 "우리는 프롬프트를 저장하지 않는다"가 "우리는 프롬프트를 볼 수 없다"로 둔갑한다.
- **완화.** 제공자 계정의 지출 상한(제2 방어선), 키별 사용량 급증 알림, 즉시 폐기 절차.

### 8.2 모드 (b): BYOK 브로커

- **구조.** 사용자가 자체 제공자 키를 게이트웨이에 등록하고, 게이트웨이가 그 키로 대신 호출한다. 클라이언트에는 키가 남지 않는다.
- **저장.** 사용자별로 분리 저장, KMS 봉투 암호화, 데이터 암호화 키는 사용자 단위. 복호화는 요청 처리 중에만 하고, 평문 수명은 요청 1건으로 제한한다(가능한 범위에서 메모리 0화).
- **절대 로그 금지.** 모드 (a)와 같고, 추가로 등록·회전 API의 요청 본문(키가 들어 있다)을 어떤 수준에서도 남기지 않는다. 감사 로그에는 "등록됨", "회전됨", "폐기됨"만 남긴다.
- **침해 시 노출.** 암호문 + KMS 복호 권한이 동시에 침해되면 사용자 키 평문이 노출된다. 노출 범위는 그 사용자의 제공자 계정이다. 우리 키는 노출되지 않는다.
- **프롬프트 노출.** 모드 (a)와 같다. 이 모드에서 게이트웨이는 사용자 키로 복호화한 뒤 요청을 처리하므로, 침해된 게이트웨이는 **키와 프롬프트를 동시에** 볼 수 있다. 두 모드의 차이는 "누구의 키가 노출되는가"이지 "프롬프트가 안전한가"가 아니다.
- **주장의 한계.** 게이트웨이가 요청을 처리하려면 키를 복호화해야 한다. 따라서 "우리는 사용자 키를 볼 수 없다"고 주장할 수 없다. 주장할 수 있는 것은 **"클라이언트는 키를 저장하지 않는다"** 와 **"서버는 키를 암호화해 저장하고 본문·키를 로그에 남기지 않는다"** 두 가지다. 이 구분을 흐리면 8.1의 실수를 반복한다.

### 8.3 두 모드 공통 금지

| 금지 | 이유 |
| --- | --- |
| 요청·응답 본문의 기본 로깅 | 프롬프트에 코드·개인정보가 들어 있다. 보존하면 삭제·통지 의무가 발생한다 |
| 오류 메시지에 업스트림 응답 원문 포함 | 업스트림이 헤더·키 조각을 되돌려 주는 경우가 있다 |
| 추적(trace)에 헤더 전체 기록 | `Authorization`이 그대로 들어간다 |
| 키를 클라이언트로 반환 | 회수 불가 |
| 키를 manifest에 포함 | manifest는 공개 배포물이다 |

리댁션은 로그 파이프라인 입구에서 적용하고, 리댁션 실패 시 해당 레코드를 **버린다**(남기지 않는다). 남기는 쪽이 안전하다고 판단하지 않는다.

### 8.4 모드 선택

| 상황 | 권장 모드 | 이유 |
| --- | --- | --- |
| 교육 과정, 소규모 팀, 데모 | (a) | 사용자에게 제공자 계정을 요구하지 않는다. 대신 쿼터를 반드시 정의한다 |
| 개인 연구, 자체 키를 이미 가진 사용자 | (b) | 비용이 사용자에게 귀속되고 우리 지출이 없다 |
| 키 취급 자체를 피하고 싶은 운영자 | 모드 없음(자체 호스팅만) | 프록시 라우트를 비활성화하면 키가 필요 없다 |

세 번째 줄을 명시하는 이유: 키를 아예 다루지 않는 구성이 존재하며, 그 구성은 `server_local` 클래스만으로 성립한다. 이 사실을 숨기고 BYOK를 강요하지 않는다.

### 8.5 이 서버에서의 저장 현실

키 저장소를 "KMS"라고 적는 것만으로는 부족하다. 이 호스트에는 root가 없고 docker도 없다. KMS는 우리가 설치할 수 있는 것이 아니다.

| 요구 | 이 호스트에서의 실현 |
| --- | --- |
| 암호화된 저장 | 애플리케이션 수준 암호화. 마스터 키는 `~/.config/<gw>/` 아래 `0600` 파일 또는 기동 시 환경변수 |
| 마스터 키 보호 | root 소유 비밀이 아니라 **우리 홈의 파일 권한**이다. 같은 기계의 다른 사용자는 권한이 없으면 읽지 못한다 |
| 복호화 시점 | 요청 처리 중 메모리에서만 |
| 회전 | `P_KEY_ROTATE_DAYS`, 수동 스크립트 |

정직하게 말한다. **"KMS"라는 단어를 이 배포에 쓰면 과장이다.** 우리가 가진 것은 파일 권한과 애플리케이션 암호화이고, 그것은 같은 계정이 침해되면 함께 무너진다. 8.1·8.2의 "침해 시 노출" 서술은 이 전제 위에서 읽어야 한다.

호스트 자체가 공용 기계라는 사실도 여기 들어간다. 다른 사용자가 우리 홈을 읽을 권한은 없지만, root는 있다. 우리 위협 모델에 root를 포함하면 파일 기반 키 보호는 성립하지 않는다. 그것을 포함하지 않는다는 결정을 여기 적어 둔다 — 포함하면 이 설계의 키 보관은 모두 무효가 되고, 그것이 이 환경의 실제 조건이다.

## 9. 쿼터와 비용 원장

### 9.1 원장 레코드

요청 1건당 1레코드. 필드는 다음과 같다. 전부 설계 필드다.

| 필드 | 뜻 |
| --- | --- |
| `request_id` / `job_id` | 상관 키 |
| `user_id`, `token_id` | 과금·감사 주체 |
| `ts`, `route_effective`, `model_id`, `upstream_id`, `upstream_class` | 무엇을 어디로 보냈는가 |
| `prompt_tokens`, `completion_tokens`, `total_tokens` | 사용량 |
| `image_count`, `video_seconds`, `gpu_seconds` | 생성 워크로드 사용량 |
| `cost_estimated`, `cost_actual`, `currency` | 비용 |
| `usage_state` | `known` / `partial` / `unknown` |
| `status` | `ok` / `refused` / `upstream_error` / `client_abort` / `gateway_restart` |
| `refusal_code` | 거부 사유(거부된 경우) |

`refused` 레코드는 비용 0이고 사용량 0이다. 이것은 "미상"과 다르다 — 거부는 확실히 0이다.

### 9.2 예약과 정산

1. **예약.** 요청 전에 최대 비용을 계산해 잔여 쿼터에서 차감한다. 텍스트는 `max_tokens` × 출력 단가 + 입력 추정. 이미지는 장수 × 단가. 영상은 `duration_s` × 초 단가.
2. **판정.** `잔여 − 예약 < 0`이면 업스트림 접촉 전에 `429 gw_quota_exhausted`. 이 순서가 중요하다. 접촉 후에 거부하면 이미 돈을 쓴 뒤다.
3. **정산.** 응답 usage로 `cost_actual`을 확정하고 예약과의 차액을 되돌린다.
4. **실패·취소·중단.** 9.2.1의 단일 규칙을 따른다. 여기서 "예약 해제"나 "예약 유지"를 따로 정하지 않는다.

### 9.2.1 실패·취소·중단의 정산 단일 규칙

동기 텍스트, 이미지, 비동기 영상, 스트리밍 중단, 작업 취소가 모두 이 표 하나를 따른다. 이전 판본은 3.5("실패 시 소모 없음"), 4장("실패하면 예약 해제"), 9.2("과금 가능성 있으면 예약 유지")에서 서로 다른 말을 했다. 하나로 통일한다.

| 업스트림이 사용량을 보고했는가 | 업스트림이 이미 과금했을 수 있는가 | `usage_state` | 원장 처리 | 사용자 표시 |
| --- | --- | --- | --- | --- |
| 보고함(성공·부분 성공·중도 종료 모두) | 무관 | `known` 또는 `partial` | 보고값으로 정산, 예약과의 차액 반환 | 사용량·비용 확정 |
| 보고 없음, 업스트림 미접촉(게이트웨이가 거부) | 아니오 — 접촉 자체가 없었다 | 해당 없음 | 예약 생성 전이므로 되돌릴 것도 없다 | 쿼터 불변 |
| 보고 없음, 업스트림 접촉 후, 업스트림이 **과금하지 않음을 확인**했다(예: 서버 자체 GPU가 산출물 없이 종료) | 아니오 | `known`(0) | 예약 전액 해제 | 쿼터 전액 복구 |
| 보고 없음, 업스트림 접촉 후, 과금 여부 **미확인**(외부 프록시·프로바이더) | 예 | `unknown` | **예약을 해제하지 않고 유지** | "미확정 1건"으로 표시, 잔여에서 차감된 채 남음 |
| 취소됨(`cancelled`) | 무관 | 보고가 있으면 `known`/`partial`, 없으면 `unknown` | 위 네 줄 중 해당하는 것 | 취소 응답에 정산 상태 동봉 |

규칙의 핵심은 하나다. **"모르면 0으로 적지 않는다."** 서버 자체 GPU(`server_local`)는 우리가 실행 주체이므로 "산출물 없이 끝났다 = 우리 자원만 소모, 외부 과금 없음"을 확인할 수 있다. 그래서 예약을 해제할 수 있다. 외부 프록시나 다이렉트 업스트림은 그 확인이 불가능하므로 `unknown`으로 남긴다. 이 비대칭은 의도된 것이고, 업스트림 class가 판정 근거다.

`unknown`이 영구히 남지는 않는다. 9.5의 대사(reconciliation) 절차가 나중에 확정하거나, `P_UNKNOWN_EXPIRY_DAYS` 경과 후 운영자가 확정한다. 그때까지는 잔여에서 차감된 상태를 유지한다 — 사용자에게 유리하게 0으로 만들면 원장이 실제 지출보다 작아진다.

비동기 영상 작업에서 이 규칙이 특히 중요하다. 제출 시 최대치로 예약하고(긴 영상 여러 개가 원장을 음수로 만드는 것을 막는다), 실패 시 위 표의 셋째·넷째 줄로 갈린다. 서버 GPU에서 큐 대기 중 취소된 작업은 GPU를 쓰지 않았으므로 전액 해제, GPU에서 실행 중 취소된 작업은 실제 소모 초로 `partial` 정산한다.

### 9.3 하드 캡과 거부

- 사용자별 캡, 일별 캡, 월별 캡(`P_QUOTA_USER`, `P_QUOTA_DAILY`, `P_QUOTA_MONTHLY`), 전역 일별 캡(`P_GLOBAL_DAILY_CAP`).
- 캡 도달 시 응답: `429` + `error.code = gw_quota_exhausted` + `X-GW-Quota-Reset`(ISO 8601) + 본문에 `scope`(user/daily/monthly/global).
- 캡은 게이트웨이에서만 강제된다. 클라이언트 표시는 참고값이며, 클라이언트가 캡을 우회할 수 없다는 것이 이 구조의 요점이다.
- 전역 캡은 남용 방어의 마지막 층이다. 사용자 캡이 정상인데 전역 캡이 걸리면, 그 사실을 사용자에게도 알린다(원인 불명의 거부를 만들지 않는다).

### 9.4 클라이언트 표시

- 모든 응답 헤더에 `X-GW-Quota-Remaining`, `X-GW-Quota-Reset`.
- `GET /v1/quota`가 상세를 준다: `limit`, `used`, `reserved`, `remaining`, `unknown_count`, `reset_at`, `scope_list`.
- 앱 UI는 "남은 쿼터"와 별도로 **"미확정 N건"** 을 표시한다. 미확정을 남은 쿼터에 합쳐 표시하면 사용자는 실제보다 많이 남았다고 오해한다.
- 표시는 마지막 조회 시점의 스냅샷이다. 실시간이 아니라는 것을 UI에 쓴다.

### 9.5 미상은 0이 아니다

원장에서 지켜야 하는 유일한 규칙: **사용량을 모르면 `unknown`으로 기록한다.** 0으로 기록하면 총합이 조용히 틀리고, 캡이 실제보다 늦게 걸리며, 비용 보고가 사실과 달라진다.

`unknown`이 생기는 경로: 업스트림이 usage를 안 주는 경우, 스트림이 중단된 경우, 게이트웨이가 재시작된 경우, 클라이언트가 먼저 끊었고 업스트림 보고가 없는 경우. 각 경우에 `usage_state = unknown`이고, 예약액은 `P_UNKNOWN_SETTLE_FACTOR`(0과 1 사이)만큼 유지한 뒤 만료 시점에 확정한다. 이 계수는 파라미터이며 값을 발명하지 않는다.

비용 보고에서 `unknown` 비율을 별도 지표로 노출한다. 이 비율이 높으면 업스트림의 usage 보고를 신뢰할 수 없다는 뜻이고, 그것은 제품 주장의 근거를 약화시킨다.

원장은 회계이지 청구서가 아니다. 이 설계에는 결제 기능이 없다. 사용자에게 금액을 청구하지 않는다.

## 10. 라우트 정책 강제

### 10.1 세 라우트

| 라우트 | 허용되는 것 | 강제 지점 | 사용자에게 약속하는 것 |
| --- | --- | --- | --- |
| `local_only` | 랩톱 로컬 추론만 | 클라이언트 (랩톱) | 프롬프트가 기기를 떠나지 않는다 |
| `zdr_cloud` | `zero_data_retention && training_opt_out`을 만족하고 근거가 있는 업스트림만 | 게이트웨이 | 제3자 보존·학습 없음(업스트림 진술 기준) |
| `any_cloud` | allowlist 전체(금지 목록 제외) | 게이트웨이 | 정책상 허용된 업스트림 어디로든 |

### 10.2 어디서 강제되는가

| 라우트 | 클라이언트의 역할 | 서버의 역할 |
| --- | --- | --- |
| `local_only` | 유일한 강제자. 로컬 엔드포인트만 호출한다 | `local_only` 요청이 게이트웨이에 도착하면 거부한다(구현은 `400 local_only_not_served`, 이 문서의 설계명은 `403 gw_route_forbidden`). 즉 **SSH로 포워딩한 게이트웨이는 `local_only`의 로컬 평면이 될 수 없다** — 그 엔드포인트를 지나면 추론은 다른 호스트에서 일어난다. 로컬 전용 클라이언트가 클라우드로 보낼 이유가 없으므로, 이 도착은 오설정 또는 우회 시도다 |
| `zdr_cloud` | 선언만. 판정하지 않는다 | 판정자. 모델별 두 플래그와 근거를 확인하고, 불충족이면 업스트림 접촉 전에 403 |
| `any_cloud` | 선언만 | 판정자. 금지 목록·폐기 목록을 적용 |

`local_only`는 서버가 강제할 수 없다는 점을 인정한다. 서버는 클라이언트가 로컬만 썼는지 관측할 수 없다. 그래서 `local_only`의 보장은 **클라이언트 소프트웨어에 대한 신뢰**이며, 이는 `zdr_cloud`의 보장과 성격이 다르다. 두 보장을 같은 무게로 쓰지 않는다.

### 10.3 A6API는 비ZDR이다

이 프로젝트는 `a6api/deepseek-chat-v3.1`을 비ZDR로 기록한다. **두 플래그의 출처가 다르므로 따로 적는다.**

| 플래그 | 값 | 지지 출처 | 출처 개수 |
| --- | --- | --- | --- |
| `zero_data_retention` | `false` | 배포 JSON `40_AI보고서/packaging/customization/catalog.json:33` **및** 원본 레지스트리 `40_AI보고서/engine/registry.py:553` | 2 (일치) |
| `training_opt_out` | `false` | 원본 레지스트리 `40_AI보고서/engine/registry.py:553`만 | 1 |

**배포 JSON에는 `training_opt_out` 필드가 존재하지 않는다.** 따라서 "배포 카탈로그가 두 플래그를 모두 false로 기록한다"고 쓰면 틀린다. 배포 파일만 가진 클라이언트는 `training_opt_out`을 알 수 없고, `zdr_cloud` 조건을 계산할 수 없다(7.6). 이 구분은 사소한 것이 아니다 — 정책 집행자가 어느 파일을 읽는지에 따라 판정 가능 여부가 갈린다.

위 기록에 따라:

- `zdr_cloud` 라우트에서 `a6api/*`는 **부적격**이다.
- 게이트웨이는 이 요청을 업스트림으로 넘기지 않고 `403 gw_route_forbidden`으로 거부한다. 거부 사유 코드는 `route_requires_zdr`이고, 응답에는 어느 플래그가 미충족인지 명시한다.
- **이 거부는 쿼터 예약보다 앞이고, 업스트림 접촉보다 앞이다.** 순서는 3.8에 고정되어 있다: allowlist 해석 → 라우트 판정(여기서 거부) → 쿼터 예약 → 업스트림 호출. 거부된 요청은 원장에 `refused`로 남고 비용은 0이다. 이 순서를 지키지 않으면 "거부했는데 쿼터가 줄었다" 또는 "거부했는데 프록시에 프롬프트가 갔다"가 된다.
- 클라이언트가 `X-GW-Route: any_cloud`를 선언해도, 토큰 정책이 `zdr_cloud`면 더 엄격한 쪽이 적용되어 여전히 거부된다(10.4).
- A6API를 `zdr_cloud`에서 쓰고 싶다면, 라우트를 바꾸는 것이 아니라 **근거를 확보**해야 한다. 제공자의 보존 정책 문서를 `retention_evidence`로 등록하고 그 사실이 확인되기 전까지는 부적격이다.

**우리 기록과 제공자의 실제 정책은 다르다.** 위 두 값은 우리 카탈로그의 기록이며 제공자의 보증이 아니다. 실제 정책 확인은 표 C에 있고, 현재 미검증이다.

이전 감사의 지적은 프록시를 근거 없이 프라이버시 안전으로 표기한 데 있었다. 같은 실수를 반복하지 않기 위한 일반 규칙을 둔다: **`retention_evidence`가 없는 모델은 `zdr_cloud`에서 자동 제외한다.** 근거 없는 `true`는 `false`와 같게 취급한다. 이 규칙 때문에 `server_local` 모델도 예외가 아니다 — 우리가 운영한다는 사실이 ZDR의 근거는 아니며, 근거는 "우리가 무엇을 보관하는지에 대한 문서"다.

### 10.4 불일치 시

규칙: **항상 더 엄격한 쪽.**

| 클라이언트 선언 | 토큰 정책 | 유효 라우트 | 결과 |
| --- | --- | --- | --- |
| `any_cloud` | `zdr_cloud` | `zdr_cloud` | 비ZDR 모델은 403 |
| `zdr_cloud` | `any_cloud` | `zdr_cloud` | 클라이언트가 더 엄격. 그 요청은 ZDR 조건으로 처리 |
| `local_only` | 무엇이든 | — | 403 (요청이 게이트웨이에 왔다는 것 자체가 모순) |
| 없음 | `zdr_cloud` | `zdr_cloud` | 기본값 적용 |
| `any_cloud` | `local_only` | — | 403 |

"클라이언트가 더 엄격하게 주장하면 그 주장을 존중한다"는 것이 두 번째 줄의 뜻이다. 서버가 클라이언트보다 느슨하게 판정하는 방향은 없다.

### 10.5 폴백은 존재하지 않는다

- 게이트웨이는 **폴백을 하지 않는다.** 선택된 업스트림이 실패하면 그 요청은 실패다(2.6). manifest의 `policy`에 폴백 허용 필드를 두지 않는다 — 필드가 있으면 "언젠가 켜질 수 있는 것"으로 읽히고, 그 순간 1:1 규칙이 조건부가 된다.
- 정책 거부(403)뿐 아니라 **업스트림 장애(502/503/504)도** 폴백으로 우회되지 않는다. 이 둘을 구분해 온 것은 "정책 위반은 재시도 대상이 아니다"라는 뜻이었고, 폴백 금지는 그보다 넓다: 어떤 실패도 다른 업스트림 선택으로 바뀌지 않는다.
- 사용자가 다른 모델을 원하면 새 요청에서 다른 모델 ID를 고른다. 클라이언트 UI는 실패 화면에서 "다른 모델로 다시 시도"를 제안할 수 있다. 그것은 **사용자의 클릭**이고, 게이트웨이는 여전히 그 새 요청 하나만 처리한다.
- 응답 스키마에 `fallback_used`를 두지 않는다. 값이 항상 `false`인 필드는 "폴백이 일어날 수 있다"는 인상을 남긴다. 실제로는 `gw.upstream_id` 하나만 노출하면 충분하다 — 어디로 갔는지가 궁금한 사용자에게 필요한 것은 그 값이다.

| **GPU 텔레메트리 상실** | 아무 표시 없음(사용자에게 무의미). 운영 로그에만 기록 | 영향 없음 | 정상 | `cuMemGetInfo`·`/api/ps`도 실패하면 **적재 판정을 거부 모드로 전환**(여유를 모르면 올리지 않는다) |

시계 오차의 구체 규칙.

- 게이트웨이는 모든 응답에 `Date`를 넣는다. 클라이언트는 자체 시계와의 차이를 계산해 `P_CLOCK_SKEW_S` 초과면 경고를 표시한다.
- manifest 만료는 `expires_at`(절대 시각)으로 판정한다. 클라이언트 시계가 뒤로 가 있어도 만료된 manifest를 유효로 만들 수 없다 — 서버가 계약 버전으로 다시 판정하기 때문이다.
- 토큰은 짧은 수명(`P_TOKEN_TTL_S`)과 `iat`/`exp`를 갖는다. 허용 오차는 `P_TOKEN_SKEW_S`이며, 그보다 큰 오차는 거부가 아니라 재인증 요구로 처리한다.

### 11.1 터널 단절이 다른 실패와 다른 점

같은 "연결 없음"처럼 보여도 원인이 다르고, 사용자가 할 일도 다르다. 그래서 표에서 분리했다.

| 원인 | 사용자가 할 일 | 우리가 할 수 있는 일 |
| --- | --- | --- |
| 터널 미개설 | SSH 명령 실행 | 문서화된 명령을 제공 |
| 터널 단절 | 재연결 | keepalive 파라미터로 조기 감지 |
| 게이트웨이 미기동 | 운영자에게 문의 | 프로세스 감시(14.2) |
| 서버 자체 다운 | 운영자에게 문의 | 없음 |

네 경우를 "서버 연결 없음" 하나로 합치면, 사용자는 자체 터널을 다시 열어야 하는 상황에서 운영자를 기다리거나 그 반대를 한다.

### 11.2 텔레메트리 상실이 설계에 강제하는 것

`nvidia-smi`가 없고 `cuMemGetInfo`·`/api/ps`에 의존하는 구조에서, 그 두 원천마저 실패하는 경우를 정한다.

- **여유를 모르면 적재하지 않는다.** 추측으로 72B를 적재했다가 다른 사용자의 작업을 OOM으로 밀어내는 것이, 기능을 잠시 거부하는 것보다 나쁘다.
- 거부 사유는 `gw_gpu_busy`가 아니라 `gw_telemetry_unavailable`로 구분한다. 원인이 다르면 운영자의 조치도 다르다.
- 5분 이상 지속되면 운영 알림을 낸다. 이 상태가 길어지면 서버 LLM 기능 전체가 멈춘 것이므로, 조용히 지나가면 안 된다.

## 12. 랩톱 평면의 불변성

서버가 없을 때 무엇이 유지되고, 무엇이 저하되고, 무엇이 실패하는지 명시한다. "저하"와 "실패"를 섞으면 사용자는 없는 기능을 기다린다.

여기서 "서버가 없을 때"는 두 경우를 모두 포함한다. **서버가 살아 있지만 터널이 없는 경우**(가장 흔하다)와 **서버 자체가 죽은 경우**다. 랩톱의 동작은 두 경우에 동일하다 — 랩톱은 차이를 관측할 수 없고, 관측할 수 없는 차이를 표시하지 않는다.

**시연 형태가 이 장의 무게를 정한다.** 심사에 제출되는 것은 사전 녹화 영상이고(0.5), 시연 시점에 서버는 필요 없다. 따라서 **랩톱 평면 하나로 시연이 성립해야 하며, 서버 평면은 시연의 구성 요소가 아니다.** 이 장의 목록이 곧 영상에 담을 수 있는 것의 상한이다. 영상에 나오는 모든 장면은 다음 둘 중 하나로 분류되고, 그 분류가 화면에 표시된다.

| 장면 종류 | 조건 | 표시 |
| --- | --- | --- |
| 랩톱 장면 | 12.1의 목록 안에 있고, 지금 사용자의 랩톱에서 재실행해 같은 결과가 나온다 | 표시 없음(기본) |
| 서버 footage | 녹화 시점에 서버에서 동작했고, 지금 재현은 보장되지 않는다 | "서버에서 촬영(녹화 시점)" 라벨(12.6) |

세 번째 종류는 없다. **랩톱에서 재현되지 않는데 랩톱 화면처럼 보이는 장면**은 이 설계에서 금지다.

### 12.1 유지된다 (서버 없이 동작)

이 항목들이 **시연의 전부**다. 영상에서 랩톱 화면으로 나오는 것은 이 목록 안에 있어야 한다(0.5.1). 목록 밖의 것을 랩톱 화면으로 보여 주려면 먼저 이 목록에 넣을 수 있는지 증명해야 한다.

- `omp` TUI 시작, `--mode rpc` stdio NDJSON 루프, 세션·대화 이력.
- **SQLite FTS5 어휘 메모리 계층**(2.1.1). 인덱스 구축·질의·갱신이 모두 로컬 파일 I/O이므로 터널·게이트웨이·서버와 무관하게 동작한다. 서버가 죽어도 과거 기록 검색은 그대로 된다. 이 항목은 "저하"가 아니라 "유지"다 — 메모리는 네트워크를 쓰지 않도록 설계되었기 때문이다. **시연에서 이 계층은 서버 장면이 아니라 랩톱 장면으로 나온다.**
- `40_AI보고서/app/`의 HTTP·WS 브리지와 웹 UI (루프백).
- 로컬 llama.cpp 호출: Qwen2.5-Coder-7B Q4_K_M(4.36 GiB)로 포그라운드 코딩. 파일 편집·도구 실행·셸.
- 마지막으로 검증된 프리셋으로 로컬 동작. 서명 검증은 로컬에서 계속 수행된다.
- 로컬 라우트(`local_only`)의 전 기능.

#### 12.1.1 시연 재현성

영상에 담긴 랩톱 장면은 **사용자의 랩톱에서 다시 실행해 같은 결과가 나와야 한다.** 재현되지 않는 장면은 시연이 아니라 일화다. 이를 위해:

- 각 장면은 스크립트로 구동되고, 그 스크립트가 저장소에 있다(규칙 V-1).
- 장면에 쓰인 모델·프리셋·파라미터를 영상과 함께 기록한다.
- 랩톱의 하드웨어 조건(8 GB급 카드, 7.77 GiB 사용 가능)이 결과에 영향을 주는 장면은 그 조건을 명시한다. 다른 기기에서 다르게 보일 수 있다는 사실을 숨기지 않는다.

**재현 시험이 곧 시연 허가다.** 스크립트를 다른 날 다시 돌려 같은 출력이 나오지 않는 장면은 영상에서 빼거나, "이 장면은 녹화 시점 1회 실행"이라고 표시한다. 표시 없는 1회성 성공은 시연이 아니다.

### 12.2 저하된다 (동작하지만 품질·범위가 줄어든다)

"저하"는 **기능이 사라지지 않는** 경우다. 사용자는 같은 일을 할 수 있지만 더 느리거나 더 약한 결과를 받는다.

| 항목 | 저하 내용 |
| --- | --- |
| 모델 품질 상한 | 7B급. 서버의 24B·32B·72B 모델 품질을 기대할 수 없다 |
| 긴 컨텍스트 | 랩톱 VRAM 제약. 서버 모델의 컨텍스트를 대체하지 못한다 |
| 카탈로그 최신성 | 마지막 검증본에 고정. 새 모델은 보이지 않는다 |
| 공유 상태 | 서버가 가진 팀 쿼터·사용 이력 조회가 불가능해진다. 대화 자체는 로컬에 남는다 |

주의: 백그라운드 모델은 이 표에 넣지 않는다. 이 PC는 Tier 2이므로 Bonsai 백그라운드가 원래 `unavailable`이고, 이는 서버 유무와 무관한 기존 조건이다. 서버 문제로 생긴 저하가 아니다.

**"저하"를 "실패"로 적지 않는 이유**와 그 반대도 마찬가지다. 저하를 실패로 적으면 사용자는 동작하는 기능을 포기하고, 실패를 저하로 적으면 없는 기능을 기다린다. 이 문서에서 저하는 12.2에만, 실패는 12.3에만 둔다.

### 12.3 실패한다 (의도된 실패, 대체 없음)

| 항목 | 표시 |
| --- | --- |
| `zdr_cloud`, `any_cloud` 라우트 | "서버 없이 사용 불가" |
| 서버 LLM(24B·32B·72B) | "서버 필요" |
| 이미지 생성 | "서버 필요"(그리고 현재는 서버에도 없음 — 13.1 A-2) |
| 영상 생성 | "서버 필요"(그리고 현재는 서버에도 없음 — 13.1 A-2) |
| 새 프리셋·모델 설치 | "서버 필요" |
| 다중 사용자 협업·세션 공유 | "서버 필요" |

**시연과의 관계를 명시한다.** 위 표의 항목은 영상에 나올 수 없다. 영상에 이미지·영상 생성 결과가 나온다면 그것은 4.7의 출처 레코드를 가진 **사전 생성 산출물**이고, 생성 장면이 아니라 결과 장면이다(0.5.2). 표 B의 서버 측정 항목도 영상에 나올 수 없다 — 측정이 끝나지 않았다면 그 수치를 자막으로 쓰지 않는다.

### 12.4 조용한 대체 금지

기존 설계의 태도를 계승한다. 적합한 모델이나 업스트림이 없으면 `unavailable`과 사유를 반환하고, 다른 모델·다른 라우트로 조용히 대체하지 않는다. 서버가 죽었을 때 클라우드 요청을 로컬 7B로 자동 전환하는 것은 대체이며, 금지한다. 사용자가 명시적으로 선택하는 것은 대체가 아니다.

이유는 품질이 아니다. **라우트는 데이터 경로에 대한 약속**이다. `zdr_cloud`를 요청한 사용자가 로컬 7B 결과를 받으면 데이터는 안전하지만, 결과의 출처가 바뀌었고 사용자는 통보받지 못했다. 약속의 내용이 조용히 바뀌는 것이 문제다.

### 12.5 이 배포 형태에서 반드시 지킬 것

터널 구조가 만드는 함정 네 개를 명시한다.

1. **터널이 없다고 로컬 엔드포인트로 대체하지 않는다.** 원격 모델을 요청했는데 연결이 없다면 실패가 정답이다. 로컬로 우회하면 사용자는 자신이 무엇을 받았는지 모른다.
2. **터널을 사용자 몫으로 두되, 문서화한다.** 터널은 클라이언트가 여는 것이므로 우리가 대신 열어 줄 수 없다. 대신 정확한 명령과 로컬 포트, 그리고 실패 시 표시를 제공한다(2.7.2). **비밀번호만 가진 사용자가 이 문서만으로 도달할 수 있어야 한다** — Tailscale을 기본값으로 만들지 않는 이유가 이것이다(2.7.5).
3. **`0.0.0.0` 바인딩을 절대 만들지 않는다.** 터널 로컬 포트를 모든 인터페이스에 열면 같은 네트워크의 다른 기기가 인증된 터널을 공유한다. 편의를 위한 선택지로도 제공하지 않는다.
4. **터널을 시연의 전제로 만들지 않는다.** 시연 영상은 랩톱 평면만으로 성립해야 한다(12.1). "터널이 열려 있어야 영상이 성립한다"는 설계는 이 문서의 프레이밍과 모순이다.

### 12.6 시연 영상에 서버 장면을 넣을 때

시연은 사전 녹화이고 서버는 시연의 구성 요소가 아니므로(0.5), 서버 장면은 **선택 사항**이다. 넣는다면 랩톱 장면과 섞이지 않게 표시 규칙을 지킨다. **랩톱 장면과 서버 장면을 섞으면 심사자는 전부 랩톱에서 일어난 일로 읽는다.**

| 규칙 | 내용 |
| --- | --- |
| 장면 라벨 | 서버 footage의 모든 화면 모서리에 "서버에서 촬영(녹화 시점)" 라벨. 녹화 후 편집으로 붙이지 않고 화면에 원래 있던 표시를 쓴다 |
| 랩톱 장면 우선 | 영상의 랩톱 부분은 12.1의 목록만 쓴다. 서버가 있어야만 되는 기능을 랩톱 화면처럼 보이게 하지 않는다 |
| 산출물 표시 | 서버가 생성한 이미지·영상은 4.7의 `captured_on`을 화면에 적는다. 산출물은 **녹화 전에 생성된 것**이며 생성 장면이 아니다 |
| 실패 장면 | 실패를 보여 주는 장면은 편집으로 지우지 않는다. 실패를 숨긴 영상은 "무엇이 안 되는가"를 심사자에게서 감춘다 |
| 서버 생략 가능 | 서버 장면을 모두 빼도 영상은 성립한다. 서버 footage가 없어서 생기는 공백을 랩톱 화면이나 자막으로 메우지 않는다 |

마지막 두 규칙이 가장 지키기 어렵고 가장 중요하다. 이 프로젝트의 이전 문제는 성공을 과장한 것이지 실패를 보여 준 것이 아니었다. 그리고 영상은 반박당하지 않으므로, **없는 서버 장면을 랩톱 화면으로 대신 채우는 유혹**이 가장 크다. 그 유혹이 이 절이 존재하는 이유다.

## 13. 주장 가능한 것

엄격하게 나눈다. 표 A는 **측정으로 검증된 것**이다. 표 B는 **서버에서 관측·측정되기 전까지** 주장할 수 없다(실제 제공자 키는 불필요). 표 C는 **실제 제공자 키·계약이 생기기 전까지** 검증할 수 없다.

한 가지 구분을 도입부에 못 박는다. **"호스트에 무엇이 설치되어 있는가"는 검증된 사실이고, "우리 게이트웨이가 그것을 정책 아래에서 중계한다"는 검증되지 않은 설계다.** 이 둘을 한 줄에 섞으면 이전 감사의 실수를 반복한다.

또 하나를 더 못 박는다. **시연이 사전 녹화 영상이므로, "시연에 등장"과 "구현됨"과 "설계만"은 서로 다른 상태다.** 이 문서는 이 셋을 한 문장 안에서도 섞지 않는다.

### 13.0 다섯 가지 상태 — 시연 등장, 사전 산출물, 구현, 설계를 분리한다

| 상태 | 뜻 | 증거 | 제품 주장 가능 |
| --- | --- | --- | --- |
| **검증됨** | 지금 이 순간 측정·실행으로 확인된다 | 로그·명령·출력 | 예 |
| **시연 등장** | 녹화 시점에 랩톱에서 동작하는 장면이 영상에 있다. 그 시점의 실행 기록이 남아 있다 | 스크립트 + 실행 로그(V-1) | "녹화 시점에 동작했다"까지만. "지금 동작한다"는 아니다 |
| **사전 생성 산출물** | 서버가 녹화 전에 만든 이미지·영상이 영상에 삽입되었다. 생성 과정은 영상에 없다 | 4.7의 출처 레코드(명령·모델·파라미터·해시) | "이 산출물이 존재한다"까지만. "생성 기능이 동작한다"는 아니다 |
| **부분 구현** | 일부 코드가 있고 일부 경로가 동작하나, 계약 전체가 관측된 적은 없다 | 코드 + 부분 시험 | 동작하는 부분만, 범위를 명시해 |
| **설계만** | 계약·정책·상태 기계가 문서에 있고 코드는 없다 | 이 문서 | 아니오. "설계했다"만 |

핵심 규칙 세 개.

1. **"시연 등장"은 "구현됨"을 함의하지 않는다.** 영상에 화면이 나왔다고 그 기능이 완성된 것이 아니다.
2. **"구현됨"은 "검증됨"을 함의하지 않는다.** 코드가 있다고 계약대로 동작한다고 주장할 수 없다.
3. **"사전 생성 산출물"은 "시연 등장"보다 약하다.** 산출물이 영상에 보인다는 사실은 그 산출물이 존재한다는 것만 말한다. 생성 파이프라인이 동작한다는 것, 지금 재현된다는 것은 말하지 않는다.

**이 문서가 설계하는 것 중 코드가 있는 부분과 없는 부분을 섞지 않는다.** 게이트웨이는 **부분 구현**이다 — 요청 검증(자체 Bearer·identity), 자체 라우트 판정, 업스트림 전달, `/api/ps` 관측, identity별 요청·토큰 쿼터 예약과 정산(`gateway/lib/quota.mjs`)은 코드가 있고, 출하 예제 구성은 `8000`에서 수신한다. 반면 GPU 중재자·리스·큐·스왑·GPU 입장 제어와 이 문서가 정의한 증명·가격·턴 원장 바인딩 및 manifest 배포는 **설계만**이다. 기존 쿼터 구현을 모든 원장 계약의 완성으로 해석하지 않는다. 정확한 경계는 13.0.2에 적는다. 이 구분이 이 장의 첫 문장인 이유는, 뒤의 어떤 표도 이 상태를 조용히 승격시키지 않기 위해서다.

이 문서가 설계하지 않은 것은 별도로 취급한다. 세 종류가 있다.

| 종류 | 예 | 상태 |
| --- | --- | --- |
| 이미 존재하고 관측된 것 | `omp` 18.16.0, `40_AI보고서/app/`의 브리지, 랩톱 llama.cpp, Ollama 0.21.0, 서버 GPU | **검증됨**(표 A). 우리가 만든 것이 아니라 관측한 것이다 |
| 이미 존재하지만 일부만 확인된 것 | 게이트웨이의 검증·라우트·업스트림·`/api/ps` 관측 경로, `app/` 브리지의 게이트웨이 연동 경로, 서버의 이미지·영상 추론 | **부분 구현** 또는 **없음**(13.0.2) |
| 이 문서가 설계한 것 | GW-1 계약, GPU 중재·리스·큐·스왑, 쿼터 원장 강제, manifest 배포 | **설계만** |

`40_AI보고서/app/`이 첫째 줄과 둘째 줄에 동시에 나오는 이유를 밝힌다. 그 디렉터리에는 `server.mjs`, `websocket.mjs`, `test/protocol.test.mjs` 등이 실제로 있고 시험이 존재한다(표 A-1). 그러나 **그 브리지는 omp의 stdio와 WebSocket 사이를 잇는 것이지, 게이트웨이의 정책·쿼터·라우트를 구현한 것이 아니다.** 브리지의 존재를 게이트웨이의 존재로 읽으면 이전 감사가 지적한 실수를 그대로 반복한다.

### 13.0.1 서버 평면의 지위 — 설계 + 부분 구현, 시연의 구성 요소 아님

시연이 사전 녹화 영상이므로(0.5), **서버 평면은 시연 시점에 존재할 필요가 없다.** 이것은 서버 평면의 완성도를 낮추는 것이 아니라, 서버 평면에 대한 주장의 성격을 바꾼다.

| 항목 | 랩톱 평면 | 서버 평면 |
| --- | --- | --- |
| 시연에서의 역할 | **유일한 필수 조건.** 영상의 화면은 여기서 나온다 | 선택. footage를 넣지 않아도 영상은 성립한다 |
| 요구되는 상태 | 검증됨(표 A) | 설계 + 부분 구현 |
| 시연 시점의 가용성 | 랩톱이 켜져 있어야 한다 | 무관하다. 꺼져 있어도 된다 |
| 실패가 시연을 막는가 | 막는다 | 막지 않는다 |
| 실패가 무엇을 막는가 | 영상 제작 자체 | 서버 footage 장면 하나 |

**이 표의 마지막 두 줄이 가장 오해되기 쉽다.** "서버가 없어도 시연이 된다"는 사실은 서버 평면의 미완성을 면제하지 않는다. 서버 평면에 대해 "구현되었다"고 쓰려면 여전히 표 B가 통과해야 한다. 달라진 것은 **시연과의 결합이 끊겼다**는 것뿐이다.

그리고 이 지위는 하나의 유혹을 만든다. **서버가 시연에 필요 없으니, 서버 기능을 랩톱 화면으로 대신 보여 주려는 유혹이 생긴다.** 그것은 금지다(12.6). 서버 기능을 랩톱에서 모방하는 장면은 랩톱 장면도 서버 footage도 아니며, 이 문서의 어떤 상태로도 분류되지 않는다.

### 13.0.2 현재 게이트웨이 코드의 실제 강제 범위 — 잔여 통합 격차

이 문서의 나머지 장은 **계약**을 적는다. 계약과 현재 코드가 같은 것을 재는지 분명히 하기 위해, 확인된 코드 거동과 아직 연결되지 않은 부분을 여기서 한 번만 정확히 나눈다. 이 절의 목적은 기능 자랑이 아니라 **격차의 명시**다.

**현재 코드가 실제로 하는 것**

| 항목 | 상태 |
| --- | --- |
| 게이트웨이 수신 포트 | 출하 예제 구성은 `8000`. 일반 기본값·스텁 구성은 `8787`. **두 값은 서로 다른 설정이며 코드를 고칠 이유가 아니다** |
| 요청 검증 | 자체 Bearer 토큰과 자체 identity 검증. **외부의 독립적 동의 증명(attestation)을 검증하지 않는다** |
| 라우트 판정 | 자체 allowlist·자체 라우트 규칙만 판정. 클라이언트가 보낸 동의 서술을 권위로 받아들이지 않는다 |
| GPU 관련 거동 | **`/api/ps` 관측과 그 결과의 `reported`/`unknown` 표시까지.** 중재·리스·큐·스왑·입장 제어는 **설계 상태이며 강제되지 않는다** |
| 앱(`40_AI보고서/app/`)의 라우팅 | **게이트웨이와 같은 3값을 쓴다.** 브리지는 `x-route` 헤더(`local_only`/`zdr_cloud`/`any_cloud`)를 만들어 모델 가용성 조회에 보내고, 클라우드 값은 그 대화의 명시적 동의 없이는 헤더를 만들지 않아 요청 자체가 나가지 않는다(`app/server.mjs`의 `routeHeaders`). **추론 요청**은 코어(`omp`)가 자기 `models.yml`로 수행하며, 브리지는 그 provider `headers`에 `x-route: OMP_BRIDGE_ROUTE`가 적혀 있을 때 자식 환경변수 `OMP_BRIDGE_ROUTE`로 대화 경로를 넣어 준다. 항목이 없으면 추론 요청에 헤더가 실리지 않는다. 브리지는 실행 전에 `models.yml`/`models.json`의 `x-route` 값을 omp와 같은 방식으로 해석해 대화 경로와 다르면 `launch_failed`로 코어를 실행하지 않는다(`routeHeaderProblem`) |
| 앱의 동의 처리 | 랩톱 UI와 브리지의 로컬 가드다. **게이트웨이 동의 헤더로 전달되는 구조가 아니다.** 따라서 "게이트웨이가 사용자 동의를 확인한다"고 쓰지 않는다 |
| 서버 1차 모델 후보 | 게이트웨이 측 검토가 진행 중이며, 후보 ID는 **현재 출하 allowlist의 활성 항목이 아니다.** 추측된 `qwen3.5` 계열 ID와 새로 검증된 Qwen3.8-27B를 자동 활성화하지 않는다(3.9.0) |

**아직 연결되지 않았거나 수정이 진행 중인 것 (문서가 강제를 주장하면 안 되는 항목)**

1. **요청별 게이트웨이 라우팅은 배선되지 않았다.** 브리지 자신이 만드는 `x-route` 헤더(위 표)는 모델 가용성 조회(`GET <endpoint>/models`)에만 붙는다. 추론 요청에 같은 값이 실리는 경우는 코어 설정(`models.yml`의 provider `headers`)이 `OMP_BRIDGE_ROUTE`를 참조하도록 **미리 적혀 있을 때뿐**이며, 그 설정이 없으면 추론 요청에는 헤더가 없다. 어느 경우든 요청은 정책 판정을 거치지 않는다. "매 추론 요청이 정책 판정을 거쳐 게이트웨이로 간다"는 문장은 현재 코드에 대해 성립하지 않는다.
2. **동의(consent)는 게이트웨이 계약이 아니다.** 동의 확인은 랩톱 UI와 브리지의 로컬 가드에 있고, 게이트웨이는 독립적 동의 증명을 검증하지 않는다. 게이트웨이가 검증하는 것은 자체 라우트·Bearer·identity다.
3. **`local_only` 거부의 균일성.** 영상 상태 폴링과 산출물 조회가 `local_only` 거부를 우회하던 결함은 수정되어 `x-route`를 검사하며, `gateway/test/routes.test.mjs`가 두 경로에서 `local_only_not_served`와 업스트림 호출 0회를 단정한다(스텁 대상). 다만 **앱 브리지가 게이트웨이를 경유해 추론을 보내지 않으므로**, 이 강제는 게이트웨이에 도착한 요청에만 적용된다.
4. **thinking 패스스루는 안전하지 않다는 검토 결과가 있어 채택하지 않는다.** 모델의 사고(reasoning) 필드를 클라이언트로 그대로 전달하는 경로는 이 계약에 넣지 않으며, 관련 수정은 게이트웨이 담당에 배정되어 있다. 따라서 이 문서는 thinking 필드의 통과·보존을 약속하지 않는다.
5. **컨텍스트·출력 상한의 균일 강제는 확인되지 않았다.** 8,192 같은 상한을 전 표면에서 강제한다고 주장하지 않는다. 상한은 릴리스에서 측정·검증할 항목이며, 강제가 확인되기 전에는 "설계값"으로만 적는다.
6. **쿼터 원장은 턴 원장이 아니다.** 원장은 요청 단위 계량이며, `TurnPlan` 계층의 턴 단위 기록과 동일한 객체가 아니다(2.1.2). 두 이름을 혼용하지 않는다.

이 격차는 실패가 아니라 **상태**다. 다만 격차를 적지 않은 문서는 계약을 성과로 읽히게 만든다. 그래서 이 절이 13장의 앞부분에 있다.

### 13.2 표 B — 서버 필요 (서버에서 관측되어야만 주장 가능, 실제 제공자 키는 불필요)

이 항목들은 스텁 업스트림·테스트 키페어·실제 Ollama로 증명할 수 있다. 실제 제공자 호출은 필요 없다.

두 가지 증거 등급을 구분하는 열을 둔다. **스텁**은 우리가 만든 가짜 업스트림으로 계약·정책 동작을 증명하는 것이고, **실측**은 서버의 실제 GPU·실제 모델에서 숫자를 얻는 것이다. 둘은 다른 주장이며, 스텁 통과를 실측으로 승격하지 않는다.

| GW-1 계약대로 `/v1/models`, `/v1/chat/completions`가 동작하고 스트리밍이 `[DONE]`으로 종료된다 | 스텁 | 스텁 업스트림 + 계약 시험 | |

**이 표에서 서버 키가 필요 없는 항목은 하나도 표 C로 가지 않는다.** 이미지·영상·VRAM·스왑·처리량은 서버 GPU에서 측정하면 끝나는 문제이고, OpenRouter나 A6API 키와 아무 관계가 없다. 이전 판본이 이 항목들을 표 C에 넣은 것은 분류 오류였다.

### 13.3 표 C — 실제 키 필요 (제공자 키·계약이 있어야만 주장 가능, 현재 미검증)

**이 표에는 제공자 의존 항목만 둔다.** 서버에서 측정 가능한 것은 모두 표 B다.

| 주장 | 왜 지금 불가능한가 |
| --- | --- |
| OpenRouter 모델의 실제 지연·품질·비용 | 실호출 필요 |
| A6API의 실제 데이터 보존·학습 정책이 카탈로그 기록과 일치한다 | 제공자 문서·계약 확인 필요. 카탈로그 값은 우리 기록이지 제공자 보증이 아니다 |
| OpenRouter 모델의 `zero_data_retention: true`가 실제로 지켜진다 | 공급자 진술이며 우리가 검증한 사실이 아니다 |
| 제공자별 레이트 리밋·오류율 | 실호출 필요 |
| 제공자 과금이 원장 예상치와 일치한다 | 실제 청구서 대조 필요 |

**표 C에 넣지 않는 것 — 키로 풀리지 않는 항목.** 이전 판본은 "다른 사용자의 점유를 정확히 귀속시킨다"를 표 C에 넣었으나, 그것은 키가 없어서 불가능한 것이 아니라 이 호스트에서 NVML을 쓸 수 없어서 불가능하다. 키를 얻어도 풀리지 않는 항목을 표 C(키가 생기면 검증 가능)에 두면 "키만 있으면 언젠가 된다"는 오해를 만든다. 그런 항목은 아래 13.3.1에만 둔다.

### 13.3.1 표 C에 넣지 않는, 키로 풀리지 않는 항목

| 항목 | 왜 표 C가 아닌가 |
| --- | --- |
| 다른 사용자의 점유를 프로세스별로 귀속 | 감사 기록상 NVML(오류 18)이 비가용이고 재부팅도 금지되어 있다(5.9.3). 제공자 키와 무관하며, 이 경로로는 해결되지 않는다. 다른 계측 수단의 불가능까지 입증한 것은 아니다 |
| GPU 온도·전력·사용률 조회 | 같은 이유. 5.9.3의 네 지표는 이 설계에서 사용하지 않는다 |

### 13.5 시연 영상이 주장할 수 있는 것

영상은 반박당하지 않으므로, 영상의 주장에도 보고서와 **같은 증거 기준**을 적용한다(규칙 V-1). 영상에 담을 수 있는 주장의 종류를 미리 고정한다.

| 영상이 말하려는 것 | 필요한 증거 | 없으면 |
| --- | --- | --- |
| "랩톱에서 이렇게 동작한다" | 12.1 목록 안의 장면 + 재현 스크립트 + 실행 로그 | 영상에 넣지 않는다 |
| "녹화 시점에 서버에서 이렇게 동작했다" | 서버 footage + 스크립트 + 로그 + 화면 라벨 | 넣지 않거나, 넣되 라벨 없이는 쓰지 않는다 |
| "이 이미지·영상이 우리 시스템의 산출물이다" | 4.7의 출처 레코드(명령·모델·파라미터·`output_sha256`) | 넣지 않는다 |
| "이 수치는 우리가 측정했다" | 표 B의 실측 등급 통과. 측정 명령과 출력 | 수치를 자막·내레이션에 쓰지 않는다 |
| "이 정책이 강제된다" | 표 B의 스텁 등급 통과(거부 응답·원장 대조) | "설계했다"로만 말한다 |

**내레이션 규칙을 한 줄로 고정한다: 화면에 없는 것은 말하지 않는다.** 영상의 해설은 화면에서 관측 가능한 것과, 그 화면에 대응하는 이 문서의 장(章)만 인용한다. "내부에서는 이렇게 처리됩니다" 같은 설명은 화면에 그 처리가 보이지 않으면 주장이고, 주장은 표 A·B·C를 통과해야 한다.

**산출물의 출처를 영상 안에서 밝힌다.** 서버가 만든 이미지·영상이 영상에 들어가면, 그 장면에 `captured_on: server`와 생성 시각을 표시한다(4.7). 표시가 없으면 심사자는 랩톱이 만든 것으로 읽고, 그것은 이 문서가 금지하는 오해다. 표시는 **녹화 후 편집으로 붙이는 자막이 아니라 4.7 레코드에서 생성한 캡션**이어야 한다 — 편집으로 붙인 라벨은 산출물과 분리되어 검증될 수 없다.
| "서버가 없으면 시연이 안 된다" | 시연은 사전 녹화다(0.5). 랩톱 화면만으로 성립한다 |
| "영상에 이 기능이 나왔으므로 구현되었다" / "시연용이므로 구현으로 쳐 준다" | 시연은 사전 녹화라 실패가 편집으로 사라진다. 영상의 주장도 보고서와 같은 증거 기준을 통과해야 한다(V-1). 시연 등장은 어떤 상태도 승격시키지 않는다(13.0, 13.0.1) |
| "서버 평면은 시연에 필요 없으므로 완성되지 않아도 된다" | 시연과의 결합이 끊긴 것과 주장 자격은 별개다. 서버 기능을 주장하려면 표 B가 통과해야 한다(13.0.1) |
| "GPU 온도·전력을 모니터링한다" / "사용률을 본다" / "프로세스별 VRAM을 본다" | `nvidia-smi`가 비가용(NVML 오류 18)이고 재부팅도 하지 않으므로 이 설계는 네 지표를 사용하지 않는다. 다른 계측 수단을 모두 시험해 배제한 것은 아니지만, 이 지표들로 제품 기능을 주장하지 않는다(5.9.3) |
| "재부팅하면 nvidia-smi가 살아난다" / "복구를 기다린다" / "다음 재부팅 때" | 연구실이 재부팅하지 않는다. 복구를 계획된 조치로 쓰지 않는다(5.9.3, 14.6) |

## 14. 배포와 운영 비용

### 14.1 사용자 공간 배포 (root 없음)

이 호스트에는 sudo가 없고 docker·podman도 없다. 따라서 이전 판의 "리버스 프록시 + TLS + KMS + 데이터베이스" 구성은 **이 서버에서 실현 불가능하다.** 없는 권한을 전제한 배포 계획은 계획이 아니다.

#### 14.1.1 가용한 도구

| 도구 | 상태 | 쓸 수 있는가 |
| --- | --- | --- |
| Node 22.23.1 | 이미 설치 | **예.** 빌드 도구 없이 게이트웨이를 돌릴 수 있는 가장 확실한 경로 |
| `python3` 3.12.3 | 설치됨, PEP-668 externally-managed | 예, `python3 -m venv ~/.venvs/gw` 안에서만 |
| `pip` 시스템 전역 | externally-managed로 거부됨 | 아니오 |
| docker·podman | 없음 | 아니오 |
| conda·uv | 없음 | 아니오 |
| torch·cmake·ninja | 없음 | 아니오(CUDA 확장 빌드 불가) |
| `systemd --user` | 유닛 0개, 등록 가능 여부 미확인 | 부분적 — 14.1.3 |
| root | 없음 | 아니오 |

CUDA를 직접 호출해야 하는 부분(5.9.2의 `cuMemGetInfo`)은 컴파일이 필요 없다. `libcuda.so`를 런타임에 바인딩하면 되고, Node에서는 `ffi` 계열, Python에서는 `ctypes`가 그 역할을 한다. `torch`가 없다는 사실이 `cuMemGetInfo`를 막지 않는다 — 이것이 `nvidia-smi` 대신 `libcuda`를 쓰는 선택의 부수적 이점이다.

#### 14.1.2 게이트웨이 프로세스

| 결정 | 선택 | 이유 |
| --- | --- | --- |
| 런타임 | Node 22.23.1 (1순위), Python venv (2순위) | Node는 이미 있고 빌드가 필요 없다. Python은 `venv`가 홈 안에서 성립한다 |
| 위치 | `~/<gw>/` 아래 전부. 설정·원장·로그·산출물 | root가 없으므로 `/opt`·`/etc`·`/var`를 쓸 수 없다 |
| 바인딩 | `127.0.0.1:<게이트웨이 포트>` | 2.3의 B-6 |
| 파일 디스크립터 | 기동 시 소프트 상한을 하드 상한 쪽으로 올린다(`P_NOFILE_SOFT`) | **소프트 1024로는 동시 SSE + 웹소켓에서 게이트웨이가 죽는다.** 연결당 최소 1개, SSE·WS·업스트림·로그·원장을 합치면 수백 개가 순식간이다. 런처가 `ulimit -n`(또는 동등 호출)로 올리지 못하면 **기동을 거부**한다 — 조용히 낮은 상한으로 뜨면 부하가 몰릴 때 원인 불명으로 죽는다 |
| 영상·이미지 산출물 | `~/<gw>/artifacts/` + TTL 삭제 | 오브젝트 스토리지가 없다. 로컬 파일 + 서명 URL로 대체 |
| 원장 | SQLite 파일 또는 JSONL + 주기적 스냅샷 | 별도 DB 서버를 띄울 권한이 없다. 단일 프로세스 전제와 맞는다 |
| 비밀 | `~/.config/<gw>/` 아래 `0600` 파일 | 8.5 |

#### 14.1.3 프로세스 수명

`systemd --user`는 현재 유닛이 0개이고, 이 환경에서 사용자 유닛이 실제로 동작하는지는 **미확인**이다(부록 B). 따라서 기본은 **tmux 세션에서 수동 기동**이다.

| 방식 | 성립 | 대가 |
| --- | --- | --- |
| tmux 수동 기동 (기본) | 예 | 재부팅·세션 종료 시 죽는다. 자동 재시작이 없다 |
| `systemd --user` | 미확인 | 확인되면 이쪽이 낫다. 실패하면 기본으로 되돌린다 |
| `nohup`/백그라운드 | 예 | 로그 회전·감시가 없다 |

기동 스크립트가 함께 수행해야 하는 것 세 가지를 고정한다.

| 단계 | 내용 | 실패 시 |
| --- | --- | --- |
| 파일 디스크립터 상향 | 소프트 상한을 `P_NOFILE_SOFT`로 올린다(하드 1048576까지 가능) | **기동 거부.** 낮은 상한으로 뜨면 부하가 몰릴 때 원인 불명으로 죽는다 |
| 포트 바인딩 확인 | `127.0.0.1:<게이트웨이 포트>`에 바인딩. `0.0.0.0`이면 거부 | 기동 거부(B-6) |
| 텔레메트리 확인 | `cuMemGetInfo` 1회, `GET /api/ps` 1회 | 경고 후 기동하되 상태를 `degraded`로 표시. 판정은 요청 시점에 다시 확인한다(5.9.4) |

**감시는 하지 않는다.** 같은 tmux 세션에서 주기적 헬스 체크를 돌릴 수는 있지만, 프로세스가 죽었을 때 **자동 재기동하지 않고 로그만 남긴다.** 자동 재기동을 약속하려면 그 감시 프로세스도 살아 있어야 하는데, 그것도 같은 방식으로 죽는다.

tmux 기본값을 택하는 이유는 정직함이다. 자동 재시작을 약속하려면 감시 프로세스가 필요하고, 그 감시 프로세스도 같은 방식으로 죽는다. **"게이트웨이는 항상 떠 있다"고 주장하지 않는다.** 대신 11장의 "게이트웨이 미기동" 행이 사용자에게 그 사실을 표시한다.

#### 14.1.4 TLS·리버스 프록시가 없는 이유

이전 판은 리버스 프록시에서 TLS를 종단한다고 적었다. 이 서버에서는 성립하지 않는다.

- 443이 열려 있지 않다.
- 인증서를 발급·갱신하려면 공인 도메인과 80/443 검증이 필요하고, 그 포워딩은 라우터 관리자(연구실)의 권한이다.
- 게이트웨이는 루프백에만 바인딩하므로, 애초에 TLS를 종단할 외부 접점이 없다.

따라서 **리버스 프록시 계층을 설계에서 제거한다.** 전송 보호는 SSH가 하고(2.3), 그 사실을 문서가 명시한다. 이 제거는 기능 축소가 아니라 실제 구조의 반영이다.

### 14.2 지속적 운영 의무

| 주기 | 의무 |
| --- | --- |
| 요청 시 | 정책 판정, 쿼터 강제, 원장 기록, 리댁션 |
| 일 | 전역 캡 확인, 오류율·`unknown` 비율 점검, 큐 적체·`external_occupancy` 확인 |
| 주 | 키 회전 점검, 폐기 목록 검토, 스왑 빈도 추이 확인, Ollama 재고(`/api/tags`)와 카탈로그 정합 확인 |
| 릴리스 시 | manifest 서명·배포, `catalog_version` 증가, 클라이언트 `min_client` 정합 확인 |
| 모델 갱신 시 | 재고 크기 확인, VRAM 재측정, `arbiter_group`·`peak_vram_gib` 갱신 |
| 상시 | 취약점 패치(우리 프로세스만 — 시스템 패치는 root 권한자 몫), 백업 검증, 사용자 삭제 요청 처리, 사고 통지 절차 유지 |
| 사고 시 | 키 폐기, 토큰 무효화, 원장 보존, 영향 범위 산정, 사용자 통지 |

`nvidia-smi` 복구는 이 표에 없다. 그것은 우리 의무가 아니기 때문이다(5.9.3). **우리는 그 복구를 계획하지 않고 현재 상태로 운영한다.** 대신 **`cuMemGetInfo`와 `/api/ps`의 응답성을 매일 확인**하는 항목을 둔다. 텔레메트리가 죽으면 기능이 멈춘다는 것을 우리가 먼저 알아야 한다.

**온도·전력·사용률을 우리가 감시하지 못한다는 사실을 운영 문서에 명시한다.** 이 네 지표가 없으면 우리는 GPU가 과열되거나 전력 한계에 걸리는 상황을 스스로 감지할 수 없다. 그 판단은 하드웨어와 연구실의 몫이며, 우리가 할 수 있는 유일한 예방은 **적재를 작게 유지하는 것**이다(5.8.3의 헤드룸 규칙). 이 문장을 "모니터링한다"로 일반화하지 않는다.

### 14.3 비용 동인 (가격 없음)

가격을 쓰지 않는다. 무엇이 비용을 만드는지만 적는다. **어떤 항목도 배수나 배가로 표현하지 않는다** — 배수를 쓰려면 단가와 수량 모델이 있어야 하고, 이 문서에는 없다.

- **GPU 시간.** 자체 호스팅은 유휴에도 비용이 발생한다. 5장의 스왑이 짧은 작업을 자주 교체하면 GPU 시간이 낭비된다.
- **전력·냉각.** 상시 가동 GPU의 부수 비용. 이 항목은 연구실 전체 비용에 섞여 있고 우리가 분리해 낼 수 없다.
- **회선 시간.** 6.5 MB/s(약 52 Mbit/s)를 다른 사용자와 공유한다. 다중 GB 모델 다운로드와 영상 전송이 이 자원을 소비한다(6.5).
- **스토리지.** 산출물 보존 기간 × 생성량. TTL이 이 비용을 직접 통제한다. `/`의 1.1 TB를 공유한다는 것을 잊지 않는다.
- **프록시 종량 과금.** OpenRouter·A6API 등은 호출량 기반이다. 원장이 이 비용의 유일한 통제점이다.
- **모니터링·백업.** 규모와 무관한 고정 성격 비용. 다만 우리가 쓰는 것은 연구실 기존 설비이므로 별도 구매가 아니다.

이전 판에 있던 "인증서" 항목은 제거한다. 인증서를 쓰지 않기 때문이다(14.1.4).

**가용성을 사려면 무엇이 필요한가 — 배수가 아니라 조건으로 적는다.** 이 설계는 단일 호스트, 단일 GPU, 단일 게이트웨이 프로세스다. 여기서 "서버가 죽어도 서비스가 계속된다"를 얻으려면 최소한 다음이 **각각** 필요하다.

| 이중화 대상 | 필요한 것 | 이 프로젝트의 상태 |
| --- | --- | --- |
| 게이트웨이 프로세스 | 두 번째 호스트 + 공유 원장 저장소 + 리더 선출 | 없음. `P_ARBITER_SINGLETON`이 오히려 두 번째 인스턴스를 거부한다 |
| GPU 추론 | 두 번째 GPU 또는 외부 프록시로의 상시 이중 경로 | 없음. 프록시 경로는 폴백이 금지되어 있으므로 이중화로 쓸 수 없다(2.6) |
| 원장 | 원격 DB 또는 복제 | 없음. 로컬 SQLite/JSONL |
| 도달 경로 | 두 번째 sshd 또는 Tailscale | 부분적. Tailscale은 계정이 필요해 기본값이 아니다(2.7.5) |

즉 가용성은 **비용이 두 배 되는 문제가 아니라, 이 프로젝트가 갖지 않은 구성 요소를 추가하는 문제**다. 어떤 항목이 얼마나 드는지는 단가가 없으므로 쓰지 않는다. 쓸 수 있는 것은 "이 설계는 단일 장애점을 가진다"는 사실과 "제거하려면 위 네 가지가 필요하다"는 목록이다.

### 14.4 디스크·회선 운영 규칙

| 자원 | 값 | 규칙 |
| --- | --- | --- |
| `/` 여유 | 1.1 TB | 산출물 TTL, 로그 상한을 이 값의 일부로 제한한다. 전체를 우리가 쓰지 않는다 |
| 미마운트 NVMe | 931.5 GB | **사용하지 않는다.** 마운트에 root가 필요하고 다른 OS 파티션을 건드린다. 6.5에 가능성만 기록 |
| 아웃바운드 | 6.5 MB/s | 모델 다운로드는 계획된 야간 작업. 요청 경로에서 트리거 금지 |
| Ollama 재고 | 321.4 GB | 이미 우리 몫이 아니다. 새 모델은 이 위에 더해진다 |

디스크가 가득 차면 게이트웨이·Ollama·다른 사용자의 작업이 함께 실패한다. 그래서 **산출물 TTL은 선택이 아니라 필수**이고, 여유가 `P_DISK_MIN_FREE_GIB` 아래로 내려가면 새 생성 작업을 거부한다. 대화는 계속 받는다 — 대화는 디스크를 거의 쓰지 않는다.

### 14.5 남용 이야기 (무료 쿼터의 필수 조건)

무료 쿼터를 열면 다음이 필요하다. 이것 없이 무료를 열면 비용은 우리 것이고 사용은 익명이 된다.

1. **계정 게이팅.** 초대 또는 소속 도메인 확인. 익명 토큰 발급 금지.
2. **사용자별 하드 캡.** 9.3. 캡 없는 무료는 무료가 아니라 개방이다.
3. **레이트 리밋.** 토큰당. 리버스 프록시가 없으므로 게이트웨이 한 곳에서만 한다 — 이전 판의 "두 곳에서"는 성립하지 않는다.
4. **전역 일일 상한.** `P_GLOBAL_DAILY_CAP`. 한 사용자의 폭주가 전체를 멈추지 않게.
5. **제공자 계정 지출 상한.** 게이트웨이 버그·우회에 대한 제2 방어선.
6. **킬 스위치.** 라우트·모델·사용자 단위 즉시 차단.
7. **이상 사용 탐지.** 짧은 시간 다량 요청, 큰 `max_tokens`, 반복 영상 제출, 큰 컨텍스트로 GPU를 오래 잡는 패턴.

한 문장으로: **무료 + 무게이팅 + 무상한은 동시에 성립하지 않는다.** 셋 중 하나를 포기한다.

### 14.6 우리가 하지 않는 운영

경계를 명시한다. 이 목록은 "나중에 할 일"이 아니라 **이 프로젝트의 권한 밖**이다.

| 일 | 왜 우리가 못 하는가 | 누가 하는가 |
| --- | --- | --- |
| `nvidia-smi` 복구용 재부팅 | 다른 사용자 2명의 tmux와 세 번째 사용자의 Claude·VSCode 작업이 종료된다. **연구실이 재부팅하지 않기로 했으므로 이 일은 계획에 넣지 않는다** | 아무도 하지 않는다. 이 프로젝트는 재부팅을 계획에 넣지 않는다 |
| GPU 온도·전력·사용률 계측 복구 | root 재부팅 없이는 이 경로로 불가능하고, 그 재부팅이 일어나지 않는다 | 아무도 하지 않는다. 5.9.3의 네 지표는 이 설계에서 사용하지 않는 지표로 문서화한다 |
| 시스템 패치·커널 교체 | root 필요 | 시스템 관리자 |
| 라우터 포트 포워딩 추가 | 라우터 관리 페이지(`:80`)는 우리 것이 아니다 | 네트워크 관리자 |
| 미마운트 NVMe 마운트 | root + 다른 OS 파티션 | 시스템 관리자 + 소유자 동의 |
| Tailscale 테넌트 승인 | 계정 소유자 권한 | 조직 계정 관리자 |
| 사용자 계정 발급 | root 필요 | 시스템 관리자 |
| `systemd` 시스템 유닛 등록 | root 필요 | 시스템 관리자 |

이 표가 길다는 것 자체가 이 배포의 성격이다. 우리는 다른 사람의 기계에서 동작하는 게스트이고, 설계는 그 사실을 존중해야 한다.

### B.2 이 문서가 하지 않는 주장

- 게이트웨이가 완성되어 구현되었다는 주장. 게이트웨이는 이 문서에서 **부분 구현 + 설계** 상태다(13.0, 13.0.2). 검증·라우트·업스트림·`/api/ps` 관측은 코드가 있으나, 중재·리스·큐·스왑·원장 강제는 설계다.
- 게이트웨이가 매 요청의 라우팅을 3분기로 합성한다는 주장. 앱은 현재 로컬·클라우드 이분 선택이며, 요청별 게이트웨이 라우팅은 배선되지 않았다(13.0.2).
- 게이트웨이가 사용자 동의를 독립적으로 검증한다는 주장. 동의는 랩톱 UI와 브리지의 로컬 가드이며 게이트웨이 계약이 아니다(13.0.2).
- 영상 폴링·산출물 조회를 포함한 모든 표면에서 `local_only`가 균일하게 강제된다는 주장. 해당 경로의 우회 결함은 수정 대기 중이다(13.0.2).
- thinking 패스스루가 지원된다는 주장. 안전성 검토 결과 채택하지 않았다(13.0.2).
- 시연 영상에 나왔다는 사실이 구현을 뜻한다는 주장. 다섯 상태를 섞지 않는다(13.0).
- 게이트웨이가 `omp`의 동작을 바꾼다는 주장. 목표는 무수정 연결이다.
- 이미지·영상이 즉시 생성된다는 주장. 스왑과 큐가 전제다.
- 서버가 고가용성이라는 주장. 단일 호스트는 단일 장애점이다.
- 원장이 청구서라는 주장. 결제 기능은 설계에 없다.
- `local_only`가 서버에서 강제된다는 주장. 그 보장은 클라이언트에 있다.
- 로컬 평면의 프리셋이 서버로 강제된다는 주장. 강제는 클라우드 요청에만 성립한다.
- **공인 주소로 게이트웨이에 접속할 수 있다는 주장.** 모든 경로는 SSH 로컬 포워드 또는 Tailscale이다(2.7).
- **GPU 상태를 모니터링한다는 주장.** 온도·전력·사용률·프로세스별 VRAM은 이 호스트에서 확인되지 않았고 이 설계가 쓰지 않는 지표다(5.9.3).
- **우리가 추론 서버를 구축했다는 주장.** Ollama는 이미 있던 별개 소프트웨어다(3.9).
- **다른 사용자의 GPU 사용을 통제한다는 주장.** 우리 작업만 순서화한다(5.8).

### B.3 다음 단계의 순서

시연이 사전 녹화이므로 순서가 달라진다. **영상 제작이 첫 단계가 아니다.** 영상은 검증된 것만 담을 수 있으므로, 검증이 먼저다. 그리고 **영상은 랩톱 평면만으로 성립하므로, 서버 단계가 막혀도 녹화를 시작할 수 있다** — 서버 footage와 사전 생성 산출물은 나중에 덧붙이는 선택 사항이다.

1. **랩톱 평면을 먼저 완성하고 스크립트화한다.** 12.1의 항목을 스크립트로 재현 가능하게 만든다. 이것이 영상의 뼈대이고, 서버 없이 끝낼 수 있는 유일한 부분이다. **이 단계만 끝나면 영상 제작이 가능하다.**
2. 표 B의 스텁 항목을 시험한다. 실제 키 없이 정책·쿼터·계약·서명·정산 통일을 증명할 수 있다.
3. 서버 GPU에서 6.2의 `P_SRV_*`와 5.3의 `P_SWAP_*`를 측정한다. 측정 전에는 카드 등급을 확정하지 않는다.
4. 이미지·영상 모델을 설치하고 4.7의 출처 레코드와 함께 산출물을 만든다. **모델이 없으면 이 단계는 건너뛰고, 영상에 생성 장면을 넣지 않는다.**
5. 위가 끝난 뒤에 녹화한다. 녹화 시점에 실제로 동작한 것만 담는다.
6. 표 C는 실제 키가 생긴 뒤에만 다룬다. 그 전까지 제품 문서에 표 C 항목을 쓰지 않는다.
7. "게이트웨이가 있다"는 문장은 2~4가 통과한 뒤에만 쓴다. 영상에 나왔다는 이유로 쓰지 않는다.
