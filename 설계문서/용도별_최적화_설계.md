**설계 대상:** 단일 자연어 입력창과 `mode="auto"` 기본값을 유지하는 Zero-Config AI 코딩 어시스턴트.

## 1. 프로필 집합

### 1.1 프로필을 가르는 네 개의 축

프로필을 "의도 이름"으로 나누면 형식만 남습니다. 이 설계는 다음 네 축 중 **최소 두 축이 실제로 달라야** 별도 프로필로 인정합니다.

1. **도구 표면(tool surface):** 쓰기(`apply_edits`)·검증 실행(`run_verification`)·검색(`HybridContextMemoryEngine.search`)·복원(`restore`) 중 무엇이 열려 있는가.
2. **컨텍스트 소스(context strategy):** 무엇을 통째로 읽고, 무엇을 AST 슬라이스로 자르고, 무엇을 FTS5로 찾고, 무엇을 요약으로 대체하는가.
3. **출력 계약(output contract):** 산출물이 패치인가, 명세 문서인가, 체크리스트인가, 단계별 힌트인가, 산문 설명인가. 기계 형식이 달라야 한다.
4. **검증 절차(verification):** 무엇을 "끝났다"의 근거로 삼는가. 고정 argv 실행인가, 재현 실패 확인인가, 인용 검사인가, 아니면 검증 자체가 없는가.

프롬프트 의도(system prompt intent)는 다섯 번째 축이지만 **단독으로는 프로필을 만들지 못합니다.**

### 1.2 다섯 개 프로필

| 프로필 ID | 대상 | 대표 요청 | 트랙/노드 구성 | 결정적으로 다른 축 |
|---|---|---|---|---|
| `profile.quick_build` | 바이브 코더, 마감 직전 단발 수정 | "이 함수 짜줘", "이 오타 고쳐줘" | Track 1 fast-path 단일 노드 | 쓰기+검증만 열림, 검색·복원 미노출, 컨텍스트 1파일 |
| `profile.project_build` | 캡스톤·팀 과제 다중 파일 구현 | "이 기능 전체를 이 구조에 맞춰 넣어줘" | Track 2 `researcher -> planner -> worker(최대 4) -> reviewer` | 조사·계획 산출물이 별도 문서 패치로 존재, 노드별 파일 분할, 격리 복원 사용 |
| `profile.repair_debug` | 원인 모를 실패를 안고 있는 사용자 | "왜 안 돌아가는지 모르겠어", 스택트레이스 붙여넣기 | Track 1/2 + 재현 노드 선행 | **수리 전 재현 실패 확인**이 검증의 필수 선행조건, 진단 산출물 존재 |
| `profile.study_concept` | 시험 대비 개념 이해 | "이 개념 설명해줘", "왜 이렇게 되는 거야" | 단일 읽기 전용 노드 | 쓰기 도구 없음, 검증=인용 검사, 산출물=산문+예제 |
| `profile.study_practice` | 과제·연습문제 코칭 | "이 문제 어디서 틀렸어", "힌트만 줘" | 읽기 전용 + 사용자 파일 검증 실행 | 쓰기 없음 + **정답 보류 게이트** + 사용자 코드 실행 결과를 근거로 사용 |

다섯 개로 끊은 이유: `quick_build`와 `project_build`는 이미 존재하는 2-Track(`direct_execute` / `survey_and_plan`)과 1:1로 대응해 새 판정기를 만들지 않습니다. `repair_debug`는 검증 순서가 반대(재현 -> 수리 -> 재검증)라서 별도가 필요합니다. 학습 쪽은 "설명"과 "코칭"이 **도구 표면과 답 보류 게이트**에서 갈리므로 둘로 나눕니다.

### 1.3 각 프로필의 작업 형태와 구별 이유

**`profile.quick_build`** — 대상: 결과물만 필요한 사용자. 작업 형태: 단일 파일 안의 함수·클래스 추가/수정, 오타·포맷·린트성 수정, 테스트 1개 추가. 구별 이유: 이 프로필은 **탐색을 하지 않습니다.** 검색 도구와 격리 복원을 열지 않고, 대상 파일 1개만 AST 슬라이스해 넘깁니다. 다중 파일 탐색을 시작하는 순간 Track 2 비용이 붙기 때문에, "빠른 구현"과 "프로젝트 구현"의 차이는 속도 감각이 아니라 **열린 도구 수와 컨텍스트 폭**입니다.

**`profile.project_build`** — 대상: 캡스톤·팀 프로젝트·랩실 코드베이스. 작업 형태: 여러 파일에 걸친 기능 추가, 인터페이스 변경, 모듈 분리. 구별 이유: 이 프로필만 **중간 산출물이 파일로 존재합니다.** `docs/investigation.md`(조사 근거)와 `docs/spec.md`(인터페이스 계약)가 실제 패치 대상이며, 이후 구현 노드는 그 계약을 컨텍스트로 받습니다. 즉 차이는 "더 똑똑한 프롬프트"가 아니라 **산출물이 다음 노드의 입력이 되는 구조**입니다.

**`profile.repair_debug`** — 대상: 마감 전에 무엇이 깨졌는지 모르는 사용자. 작업 형태: 예외·스택트레이스·테스트 실패·"분명 맞게 했는데 안 됨". 구별 이유: 다른 프로필은 "요청 -> 패치 -> 검증"이지만 이 프로필은 **"요청 -> 재현 -> 진단 -> 최소 패치 -> 같은 명령으로 재검증"**입니다. 재현이 성공하지 않으면 패치를 쓰지 않습니다. 진단 문장(원인 1~3줄)이 출력 계약의 필수 필드라는 점도 다릅니다.

**`profile.study_concept`** — 대상: 시험·면접·발표 준비. 작업 형태: 개념 정의, 원리, 시간/공간 복잡도 비교, 두 알고리즘의 차이, "이 코드가 왜 이렇게 동작하는가"(자체 코드 포함). 구별 이유: **쓰기 도구가 아예 열려 있지 않습니다.** 그래서 "과제를 대신 끝내는" 사고가 구조적으로 불가능합니다. 검증도 실행이 아니라 인용 검사입니다.

**`profile.study_practice`** — 대상: 제출 전 자체 점검, 연습문제 풀이. 작업 형태: "이 문제 접근이 맞아?", "어디서 틀렸어?", "힌트만". 구별 이유: `study_concept`와 모델·프롬프트 의도는 같지만, **사용자가 작성한 파일을 실제로 실행해 그 결과를 근거로 말하고, 최종 산출물은 정답이 아니라 단계 게이트**입니다. 이 둘을 합치면 "설명" 요청에 실행 권한이 딸려 오거나, "코칭" 요청이 정답을 그대로 내놓게 됩니다.

### 1.4 프로필로 채택하지 않은 후보

정직하게 먼저 적습니다. 아래는 "이름은 그럴듯하지만 기계적으로 구별되지 않거나, 이번 설계 범위 밖"인 후보입니다.

| 후보 | 채택하지 않은 이유 |
|---|---|
| `profile.survey_research` (조사 전용) | 이미 Track 2의 `researcher` 노드로 표현됩니다. 독립 프로필로 만들면 오케스트레이션 파라미터만 달라지고 도구 표면·출력 계약은 `project_build`와 같습니다. -> 프로필이 아니라 **노드 구성**입니다. |
| `profile.doc_write` (보고서·발표자료 작성) | 실제 사용자 수요는 크지만, "근거 인용 의무 + 서식 계약 + 원문 대조"라는 별도 기계가 필요합니다. 코딩 엔진 자산(AST 슬라이싱, 고정 검증 argv)을 거의 쓰지 않으므로 v1 범위에서 제외합니다. 여섯 번째 프로필로 추가할 후보 1순위입니다. |
| `profile.vision` (도표·스크린샷 이해) | 카탈로그에 `vision_worker` 역할과 이를 선언한 모델(`anthropic/claude-sonnet-4.5`, `anthropic/claude-haiku-4.5`, `google/gemini-2.5-flash`)이 있으나, 입력 첨부 UI와 이미지 컨텍스트 전달 경로가 인벤토리 대상입니다. **PENDING**(§7). |
| `profile.background` (압축·제목·증류) | 사용자 프로필이 아니라 백그라운드 트랙입니다. 승인 목록(`bg_approved`)에서 적재 산술로 하나를 고르고 대체 배정을 금지하는 규칙이 이미 있으며, 사용자 요청을 받지 않습니다. 프로필 집합에 넣으면 "사용자가 고를 수 있는 것"처럼 보이므로 제외합니다. |

## 2. 프로필별 차이 명세

### 2.0 공통 기반 (다섯 프로필이 공유하는 것)

프로필이 달라도 아래 항목은 변하지 않습니다. 이 공통 기반 위에 차이만 추가합니다.

- **실행 게이트:** 모든 노드는 `DeterministicDAGOrchestrator.validate_plan`(예산 상한 검사)을 통과해야 하고, 예산 초과 시 `BudgetExhaustedError`로 중단합니다. 프로필은 상한을 올리지 않습니다.
- **경로 격리:** 파일 접근은 `resolve_within`으로 작업 루트 밖을 거부합니다. 프로필별 도구 표면은 이 위에 추가되는 **부분집합**입니다.
- **쓰기 계약:** 편집은 `{"path", "expected_pre_hash", "new_content"}` 전체 교체이며, 해시 불일치는 `HashMismatchError`로 거부됩니다. 부분 패치(diff) 형식은 계약에 없습니다.
- **검증 계약:** 검증 argv는 `_verification_for`가 만든 고정 명령이거나 `python -m pytest -q` 기본값만 허용됩니다(`runner.py`의 allowlist 검사). 모델이 명령을 제안할 수 없습니다.
- **성공 주장 금지:** 모델은 "테스트 통과"를 주장할 수 없고, 검증은 하네스가 실행한 `VerificationRecord`로만 판정됩니다.
- **라우팅:** 역할(role) -> 모델 선택은 ECPS(`expected_cost_per_success`) 기반이며, 기본 경로는 `zdr_cloud`(제로 데이터 보존 + 학습 미사용 모델만)입니다. `rank_models`/`select_model`은 기본값 `include_local=False`이므로 **이 경로로는 로컬 모델이 선택되지 않습니다.** 로컬 모델은 1\) `_make_node(preferred_model_id=...)`로 직접 지정되거나 2\) 조사 노드에서 티어의 `registry_model_id`가 주입될 때만 들어옵니다.

### 2.1 `profile.quick_build`

| 항목 | 명세 |
|---|---|
| **모델 티어** | `light_worker` 역할, Track 1 fast-path. Tier 0: `deepseek/deepseek-v4.1-flash-1017` (클라우드). Tier 1: `local/qwen2.5-coder-1.5b-gguf`. Tier 2: `local/qwen2.5-coder-7b-gguf`. Tier 3: `local/qwen2.5-coder-7b-gguf`(포그라운드 상한) + 백그라운드 전담 후보. |
| **역할 적합성 주의** | `local/bonsai-2-27b-pq2`는 카탈로그에서 포그라운드 역할을 하나도 선언하지 않습니다. `engine/registry.py`의 `_bonsai_entries()`가 이 계열 전체에 부여하는 역할은 `background_worker`, `memory_distiller`, `compactor` 세 개뿐이고 provider는 `local`입니다. 따라서 Bonsai 2를 `light_worker`·`worker`·`planner`·`researcher`·`reviewer` 노드에 배정하는 표기는 코드와 어긋납니다. Tier 3의 포그라운드는 7B GGUF(또는 14B 항목이 요구량을 확보한 뒤)이고, Bonsai는 백그라운드 선택기(`select_background_model`)의 후보입니다. |
| **시스템 프롬프트 의도** | "지시된 한 가지 변경만 한다. 기존 공개 인터페이스(함수 시그니처·반환형·예외)를 보존한다. 요청 밖 개선·리팩터링·주석 확장을 하지 않는다. 불명확하면 가장 작은 해석을 택한다." |
| **도구 표면** | 읽기(대상 1파일) + `apply_edits` + `run_verification`. **미노출:** FTS5 검색, 격리 복원, 다중 파일 읽기. |
| **컨텍스트 전략** | `detect_target_files`가 프롬프트에서 찾은 파일 1개. `.py`/`.pyi`면 `slice_code`로 심볼 슬라이스 + 전체 원문은 문법 오류 시에만. 그 외 확장자는 원문 그대로. 검색·요약 없음. |

### 2.6 자체 검증: 프롬프트만 다른 프로필은 없는가

| 프로필 | 두 개 이상 축에서 실제로 다른가 | 판정 |
|---|---|---|
| `quick_build` | 도구(쓰기+검증만) + 컨텍스트(1파일) + 검증(고정 argv, attempt 3 승격) | 통과 |
| `project_build` | 출력 계약(문서 패치가 다음 노드 입력) + 도구(검색·복원) + 컨텍스트(노드별 분할) | 통과 |
| `repair_debug` | 검증 절차(재현 선행) + 출력 계약(진단 필수) + 컨텍스트(실패 로그 우선) | 통과 |
| `study_concept` | 도구(쓰기 불가) + 출력(산문) + 검증(인용 검사) | 통과 |
| `study_practice` | 도구(검증 실행 있음, 쓰기 없음) + 출력(게이트) + 검증(사용자 코드 실행 결과) + 컨텍스트(모범답안 미로드) | 통과 — 단 **조건부** |

**조건부 판정의 정직한 내용:** `study_practice`는 `study_concept`와 모델·프롬프트 의도가 같습니다. 이 프로필이 독립적으로 성립하는 이유는 오직 **검증 도구 노출 + 답 보류 게이트 + 모범답안 미로드**입니다. 만약 기본 애플리케이션의 확장 표면이 "프로필별 도구 부분집합"을 지원하지 않는다고 인벤토리에서 판명되면(§7 PENDING), 두 학습 프로필은 **하나로 합쳐야 합니다.** 그 경우 `study` 단일 프로필은 쓰기 도구가 없고 검증 실행도 없는 `study_concept` 쪽으로 수렴해야 안전합니다(느슨한 쪽이 아니라 좁은 쪽으로).

또한 정직하게: `quick_build`와 `project_build`의 시스템 프롬프트 문구는 의도적으로 거의 같습니다. 두 프로필의 차이는 문구가 아니라 **열린 도구와 산출물 구조**입니다. 만약 이 문서에서 프롬프트만 떼어내 비교한다면 두 프로필은 구별되지 않습니다 — 그게 정상입니다.

## 3. 선택 정책 (사용자 결정 0회)

### 3.1 신호 네 종류

| 신호 | 원천 | 현재 상태 |
|---|---|---|
| **S1 명시적 호출** | 첫 토큰의 `/build`, `/project`, `/fix`, `/learn`, `/practice` 또는 문장 내 "코드는 짜지 마", "그냥 만들어줘" 같은 명시 전환어 | 새로 추가해야 함. 프롬프트에서 토큰을 제거한 뒤 나머지를 정상 처리 |
| **S2 프롬프트 텍스트** | 결정론적 키워드 표(아래 3.2) | `classify_execution_track`의 기존 패턴(`CLEAR_DIRECT_PATTERNS`, `EXPLORATORY_UNCLEAR_PATTERNS`)을 확장해 재사용 |
| **S3 워크스페이스 파일 유형** | 대상 파일 확장자, 실행 가능 코드 존재 여부 | **부분적으로만 존재.** `detect_target_files`는 **프롬프트 문자열에서만** 파일명을 뽑고 워크스페이스를 스캔하지 않습니다. 게다가 아래 파싱 한계가 있어 S3를 신뢰할 수 없습니다. 실제 스캔 신호는 신규 구현 -> **PENDING** |
| **S4 세션 이력** | 직전 3턴의 확정 프로필, 편집된 파일, 검증 실패 여부 | 신규. 오케스트레이터/세션 저장소에서 읽어야 함 |

### 3.1-가 S3의 현재 파싱 한계 (실측)

`detect_target_files`는 `_FILE_PATTERN = [\w./\\-]+\.(?:확장자)\b` 정규식입니다. 이 정규식은 확장자 뒤에 조사가 **공백 없이** 붙으면 매치에 실패합니다. 엔진을 직접 실행해 확인한 결과는 다음과 같습니다.

| 프롬프트 | `detect_target_files` 결과 |
|---|---|
| `src/a.py 와 src/b.py 에 로그 추가` | `['src/a.py', 'src/b.py']` (공백 있음 -> 성공) |
| `src/a.py, src/b.py 로그 추가` | `['src/a.py', 'src/b.py']` (성공) |
| `a.py 파일 고쳐줘` | `['a.py']` (성공) |
| `src/a.py와 src/b.py에 로그 추가해줘` | `[]` (**실패**) |
| `a.py파일 고쳐줘` | `[]` (**실패**) |

한국어에서는 조사가 붙어 쓰이는 것이 자연스러우므로, 이 실패 모드는 예외가 아니라 **기본값**입니다. 따라서 §3.2-가의 `N = target_files 개수`를 그대로 쓰면 "파일 2개를 요구했는데 N=0"이 되어 `project_build` 대신 `quick_build`로 떨어집니다. 이 설계는 다음 정규화 규칙을 선행 요구사항으로 둡니다.

1. 프롬프트에서 확장자 뒤에 붙은 한국어 조사·어미를 분리한다(확장자 직후 한글 음절 1~2자를 경계로 취급). 예: `a.py파일` -> `a.py`, `a.py와` -> `a.py`, `a.py에서` -> `a.py`.
2. 분리 후 `detect_target_files`를 호출한다.
3. 이 정규화는 **판정 입력에만** 적용하고, 실제 파일 경로로 쓰이는 값은 `resolve_within`이 검증한다. 즉 정규화가 잘못되어도 경로 탈출은 일어나지 않는다.

이 규칙이 없으면 S3 신호는 사실상 항상 0이고, §3.2의 "파일 경로 + 구현 동사" 충돌 규칙도 작동하지 않습니다(§7 E7).

### 3.2 결정 순서 (결정론적, 위에서부터 첫 성립 규칙 적용)

1. **S1 명시 호출이 있으면 그것으로 확정한다.** 신뢰도 1.0, `resolved_by="explicit"`. 다른 신호는 무시하되 로그에 남긴다.
2. **학습 게이트:** 학습 표지가 2개 이상이고 구현 동사가 없으면 학습 계열로 확정한다(연습 표지가 함께 있으면 `study_practice`, 없으면 `study_concept`). 학습 표지 1개 + 연습 표지 1개 이상 + 구현 동사 없음이면 `study_practice`.
3. **재현/실패 표지:** 실패 표지가 1개 이상이면 `repair_debug`로 간다. 단 학습 표지가 2개 이상이면 학습이 우선한다("이 에러가 왜 나는지 설명해줘"는 설명 요청).
4. **구현 규모:** `classify_execution_track`이 `survey_and_plan`을 반환하거나, 대상 파일이 2개 이상이거나, `estimate_complexity`가 6 이상이면 `project_build`. 아니면 `quick_build`.
5. **모호성 처리:** 위 규칙이 "표지 0개"로 끝나고 S3/S4도 비어 있으면 **폴백**으로 간다(3.3).
6. **전환 규칙(S4):** 직전 턴이 학습 프로필이고 현재 턴에 구현 동사(만들어, 구현, 고쳐, 짜)가 있으면 현재 턴 요청만 구현 프로필로 처리한다. 반대 방향도 동일. 세션 전체 프로필을 변경하지 않는다.

학습 표지(결정론적 목록): 설명, 이해, 개념, 원리, 왜, 증명, 유도, 차이, 비교, 복잡도, 시간복잡도, 공간복잡도, 시험, 중간고사, 기말, 예제로, "무슨 뜻", "어떻게 동작", "정리해줘".
구현 동사: 만들어, 작성, 구현, 추가, 수정, 고쳐, 리팩터, 변환, 바꿔, 짜.
재현 표지: 에러, 오류, 예외, 실패, 스택, traceback, 로그, 안 됨, 안돼, 깨짐, 디버그.

충돌 규칙(반드시 고정, 위 의사코드와 동일한 결론):

- **"왜" 1개는 학습을 확정하지 못합니다.** 학습 확정은 서로 다른 학습 표지 2개 이상(`L >= 2`)을 요구하고, 그 조건이 성립하면 실패 표지(`F`)가 있어도 학습이 우선합니다. 예: "이 에러가 왜 나는지 원리 설명해줘" -> `L=2`, `B=0` -> `study_concept`.
- **학습 표지가 1개뿐이면 실패 표지에 집니다.** 예: "왜 이게 안 되지" -> `L=1`("왜"), `P=0`, `B=0`, `F=1`("안 되지"는 실패 표지 `안 됨` 계열) -> `repair_debug`.
- **구현 동사가 하나라도 있으면 학습 계열은 성립하지 않습니다.** 예: "이 코드 왜 이래? 고쳐줘" -> `B=1` -> 구현 규모 신호(`N`, `C`, `X`)에 따라 `quick_build`/`project_build`.
- **파일 경로 + 구현 동사 없음**은 학습(자체 코드 설명 요청 포함), **파일 경로 + 구현 동사**는 구현입니다.

### 3.2-가 구현 가능한 판정 의사코드

문장 서술만으로는 "표지 2개 이상"의 경계에서 구현자가 다시 판단하게 됩니다. 아래를 그대로 옮기면 추가 결정이 필요 없습니다.

```
resolve_profile(prompt, target_files, session) -> ProfileDecision

  # 0) 정규화: 소문자화, 전각/반각 통일, 파일 경로 토큰 분리, 프롬프트 길이 보존
  # 1) 신호 추출 (각 표지 목록은 3.2의 고정 목록, 부분 문자열 1회 카운트)
  L = 학습 표지 히트 수          (중복 제거 후, 서로 다른 표지의 개수)
  P = 연습 표지 히트 수          ("풀어", "채점", "틀렸", "제출", "과제", "연습문제", "힌트")
  F = 실패 표지 히트 수
  B = 구현 동사 히트 수
  N = target_files 개수
  X = (classify_execution_track(prompt) == "survey_and_plan")
  C = estimate_complexity(prompt)

  # 2) 우선순위. 위에서부터 첫 성립 규칙이 결론이며, 신뢰도는 오른쪽 값.
  #    학습 계열 규칙은 모두 "구현 동사 없음(B == 0)"을 요구한다.
  if explicit_token or explicit_phrase:   -> S1이 지시한 프로필, 1.00
  if L >= 2 and B == 0 and P >= 1:        -> study_practice,   0.90
  if L >= 2 and B == 0:                   -> study_concept,    0.90   # F 유무와 무관하게 학습이 이김
  if L == 1 and B == 0 and P >= 1:        -> study_practice,   0.80
  if F >= 1 and B == 0:                   -> repair_debug,     0.85
  if F >= 1 and B >= 1:                   -> repair_debug,     0.80
  if X or N >= 2 or C >= 6:               -> project_build,    0.80
  if B >= 1 or N == 1:                    -> quick_build,      0.75
  else:                                   -> quick_build,      0.0   (fallback)
```

판정 규칙이 겹칠 때의 결론을 표로 못 박습니다(구현자가 다시 고민하지 않도록). 모든 행은 위 의사코드를 그대로 적용한 결과입니다.

| L | P | F | B | N/C/X | 결과 | 비고 |
|---|---|---|---|---|---|---|
| 0 | 0 | 0 | 0 | 없음 | `quick_build` (fallback) | `resolved_by="fallback"`, 폴백 표시 필수 |
| 2+ | 1+ | 무엇이든 | 0 | 무엇이든 | `study_practice` | 개념 + 연습 요청은 코칭으로 |
| 2+ | 0 | 0 | 0 | 무엇이든 | `study_concept` | 순수 개념 질문 |
| 2+ | 0 | 1+ | 0 | 무엇이든 | `study_concept` | "이 에러 왜 나는지 설명해줘" — 설명 요청이 우선한다 |
| 1 | 0 | 1+ | 0 | 무엇이든 | `repair_debug` | 개념 어휘 1개는 실패 표지에 진다 |
| 1 | 1+ | 0 | 0 | 무엇이든 | `study_practice` | 연습 표지가 게이트를 연다 |
| 0 | 1+ | 0 | 1+ | 1파일 | `quick_build` | "과제"라는 단어만으로 학습이 되지 않음 |
| 0 | 0 | 0 | 1+ | 2파일 이상 | `project_build` | 규모 신호가 구현 강도 결정 |
| 0 | 0 | 1+ | 1+ | 무엇이든 | `repair_debug` | 수리 요청은 규모보다 우선(재현이 먼저) |
| 2+ | 0 | 0 | 1+ | 무엇이든 | `project_build` 또는 `quick_build` | 구현 동사가 있으면 학습 표지가 많아도 구현. "설명해주고 만들어줘"는 §3.3 두 번째 경우 |
| 0 | 0 | 0 | 0 | 1파일 | `quick_build` | 신뢰도 0.75, 폴백 아님 |

동점·경합 시 타이브레이크는 **위 우선순위 목록의 순서**가 유일한 기준입니다. 별도 가중치 합산을 두지 않는 이유: 합산 점수는 경계값에서 재현 불가능한 판정을 만들고, Zero-Config 제품에서 "왜 이 답이 나왔는지"를 설명할 수 없게 만듭니다.

**명시 호출 토큰의 파싱 규칙**(구현자가 추가 결정을 하지 않도록): 프롬프트를 트림한 뒤 첫 공백 이전 토큰이 아래 표에 있으면 그 토큰을 **소비**하고 나머지를 요청 본문으로 씁니다. 토큰이 문장 중간에 있으면 소비하지 않고 S2 텍스트로만 취급합니다. 소비 후 본문이 비면 프로필만 확정하고 "무엇을 할지" 1문장을 요청합니다(빈 요청으로 실행하지 않음).

| 토큰 | 확정 프로필 |
|---|---|
| `/build` | `profile.quick_build` |
| `/project` | `profile.project_build` |
| `/fix` | `profile.repair_debug` |
| `/learn` | `profile.study_concept` |
| `/practice` | `profile.study_practice` |

문장 내 전환어도 같은 표로 사상합니다: "그냥 만들어줘" -> `quick_build`, "전체 구조까지" -> `project_build`, "고쳐줘/디버깅" -> `repair_debug`, "설명만/코드는 짜지 마" -> `study_concept`, "힌트만/채점해줘" -> `study_practice`.

### 3.3 모호할 때의 폴백

폴백 프로필은 **`profile.quick_build`**입니다. 이유는 세 가지입니다. (1) 이 제품의 기본 사용자는 코드를 얻으러 오고, 학습 답변만 돌려주면 실망이 크다. (2) `quick_build`는 쓰기 범위가 가장 좁고(단일 파일), 계획 오버헤드가 없으며(fast-path), 검증이 강제된다. (3) 모든 쓰기는 해시 검증 + 격리 스냅샷으로 되돌릴 수 있다.

단, 폴백은 **조용히 일어나지 않습니다.** 폴백이 발동하면 다음을 반드시 함께 낸다.

- 응답 첫 줄에 선택된 프로필과 이유 1개를 표시한다(예: "일반 구현으로 처리합니다 — 요청에 실패 증상이 없고 대상 파일이 1개입니다").
- 화면의 프로필 칩에 "다른 용도로" 전환 지점을 항상 노출한다(설정 화면 아님, 같은 화면).
- 로그에 `resolved_by="fallback"`, `top_alternative`, 점수 차이를 남긴다.

**모호성의 두 번째 경우(설명 + 구현이 한 문장에 있는 경우):** 의사코드에서 학습 계열 규칙은 모두 `B == 0`을 요구합니다. 따라서 "이거 왜 이렇게 되는지 설명하고 고쳐줘"(`L >= 1`, `B >= 1`)는 학습 규칙에 걸리지 않고 **구현 계열로 확정**됩니다(`F >= 1`이면 `repair_debug`, 아니면 `N`/`C`/`X`에 따라 `quick_build` 또는 `project_build`). 이때 쓰기 도구는 열려 있고, 응답은 **(1) 구현 결과 -> (2) 왜 그렇게 했는지에 대한 설명** 순서로 붙습니다. (2)에 학습 프로필의 게이트를 적용하지 않는 이유: 이미 패치가 나갔으므로 감출 답이 없습니다. 순서를 바꾸지 않는 이유: 설명을 먼저 쓰면 사용자가 "그래서 고쳐줬어?"를 다시 물어야 합니다. 이 분해는 기존 `decompose`를 재사용하되, 프로필은 **하나만** 확정합니다(두 프로필을 동시에 실행하지 않음).

이 선택은 교육적 의도와 충돌할 수 있습니다(설명을 요청했는데 코드가 나감). 그래서 §4.5와 §7 Q1에 남깁니다. 대안(학습 우선으로 뒤집기)은 쓰기 요청을 무시하는 결과를 낳으므로, 이 설계는 **요청된 산출물을 먼저 주고 설명을 붙이는 쪽**을 택합니다. 사용자가 원하지 않으면 `/learn`으로 명시 전환하면 됩니다.

### 3.4 설정 없이 하는 오버라이드

| 방법 | 동작 | 지속성 |
|---|---|---|
| 접두 토큰 `/build`, `/project`, `/fix`, `/learn`, `/practice` | 해당 프로필로 고정, 토큰은 프롬프트에서 제거 | 그 턴만 |
| 문장 내 전환어("코드는 짜지 마", "그냥 만들어줘") | 해당 프로필로 고정 | 그 턴만 |
| 화면의 프로필 칩 클릭 | 다음 턴부터 적용 | 세션 동안 유지 |
| "계속 이 용도로" | 세션 고정 | 세션 종료 시 해제 |

**설정 파일은 만들지 않습니다.** 영구 고정·프로필별 모델 선택·도구 토글 UI는 이번 설계 범위에 없습니다. 이유는 §1.2의 "설정 제로" 철학과, 프로필별 모델 선택을 허용하는 순간 검증되지 않은 조합(카탈로그 역할 불일치)이 사용자 손에 들어가기 때문입니다. 오버라이드는 **의도(용도)** 에만 작용하고 **모델·도구·예산**에는 작용하지 않습니다.

### 3.5 실패 안전 불변식

선택 정책이 틀렸을 때 피해가 한 방향으로만 흐르도록 다음을 고정합니다.

1. **학습 프로필에는 쓰기 도구가 없다.** 학습으로 잘못 분류되면 최악의 결과는 "코드를 안 만들어 줌"이고, 이는 `/build` 한 번으로 복구된다. 반대 오분류(구현으로 처리)는 파일을 변경하지만 해시 검증·격리 복원·검증 실행이 방어한다. **전제:** 이 불변식은 도구 차단이 실제로 가능할 때만 성립합니다(D1 PENDING). 차단이 불가능하면 이 항목은 "프롬프트 지시로만 참는" 수준으로 약화되며, 그 사실을 문서에 명시해야 합니다.
2. **검증 없는 성공 보고 금지.** 어떤 프로필도 `VerificationRecord` 없이 "됐다"고 말할 수 없다.
3. **없는 모델을 이름 붙이지 않는다.** 자원이 없으면 이름 대신 상태와 사유를 낸다(`BackgroundModelSelection`이 `status="unavailable"` + `reasons`를 내는 방식과 동일한 형태).
4. **프라이버시 기본값은 `zdr_cloud`.** `a6api/deepseek-chat-v3.1`처럼 `zero_data_retention=False`인 항목은 동의 없이는 후보에서 제외되며, 후보가 하나도 없으면 `rank_models`가 조용히 대체하지 않고 예외로 실패한다(현재 `RuntimeError` 503 형태).
5. **강등은 보이게.** 티어·프로필·모델 중 무엇이든 하향되면 응답 헤더와 로그에 남긴다.

### 3.6 관측 필드 (구현 계약)

프로필 판정 1건은 다음 필드를 남깁니다. 이것이 있으면 "왜 이 답이 나왔는지"를 사용자와 개발자 모두 재구성할 수 있습니다.

`profile_id`, `resolved_by`(explicit | rules | fallback | session_override), `confidence`, `signals[]`(S1~S4 각각의 히트와 가중치), `top_alternative`, `tier`, `capability_tier`, `route`, `role_to_model_id` 맵, `unavailable_reasons[]`, `write_surface`(열린 쓰기 도구 목록), `verification_plan`.

## 4. 학습 프로필 상세

### 4.1 "만들기"가 아니라 "공부"임을 탐지하는 방법

학습 요청은 코드 요청과 **목적어가 다릅니다.** 학습의 목적어는 "내가 이해하는 상태"이고, 구현의 목적어는 "파일". 탐지는 다음 순서로 합니다.

1. **산출물 지시 유무:** "만들어/고쳐/추가해 + 파일 경로" 조합이 있으면 구현 계열로 확정. 이 규칙이 가장 강합니다(§3.2-가 의사코드의 `B == 0` 조건).
2. **설명 요구 어휘:** 설명·이해·원리·왜·증명·차이·복잡도·시험. 서로 다른 표지가 2개 이상이고 구현 동사가 없으면 학습(§3.2-가의 `L >= 2 and B == 0`).
3. **연습 맥락:** "풀어/채점/틀렸/제출/과제/연습문제/힌트"가 있으면 학습 중에서도 코칭 쪽(`study_practice`)으로 보냅니다. 이 표지만으로는 학습이 되지 않습니다(`B >= 1`이면 구현).
4. **대상의 성격:** 지목된 파일이 이미 존재하고 사용자가 "이 코드"라고 부르면, 구현 동사가 없을 때 학습(코드 이해)입니다. 새 파일을 요구하면 구현입니다.
5. **검증 가능성:** 요청이 "실행해서 통과해야 하는 것"을 요구하면 구현/수리, "설명이 맞아야 하는 것"을 요구하면 학습. 이 판단은 판정기가 아니라 §2의 프로필 검증 계약이 결정합니다.

**탐지가 실패하는 경우를 인정합니다.** 사용자가 "과제 코드 좀 완성해줘"라고 쓰면 그것은 구현 요청이고, 탐지기는 그것을 학습으로 분류하지 않습니다. 이 설계는 **의도 탐지기**가 아니라 **용도 탐지기**입니다. 과제 대리 수행을 막는 것은 탐지가 아니라 §4.2의 거부/대체 규칙과 §6의 인간 결정입니다.

### 4.2 무엇을 거부하고 무엇으로 대체하는가

| 거부하는 요청 | 대체물 | 근거(기계적) |
|---|---|---|
| 과제·연습문제의 완성 코드 작성 | 개념 설명 + 사용자 시도에 대한 반증 + 의사코드 | 쓰기 도구가 없고, 산문 코드 블록은 짧은 예시로 제한 |
| 시험·퀴즈 문제의 즉답 | 문제 재진술 + 필요한 개념 목록 + 스스로 확인할 체크리스트 | 게이트 상태 `hint_1` 고정 |
| "내 코드가 왜 틀렸는지"에 대한 수정본 | 실패 지점 위치 + 반례 입력 + 질문 1개 | `apply_edits` 미노출 |
| 특정 교재·강의의 전문 재현 | 요약 + 개념 구조 + "원문 확인 필요" 표시 | 외부 자료 미로드, 인용 검사 |
| 리포트·보고서 대필 | 목차·논점 구조·검토 질문 | `profile.doc_write` 자체가 v1 제외(§1.4) |

**대체물의 상한을 명시합니다.** 학습 프로필이 내놓을 수 있는 가장 구체적인 것은 **의사코드와 경계 조건 체크리스트**입니다. 완성 함수 본문, 채점 통과를 목표로 한 전체 파일, "이대로 제출하면 됨" 수준의 산출물은 나오지 않습니다.

### 4.3 게이트 상태 기계

`study_practice`의 상태는 다음 다섯 개뿐이며, 뒤로 갈 수 없습니다(되돌리려면 사용자가 "더 자세히" 요청).

| 상태 | 내놓는 것 | 다음 상태로 가는 조건 |
|---|---|---|
| `diagnose` | 시도 파일 실행 결과 인용, 실패/미완 지점 1개 | 자동 |
| `hint_1` | 개념 질문 1개(정의 확인) | 사용자가 답하거나 "모르겠어" |
| `hint_2` | 접근 방향 1문장 + 반례 1개 | 사용자가 재시도 |
| `hint_3` | 의사코드(함수 시그니처 + 단계 주석) | 사용자가 여전히 막힘 |
| `checklist` | 경계 조건·자료구조·복잡도 점검표 | 종료 |

`final_answer` 상태는 **정의하지 않습니다.** 상태 기계에 존재하지 않는 상태는 나올 수 없습니다.

### 4.4 구현 프로필과의 기계적 차이 (요약)

| 축 | `profile.quick_build` | `profile.study_concept` / `study_practice` |
|---|---|---|
| 쓰기 | `apply_edits` 열림, 해시 검증 필수 | 닫힘(구조적으로 불가) |
| 검증 | 고정 argv 실행 -> 종료 코드로 성공 판정 | 인용 검사(개념) / 사용자 코드 실행 결과 인용(코칭) |
| 컨텍스트 | 대상 파일 심볼 슬라이스 | 개념 검색 히트 + 참조 슬라이스 / 문제·채점기준·시도 파일 |
| 출력 | JSON edits + 1~2문장 요약 | 산문 설명 / 게이트 상태 + 체크리스트 |
| 실패 시 | attempt 1·2 같은 모델 재시도 -> attempt 3 승격 모델 -> 그래도 실패면 실패 보고 | 근거 부족 표시, 불확실한 부분 명시 |

### 4.5 남는 약점 (숨기지 않음)

- 학습 프로필은 파일에 기록할 수 없지만 **응답 본문에 코드를 텍스트로 넣을 수 있습니다.** 이 경계는 프롬프트 지시로만 강제되며, 현재 엔진에는 산문 코드 블록 길이를 검사하는 장치가 없습니다 -> **PENDING**(검사기 필요).
- "시험 중 사용" 같은 맥락은 텍스트로 탐지할 수 없습니다. 이 설계는 그런 사용을 막는다고 주장하지 않습니다.
- 사용자가 학습 프로필에서 `/build`로 전환하면 구현이 수행됩니다. 이것을 막을지는 정책 결정입니다(§7 질문). 조용히 회피하는 것보다 명시적 전환이 정직하다고 판단했지만, 기관·교수 정책에 따라 전환 자체를 막아야 할 수 있습니다.

### 5.1 티어별 프로필 매트릭스 (설계 의도)

표기: **로컬** = 로컬 모델만으로 완결, **혼합** = 일부 노드가 클라우드 필수, **클라우드** = 로컬 모델 없음, **불가** = 해당 경로 없음(사유 표시).

근거: `LOCAL_TIER_MODEL_IDS`가 티어별 모델을 고정하고, 카탈로그의 역할 선언이 가능한 조합을 제한합니다. `local/qwen2.5-coder-1.5b-gguf`는 `light_worker`, `worker`와 백그라운드 3종(`background_worker`, `memory_distiller`, `compactor`)을 선언합니다. `local/qwen2.5-coder-7b-gguf`는 `worker`, `light_worker`, `frontend_worker`, `backend_worker`, `reviewer`, `researcher`와 백그라운드 3종을 선언하고 `planner`는 없습니다. `local/bonsai-2-27b-pq2`는 백그라운드 3종만 선언하고 포그라운드 역할은 하나도 갖지 않습니다. `local/qwen2.5-coder-14b-gguf`는 `planner`, `worker`, `heavy_worker`, `reviewer`, `security_reviewer`, `researcher`를 선언하지만 `LOCAL_TIER_MODEL_IDS`의 어떤 티어에도 배정되지 않습니다(카탈로그에만 존재). 전수 확인 기준은 다음과 같습니다: 커밋된 `catalog.json`은 27개(로컬 13개), `engine/registry.py`는 29개(로컬 15개, `local/aux-embed-gguf`·`local/aux-tiny-gguf` 추가). 2026-11-06 현재 `scripts/verify_customization.ps1`이 이 드리프트로 실패하므로, 두 집합의 차이는 미해결입니다. 위 역할 서술은 양쪽에서 동일합니다.

**이 표는 설계 의도이고, 현재 엔진 동작이 아닙니다.** 특히 `project_build`/`repair_debug`의 Tier 1·2 칸("구현 1.5B/7B 로컬")은 엔진 변경을 전제합니다. 현재 `_build_plan`은 워커 노드에 로컬 모델을 배정하는 조건을 `tier == ADVANCED_LOCAL`로만 두고, 그 아래 티어에서는 워커를 클라우드 `deepseek/deepseek-v4.1-flash-1017`로 보냅니다. 이 조건을 `tier >= STANDARD_LOCAL`(7B는 `worker` 선언)까지 넓히는 것이 이 설계의 요구사항이며, 아직 반영되지 않았습니다(§7 E8).

각주(모순 해소): `quick_build`의 Tier 3 칸에서 `LOCAL_TIER_MODEL_IDS`는 `local/bonsai-2-27b-pq2`를 가리키지만, 그 모델은 `light_worker`를 선언하지 않고 `_gate`가 `role_not_supported`를 돌려준다. 같은 이유로 Tier 3의 구현 노드(`worker`)도 실행 불가(`executable=False`)가 된다. 즉 Bonsai 계열은 27B 세 양자화를 포함해 **백그라운드 전담**이며, 포그라운드 로컬 상한은 현재 `local/qwen2.5-coder-7b-gguf`다. `local/qwen2.5-coder-14b-gguf`는 `planner`·`heavy_worker` 등을 선언하지만 카탈로그에서 `weights_bytes=None`·`pending_confirmation=True`라 준비된 적재 근거가 없고 `LOCAL_TIER_MODEL_IDS`의 어떤 티어에도 배정되지 않는다.

| Track 2 | Tier 2 | `researcher` = `local/qwen2.5-coder-7b-gguf`, `planner` = `baseten/mammoth-1`, `backend_worker` = `deepseek/deepseek-v4.1-flash-1017`, `reviewer` = `anthropic/claude-sonnet-4.5` |
| Track 2 | Tier 3 | `researcher` = `local/qwen2.5-coder-7b-gguf`(7B는 `researcher`를 선언한다), `backend_worker` = **로컬 실행 불가**(`LOCAL_TIER_MODEL_IDS`가 `local/bonsai-2-27b-pq2`를 주지만 이 모델은 `worker` 계열을 선언하지 않아 `_gate`가 `role_not_supported`로 막는다), `planner` = `baseten/mammoth-1`, `reviewer` = `anthropic/claude-sonnet-4.5` |

별도로 확인한 라우팅 사실: `rank_models`/`select_model`은 기본값 `include_local=False`이므로 **로컬 모델은 이 경로로 절대 선택되지 않습니다.** 로컬 배정은 `preferred_model_id`(fast-path, Tier 3 워커)와 티어 `registry_model_id`(Tier 2 이상 조사)로만 들어옵니다. 그래서 `reviewer` 역할은 어떤 티어에서도 로컬이 될 수 없고(`_make_node`가 리뷰 노드에 `preferred_model_id`를 주지 않음), `planner`도 항상 클라우드입니다.

설계 의도와의 차이는 네 가지이며, 모두 §7에 확인 항목으로 등록합니다.

1. **`reviewer`는 어느 티어에서도 로컬이 아닙니다.** 리뷰 노드는 `preferred_model_id` 없이 만들어져 `select_model("reviewer", ...)`로 위임되고, `include_local=False`이므로 로컬 후보가 아예 없습니다. `quality` 모드에서는 `anthropic/claude-sonnet-4.5`, `balanced`/`cost` 모드에서는 `deepseek/deepseek-v4.1-flash-1017`입니다. 따라서 보고서 §1.2의 "Tier 3는 전 구간 로컬" 서술은 현재 배정과 일치하지 않습니다(§7 E8).
2. **`planner`도 어느 티어에서도 로컬이 아닙니다.** `select_decision_model`이 (a) 분기에서 `baseten/mammoth-1`을 반환합니다. Bonsai 계열은 `planner`를 선언하지도 않으므로(백그라운드 3종 전담), 로컬 계획 노드는 현재 카탈로그에 존재하지 않습니다(§7 E8).
3. **Tier 0/1의 `researcher`도 결정 모델로 갑니다.** 조사 노드도 로컬 모델이 없는 티어에서는 `select_decision_model("researcher", ...)`를 타므로, `quality`/`balanced`에서 `baseten/mammoth-1`, `speed`에서 `openrouter/subq-snap-1.1`입니다. Tier 0에서 "규칙 기반으로 조사한다"는 서술과 다릅니다.
4. **`baseten/mammoth-1`이 `quality`/`balanced` Track 2의 조사·계획 상시 노드입니다.** 문맥창 16,384인 이 모델이 그 두 노드에 고정 배정되므로, 다중 파일 조사 입력이 이 한도를 넘는 경우가 이 설계의 실제 위험 지점입니다(§7 E5).

이 실측은 "성능"이 아니라 **배정 경로**의 관측입니다. 어떤 모델이 더 나은지에 대해서는 아무것도 말하지 않습니다.

### 5.2 강한 로컬 모델이 없을 때 (Tier 0·1) 무엇을 하는가

원칙은 하나입니다. **대체하지 않고, 상태와 사유를 낸다.** 이는 백그라운드 트랙이 이미 채택한 방식(`select_background_model`이 `status="unavailable"` + `reasons`를 돌려주고 Qwen·클라우드로 조용히 갈아타지 않는 계약)과 동일합니다. 프로필 실행 계층도 같은 형태의 결과를 내야 합니다.

```
profile_execution = {
  profile: "study_practice",
  status: "local" | "hybrid" | "cloud" | "unavailable",
  tier: "lightweight_local",
  capability_tier: "lightweight_local",
  required: "researcher 역할을 선언한 로컬 프리셋 (standard_local 이상)",
  role_to_model_id: { "researcher": null, "reviewer": "anthropic/claude-sonnet-4.5" },
  reasons: ["role 'researcher' has no local preset at this tier"]
}
```

`status` 판정 규칙은 결정론적입니다.

| 조건 | `status` |
|---|---|
| 모든 노드가 로컬 모델 | `local` |
| 일부 노드만 로컬, 나머지는 **허용된** 클라우드 경로 | `hybrid` |
| 로컬 노드 없음, 전부 클라우드 | `cloud` |
| 필요한 역할을 채울 모델이 로컬에도 클라우드에도 없음(프라이버시·키·티어) | `unavailable` + `reasons` |

**Tier 0에서 실제로 남는 것:** 로컬 LLM은 없지만 AST 심볼 슬라이싱, FTS5 검색, 고정 검증 실행, 스냅샷 복원은 그대로 쓸 수 있습니다. 그러나 다섯 프로필 모두 **답변 생성에는 모델이 필요**하므로 Tier 0의 모든 프로필은 클라우드 경로(`deepseek/deepseek-v4.1-flash-1017` 및 Track 2의 결정 라인업)로 갑니다. **클라우드 경로가 없으면(키 없음·네트워크 없음·프라이버시 동의 부족) 프로필은 `unavailable`로 끝납니다.** 규칙 기반으로 개념 설명이나 코드 생성을 대신하지 않습니다. 규칙 기반이 잘하는 것(심볼 추출, 검색, 검증, 복원)은 LLM 없이 제공하되, 그것을 "프로필 응답"이라 부르지 않습니다.

**Tier 0/1에서 프로필별로 실제로 일어나는 일** (현재 엔진 배정 기준, §5.1-가와 동일):

| 프로필 | Tier 0 | Tier 1 | 불가 경로가 되는 조건 |
|---|---|---|---|
| `quick_build` | `cloud` (flash) | `local` (1.5B, `light_worker`) | 클라우드 불가 시 Tier 0은 `unavailable` |
| `project_build` | `cloud` (조사·계획 결정 모델 + 워커 flash + 리뷰 sonnet) | 동일 | 클라우드 불가 시 `unavailable`. Tier 1에서 로컬로 대체할 수 있는 노드는 워커뿐이고, 현재 엔진은 Tier 1 워커도 클라우드로 보냄(§7 E9) |
| `repair_debug` | `cloud` | `cloud` | 동일 |
| `study_concept` | `cloud` (조사 계열 = 결정 모델) | `cloud` | 클라우드 불가 시 `unavailable` |
| `study_practice` | `cloud` + 로컬 검증 실행 | `cloud` + 로컬 검증 실행 | 동일 |

즉 **Tier 1에서 학습 프로필은 로컬로 갈 수 없습니다**(1.5B가 `researcher` 미선언). 이때 화면에는 "클라우드 사용" 사실이 표시되어야 하고, 클라우드가 불가하면 `unavailable` + 사유("researcher 역할을 선언한 로컬 프리셋 없음")입니다. 학습 프로필을 1.5B로 억지 실행하는 경로는 만들지 않습니다. 1.5B가 `researcher` 역할을 선언하지 않은 것은 카탈로그 계약이고, 그 계약을 깨는 것보다 "이 기기에서는 클라우드가 필요하다"고 말하는 편이 정직합니다.

**Tier 0/1에서 로컬로 남길 수 있는 것(설계 요구, 미구현):** `study_practice`의 검증 실행은 모델이 필요 없으므로 로컬에서 그대로 돌 수 있습니다. 즉 학습 코칭에서 "사용자 파일 실행 결과"라는 근거는 클라우드 없이도 확보됩니다. 다만 그 결과를 해석해 말하는 것은 여전히 모델의 몫입니다.

### 5.3 비용 원칙

- 로컬 모델의 카탈로그 단가는 0입니다(`local/*`의 `PricingInfo(0.0, 0.0, 0.0)`). 따라서 "로컬 완결" 티어·프로필 조합의 모델 토큰 비용은 0입니다. 이 문서는 그 외의 금액을 추정하지 않습니다.
- 클라우드 프로필의 비용은 카탈로그 단가 필드로만 계산됩니다(`PricingInfo.attempt_cost_usd`). 구체적 총액은 프롬프트·파일 크기에 의존하므로 여기서 주장하지 않습니다.
- 예산 상한은 `DeterministicDAGOrchestrator(max_budget_usd=...)`(기본 1.0)이며, 프로필은 상한을 **올리지 않습니다.** 계획 추정치가 상한을 넘으면 실행 전에 거부됩니다. 상한 인상은 인간 결정입니다(§6).
- 승격은 비용을 늘리는 유일한 자동 동작입니다. 승격은 검증 실패가 두 번 확인된 뒤 attempt 3에서 한 번만 일어나고(`_prepare_node`가 `attempt == 3`에서만 모델을 교체), 결과 레코드에 `escalated`와 `final_model`이 남습니다. 조용한 승격은 없습니다.

### 5.4 대체 금지 규칙 (프로필 공통)

1. 티어가 감당하지 못하는 로컬 모델을 "선택된 것처럼" 표시하지 않습니다. `override_tier`로 티어를 강제해도 `capability_tier`를 함께 기록하고, 실제 실행 티어는 둘 중 **낮은 쪽**을 씁니다. 백그라운드 경로는 이 규칙을 이미 지킵니다: `select_background_model`이 후보를 못 고르면 `model_id`가 빈 문자열·`entry`가 `None`이고, `build_background_plan`은 그 빈 id로 노드를 만들어 `executable=False`, `block_reason=background_role_requires_background_plan:<role>`을 남깁니다(2026-11-06 실측, Tier 0·Tier 3 모두 동일). `require_entry()`는 이 상태에서 `BackgroundModelUnavailableError`를 던집니다.
2. 프라이버시 요건을 만족하지 않는 모델로 내려가지 않습니다. `a6api/deepseek-chat-v3.1`은 `zero_data_retention=False`이므로 기본 `zdr_cloud` 경로에서 후보가 아니며, 후보가 없으면 예외로 실패합니다. 이를 "그럼 아무 클라우드나"로 메우지 않습니다.
3. 역할을 선언하지 않은 모델을 그 역할에 배정하지 않습니다. 위반이 의심되는 지점은 `preferred_model_id` 경로(§2.1)이며, 검증 항목으로 남깁니다.
4. 백그라운드 인지 작업(압축·제목·증류·트리아지)은 프로필과 무관하게 `select_background_model`이 고른 로컬 모델 하나가 담당하며, 불가 시 `unavailable`입니다. 고정된 모델 이름은 없습니다(`BACKGROUND_MODEL_ID`는 레거시 진단용 이름일 뿐 선택 근거가 아닙니다). 프로필이 이 경로를 빌려 쓰지 않습니다.

## 6. 자동화하지 않는 것

목표는 "설정 최소"이지 "인간 판단 0"이 아닙니다. 아래는 자동화하지 않습니다.

| 항목 | 왜 자동화하지 않는가 | 언제 필요한가 |
|---|---|---|
| API 키·로컬 엔드포인트 입력(`HARNESS_LLM_API_KEY`, `HARNESS_LOCAL_BASE_URL` 등) | 비밀값은 사용자 환경에만 있어야 함 | 최초 1회, 클라우드 또는 로컬 서버 사용 시 |
| 프라이버시 동의(`any_cloud` 전환) | 데이터 보존 정책 변경은 사용자 권한 | 비-ZDR 모델을 쓰려 할 때만 |
| 세션 예산 상한 인상 | 지출 결정 | 계획 추정치가 기본 상한을 넘을 때 |
| 학습 프로필에서 구현 프로필로의 전환 승인 | 교육적 판단 | 과제 대리 수행 경계에서 |
| 모호한 요청의 최종 확정(프로필 칩 클릭/한 문장) | 의도는 사용자만 아는 경우가 있음 | 폴백 표시가 나온 턴 |
| 하드웨어 티어 강제(원격 Ollama 등) | 환경 사실은 사용자만 앎 | 선택 사항, 기본은 자동 감지 |
| 다중 파일 삭제·대규모 리팩터링 범위 확정 | 되돌리기 어려운 변경 | 격리 복원으로도 부담이 큰 경우 |
| 프리셋 카탈로그 갱신 | 검증된 조합만 배포(`periodic_developer_release`) | 앱 릴리스 시 |
| 프로필별 모델 수동 선택 | 검증되지 않은 역할-모델 조합을 사용자에게 열지 않음 | 제공하지 않음(의도적 미제공) |

마지막 항목을 "자동화하지 않는 것"에 넣은 이유는 분명합니다. 프로필별 모델 선택을 열면 Zero-Config가 깨지고, ECPS 라우팅이 보장하던 프라이버시·역할 적합성이 사용자 입력으로 우회됩니다. 편의를 위해 열지 않습니다.

### 7.2 엔진 쪽에서 확인·보완해야 할 것

| # | 항목 | 근거 | 확인 내용 |
|---|---|---|---|
| E1 | 역할 검사 구현됨 / 티어 매핑은 미해결 | `_gate`는 역할 선언을 검사하며 Bonsai의 `light_worker`·`worker` 배정을 `role_not_supported`로 차단한다 | 검사를 추가할 문제가 아니라 Tier 3 포그라운드 매핑을 수정할 설계 결정이 남아 있다. Bonsai는 `worker`도 선언하지 않으므로 역할 이름만 변경하는 것으로는 실행되지 않는다 |

### 7.3 검증해야 주장할 수 있는 것 (측정 계획, 결과 아님)

1. **프로필 분류 일치율:** 사용자 요청 표본(구현/수리/설명/코칭 각 범주)에 대해 규칙 기반 판정이 사람 라벨과 얼마나 일치하는지. 측정 전에는 어떤 수치도 주장하지 않습니다.
2. **오분류 피해 방향:** 학습->구현 오분류가 실제로 파일을 얼마나 변경하는지(쓰기 0회여야 함), 구현->학습 오분류가 몇 번의 추가 발화로 복구되는지.
3. **학습 응답의 정답 누출:** 산문 코드 블록이 "제출 가능한 완성도"에 도달하는 비율. 자동 검사기가 없으므로 사람 평가가 필요합니다.
4. **Tier 0/1 불가 경로의 정직성:** 클라우드 키가 없을 때 실제로 `unavailable` + 사유가 나오고, 다른 모델이 조용히 호출되지 않는지(네트워크 로그로 확인).
5. **도구 표면 차단의 실효성:** D1 결과에 따라, 학습 프로필 턴에서 `apply_edits` 호출이 실제로 거부되는지.
6. **예산 가드:** 프로필이 상한을 올리지 않는다는 주장이 `validate_plan` 거부로 확인되는지.
