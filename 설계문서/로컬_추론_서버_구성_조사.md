# 로컬 추론 서버 구성 조사 — 소형 instruct 모델 + 임베딩 모델을 OpenAI 호환 엔드포인트로

> **문서 지위.** 조사 기록이다. 이 문서에 적힌 어떤 구성도 아직 이 프로젝트에서 실행되지 않았다. 설치·가중치 다운로드·코드 수정은 이 작업의 범위가 아니며, 수행하지 않았다. 수치는 성격에 따라 `[게시]`, `[계산]`, `[측정필요]`로 구분한다.

## 0. 표기 규칙과 판정 요약

### 0.1 수치의 성격 구분

| 표기 | 뜻 | 이 문서에서의 신뢰도 |
| --- | --- | --- |
| `[게시]` | 업스트림 문서·릴리스·모델 저장소가 공개한 값 | 그대로 인용. 링크를 함께 적는다 |
| `[계산]` | 이 문서가 `[게시]` 값(파일 바이트 수, 파라미터 수, config.json)에서 산술로 유도한 값 | 산술은 검산 가능. 하드웨어·런타임 실측이 아니다 |
| `[측정필요]` | 두 타깃 머신에서 직접 재야만 알 수 있는 값 | 어떤 숫자도 여기에 미리 채우지 않는다 |

`[계산]` 값은 **추정이 아니라 산술**이다. 예를 들어 0.81 GB 파일이 1.28 B 파라미터라면 5.08 bit/param이라는 것은 나눗셈이다. 그러나 그것이 **실제 VRAM 사용량**이라는 주장은 아니다. VRAM에는 가중치 외에 KV 캐시와 연산 버퍼가 더 붙고, 연산 버퍼 크기는 게시되지 않았다.

바이트 → GiB는 1 GiB = 1,073,741,824 B로 환산했다. `nvidia-smi`류 도구와 엔진이 보고하는 VRAM은 GiB 기준이므로, GB로 적힌 파일 크기를 그대로 예산에 넣으면 7%가량 과대평가된다.

## 1. 문제의 형태

두 타깃 머신에서 같은 OpenAI 호환 표면이 필요하다.

1. **사용자 Windows 머신** — 개발과 시연용. CPU 전용이거나 소형 소비자 GPU. 로컬 추론 런타임과 가중치가 **없는 상태**에서 시작한다.
2. **연구실 Ubuntu 서버** — RTX 5090 1장, 총 VRAM 31.36 GiB, RAM 125 GiB. Ollama 0.21.0이 이미 설치되어 있다. sudo 없음. `nvidia-smi`는 비가용이며 리부팅은 금지다. 외부에서는 **포워딩된 SSH 포트 하나**로만 도달한다.

필요한 표면은 두 개다: `/v1/chat/completions`(한국어 가능 소형 instruct)와 `/v1/embeddings`(한국어 가능 임베더). 클라이언트는 OpenAI SDK 형태의 `base_url` + 임의의 `api_key`만 변경해 두 머신을 오갈 수 있어야 한다.

### 2.1 OpenAI 호환 표면

README의 기능 목록 첫 줄들이 그대로 답이다 `[게시]`.

> "OpenAI API compatible chat completions, responses, and embeddings routes"

구체적 경로와 제약:

| 경로 | 성격 | 문서가 명시한 제약 |
| --- | --- | --- |
| `POST /v1/chat/completions` | OpenAI 호환 | 스트리밍·동기 모두 지원. "OpenAI 스펙과의 강한 호환을 주장하지는 않으나, 경험상 많은 앱을 지원하기에 충분하다" |
| `POST /v1/embeddings` | OpenAI 호환 | "**pooling이 `none`이 아닌 모델을 요구한다.** 임베딩은 유클리드 노름으로 정규화된다" |
| `POST /embeddings` | 비호환 | `--pooling none`을 포함한 모든 pooling 지원. 응답 형식이 `/v1/embeddings`와 다르다 |
| `POST /v1/completions`, `/v1/responses`, `/v1/messages`(Anthropic) | 호환 | 이번 범위 밖 |
| `GET /v1/models` | 호환 | **추론 모드에서는 항상 원소 1개**를 돌려준다. 모델 `id`는 기본이 파일 경로이고 `--alias`로 바꾼다 |
| `GET /health` | 공개 | 503 = 로딩 중, 200 = 준비 완료. API 키 검사 없음 |
| `GET /props` | 진단 | `is_sleeping` 필드가 있다(2.5 참조) |

`/v1/chat/completions`는 요청 `model` 필드를 사실상 무시한다(로드된 모델 하나뿐이다). `api_key`도 검사하지 않는다 — `--api-key`를 주지 않으면 아무 문자열이나 통한다. OpenAI SDK는 키를 요구하므로 `sk-no-key-required` 같은 더미를 넣으면 된다.

### 2.2 한 프로세스가 chat과 임베딩을 함께 서비스할 수 있는가

**추론 모드(기본)에서는 불가능하다.** 서버는 `-m`으로 지정한 GGUF 파일 **하나**를 로드하고, 그 모델의 슬롯은 생성 아니면 임베딩 중 하나다. `--embeddings` 플래그의 설명이 이를 확정한다 `[게시]`:

> `--embedding, --embeddings` — "restrict to only support embedding use case; use only with dedicated embedding models" (기본값: 비활성)

즉 `--embeddings`를 활성화한 프로세스는 **전용 임베딩 서버**가 되어 생성 경로를 포기한다. `GET /v1/models`가 원소 1개를 돌려주는 것도 같은 사실의 다른 표현이다.

**라우터 모드에서는 포트 하나로 둘 다 서비스할 수 있다.** README의 "Using multiple models" 절 `[게시]`:

- `llama-server`를 **모델 지정 없이** 실행하면 라우터가 된다: "주 프로세스(라우터)가 각 요청을 적절한 모델 인스턴스로 자동 전달한다."
- 모델 공급원은 세 가지: 캐시(`LLAMA_CACHE`), `--models-dir`, `--models-preset`(INI).
- 모델 인스턴스는 라우터의 **자식 프로세스**다. "모델 인스턴스는 라우터 서버의 명령행 인자와 환경변수를 모두 상속한다."
- 프리셋 INI의 키는 **선행 대시를 뺀 명령행 인자**다. 예: `--n-gpu-layers 123` → `n-gpu-layers = 123`. 불리언 플래그는 값 `true`로 켠다(`jinja = true`).
- POST 경로는 본문의 `"model"` 필드로, GET 경로는 `?model=` 쿼리로 라우팅한다.
- 관련 상한: `--models-max`(동시 로드 모델 수, 기본 4, 0 = 무제한), `--models-memory-margin`(2.5), `--models-autoload`(기본 켜짐).

따라서 "프로세스 하나에 두 모델"은 **아니고**, "리스닝 포트 하나에 두 모델, 뒤에 자식 프로세스 둘"이다. 이 구분은 VRAM 회계에서 중요하다. 자식마다 별도 `llama_context`, 별도 KV 캐시, 별도 연산 버퍼를 잡는다.

라우터 모드로 임베딩 자식을 실행하는 프리셋은 문서화된 키 매핑으로부터 유도된다 `[계산]`. 아래는 **아직 실행하지 않은** 형태다. 프리셋 키는 CLI 인자와 1:1이므로 `embeddings = true`, `pooling = mean`이 그대로 적용되어야 하지만, 이것이 실제로 임베딩 자식 프로세스를 만드는지는 1회 호출로 확인해야 한다 `[측정필요]`.

```ini
version = 1

[*]
host = 127.0.0.1
port = 9931
n-gpu-layers = 99
fit-target = 2048

[chat]
model = /path/EXAONE-4.0-1.2B-Q4_K_M.gguf
alias = local-chat
c = 4096
n-predict = 1024

[embed]
model = /path/Qwen3-Embedding-0.6B-Q8_0.gguf
alias = local-embed
embeddings = true
pooling = mean
c = 1024
batch-size = 1024
ubatch-size = 1024
```

주의: `c`/`ngl` 같은 단축형과 `LLAMA_ARG_*` 환경변수 이름도 키로 쓸 수 있다고 문서가 명시한다. 반면 `host`, `port`, `api-key`, `hf-repo`, `alias`는 라우터가 관리하므로 "제거되거나 덮어써진다"고 문서가 말한다 — 즉 `alias`를 프리셋에 넣는 것은 신뢰하면 안 된다 `[게시]`. 라우팅 이름은 라우터가 정한 모델 id를 `GET /models`로 확인해 고정하는 편이 안전하다.

### 2.3 `--embeddings`와 pooling 플래그

| 플래그 | 문서 값 | 의미 |
| --- | --- | --- |
| `--embedding, --embeddings` | 기본 비활성, env `LLAMA_ARG_EMBEDDINGS` | 프로세스를 임베딩 전용으로 제한 |
| `--pooling {none,mean,cls,last,rank}` | 미지정 시 **모델 기본값** 사용, env `LLAMA_ARG_POOLING` | 토큰 벡터를 문장 벡터로 접는 방식 |
| `--embd-normalize N` | 기본 `2` (= 유클리드/L2) | `-1`=없음, `0`=최대절대값, `1`=택시, `2`=L2, `>2`=p-노름 |
| `--rerank, --reranking` | 기본 비활성 | 리랭킹 경로(`/v1/rerank` 계열). `--pooling rank` 계열과 함께 쓴다 |
| `--ubatch-size` | 기본 512 | 양방향 인코더 리랭커는 **프롬프트 전체가 ubatch에 들어가야 한다**고 문서가 경고한다 |

`--pooling`을 생략하면 GGUF 메타데이터의 `pooling_type`을 따른다 `[게시]`. 이는 HF API에서 모델별로 읽을 수 있다: `bge-m3`는 `pooling_type: 2`(CLS), `embeddinggemma-300M`은 `1`(mean), `Qwen3-Embedding-0.6B`는 `3`(last token) `[게시]`. `3`이 llama.cpp의 `last`에 대응한다는 매핑은 문서에 표로 없으므로, 첫 호출에서 벡터 차원과 정규화(norm≈1)를 확인하는 편이 좋다 `[측정필요]`.

`/v1/embeddings`는 pooling이 `none`이면 동작하지 않고, 응답은 L2 정규화된다. Ollama의 `/api/embed`도 L2 정규화 벡터를 돌려주므로(3.1), 두 엔진 사이를 오갈 때 코사인 유사도 기반 코드는 그대로 쓸 수 있다.

### 2.4 백엔드와 Windows 프리빌트 바이너리

릴리스 자산 이름으로 확인한 사실 `[게시]` (릴리스 `b12110`, `https://github.com/ggml-org/llama.cpp/releases/tag/b12110`):

| 자산 | 용도 |
| --- | --- |
| `llama-b12110-bin-win-cpu-x64.zip` (24.7 MB) | Windows x64, CPU 전용 |
| `llama-b12110-bin-win-vulkan-x64.zip` | Windows x64, Vulkan. NVIDIA·AMD·Intel 모두 가능 |
| `llama-b12110-bin-win-vulkan-arm64.zip` | Windows on ARM |
| `llama-b12110-bin-win-cuda-12.4-x64.zip` (287 MB) | Windows x64, CUDA 12.4 |
| `llama-b12110-bin-win-cuda-13.4-x64.zip` (169 MB) | Windows x64, CUDA 13.4 |
| `llama-b12110-bin-win-sycl-x64.zip`, `-rocm-10.0-x64.zip`, `-openvino-*.zip`, `-opencl-adreno-arm64.zip` | Intel·AMD·Adreno |
| `cudart-llama-bin-win-cuda-*.zip` | 위 CUDA zip에 없는 CUDA 런타임 DLL 묶음 |
| `llama-b12110-bin-ubuntu-*`, `-macos-*`, `-android-*` | 각 플랫폼 |

빌드 문서가 명시하는 두 가지가 구성 판단에 중요하다 `[게시]` (`https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md`):

1. Vulkan 빌드는 Windows에서 **Vulkan SDK를 필요로 한다**(빌드 시에만). 반면 Vulkan **런타임**은 대부분의 GPU 벤더 드라이버에 포함된다. 즉 "프리빌트 zip을 풀어서 실행"하는 경로에는 SDK가 필요 없다.
2. CUDA 빌드는 "기본적으로 CPU 백엔드도 함께 빌드한다". 따라서 CUDA/Vulkan 바이너리 하나로 `-ngl 0`을 주면 CPU 추론으로 되돌릴 수 있다. `--list-devices`로 실제 인식된 장치를 확인할 수 있다.

RTX 5090은 compute capability 12.0(Blackwell)이다 `[게시]` (`https://docs.ollama.com/gpu`). CUDA 12.4 빌드가 sm_120 커널을 포함하는지는 릴리스 노트에 명시되지 않았다. 리눅스 쪽에서 CUDA 바이너리를 쓴다면 **CUDA 13.4 자산 또는 직접 빌드**를 우선하고, 첫 실행에서 `--list-devices`와 로그의 `ggml_cuda` 초기화 줄을 확인해야 한다 `[측정필요]`. 다만 이 서버에는 sudo가 없고 CUDA 툴킷이 없으므로(프로젝트 감사 기록) **직접 빌드는 사실상 불가**하고, 프리빌트 압축 해제가 유일한 무설치 경로다.

Windows 쪽 권고는 Vulkan zip이다. 이유: (1) CUDA zip은 드라이버 CUDA 버전과 맞물려 실패 지점이 생기고, (2) 사용자 머신은 CPU 전용일 수도 있는데 Vulkan zip도 CPU 백엔드를 포함하며, (3) Vulkan은 소비자 GPU에서 드라이버만 있으면 된다. 이 권고는 "CUDA가 더 빠르다"는 통상 관찰을 부정하지 않는다 — 어느 쪽이 실제로 몇 tok/s인지는 `[측정필요]`다.

### 2.5 메모리 관련 플래그 — 공유 GPU에서 결정적인 것들

이번 조사의 핵심 발견은 llama.cpp가 **유휴 시 메모리를 반납하고 요청 시 다시 올리는** 기능을 이미 갖고 있다는 점이다. Ollama의 `keep_alive`에 대응하는 기능이 llama-server에도 있다.

| 플래그 | 기본값 | 문서가 말하는 동작 |
| --- | --- | --- |
| `--fit` | `on` | "맞지 않는 인자를 장치 메모리에 맞도록 자동 조정" |
| `--fit-target MiB` | `1024` | `--fit`이 각 장치에 남겨 둘 여유. 단일 값은 전 장치에 방송 |
| `--fit-ctx N` | `4096` | `--fit`이 줄일 수 있는 최소 컨텍스트 |
| `--sleep-idle-seconds N` | `-1`(비활성) | "유휴 후 서버가 잠든다". 잠들면 **모델과 KV 캐시를 포함한 관련 메모리를 해제**한다. 새 요청이 오면 자동 재로드 |
| `--models-max N` | `4` (0=무제한) | 라우터 모드 동시 로드 상한 |
| `--models-memory-margin N` | `0`(비활성) | 라우터가 장치별로 `N` MiB를 남기고, 새 모델이 들어가도록 LRU 모델을 언로드 |
| `--cache-ram N` | `8192` MiB | 프롬프트 캐시 상한 (호스트 RAM) |
| `-ctk/-ctv`, `--cache-type-k/v` | `f16` | KV 캐시 양자화: f32/f16/bf16/q8_0/q4_0/q4_1/iq4_nl/q5_0/q5_1 |
| `--no-warmup` | 워밍업 켜짐 | 시작 시 빈 실행 생략 → 콜드 스타트 단축 |
| `--api-key`, `--api-key-file` | 없음 | 인증. 여러 키를 쉼표/파일로 |

`--sleep-idle-seconds`는 `--metrics`/`/health`/`/props`/`/models` 요청에 의해 깨어나지 않는다고 문서가 명시한다 — 모니터링이 상주를 망치지 않는다 `[게시]`.

`--models-memory-margin`의 동작은 라우터가 **자식 프로세스를 하나씩 실행해 실측**한다고 설명된다: 메모리를 할당하지 않고 GGUF 메타데이터만 읽어 `min`(=`--fit-ctx`에서의 필요량)과 `max`(현재 여유 메모리로 `--fit`이 고를 최대 컨텍스트에서의 필요량)를 보고한다. 그리고 "요청을 처리 중인 모델은 절대 언로드하지 않는다", "언로드할 것이 없는데도 맞지 않으면 그냥 로드하고 `--fit`이 결정한다" `[게시]`. 이 마지막 문장이 공유 GPU에서의 정직한 한계다 — **맞지 않아도 로드한다.**

### 3.2 keep-alive와 언로드

출처: `https://docs.ollama.com/faq`, `https://github.com/ollama/ollama/blob/main/envconfig/config.go`

`[게시]` 사실:

- 기본 keep-alive는 **5분**이다. `envconfig.KeepAlive()`가 `5 * time.Minute`를 기본으로 두고, 음수는 `math.MaxInt64`(=무한), 0은 "keep alive 없음"으로 처리한다.
- `keep_alive` 값의 형태: 기간 문자열(`10m`, `24h`), 초 단위 수(`3600`), 음수(무한), `0`(생성 후 즉시 언로드).
- 요청 단위 `keep_alive`가 서버 환경변수 `OLLAMA_KEEP_ALIVE`를 덮어쓴다.
- 빈 프롬프트로 `POST /api/generate` 또는 `/api/chat`을 호출하면 **프리로드**된다. `keep_alive: -1`이면 무한 상주.
- `keep_alive: 0` + 빈 프롬프트 = 언로드. 응답의 `done_reason`이 `"unload"`가 된다.
- `ollama stop <model>` CLI도 즉시 언로드한다.
- 로드 중 정체 감지 상한은 `OLLAMA_LOAD_TIMEOUT`(기본 5분, 0 이하는 무한)이다.

**함의.** "상시 상주"를 원하면 `keep_alive: -1`을, "필요할 때만" 원하면 `keep_alive: 0` 또는 짧은 값을 쓴다. 임베딩 모델은 요청마다 호출되므로 매번 콜드 스타트하면 손해다 — 임베딩 모델만 무한 상주시키고 채팅 모델은 짧게 두는 조합이 합리적이다(7.3).

### 3.3 `OLLAMA_MAX_LOADED_MODELS`와 VRAM 배분

`[게시]` (`envconfig/config.go` + FAQ):

| 변수 | 기본값(코드) | 문서 설명 |
| --- | --- | --- |
| `OLLAMA_MAX_LOADED_MODELS` | `0` (자동) | FAQ: "동시에 로드할 수 있는 최대 모델 수. 기본은 GPU 수 × 3, CPU 추론이면 3" |
| `OLLAMA_NUM_PARALLEL` | `1` | 모델당 동시 요청 수. "필요 RAM은 `NUM_PARALLEL × CONTEXT_LENGTH`로 늘어난다" |
| `OLLAMA_CONTEXT_LENGTH` | `0` (자동) | 코드 설명: "VRAM에 따라 4k/32k/256k". FAQ는 "기본 4096"이라 적는다 — **두 문서가 어긋난다** |
| `OLLAMA_KV_CACHE_TYPE` | `f16` | `q8_0`은 약 1/2, `q4_0`은 약 1/4 메모리 |
| `OLLAMA_FLASH_ATTENTION` | 지원 시 자동 | KV 캐시 양자화의 전제 |
| `OLLAMA_GPU_OVERHEAD` | `0` | "GPU별 VRAM 일부를 예약" (바이트) |
| `OLLAMA_SCHED_SPREAD` | 꺼짐 | "항상 모든 GPU에 걸쳐 스케줄" |
| `OLLAMA_MAX_QUEUE` | `512` | 초과 시 503 |
| `OLLAMA_NUM_PARALLEL` | `1` | 위 참조 |

FAQ의 동시성 설명이 가장 중요하다 `[게시]`:

> "시스템에 충분한 여유 메모리(CPU 추론이면 시스템 메모리, GPU 추론이면 VRAM)가 있으면 여러 모델을 동시에 로드할 수 있다. … 새 모델 요청을 로드할 여유가 없으면 모든 새 요청은 큐에 들어가고, 앞선 모델들이 유휴해지면 하나 이상이 **언로드되어** 새 모델 자리를 만든다. … GPU 추론에서는 새 모델이 VRAM에 **완전히 들어가야** 동시 로드가 허용된다."

그리고 다중 GPU 배분: "새 모델의 필요 VRAM을 현재 가용량과 비교해, 단일 GPU에 전부 들어가면 그 GPU에 로드한다. 들어가지 않으면 전체 GPU에 분산한다."

`OLLAMA_CONTEXT_LENGTH` 기본값의 문서 불일치는 실무적으로 중요하다. 4096과 32768은 KV 캐시에서 8배 차이다. 추측하지 말고 **명시적으로 고정**하는 편이 옳다(모델별 Modelfile `PARAMETER num_ctx`, 또는 클라이언트의 `options.num_ctx`).

### 3.4 32 GiB 공유 카드에서의 실제 동작 — 무엇이 보장되지 않는가

여기가 이 조사에서 가장 정직해야 하는 지점이다.

1. **Ollama의 스케줄러는 자체 자식 러너만 관리한다.** 다른 연구자가 자체 셸에서 실행한 프로세스(별도 Ollama, PyTorch, vLLM 등)는 Ollama의 통제 밖이다. Ollama가 그 프로세스를 "축출"할 방법은 없다. 드라이버 수준에서 이미 점유된 VRAM은 그저 **여유가 아닌 메모리**로 보일 뿐이다.
2. **여유 VRAM이 부족할 때 Ollama는 실패하지 않고 부분 오프로드로 떨어진다.** FAQ의 `ollama ps` 예시가 `48%/52% CPU/GPU`를 보여준다. 즉 "로드 성공"이 "GPU에서 돈다"를 뜻하지 않는다. 공유 카드에서 이는 조용한 성능 저하다 — 오류가 아니라 지연으로 나타난다.
3. **VRAM 조회가 실패하면 근사값으로 스케줄한다.** Vulkan 문서가 명시한다: "Vulkan은 가용 VRAM 데이터를 노출하려면 추가 권한이나 root가 필요하다. 둘 다 없으면 Ollama는 모델의 대략적 크기로 최선의 스케줄 결정을 한다" `[게시]`. 이 호스트는 `nvidia-smi`가 비가용이므로 **Ollama가 실제로 정확한 여유 VRAM을 보는지 자체가 미확인**이다 `[측정필요]`.
4. **`OLLAMA_MAX_LOADED_MODELS`는 상한일 뿐 예약이 아니다.** 값을 2로 두어도 "두 모델이 항상 상주"를 보장하지 않는다. 다른 프로세스가 먼저 잡으면 하나만 뜨거나 둘 다 부분 오프로드된다.
5. **모델 저장소 권한.** 프로젝트 감사 기록에 따르면 `/usr/share/ollama`는 `ollama:ollama 0750`이고 일반 사용자는 읽을 수 없다. 따라서 모델 목록·블롭 크기를 파일로 검사할 수 없고, `ollama` API로만 확인해야 한다. 또한 `OLLAMA_MODELS`를 바꾸려면 서버 재시작이 필요한데 sudo가 없다.

**sudo 없이 환경변수를 변경하는 두 가지 경로** (모두 2차 인스턴스이므로 VRAM 관리가 이중화된다는 비용이 있다):

- (A) 기존 11434 서버를 그대로 쓰고, **클라이언트 측에서** `keep_alive`와 `options.num_ctx`로만 정책을 건다. 가장 침습이 적다.
- (B) 동일 사용자로 `OLLAMA_HOST=127.0.0.1:<다른 포트>`, `OLLAMA_MODELS=<자체 디렉터리>`, `OLLAMA_NO_CLOUD=1`, `OLLAMA_MAX_LOADED_MODELS=2`, `OLLAMA_CONTEXT_LENGTH=<고정값>`으로 `ollama serve`를 하나 더 실행한다. 자체 정책을 완전히 통제할 수 있지만, 모델을 자체 디렉터리에 다시 받아야 하고(이 작업 범위에서는 다운로드 금지), VRAM은 결국 같은 카드에서 경쟁한다.

`OLLAMA_NO_CLOUD=1`(또는 `~/.ollama/server.json`의 `disable_ollama_cloud`)은 "비용 0"과 프라이버시 양쪽에서 의미가 있다 `[게시]` (`https://docs.ollama.com/faq`). 기존 서버 설정은 우리가 바꿀 수 없으므로, **모델 이름을 로컬 태그로만 고정**해 클라우드 모델로 라우팅될 여지를 제거하는 것이 우리가 통제 가능한 조치다.

### 4.2 한국어 성능에 대해 이 문서가 주장하지 않는 것

"한국어 가능"의 근거는 **모델 카드의 언어 태그와 학습 데이터 기술**이지, 우리 과제에서의 성능이 아니다. 게시된 한국어 벤치마크 수치를 이 문서가 인용하지 않는 이유는, 후보별로 비교 가능한 동일 조건의 한국어 수치를 확인하지 못했기 때문이다. 따라서 모델 선택은 다음 측정으로 확정해야 한다 `[측정필요]`:

- 채팅: 동일 프롬프트 30~50개에 대해 (a) 한국어로 응답하는 비율, (b) 지시 준수(JSON 스키마, 도구 호출), (c) 초당 토큰.
- 임베딩: 우리 문서 청크 200~500개에 대해 알려진 질의 30~50개로 recall@5와 MRR. 두 모델 이상을 같은 청크로 비교.

## 5. 단일 프로세스 vs 분리 프로세스

### 5.1 세 가지 배치

| 배치 | 프로세스 | 포트 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| A. 완전 분리 | llama-server ×2 또는 Ollama 단일 | 2개 | 각 프로세스의 수명·VRAM·정책을 독립 제어. 한쪽이 죽어도 다른 쪽 산다. 실패 원인 분리가 쉽다 | 클라이언트가 `base_url`을 두 개 관리. `/v1/models`가 두 곳으로 갈린다 |
| B. llama.cpp 라우터 | llama-server ×1 + 자식 N | 1개 | OpenAI 클라이언트에 `base_url` 하나. `--models-memory-margin`으로 자식 간 LRU 조정 | 자식은 라우터가 관리. 라우터 자체가 새 기능이므로 두 타깃에서 동작 확인 필요 `[측정필요]` |
| C. Ollama 단일 | ollama serve ×1 | 1개 | 설치가 가장 단순(서버는 이미 설치됨). `keep_alive`·`MAX_LOADED_MODELS`로 상주 정책 | 정책이 프로세스 전역. 다른 사용자와 같은 서버를 공유할 때 정책 충돌. 버전 0.21.0 고정 |

**권고.** 사용자 Windows 머신은 **B(라우터)** 또는 A. 서버는 **A**(기존 11434 Ollama를 채팅에 쓰고, 임베딩은 별도 포트) 또는 우리 소유의 두 번째 llama-server 쌍. 라우터 모드는 편의가 크지만 새 기능이고, 공유 GPU에서 디버깅 비용이 더 크다. 1차 시연 경로는 A로 두고 B를 개선 경로로 두는 것이 위험 대비 효율이 좋다.

### 5.2 콜드 스타트 — 게시된 수치는 없다

**콜드 스타트 시간은 어느 프로젝트도 게시하지 않는다.** 이 문서가 인용할 수 있는 것은 측정 수단뿐이다.

- Ollama는 응답마다 `load_duration`(ns)을 준다 `[게시]`. 콜드 스타트 실측치는 언로드 후 첫 호출의 이 값이다.
- llama-server는 시작 시 로그에 모델 로드 시간과 버퍼 크기를 남기고, 응답 `timings`에 `prompt_ms`/`predicted_ms`를 준다 `[게시]`. 프로세스 시작부터 `/health` 200까지의 벽시계 시간이 콜드 스타트다.
- 모델 파일을 mmap으로 읽으므로 이론적 하한은 `파일크기 ÷ 디스크 순차 읽기 대역`이다 `[계산]`: 0.76 GiB / 1 GB/s ≈ 0.8 s, 2.32 GiB / 1 GB/s ≈ 2.5 s. 실측은 이보다 크다 — VRAM 복사, 컨텍스트 할당, (기본값인) 워밍업 실행이 더해진다. 워밍업은 `--no-warmup`으로 끌 수 있다.
- Ollama의 로드는 정체 감지 상한(`OLLAMA_LOAD_TIMEOUT`, 기본 5분) 안에서 진행된다 `[게시]`.

`[측정필요]` 항목: (1) EXAONE-4.0-1.2B Q4_K_M의 llama-server 콜드 스타트, (2) Qwen3-Embedding-0.6B Q8_0의 콜드 스타트, (3) 같은 두 모델의 Ollama 콜드 스타트(비교용), (4) 워밍업 유무 차이.

### 5.3 유휴 메모리 비용

| 상태 | llama-server | Ollama |
| --- | --- | --- |
| 상주 | 가중치 + KV + 연산 버퍼 전부 유지 | 동일 |
| 유휴 반납 | `--sleep-idle-seconds`(2.5). 반납 후 첫 요청에 재로드 비용 | `keep_alive` 만료 또는 `keep_alive: 0` |
| 반납 후 비용 | 프로세스는 살아 있고 호스트 RAM만 소량. VRAM ≈ 0 | 러너 프로세스 종료. VRAM ≈ 0 |

즉 **"유휴 시 0에 가깝게" 만드는 수단은 양쪽 다 있다.** 차이는 정책의 소유자다: llama-server는 프로세스 인자로, Ollama는 요청 파라미터 또는 서버 환경변수로 정한다. 공유 서버에서는 프로세스 인자가 더 안전하다 — 다른 사용자의 요청이 우리 정책을 변경하지 못한다.

정량적으로 남는 것은 두 가지다 `[계산]`:

- 호스트 RAM: 0.3~2.5 GiB (모델 파일이 페이지 캐시에 남으면 그만큼). 서버는 125 GiB이므로 무시 가능.
- VRAM: 0. 연산 버퍼까지 해제된다고 문서가 명시한다("모델과 그에 딸린 메모리, KV 캐시 포함").

## 6. 단일 SSH 포워딩 포트로 안전하게 노출하기

### 6.1 전제

서버는 NAT 뒤에 있고 라우터가 SSH 포트 하나만 포워딩한다. 서버 측 `GatewayPorts no`이므로 서버에서 바깥으로 포트를 열 수 없다. 역방향 터널도, 새 인바운드 포트도 선택지가 아니다. 따라서 **인바운드 SSH 연결 하나 위에 여러 개의 로컬 포워드를 구성한다.**

### 6.2 터널 명령

```bash
# 서버의 루프백 포트 2개를 로컬 루프백 포트 2개로 당긴다.
# 연결 1개, 로컬 리스너 2개. -N = 원격 명령 실행 안 함.
ssh -N \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:18000:127.0.0.1:9931 \
  -L 127.0.0.1:18001:127.0.0.1:11434 \
  -p <포워딩된포트> <user>@<host>
```

클라이언트는 이제 `base_url=http://127.0.0.1:18000/v1`(llama-server), `http://127.0.0.1:18001/v1`(Ollama)로 접근한다. `api_key`는 아무 문자열이나 된다(`--api-key`를 설정했다면 그 값).

핵심 옵션의 의미 `[게시]` (`https://man.openbsd.org/ssh.1`):

- `-L [bind_address:]port:host:hostport` — "로컬 포트로의 연결을 원격 측의 주어진 호스트·포트로 포워딩한다. 기본적으로 로컬 포트는 `GatewayPorts` 설정에 따라 바인딩되지만, **명시적 bind_address를 쓸 수 있다. bind_address `localhost`는 그 리스닝 포트를 로컬 전용으로 바인딩함을 뜻하고, 빈 주소나 `*`는 모든 인터페이스에서 사용 가능함을 뜻한다.**"
- `-N` — "원격 명령을 실행하지 않는다. 포트 포워딩만 할 때 유용하다."
- `ExitOnForwardFailure=yes` — 포워드 실패 시 조용히 살아 있는 좀비 터널을 만들지 않는다.
- `ServerAliveInterval` — 끊긴 터널을 감지한다. 유휴 시간이 긴 추론 서버에서 특히 필요하다.
- `-R`(역방향)의 기본값도 참고: "기본적으로 서버의 TCP 리스닝 소켓은 **루프백 인터페이스에만** 바인딩된다. 이는 bind_address로 덮어쓸 수 있으나, 원격 bind_address 지정은 서버의 `GatewayPorts` 옵션이 켜져 있어야만 성공한다."

`-L 127.0.0.1:...`처럼 **바인드 주소를 명시**하는 것이 요점이다. 생략하면 클라이언트 측 `GatewayPorts` 설정에 따라 LAN에 열릴 수 있다.

### 6.3 왜 loopback 바인딩 + SSH 터널이 옳은 경계인가

네 가지 이유다.

1. **인증과 기밀성이 SSH 계층에 있다.** 추론 API 자체에는 인증이 없거나 약하다. Ollama의 `/v1/*`는 `api_key`를 무시하고, llama-server도 `--api-key`를 주지 않으면 아무 키나 통한다. 노출 경로에 인증을 부여하는 가장 저비용 방법은 이미 인증된 채널(SSH)을 재사용하는 것이다. 별도 리버스 프록시 + TLS + 토큰을 세우는 것은 이 규모에서 과잉이고, sudo 없이는 사실상 불가능하다.
2. **공격면이 0에 가깝다.** 서버에서 리스닝 소켓은 `127.0.0.1`에만 있다. NAT 뒤 내부망에서도, 라우터의 포워딩 테이블에서도 도달 불가다. 포트 스캔으로 발견되지 않는다. `0.0.0.0`에 바인딩하면 라우터가 그 포트를 포워딩하지 않는 한 도달은 안 되지만, **내부망 전체**와 **서버의 다른 사용자**에게는 열린다.
3. **수명이 연결에 묶인다.** SSH 연결이 끊기면 포워드도 사라진다. "잊고 열어 둔 포트"가 생기지 않는다.
4. **감사 가능하다.** `sshd` 로그에 접속 기록이 남고, 애플리케이션 로그에 요청이 남는다. 누가 언제 붙었는지가 한 곳에 모인다.

**정직한 한계 두 가지.** (a) 루프백 바인딩은 **같은 호스트의 다른 로컬 사용자를 배제하지 않는다.** 서버의 다른 사용자는 `127.0.0.1:9931`에 그대로 접근할 수 있다. 이 호스트는 9개 계정이 공유되고 `/dev/nvidia0`이 전 사용자 쓰기 가능인 환경이므로(프로젝트 감사 기록), 서버는 "반신뢰"로 취급해야 한다. 완화책은 (i) 예측 불가능한 높은 포트 번호, (ii) `--api-key`(llama-server) 사용, (iii) `--tools`/`--agent`/MCP 프록시를 절대 활성화하지 않기 — 문서가 "신뢰할 수 없는 환경에서는 활성화하지 말라"고 두 번 경고한다. (b) SSH 포트 하나를 공유하므로 그 포워딩이 죽으면 두 서비스가 동시에 사라진다. 단일 장애점이며, 이는 환경 제약이지 설계 선택이 아니다.

**절대 하지 말 것** `[게시]` (llama-server README, CORS·tools 절):

- `--host 0.0.0.0` — 이유는 위 2번.
- `--tools all`, `--agent`, `--ui-mcp-proxy` — 로컬 파일 읽기/쓰기와 셸 실행을 HTTP로 노출한다. 문서가 "서버와 같은 권한으로 자식 프로세스가 돈다"고 명시한다.
- `--cors-origins *` 를 인증 없이 유지 — 기본값이 이미 `*`이고 credentials를 허용하므로, 브라우저에서 접근 가능한 환경이면 `--cors-origins localhost`로 좁힌다.
- `--reuse-port` — 다중 인스턴스 디버깅 중이 아니라면 불필요한 혼란만 만든다.

## 7. 31.36 GiB 공유 GPU에 대한 정직한 평가

### 7.1 산술: 필요한 양은 작다

카드 총량 31.36 GiB(= 33,673,805,824 B) `[게시]`(프로젝트 감사 실측).

KV 캐시는 게시된 config.json에서 계산할 수 있다 `[계산]`. 공식은 `레이어수 × KV헤드수 × head_dim × 2(K,V) × dtype바이트 × 토큰수`다.

| 모델 | 레이어 | KV 헤드 | head_dim | dtype | 바이트/토큰 | 4096 ctx | 8192 ctx |
| --- | --- | --- | --- | --- | --- | --- | --- |
| EXAONE-4.0-1.2B | 30 | 8 | 64 | f16 | 61,440 | 240 MiB | 480 MiB |
| Qwen3-1.7B | 28 | 8 | 128 | f16 | 114,688 | 448 MiB | 896 MiB |
| Qwen3-Embedding-0.6B | 28 | 8 | 128 | f16 | 114,688 | 448 MiB | 896 MiB |

KV를 `q8_0`으로 두면 절반, `q4_0`이면 1/4이 된다 `[게시]`(Ollama FAQ의 비율). 임베딩 모델은 생성하지 않으므로 컨텍스트를 512~1024로 줄이면 KV는 56~112 MiB로 떨어진다 `[계산]`.

권고 조합의 VRAM 예산:

| 항목 | 가중치 `[게시]` | KV `[계산]` | 연산 버퍼 `[측정필요]` | 소계 |
| --- | --- | --- | --- | --- |
| 채팅: EXAONE-4.0-1.2B Q4_K_M, ctx 4096 | 0.76 GiB | 0.23 GiB | 0.3~0.6 GiB(가정) | 1.3~1.6 GiB |
| 임베딩: Qwen3-Embedding-0.6B Q8_0, ctx 1024 | 0.60 GiB | 0.11 GiB | 0.2~0.4 GiB(가정) | 0.9~1.1 GiB |
| **합계** | 1.36 GiB | 0.34 GiB | 0.5~1.0 GiB | **2.2~2.7 GiB** |
| 참고: 4B 채팅으로 올릴 때 | +1.56 GiB | +0.3~0.5 GiB | +0.2 GiB | **≈ 4.3~5.0 GiB** |

연산 버퍼는 어느 문서에도 수치가 없다. 위 "가정"은 **가정**이며 측정으로 대체해야 한다. 어떤 경우든 전체의 **7~16%**다. 수치상 여유는 명백하다.

### 7.2 수치상 여유와 실제 위험은 다르다

위 표가 "올라간다"를 뜻하지 않는 이유:

1. **여유 VRAM의 현재 값은 우리가 통제하지 않는다.** 다른 연구자의 장기 세션이 지금 얼마를 잡고 있는지, 앞으로 늘어날지 알 수 없다. 프로젝트 감사 시점 기록은 "여유 30.83 GiB"였으나 이는 그 시점의 스냅샷이고, **모델 로드 직전에 다시 재야 하는 값**이다.
2. **`nvidia-smi`는 비가용이며 재부팅은 금지다.** 기존 감사 기록은 커널 모듈 595.84 / 유저스페이스 595.99 불일치와 NVML 오류 18을 보고했다. 이 설계는 해당 명령의 복구나 재부팅을 전제로 하지 않는다. 확인된 관측 경로는 `cuMemGetInfo`(총량/여유)이며, 온도·전력·사용률·프로세스별 VRAM은 미확인이다. 다른 계측 수단까지 불가능하다고 입증한 것은 아니다.
3. **엔진이 여유 VRAM을 정확히 보는지가 미확인이다.** 3.4의 3번. Ollama가 근사값으로 스케줄하면 "들어간다"는 판단 자체가 틀릴 수 있다.
4. **"들어간다"와 "성능이 나온다"가 다르다.** 부분 오프로드로 CPU/GPU 분할되면 로드는 성공하고 지연만 10배가 된다. 오류가 없으므로 조용히 넘어간다.
5. **호스트 RAM은 안전하다.** 125 GiB이므로 CPU 폴백은 언제나 가능하다. 즉 **최악의 경우는 실패가 아니라 느려짐**이다. 이는 위험이 낮다는 뜻이지 없다는 뜻이 아니다 — 시연 중 느려짐은 실패와 같다.

**판정.** "다른 사람의 장기 세션을 축출하지 않고 두 모델을 상주시킬 수 있는가"에 대한 답은 조건부 "예"다. 조건은 (a) 로드 직전 여유 VRAM이 3~5 GiB 이상이고, (b) 우리 프로세스가 자체 상한을 스스로 지키고, (c) 부분 오프로드로 떨어졌는지 **탐지**할 수 있을 때다. (c)가 없으면 "예"라고 말해서는 안 된다.

### 7.3 필요한 중재·상주 정책

두 엔진이 공유 카드에서 지켜야 할 규칙. 이 목록은 **설계 제안**이며 검증되지 않았다.

1. **소유 경계를 지킨다.** 우리는 우리 프로세스만 시작·중지한다. 남의 프로세스를 죽이거나, `kill -9`로 VRAM을 회수하거나, `CUDA_VISIBLE_DEVICES` 조작으로 남의 장치를 가져오지 않는다. 어떤 엔진도 남의 할당을 축출할 수 없다(3.4의 1번).
2. **상한을 스스로 건다.** llama-server: `-c`를 **고정**(자동 확장 금지), `-ngl`을 명시(자동 전체 오프로드 금지), `--fit-target 2048`(2 GiB 여유 유지). Ollama: `OLLAMA_GPU_OVERHEAD`로 여유분 예약, `OLLAMA_MAX_LOADED_MODELS=2`, `OLLAMA_CONTEXT_LENGTH` 고정.
3. **유휴 반납을 켠다.** llama-server `--sleep-idle-seconds 300`; Ollama `keep_alive` 5분 이하 또는 `OLLAMA_KEEP_ALIVE`. 예외: 임베딩 모델은 호출 빈도가 높으므로 상주가 합리적이나, 반납 정책을 끄는 대신 **컨텍스트를 512~1024로 줄여 상주 비용을 1 GiB 이하로** 만든다.
4. **라우터를 쓴다면 여유 마진을 건다.** `--models-memory-margin 2048`, `--models-max 2`. 단, 문서가 "맞지 않아도 로드한다"고 명시하므로(2.5) 이는 예방이지 보장이 아니다.
5. **로드 전에 잰다.** 아래 7.4의 측정을 로드 절차에 넣는다. 여유가 임계 미만이면 **부분 오프로드나 CPU 전용으로 내려간다**(`-ngl 0`). 서버 RAM이 125 GiB이므로 CPU 폴백은 현실적이다.
6. **탐지한다.** 로드 후 `ollama ps`의 PROCESSOR가 `100% GPU`인지, llama-server 로그의 오프로드 레이어 수가 의도와 같은지 확인한다. 다르면 그 사실을 기록하고 성능 기대치를 낮춘다.
7. **버전을 고정한다.** Ollama 0.21.0은 이미 설치된 것이고 sudo 없이는 올릴 수 없다. 문서(0.40.x)와 동작이 다를 수 있으므로, 우리가 쓰는 표면은 **설치본에서 1회 검증한 것만** 쓴다.

### 7.5 계측 수단 — `cuMemGetInfo`

`nvidia-smi` 없이 VRAM을 재는 경로. 프로젝트 감사에서 이 호출이 정확한 바이트를 반환함을 확인했다(프로젝트 기록, 게시 문서 아님). Python 3.12가 이미 있으므로 추가 설치가 필요 없다.

```python
import ctypes
cu = ctypes.CDLL("libcuda.so.1")
cu.cuInit(0)
dev = ctypes.c_int()
cu.cuDeviceGet(ctypes.byref(dev), 0)
free, total = ctypes.c_size_t(), ctypes.c_size_t()
cu.cuMemGetInfo_v2(ctypes.byref(free), ctypes.byref(total))
gib = 1024 ** 3
print(f"total={total.value/gib:.2f} GiB free={free.value/gib:.2f} GiB")
```

한계를 명시한다: 이 함수는 **총량과 여유**만 준다. 프로세스별 사용량, 온도, 전력, 사용률은 주지 않는다. 이 호스트에서는 `nvidia-smi`가 비가용이고 재부팅도 하지 않으므로 그 값들은 확인되지 않았으며, 다른 계측 수단을 모두 시험해 배제한 것은 아니다.

### 8.2 연구실 Ubuntu 서버

전제: sudo 없음, 재부팅 금지, `nvidia-smi` 비가용, 외부는 SSH 포트 하나.

| 결정 | 선택 | 근거 |
| --- | --- | --- |
| 1차 구성 | 기존 Ollama 0.21.0(11434) + 우리 소유 llama-server(임베딩, 127.0.0.1:9931) | 설치 최소. Ollama는 이미 있고 sudo 불필요 |

| 노출 | 클라이언트에서 `ssh -N -L ...` 다중 포워드 | 6.2 |
| VRAM 상한 | `-c` 고정, `-ngl` 명시, `--fit-target 2048` | 7.3 |

런타임 선택에 대한 정직한 유보: 리눅스에서 프리빌트 CUDA 바이너리가 드라이버(595.x, CUDA 13.2 API)와 맞물려 동작하는지는 확인되지 않았다 `[측정필요]`. 맞지 않으면 CPU 전용(`-ngl 0`)으로도 1.2B 채팅과 0.6B 임베딩은 현실적인 속도를 낼 수 있으나, 그 속도 역시 `[측정필요]`다.

### 8.3 비용

과금 API를 호출하지 않으므로 **API 비용은 0원**이다. 남는 비용은 전력과 기존 하드웨어의 감가상각뿐이며, 두 머신 모두 이미 가동 중인 장비다. 클라우드 임베딩 API와 비교한 절감액을 이 문서가 수치로 주장하지 않는 이유는, 호출량과 단가가 확정되지 않았기 때문이다. 비용 관점에서 중요한 것은 절감액이 아니라 **과금 표면이 코드에 존재하지 않는다**는 사실이다 — `base_url`이 `127.0.0.1`을 가리키므로 유출 경로가 없다. 단, 3.4에서 언급한 대로 Ollama의 클라우드 기능이 켜져 있으면 예외이므로 모델 이름을 로컬 태그로 고정한다.

## 9. 검증 절차 (수행하지 않음 — 다음 단계의 체크리스트)

이 문서는 조사 기록이므로 아래를 실행하지 않았다. 순서대로 하면 7.4의 M1~M12를 채울 수 있다.

```text
1. (서버) cuMemGetInfo로 로드 전 여유 VRAM 기록            → M1
2. (서버) curl /api/ps 로 현재 상주 모델과 size_vram 확인    → M3 일부
3. (서버) GET /health 가 200이 될 때까지 시간 측정           → M4
4. (서버) /v1/embeddings 1회 호출, 차원·norm 확인            → M11, M12
5. (서버) cuMemGetInfo 재측정, 차분 = 우리 프로세스 사용량     → M2
6. (서버) 고정 프롬프트 3종 × 5회, timings 수집              → M6
7. (서버) 유휴 반납 유발 후 cuMemGetInfo                     → M5
8. (서버) 시간대 2회 반복                                     → M8
9. (Windows) 같은 벤치, Vulkan과 -ngl 0 비교                  → M10
10. (양쪽) 한국어 품질 세트                                   → M9
```

각 단계의 성공 기준은 **숫자를 얻는 것**이지 "동작함"을 확인하는 것이 아니다. 예를 들어 5번에서 차분이 3 GiB를 넘으면 7.1의 예산 가정이 틀린 것이고, 3번에서 `processor`가 `100% GPU`가 아니면 7.2의 5번 위험이 실현된 것이다.
