# 무설정 자동화 설계

**부제:** 설치에서 완료된 작업까지 — 사용자가 설정 화면을 열지 않는 경로

**문서 상태:** 설계 문서(design only). 코드 없음. 이 문서의 규칙은 현재 구현되어 있지 않다.  
**기준일:** 2026-11-04 (현행화 고지 추가: 2026-11-05)  
**기반 및 아키텍처 전환 고지:** 본 설계 문서는 초기 Mixdog 1.4.5 기반 검토안을 서술하고 있으나, 현행 아키텍처는 **`omp` 18.16.0 Windows 로컬 하네스(기본) + loopback SSH 서버 게이트웨이(Ubuntu 24.04 RTX 5090 31.36 GiB)** 2평면 구조로 전환되었습니다. Mixdog 데스크톱 에이전트 의존은 제거되었고, DSH는 기본 경로가 아니라 `-Runtime dsh`로만 도달하는 선택 경로로 남아 있습니다(그 경로만 `npx`로 패키지를 받을 수 있습니다). 클라우드 전송은 독립적 명시 동의를 요구합니다. 공급자 전략은 여전히 로컬 우선(local-first)이며, 계정을 요구하는 클라우드가 기본값이 되지 않습니다.  
**근거:** 이 저장소의 Python 계층(`engine/`, `prototype/`, `harness/`), 로컬 하네스(`omp` 18.16.0 RPC 브리지), 그리고 원격 게이트웨이 사양.  
**짝 문서:** 프로필·페르소나 설계는 별도 문서가 소유한다. 이 문서는 그 내용을 다루지 않는다.

## 0. 기준선: 지금 무엇이 있고 무엇이 없는가

### 0.1 기반과 이 저장소의 관계

기반 애플리케이션은 **`omp`(oh-my-pi) 18.16.0**이며, 프로젝트 로컬 Bun이 실행하고 `app/`의 Node 브리지가 stdio NDJSON으로 감쌉니다. 단일 실행 진입점은 `40_AI보고서/launch.cmd` → `launch.ps1`이고, 기본 런타임은 `omp`, `-Runtime dsh`일 때만 DSH(`scripts/launch.ps1`)로 갑니다. 이 저장소의 Python 계층(`engine/`, `harness/`, `prototype/`)은 `omp` 안에서 실행되는 제품 코드가 아니라 **별도 계층**이며, 둘을 잇는 배선은 아직 없습니다(대화 실행은 `omp` 코어가 자기 `models.yml` 프로바이더로 직접 호출).

이 절의 아래 표는 **초기 검토 기준선(Mixdog 1.4.5 전제)** 이며, 현행 기반은 위 §0.1의 `omp` 18.16.0입니다. 두 기반을 같은 것으로 읽지 않습니다.

| 사실 | 출처 |
| --- | --- |
| 기반은 Mixdog 1.4.5이며 Apache-2.0으로 배포된다. | 기반 전환 고지(2026-11-04) |
| 기반은 Electron 에이전트다. Chromium/Node 런타임을 자체적으로 포함한다. | 기반 전환 고지 |
| 공급자 전략은 로컬 우선이고, OpenRouter는 명시적 opt-in 클라우드 경로다. | 기반 전환 고지 |
| 계정을 요구하는 클라우드 경로는 기본값이 아니다. | 기반 전환 고지 |

확인되지 않은 사실은 다음과 같다. 이 문서는 이 묶음을 **`pending — extension surface under inventory`**로 표시한다.

- Mixdog의 설정 키 이름, 설정 파일 위치, 스키마.
- 요청 실행·파일 편집·권한·동의·텔레메트리·업데이트를 가로챌 수 있는 훅의 존재와 형태.
- 로컬 추론 런타임을 어떻게 발견·기동하는지.
- OpenRouter 자격증명을 어디에 저장하는지.
- 모델 카탈로그와 컨텍스트 상한을 어디에서 읽는지.

따라서 **오늘 제품 경로에서 자동화가 구현되어 있다고 말할 수 있는 것은 없다.** 이 문서는 기반의 표면이 재고되기 전까지 모든 L2 규칙을 `pending`으로 둔다. 규칙의 목적지는 이름을 확인한 곳에만 이름을 쓰고, 이름을 모르면 “목적지 미확인”이라고 적는다.

### 0.2 참조 구현이 이 PC에서 측정한 값

아래는 **참조 구현**(Python 엔진)의 실제 출력이다(2026-11-04). Mixdog의 상태가 아니며, 제품 경로의 준비 상태를 뜻하지 않는다.

| 항목 | 값 |
| --- | --- |
| CPU 코어 | 12 |
| 물리 RAM | 39.31 GB |
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU, 8.0 GB VRAM |
| 판정 티어 | `standard_local` (Tier 2) |
| 티어 양자화 라벨 | `Q4_K_M` |
| 티어 로컬 프리셋 | `local/qwen2.5-coder-7b-gguf` |
| 기본(프리셋) 모델 | `deepseek/deepseek-v4.1-flash-1017` |
| 백그라운드 모델 | 없음(`select_background_model().model_id == ""`, `entry is None`, `status="unavailable"`) |
| 실행 경로 | `zdr_cloud`(참조 구현 기본값), `configured: false`. **제품 기본값은 `local_only`이며 이 표와 다르다(§2.3.1).** |
| 미설정 사유 | `no endpoint configured` (참조 구현 기준) |
| 메모리 계층 | `extractive_only` (모델 호출 없음) |
| 선택 출처(참조 구현) | `engine/`의 티어 인지 프리셋 선택 |

이 표는 네 가지를 말해준다.

1. **Tier 2는 이 PC의 사실이다.** RAM 39.31GB는 Tier 3의 RAM 조건(≥32GB)을 넘지만, VRAM 8.0GB가 Tier 3의 VRAM 조건(≥12GB)에 미달하므로 Tier 2다. Tier 3는 `AND`, Tier 2는 `OR` 조건이라는 규칙의 직접적인 결과다.
2. **티어가 능력이지 준비 상태가 아니다.** 로컬 프리셋 이름이 보여도 로컬 엔드포인트가 없으므로 실제 로컬 호출은 불가능하다.
3. **선택된 모델은 가용 모델이 아니다.** `selected_model`은 릴리스 프리셋 라벨이고, `configured: false`가 실제 상태다. 이 둘을 같은 화면에서 구분하지 않으면 “준비됨”이라는 거짓 성공이 만들어진다.
4. **이 PC에는 추론 런타임도 모델 가중치도 없다.** 따라서 로컬 우선 기본값은 아직 관찰된 적이 없다.

> **로컬 우선 기본값은 검증되지 않았다.** 최선 경로(§5.3 A)는 로컬 추론이 동작한다는 가정 위에 서 있다. 이 PC에는 추론 런타임도, 모델 가중치도 없다. 엔드포인트가 생기기 전까지 로컬 우선은 **설계 주장**이지 실측이 아니다. 런타임이 없을 때 앱이 해야 할 일은 클라우드로 넘어가는 것이 아니라 `unavailable`과 사유를 표시하는 것이다(§2.3.1 4번, E-LOC-01).

### 0.3 하드웨어 티어 규칙: 이 문서가 확장할 규율

`engine/hardware_profiler.py`의 판정은 다음 순서를 따른다. 위에서부터 평가하고 첫 일치를 채택한다.

| 순서 | 조건 | 결과 |
| --- | --- | --- |
| 1 | `ram_gb >= 32.0` **AND** `vram_gb >= 12.0` | `advanced_local` (Tier 3) |
| 2 | `ram_gb >= 16.0` **OR** `vram_gb >= 6.0` | `standard_local` (Tier 2) |
| 3 | `ram_gb >= 8.0` **OR** `vram_gb >= 2.0` | `lightweight_local` (Tier 1) |
| 4 | 그 외 | `rule_based_only` (Tier 0) |

이 규칙이 좋은 이유는 숫자가 아니라 **태도**다.

- 측정 가능한 것만 측정한다. GPU는 `nvidia-smi`가 PATH에 있고 정상 응답할 때만 인정한다. GPU 이름으로 VRAM을 추측하지 않는다.
- 측정 실패는 낮은 쪽으로 수렴한다. RAM 조회가 모두 실패하면 `0.0`이 되고, VRAM도 낮으면 Tier 0이 된다.
- 판정은 순서가 있는 결정론이다. 같은 입력은 같은 출력을 낸다.
- 티어는 능력 상한이지 실행 약속이 아니다.

이 문서는 같은 태도를 하드웨어 밖의 결정(경로, 모델, 컨텍스트, 권한)에 반복 적용한다.

**기준선 정합성 점검 두 가지(설계 입력):**

- **문서-코드 불일치(설계 선택이 아니라 결함).** 모듈 docstring은 “RAM 조회가 모두 실패하면 안전하게 Tier 0으로 수렴한다”고 서술한다. 그러나 실제 판정은 `OR` 조건이므로, RAM 측정이 실패해도 VRAM ≥ 6GB인 GPU가 있으면 Tier 2가 된다. 측정 실패와 저사양은 다른 사건인데 코드에서는 둘 다 `ram_gb = 0.0`으로 표현된다. 이 문서는 이 동작을 의도된 설계로 취급하지 않는다. `ram_measured` 같은 측정 상태 플래그가 추가되기 전까지 이 불일치는 **미해결 결함**이다(§9 P-08).
- `LOCAL_TIER_QUANTIZATION`은 Tier 3에 `PQ2_0 (Ternary 2.13 bpw, VRAM 6.7GB)`를 적지만, Tier 3 게이트는 VRAM ≥ 12GB다. 두 숫자는 서로 다른 것을 잰다(가중치 크기 대 총 적재 예산). 게이트를 가중치 크기에서 역산해서는 안 되며, 카탈로그에 `weights_bytes`가 없으면 “적재 가능”을 계산할 수 없다(§9 P-07).

### 0.4 이 저장소가 이미 지키는 선례

설계 원칙을 새로 발명하는 것이 아니라, 이미 있는 태도를 제품 전체로 넓힌다.

| 선례 | 근거 |
| --- | --- |
| 엔드포인트가 없으면 placeholder 호스트나 모델을 만들지 않고 `NOT CONFIGURED`와 사유를 표시한다. | `prototype/main.py` `endpoint_status()`, `harness/ui.py` `render_text()` |
| 페이로드 모듈이 없으면 대체 출처를 `selection_source`에 이름으로 남긴다. | `prototype/main.py` `preset_status()` |
| 로컬 엔드포인트가 없으면 모델 호출 없이 `extractive_only`라고 말한다. | `prototype/main.py` `memory_status()` |
| 백그라운드 모델을 실행할 수 없으면 `unavailable`과 사유를 반환하고 Qwen/클라우드로 대체하지 않는다. | `engine/registry.py` `select_background_model()` |
| API 키는 존재 여부만 보고하고 `__repr__`에서 마스킹한다. | `engine/lm_client.py` |
| 공급자가 `usage`를 보고하지 않으면 비용을 `None`으로 두고 0으로 위장하지 않는다. | `engine/lm_client.py` `Usage`, `_build_usage()` |

### 0.5 이 문서가 주장하지 않는 것

- 어떤 규칙도 구현되어 있다고 주장하지 않는다. `[확인]`은 기준선 사실에만 붙는다.
- 성능, 절감률, 품질 향상 수치를 주장하지 않는다.
- Mixdog이 설정 화면 밖의 확장점을 제공한다고 가정하지 않는다. 필요한 훅은 전부 `pending — extension surface under inventory`다.
- Mixdog의 설정 키나 파일 경로를 발명하지 않는다. 이름을 모르는 목적지는 “목적지 미확인”으로 적는다.
- 보안 인증이나 법적 적합성을 주장하지 않는다. 동의 문구는 설계 카피이며 법적 검토를 대체하지 않는다.

### 0.6 라이선스 의무: 개발자 고정 제약

Mixdog은 Apache-2.0으로 배포된다. 이 절의 항목은 **사용자가 고르는 설정이 아니라 개발자가 릴리스에서 고정하는 의무**다. 따라서 §1의 결정 인벤토리에 넣지 않고, §8의 수동 잔류 목록에도 넣지 않는다. 사용자에게 물어도 면제되지 않는 조건이기 때문이다.

| ID | 의무 | 근거 | 제품에서의 자동 처리 | 위반 시 |
| --- | --- | --- | --- | --- |
| L-01 | 라이선스 사본이 제품에 동봉된다 | Apache-2.0 §4(a): 수령자에게 라이선스 사본 제공 | 설치 번들에 `LICENSE`를 포함하고, 첫 실행의 번들 무결성 검사가 그 존재를 확인한다 | 배포 중단. 앱은 “배포물이 불완전함”을 표시하고 정상 상태를 주장하지 않는다 |
| L-02 | 수정한 파일에 변경 고지가 붙는다 | Apache-2.0 §4(b): 변경한 파일에 눈에 띄는 고지 | 이 계층이 수정·재배포하는 Mixdog 파일마다 변경 고지 헤더를 유지한다 | 수정본 배포 중단 |
| L-03 | NOTICE 귀속 문구가 유지된다 | Apache-2.0 §4(c): NOTICE의 귀속 고지를 제거하지 않음 | `NOTICE`를 번들에 포함하고 앱의 “정보” 화면에서 읽을 수 있게 한다 | 배포 중단 |
| L-04 | 상표 사용을 주장하지 않는다 | Apache-2.0 §6: 라이선스는 상표권을 부여하지 않음 | 제품명·아이콘·문구가 Mixdog의 공식 배포물이나 보증으로 오인되지 않게 한다. “Mixdog 기반”은 사실 서술로만 쓴다 | 명칭·표시 수정 전 배포 중단 |
| L-05 | 번들한 GPL 구성요소는 자체 소스 제공 의무를 진다 | GPL 계열은 배포 시 대응 소스 제공 의무를 진다(버전별 조항) | GPL 구성요소를 번들하려면 대응 소스 제공 경로를 릴리스 게이트에서 확인한다. 확인되지 않으면 번들하지 않고 해당 기능을 `unavailable`로 표시한다 | 해당 구성요소 제거 또는 소스 제공 경로 확보 전 배포 중단 |

자동화에 주는 세 가지 제약:

1. **첫 실행은 배포물의 완전성을 검사한다.** `LICENSE`와 `NOTICE`가 번들에 없으면 앱은 정상 상태를 주장하지 않는다. 이것은 사용자 동의가 아니라 개발자 의무의 자기 점검이다.
2. **재배포에도 같은 의무가 따라간다.** 학교 랩 이미지나 USB 사본으로 재배포해도 `LICENSE`·`NOTICE`·변경 고지가 함께 있어야 한다. 없으면 앱은 “이 사본은 재배포 요건을 충족하지 않음”을 표시한다.
3. **GPL 구성요소의 부재는 기능 부재로 처리한다.** 소스 제공 의무를 이행할 수 없으면 그 구성요소를 빼고, 그에 의존하는 기능을 조용히 다른 구현으로 대체하지 않는다. 대체 구현이 없으면 `unavailable`과 사유를 표시한다.

이 절은 법적 조언이 아니다. 조항 해석과 관할별 요구는 릴리스 전 법적 검토가 필요하다(§9.3).

## 1. 결정 인벤토리

### 1.1 읽는 법

AI 코딩 도구를 처음 실행한 사용자가 오늘 마주치는 결정을 80개 항목으로 열거한다. 각 항목은 다음을 답한다.

- **결정**: 무엇을 정해야 하는가.
- **오늘 사용자가 하는 일**: 일반적인 도구에서 사용자가 실제로 하는 조작.
- **설계상 결정 주체**: 앱, 릴리스, 사용자(동의), 사용자(선택), OS 중 누가 정하는가.
- **앱이 읽는 입력**: 앱이 그 결정을 내리기 위해 측정하거나 읽는 값.
- **해석**: 이 문서에서 그 결정을 처리하는 규칙·동의·수동 항목의 ID.

“결정 주체 = 앱”은 **앱이 임의로 고른다**는 뜻이 아니다. 앱이 측정 가능한 입력을 읽고 결정론적 규칙으로 고른다는 뜻이다. 규칙은 §2에 있다.

괄호 표기: `[일반]`은 이 저장소의 코드 근거가 없는 일반 범주, `[확인]`은 코드·문서·측정으로 확인된 항목이다. 표에서는 그룹 도입부에 근거를 밝히고, 개별 행에는 반복하지 않는다.

### 1.10 인벤토리 요약

80개 항목의 분포는 다음과 같다.

- **앱이 자동으로 정하는 것**: 대부분의 설치·모델·로컬·생성·에이전트 항목. 사용자는 모델 이름, 컨텍스트 크기, 양자화, GPU 레이어, temperature를 보지 않는다.
- **릴리스가 고정하는 것**: 런타임 pin, 기본 모델, 카탈로그 릴리스, 티어별 양자화·프리셋, 백그라운드 모델, 샘플링 표. 사용자에게서 앱으로, 앱에서 릴리스로 옮긴 결정이다.
- **사용자 동의가 필요한 것**: 데이터 반출, 텔레메트리, 쓰기 범위, 명령 실행, 비밀 파일, 외부 도구, 모델 라이선스, 프라이버시 등급 하향, 이력 변경. §4와 §8에서 다룬다.
- **사용자 선택으로 남는 것**: 업데이트 채널, 언어·접근성, 키보드 단축키. 기본값은 자동이지만 틀렸을 때 고칠 수 있어야 한다.

**전역 “권한 수준(permission level)” 다이얼은 인벤토리에서 제거한다.** 그 자리는 D68–D72의 행위 클래스별 동의가 대신한다. 전역 다이얼은 사용자가 그 의미를 알 수 없고, 한 번 “자동 승인”으로 두면 모든 경계가 한꺼번에 열리기 때문이다.

## 2. 자동 해석 규칙

### 2.1 규칙의 형식과 계층

모든 규칙은 다음 네 가지를 갖는다.

1. **입력**: 앱이 측정하거나 읽는 값.
2. **조건·임계값**: 결정론적 비교. 측정된 사실이면 단위와 출처를, 조정 가능한 값이면 `P_*` 파라미터 이름을 쓴다.
3. **결과**: 선택되는 값 또는 상태.
4. **실패 시**: 결정할 수 없을 때의 상태와 메시지 ID.

규칙은 구현 계층에 배정된다.

| 계층 | 의미 | 현재 상태 |
| --- | --- | --- |
| **L1** | 프로세스 시작 전 경계: 설치 확인, 하드웨어 측정, 상태·영수증 렌더링, 동의 원장, 배포물 무결성. | 저장소 경계에서 설계 가능. 단, 사용자용 카드 UI는 제품 셸이 필요하다(`pending`). |
| **L2** | **하네스(기본 `omp`)가 요청을 실행하고 파일을 편집하는 계층.** 라우팅·권한·동의 카드·상태 표시·영수증이 여기에 배정된다. | **인터페이스 대부분 `pending`.** 이 절의 초기 검토는 Mixdog의 훅·설정 키·이벤트 이름을 전제했으나, 현행 `omp` 경로에서 실제로 확인된 인터페이스는 브리지의 RPC 프레임(승인 왕복 `extension_ui_request`/`response`, `available_commands_update`)이다. 규칙의 목적지는 이름을 확인한 곳에만 쓰고, 나머지는 “목적지 미확인”으로 둔다. |
| **L3** | Python 엔진(`engine/`)의 계획·레지스트리·티어 판정 로직. | 존재하지만 Mixdog에 연결되지 않았다. 제품 경로에서는 참조 구현이며, 알고리즘의 근거로만 인용한다. |

L2는 “Mixdog 안에서 돌아갈 것”이 아니라 **“Mixdog이 실행 주체인 계층”**이라는 뜻이다. 이 문서는 L2에 필요한 계약을 정의하되, Mixdog의 확장 표면이 재고되기 전까지 어떤 L2 규칙도 구현된 것으로 취급하지 않는다. 확장점이 하나도 확인되지 않으면 §9.2의 금지선이 적용된다.

L2 규칙의 목적지 표기 원칙:

- 확인된 훅이 있으면 그 이름을 쓴다.
- 확인되지 않았으면 `목적지 미확인`이라고 쓴다. 추정해서 제품의 설정 키처럼 쓰지 않는다.
- “아마 Mixdog이 지원할 것”이라는 서술은 규칙이 아니라 의존성(§9)에 적는다.

### 2.2 환경·런타임 규칙 (R-ENV)

#### 2.3.1 R-CRED-04 실행 경로 결정 (정밀)

입력:

- `required_roles`: 계획이 요구하는 역할 집합. 계획은 결정론적 플래너가 만들므로 모델 호출 없이 계산된다.
- `local_tier`, `local_model`, `local_roles`: 티어와 해당 티어 프리셋의 카탈로그 역할.
- `local_ready`: 로컬 엔드포인트가 loopback이고, `/models`에 요구 모델이 있으며, 무결성 검사를 통과한 상태.
- `local_ctx_ok`: 계획의 추정 입력 + 출력 예약이 로컬 컨텍스트 안에 들어오는가.
- `cloud_opt_in`: 사용자가 OpenRouter를 명시적으로 켰는가. **기본값은 false다.**
- `egress_granted`: 호스트·정책 버전·데이터 클래스에 대한 유효한 동의.
- `credential_present`: 자격증명 존재(값 아님).
- `cloud_healthy`: OpenRouter 도달성. **opt-in과 동의가 있을 때만 확인한다.**
- `quality_requested`: 사용자가 “더 좋은 모델로”를 명시했는가.

순서(첫 일치 채택):

| 순서 | 조건 | 결과 | 이유 |
| --- | --- | --- | --- |
| 1 | `quality_requested` = false AND `local_ready` AND `required_roles ⊆ local_roles` AND `local_ctx_ok` | `local_only` | 반출 없이 작업이 성립한다. 기본값이다. |
| 2 | `cloud_opt_in` AND `egress_granted` AND `credential_present` AND `cloud_healthy` | `opt_in_cloud` | 로컬이 역할을 못 덮거나 사용자가 더 좋은 모델을 요청했고, 사용자가 클라우드를 켰다. |
| 3 | `cloud_opt_in` = false OR `egress_granted` = false, AND (1이 성립하지 않음) | **클라우드로 자동 전환하지 않는다.** 로컬 준비 안내 또는 동의 카드 1회 | 클라우드는 opt-in이고 동의가 필요한 경계다. |
| 4 | `local_tier >= lightweight_local` AND `local_ready` = false | `BLOCKED_LOCAL_NOT_READY` | 능력은 있으나 준비가 안 됐다. 클라우드로 조용히 넘어가지 않는다. |
| 5 | `local_tier = rule_based_only` AND `cloud_opt_in` = false | `BLOCKED_LOCAL_NOT_READY` + 로컬 런타임 필요 안내 | 로컬 LLM이 없고 클라우드도 활성화되지 않았다. |
| 6 | 그 외 | `BLOCKED_NO_ROUTE` | 모델 호출 경로가 없다. |

이 순서의 핵심은 두 가지다.

1. **로컬이 역할을 덮으면 묻지 않고 로컬로 간다.** 역할 커버리지는 카탈로그에 선언되어 있어 추측 없이 계산된다.
2. **클라우드는 opt-in 없이는 후보가 아니다.** 3번은 “동의 카드를 띄우고 허용하면 클라우드로 간다”가 아니라 **“클라우드를 활성화하지 않았으면 클라우드로 가지 않는다”**이다. 동의 카드는 이미 opt-in한 사용자에게 반출 범위를 확인하는 절차이지, opt-in을 대신하지 않는다.

`quality_requested`는 설정이 아니라 그 작업에 대한 명시적 요청이다. “이 작업은 더 좋은 모델로”라고 말하면 그 작업에 한해 1번을 건너뛴다. 다만 `cloud_opt_in`이 false면 2번에 도달하지 못하므로, 앱은 “더 좋은 모델을 쓰려면 클라우드 경로를 활성화해야 한다”고 안내하고 멈춘다. 요청이 동의를 만들지는 않는다.

**역할 커버리지는 품질 보장이 아니다.** 카탈로그의 역할은 “이 모델이 그 역할을 맡을 수 있다”는 릴리스 선언이다. 결과가 도움이 되지 않으면 T-04(실패한 실행)가 재결정을 트리거하고, 사용자는 그때 클라우드 opt-in을 선택할 수 있다. 앱은 품질을 측정한 것으로 가장하지 않는다.

### 2.4 모델 선택 규칙 (R-MODEL)

| ID | 입력 | 조건·임계값 | 결과 | 실패 시 | 계층 |
| --- | --- | --- | --- | --- | --- |
| R-MODEL-01 | 카탈로그 `primary_model` | 항상 릴리스 고정값 | `deepseek/deepseek-v4.1-flash-1017` | — | L3(참조) |
| R-MODEL-02 | role, route, ECPS, Beta 사후 확률 | route 필터 → 모드별 고정 정렬 키(마지막 tie-break는 `model_id`) | 역할별 모델 1개 | E-MODEL-02 | L3(참조) |
| R-MODEL-03 | 오류 분류, 현재 role | `ESCALATION_ROLE_MAP` 적용. 프라이버시 등급은 같거나 더 엄격한 쪽만 | 승격 모델 | E-MODEL-03 | L2 |
| R-MODEL-04 | complexity, mode | `select_decision_model`의 고정 순서 | 결정·계획 모델 | E-MODEL-02 | L3(참조) |
| R-MODEL-05 | 요청 모델 불가 | 같은 프라이버시 등급 안에서만 재매핑. 등급 상향은 동의 | 재매핑 + 영수증 기록 | E-MODEL-01 | L2 |
| R-MODEL-06 | 카탈로그 ID, `/models` ID | 정확 일치만. 별칭 추측 금지 | ID 확정 | E-MODEL-01 | L2 |
| R-MODEL-07 | `/models` + 실제 요청 결과 | 카탈로그는 라벨, 성공은 요청 결과로만 판정 | 가용성 상태 | E-MODEL-01 | L2 |

**R-MODEL-02의 정확한 필터와 정렬(코드 기준):**

- `role ∈ entry.roles`
- `route = local_only`이면 `provider == "local"`만. 그 외에는 기본적으로 `provider != "local"`(로컬은 티어 기반 선택기가 직접 지정).
- `route = zdr_cloud`이면 `zero_data_retention AND training_opt_out`인 모델만. `any_cloud`이면 프라이버시 필터 없음.
- 후보가 비면 `503 Service Unavailable (No Compliant Route for role=..., privacy_consent=...)`로 명시 실패한다. 빈 목록을 다른 모델로 채우지 않는다.
- 점수는 `ECPS = c/p + λ·c·(1-p)/p`다. `c`는 카탈로그 단가, `p`는 역할×모델 Beta 사후 평균, `λ = 0.5`는 코드 상수다.
- 정렬 키는 모드별로 고정되어 있고, 마지막 tie-break가 `model_id`이므로 같은 입력은 항상 같은 순서를 낸다.
- Beta 추적기는 현재 프로세스 메모리에만 있다. 직렬화가 없으므로 재시작하면 사후 확률이 초기화된다(§9 P-10).

#### 2.5.1 R-LOCAL-01 티어 결정 (정밀)

입력은 `detect_hardware()`가 반환하는 `cpu_cores`, `ram_gb`, `has_gpu`, `vram_gb`, `gpu_name`이다. 판정은 위에서부터 첫 일치를 채택한다(§0.3과 동일).

추가 규칙:

- `vram_gb`는 `nvidia-smi --query-gpu=name,memory.total --format=csv,noheader,nounits`가 성공했을 때만 0보다 크다. GPU 이름에서 VRAM을 추론하지 않는다.
- RAM 조회는 `psutil` → Windows `GlobalMemoryStatusEx` → POSIX `os.sysconf` 순으로 시도하고, 모두 실패하면 `0.0`이다.
- **측정 실패를 저사양으로 표시하지 않는다.** 화면과 영수증에는 “RAM 측정 실패”와 “RAM 8GB 미만”을 구분해 기록한다. 이를 위해 `HardwareSpec`에 `ram_measured`, `vram_measured` 플래그가 필요하다(§9 P-08).
- `override_tier`는 사용자가 명시한 경우에만 적용하고, `capability_tier`에 하드웨어가 실제로 감당 가능한 티어를 함께 남긴다. 실행 티어는 `min(override, capability)`로 계산한다. 이 규칙은 `select_background_model()`에 이미 구현된 태도와 같다.

#### 2.6.1 R-GEN-01 컨텍스트 결정 (정밀)

`ctx_effective = min(알려진 값들)`이다.

- `ctx_catalog`: 카탈로그의 `context_window`. 모델마다 다르다(예: 7B 로컬 65,536, 1.5B 로컬 32,768, Bonsai 27B 262,144, Bonsai 9B·4B·2B 32,768, primary 131,072).
- `ctx_endpoint`: 게이트웨이가 `/models`에서 보고한 값. 보고하지 않으면 `None`(unknown)이며, 이때 카탈로그 값을 “상한”이 아니라 “추정”으로 표시한다.
- `ctx_local`: 로컬 서버가 노출한 값. 노출하지 않으면 `None`.
- `ctx_usable = ctx_effective - max(계획 출력 토큰, P_CTX_OUTPUT_RESERVE)`.

입력 추정이 `ctx_usable`을 넘으면 다음 순서로 처리한다.

1. 백그라운드 모델이 `ready`이면 압축한다. 압축 결과에는 보존한 결정·인터페이스·미해결 과제 목록이 포함된다.
2. `ready`가 아니면 추출적 축소를 하고, **모델 호출이 없었음을 명시**한다.
3. 그래도 넘으면 요청을 보내지 않고 E-CTX-01로 중단한다. 공급자가 잘라내게 두지 않는다.

토큰 추정은 `estimate_tokens`(약 3자/토큰) 휴리스틱이다. 추정치와 공급자 보고 `usage`를 같은 것으로 표시하지 않는다.

### 2.10 규칙 우선순위와 충돌 해소

1. **안전·동의 규칙이 성능 규칙보다 우선한다.** 반출 동의가 없으면 `quality_requested`도 클라우드로 보내지 못한다.
2. **측정된 사실이 릴리스 라벨보다 우선한다.** 카탈로그가 262,144 context를 선언해도 엔드포인트가 65,536을 보고하면 65,536이 상한이다.
3. **더 엄격한 프라이버시가 더 느슨한 프라이버시보다 우선한다.** `zdr_cloud` 후보가 없으면 `any_cloud`로 자동 승격하지 않는다.
4. **명시적 사용자 요청이 자동 선호보다 우선한다.** 단, 요청이 동의 경계를 넘으면 동의가 먼저다.
5. **결정 불가는 추측이 아니다.** 어떤 규칙도 “아마 이 모델이면 될 것”으로 진행하지 않는다.

### 3.3 금지되는 세 가지

1. **조용한 모델 대체(silent substitution).** 요청한 모델이 없을 때 다른 모델로 변경해 성공한 것처럼 가장하지 않는다. 같은 프라이버시 등급 안에서의 재매핑도 영수증에 남긴다. 등급이 달라지면 동의가 먼저다.
2. **가짜 성공(fake success).** 부분 응답, 잘린 출력, 검증하지 않은 결과, 비용 미보고를 성공으로 표시하지 않는다. `finish_reason=length`는 “잘림”, `usage` 없음은 “비용 unknown”, `[DONE]` 없음은 “중단”이다.
3. **부분 산출물 이어붙이기(partial splice).** 작업 도중 모델이 바뀌면, 앞 모델이 만든 부분 산출물에 뒤 모델의 출력을 이어 붙여 하나의 답처럼 보이게 하지 않는다. 작업을 중단하고, 새 결정으로 처음부터 다시 할지 사용자에게 묻는다.

### 3.4 메시지 문법

모든 메시지는 네 요소를 갖는다.

1. **무슨 일이 있었는가** — 사실, 코드, 측정값.
2. **무엇을 하지 않았는가** — 추측 호출, 대체 모델, 삭제, 전송.
3. **다음 행동 1개** — 버튼 하나 또는 확인할 항목 하나.
4. **안정적인 ID** — `E-*`, 로그와 지원에 쓸 수 있는 값.

금지: “문제가 발생했습니다”, “알 수 없는 오류”, “설정을 확인하세요”만 있는 메시지. 사용자는 무엇을 확인해야 하는지 모른다.

## 4. 동의 경계

### 4.1 원칙

**최소 설정은 동의를 제거하는 것이 아니다.** 설정은 “어떻게 동작할지”를 정하는 일이고, 동의는 “무엇을 해도 되는지”를 허용하는 일이다. 앱은 전자를 대신할 수 있지만 후자를 대신할 수 없다.

열 가지 규칙:

1. **필요한 순간에 묻는다.** 설치 첫 화면에서 미래의 모든 동의를 한꺼번에 받지 않는다.
2. **한 카드에 한 결정만.** “모두 허용” 버튼을 주 버튼으로 두지 않는다.
3. **경계를 구체적으로 말한다.** 목적지 호스트, 데이터 종류, 모델 ID, 보존 정책을 적는다.
4. **기본은 거부다.** 동의하지 않아도 막다른 길이 아니어야 한다. 로컬 경로나 범위 축소를 제시한다.
5. **가장 좁은 범위로 받는다.** 이 작업, 이 폴더, 이 호스트, 이 정책 버전.
6. **철회 가능해야 한다.** 철회는 새 반출을 즉시 멈춘다. 이미 끝난 요청은 되돌릴 수 없다고 정직하게 말한다.
7. **동의를 갱신·확대할 때 다시 묻는다.** 정책 버전이 바뀌어 범위가 넓어지면 이전 동의를 재사용하지 않는다.
8. **동의를 다크 패턴으로 유도하지 않는다.** 사전 체크, 숨은 기본값, 거부 버튼 흐리게 처리 금지.
9. **동의 없이도 상태를 볼 수 있다.** 무엇이 꺼져 있는지, 왜 꺼졌는지 읽을 수 있어야 한다.
10. **동의는 설정 화면이 아니다.** 동의 원장은 “내가 허용한 것”의 목록이고, 조정할 값이 없다.

### 4.3 설정 화면이 되지 않는 방법

동의 카드는 다음 다섯 줄을 넘지 않는다.

```
무엇을:   선택한 파일 3개의 내용과 이 대화
어디로:   {host} (Zero Data Retention)
안 보냄:  자격증명, 이 폴더 밖의 파일
보존:     요청 처리 후 저장하지 않음 (공급자 정책)
선택:     [허용]  [이 PC에서만]  [나중에]
```

- 카드에는 **하나의 결정**만 있다. “반출 + 텔레메트리 + 쓰기”를 한 번에 묻지 않는다.
- “이 PC에서만”은 실제 경로다. 로컬이 준비되지 않았으면 그 버튼은 비활성이 아니라 **“로컬 준비가 필요합니다”라는 설명과 함께** 표시한다.
- “나중에”는 작업을 저장하고 나중에 다시 시작할 수 있게 한다. 작업 내용을 버리지 않는다.
- 동의 후에는 같은 범위에서 다시 묻지 않는다. 범위가 바뀔 때만 묻는다.
- 동의 카드는 작업 흐름 안에 인라인으로 뜬다. 별도 설정 화면으로 이동하지 않는다.

### 4.4 동의 원장

동의 원장은 다음 필드만 가진다. 비밀 값은 저장하지 않는다.

| 필드 | 의미 |
| --- | --- |
| `scope` | 작업 / 폴더 / 호스트 / 명령 클래스 |
| `host` | 반출 목적지(해당 시) |
| `data_class` | 소스 코드, 대화, 진단, 비밀 파일 등 |
| `policy_version` | 동의 당시 정책 버전 |
| `granted_at` | 시각 |
| `revoked_at` | 철회 시각(없으면 유효) |
| `evidence` | 어떤 카드로 동의했는지의 ID |

원장은 읽기 전용 목록이며, 각 항목에 “철회” 버튼이 있다. 이 화면에는 조정할 값이 없으므로 설정 화면이 아니다. 저장 위치는 `%LOCALAPPDATA%\DeepSeekHarness\state\` 계열을 설계 경로로 제안한다. `$DSH_HOME\.credentials.yaml`은 런타임의 자격증명 파일이므로 이 원장을 그곳에 쓰지 않는다.

### 4.5 철회와 결과

- 철회는 **새 요청**을 즉시 막는다. 이미 전송된 요청은 되돌릴 수 없다고 명시한다.
- 철회 후 로컬 경로가 가능하면 전환하고, 불가능하면 `BLOCKED_CONSENT`로 멈춘다.
- 철회는 파일을 삭제하지 않는다. 삭제는 M-11의 별도 동의다.
- 철회 사실은 감사 로그에 남긴다.

## 5. 최초 실행 시퀀스

### 5.1 단계

전제: 사용자는 `launch.cmd` 또는 그 단축키를 더블클릭한다. 아래에서 “사용자 입력”은 설정·동의·자격증명 입력을 뜻하며, 작업 지시문은 별도로 센다.

**기본 경로(`omp`)는 이 표의 S2·S3를 설치 단계로 쓰지 않는다.** `40_AI보고서/launch.cmd`는 같은 폴더의 `launch.ps1`을 호출하고, 그 스크립트는 `-Runtime` 값을 읽어 기본값 `omp`일 때 `app\launch.ps1`로 넘긴다. `app\launch.ps1`은 **이미 디스크에 있는 것만 실행**한다: Node 26 이상 확인, `.omp-runtime\`의 Bun과 `cli.js` 존재 확인, 설정 JSON 파싱, 포트 범위 확인. 내려받기·설치·권한 상승·다른 런타임 폴백은 하지 않으며, 런타임이 없으면 UI를 띄우지 않고 `launch_failed`와 **없는 경로 이름**을 남기고 멈춘다. 브리지도 세션마다 같은 검사를 반복하므로, 실행 후 런타임이 지워져도 준비 완료로 보고하지 않는다. 아래 S3 행은 **`-Runtime dsh` 선택 경로에만** 해당한다.

| 단계 | 하는 일 | 사용자에게 보이는 것 | 건너뛰는 조건 | 실패 분기 | 계층 |
| --- | --- | --- | --- | --- | --- |
| S0 | 실행 제스처 | 아무것도 없음(창이 뜨기 전) | — | — | L1 |

S4는 건너뛰지 않는다. 하드웨어 측정은 저렴하고, 캐시된 지문을 티어 결정에 쓰면 하드웨어 변경을 놓친다. “이미 알면 건너뛴다”는 것은 **UI 표시를 접는다**는 뜻이지, 안전 측정을 생략한다는 뜻이 아니다.

이 절의 설치 방식 서술은 `-Runtime dsh` 경로에만 해당한다: 권한 상승을 요구하지 않는 쪽을 먼저 시도하고, 전역 npm 설치가 권한 때문에 실패하면 npx로 전환하고 그 사실을 상태 줄에 남긴다. 사용자에게 “관리자 권한으로 실행”을 요구하지 않는다. 기본 `omp` 경로는 설치가 아니라 **존재 확인**만 한다(위 전제 참조).

### 5.3 사용자 입력 수 (정확한 수)

“설정 입력”은 동작을 조정하는 값(모델, 컨텍스트, 양자화, temperature, 권한 다이얼 등)을 말한다. “동의 입력”은 경계를 허용하는 클릭이다. “자격증명 입력”은 키/로그인을 제공하는 행위다. 작업 지시문은 어느 쪽도 아니다.

| 경로 | 설정 입력 | 동의 입력 | 자격증명 입력 | 작업 지시 | 전제 |
| --- | --- | --- | --- | --- | --- |
| **A. 최선 경로(읽기 전용·로컬)** | **0** | **0** | **0** | 1 | Tier ≥ 1, 로컬 모델 준비 완료, 계획 역할 ⊆ 로컬 역할, 컨텍스트 충족, 첫 작업이 읽기 전용 |
| B. 첫 쓰기 작업(로컬) | 0 | 1(쓰기 범위) | 0 | 1 | A + 쓰기 필요 |
| C. 클라우드 필요 | 0 | 1(반출) | 0 | 1 | 자격증명이 이미 있거나 앱이 프로비저닝 |
| D. 클라우드 + 자격증명 없음 | 0 | 1(반출) | 1 | 1 | 자격증명 1회 |
| **E. 현행 저장소 구성** | **0** | **1** | **1** | 1 | 로컬 가중치 없음, 내장 자격증명 없음 |

**최선 경로 A의 필수 입력은 0개(설정) + 0개(동의) + 0개(자격증명)이며, 작업 지시 1개만 남는다.** 이 0은 “앱이 동의를 건너뛴다”는 뜻이 아니다. 읽기 전용·로컬 작업은 반출도, 쓰기도, 명령 실행도, 결제도 발생하지 않으므로 동의할 경계가 없기 때문이다.

**현행 저장소 구성에서 실제 최선 경로는 E다.** 로컬 가중치가 없고 앱 프로비저닝 자격증명도 없으므로, 첫 답변에는 반출 동의 1회와 자격증명 1회가 필요하다. 설정 입력은 여전히 0이다. 이 차이를 숨기지 않는 것이 이 문서의 정직성 조건이다.

### 5.4 실패 분기

- S2 실패: 카드 1장, “Node 설치” 또는 “폴더 권한” 중 하나. 앱은 시작하지 않는다.
- S3 실패: pin이 맞는 런타임을 찾지 못하면 `BLOCKED_RUNTIME`. 소스 체크아웃은 “고급”에서만.
- S4 실패: 측정 실패는 저사양이 아니다. E-HW-02로 구분해 표시하고 Tier 0으로 수렴한다.
- S5 실패: 로컬은 `DEGRADED_NO_LOCAL`. 클라우드가 준비되어 있으면 계속, 아니면 `BLOCKED_NO_ROUTE`.
- S10 실패: 동의 거부 → 로컬 경로가 있으면 `local_only`, 없으면 `BLOCKED_CONSENT`. 클라우드로 몰래 가지 않는다.
- S11 실패: §3.2의 상태로 전환하고, 부분 산출물을 완료로 표시하지 않는다.

## 6. 재결정 트리거

### 6.1 원칙

- 재결정은 **작업 경계**에서 한다. 작업 시작 전, 작업 종료 후, 그리고 안전 사건(자격증명 철회, 동의 철회, 하드웨어 상실)에서만.
- 진행 중인 작업의 모델을 바꾸지 않는다. 안전 사건이면 작업을 멈추고 새 결정으로 다시 시작할지 묻는다.
- 재결정은 **영수증**을 남긴다. 무엇이, 왜, 언제 바뀌었는지 한 줄로 보여준다.
- 재결정이 동의 범위를 넓히면 자동으로 진행하지 않고 다시 묻는다.
- 재결정이 범위를 좁히면 조용히 반영하되, 상태 줄에 표시한다.

### 7.3 이 PC에서 가능한 것과 불가능한 것

**이 PC(RTX 4060 Laptop 8GB, RAM 39.31GB, Tier 2)에서 지금 검증 가능한 것:**

- 티어 판정이 Tier 2라는 사실, 그리고 Tier 3가 아닌 이유(VRAM 8.0 < 12).
- 백그라운드가 `unavailable`이고 `model_id`가 빈 문자열(`entry is None`)이라는 사실. 2026-11-06 실측 사유: `tier standard_local below required advanced_local`(측정 RAM 39.3GB / VRAM 8.0GB), `HARNESS_LOCAL_BASE_URL` 미설정, `runtime_absent`. 후보가 없을 때 대체 모델로 넘어가지 않는다.
- 자격증명/엔드포인트가 없을 때 “호출 0, 미설정 사유 표시”가 되는지.
- `launch.ps1`의 모델 ID 거부, URL 검증, 패치 placeholder 거부는 `-DryRun`으로 확인 가능하다. 단, **pin 불일치 거부는 설치된 `dsh`가 있어야 관찰된다**. 이 PC에는 아직 없으므로 지금은 스크립트 로직 검사이지 관찰이 아니다.
- 스텁 게이트웨이를 통한 401/429/5xx/400/스트림 절단/usage 누락 처리.
- `nvidia-smi`를 PATH에서 숨겨 무GPU 경로를 시뮬레이션.
- 비밀 마스킹과 로그 스캔.
- 플래너의 검증 명령 출처 고정(프롬프트 주입이 argv를 바꾸지 않음).

**이 PC에서 검증 불가능한 것:**

- Tier 3(VRAM ≥ 12GB)에서 Bonsai-2 27B가 실제로 적재·실행되는지.
- 실제 공급자의 ZDR 준수, 실제 모델 품질·지연·비용.
- 7B 로컬 모델의 실제 추론 속도와 품질.
- macOS/Linux 설치·패치·실행 경로.
- `dsh` 세션 안의 동의 카드·권한 게이트·상태 표시(L2 확장점 미확인).
- 자동 업데이트, 패키징된 설치 프로그램, 제거 프로그램.
- 배터리 API 기반 지연 로드.

### 7.4 검증 전 상태

이 문서의 주장은 **검증 전**이다. `scripts/verify_customization.ps1`은 오프라인 자기 일관성 검사이고, 이 문서가 정의한 사용자 경험 검증이 아니다. 검증 계획을 실행하려면 먼저 §9의 `pending` 항목이 해소되어야 한다.

### 8.2 자동화되는 것 (대조)

다음은 사용자에게 보이지 않는다.

- 공급자 선택, 게이트웨이 URL, API 키 저장 위치
- 기본 모델, 역할별 모델, 승격 모델, 결정 모델, 백그라운드 모델
- 실행 경로(local/cloud/ZDR), 프라이버시 필터
- 실행 티어, 로컬 프리셋, 양자화, GPU 레이어, KV 캐시, 스레드
- 컨텍스트 크기, temperature, top_p, 최대 출력, reasoning effort
- 에이전트 모드, 2-track, 최적화 모드, 병렬 워커, 재시도
- 검증 명령 선택(실행 동의는 별도)
- 상태 표시, 오류 상세, 로그 수준, 알림

이 목록은 “사용자가 영원히 볼 수 없다”는 뜻이 아니다. 기본 경로에서 보이지 않고, 고급/진단에서만 보인다는 뜻이다.

### 8.3 설정 표면의 상한

- **필수 설정 화면: 0개.**
- **선택 표면: 3개.** ① 동의 원장(허용/철회), ② 상태·결정 영수증(읽기 전용), ③ 고급(진단·override, 기본 접힘).
- 이 셋은 “설정”이 아니라 각각 “권한”, “기록”, “진단”이다.
- 새 설정 항목을 추가하려면 다음 질문을 통과해야 한다. “이 값을 앱이 측정하거나 릴리스가 큐레이션할 수 없는가?” 통과하지 못하면 설정이 아니라 자동 결정이다.

**왜 이 선을 넘으면 부정직한가:** 설정을 제거하는 것은 좋은 목표지만, 동의·결제·삭제·반출까지 제거하면 사용자는 자신의 권리를 행사할 자리를 잃는다. 그것은 “간편함”이 아니라 “대리 결정”이다. 반대로 모델·컨텍스트·temperature를 사용자에게 다시 노출하면, 앱이 측정할 수 없는 값을 사용자가 추측해야 한다. 이 문서는 그 둘을 구분한다.

### 9.2 확장점이 없을 때의 금지선

`dsh`에 권한·동의 훅이 없을 때, 트래픽을 가로채는 로컬 프록시로 모델을 변경하거나 권한을 모방하지 않는다. 사용자가 보는 모델과 실제 호출 모델이 달라질 수 있고, 동의 없이 전송되는 경로를 앱이 숨기게 되기 때문이다. 확장점이 없으면 **세션 시작 전에 거친 동의를 받고, 그 한계를 화면에 적는다.** 이것이 “완전 자동”보다 정직하다.

### 9.3 릴리스 전에 필요한 데이터

- 로컬 모델별 `weights_bytes`, 라이선스, 컨텍스트, 역할.
- 티어별 실제 적재 프로파일(가중치 + KV + 여유).
- 공급자별 `/models` 응답 형식과 컨텍스트 보고 여부.
- 동의 문구의 법적 검토(관할별).
- “측정 실패”와 “저사양”을 구분하는 UI 카피.
- 사용자 입력 수 측정을 위한 이벤트 정의.
