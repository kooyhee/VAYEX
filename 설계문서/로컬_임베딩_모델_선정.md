# 로컬 임베딩 모델 선정 (한국어 + 영어 검색 최적화)

작성 목적: **API 비용 0원의 로컬 임베딩 엔드포인트**를 세우기 위한 모델 선정.
용도는 두 가지다.

1. **장기 기억(memory) 검색** — 한국어/영어 대화 기록, 문서 조각, 노트를 벡터로 색인하고 질의로 회수.
2. **재탐색 비용 절감** — 이미 확보한 자료를 외부 모델이 다시 훑지 않도록, 로컬 검색으로 1차 후보를 좁힌다.

전제:

- 가중치 다운로드·설치·실행은 하지 않았다. 아래 수치는 **공개 모델 카드·논문·공개 리더보드**에서만 인용했다.
- 대상 기기는 **사용 가능한 GPU가 없을 수 있는 CPU 전용 환경**을 상정한다.
- 서빙은 **OpenAI 호환 `/v1/embeddings`** 노출을 목표로 한다.

## 0. 결론 요약

| 항목 | 기본안 | 경량 폴백 |
| --- | --- | --- |
| 모델 | `nlpai-lab/KURE-v1` | `Qwen/Qwen3-Embedding-0.6B` |
| 벡터 차원 | **1024** (MRL 없음, 절단 불가) | **1024 기본 / 512 절단 권장** (MRL 32~1024) |
| 최대 입력 | 8192 토큰 (실운영 1024 권장) | 32768 토큰 (실운영 1024 권장) |
| 양자화 | 커뮤니티 Q8_0 GGUF 634,554,240바이트(≈0.63 GB) 또는 fp32 | 공식 q8_0 GGUF |
| 예상 상주 RAM | fp32 약 3.5~5 GB / Q8 GGUF 약 1.2~2 GB | q8_0 약 1.5~2.5 GB |
| 프롬프트 | **불필요**(질의·문서 모두 원문) | 질의에 지시문 권장 |
| 라이선스 | MIT(상업 가능) | Apache-2.0(상업 가능) |
| 서빙 | TEI `/v1/embeddings` 또는 `llama-server --embedding` | `llama-server --embedding` |
| 한국어 근거 | MTEB(kor,v2) 9과제 0.7616 | MTEB(kor,v2) 9과제 0.7140 |

핵심 판단 3줄:

1. 한국어 검색 품질은 **1.1B KURE-v3(0.8027) > 568M KURE-v1(0.7616) > 568M bge-m3(0.7509) > 596M Qwen3-0.6B(0.7140)** 순이다. 3B 이상 모델은 품질이 더 높지만 CPU 전용 환경에서 RAM과 지연이 감당 범위를 넘는다.
2. **프롬프트 없는 모델**을 기본으로 둔다. 대화 기록을 그대로 색인하는 구조에서 접두사 규약은 조용한 품질 손실의 원인이 된다.
3. **차원과 RAM은 색인 스키마 결정**이다. 모델을 바꾸면 벡터 공간이 달라져 전체 재색인이 필요하므로, `model_id`·`dim`을 스키마에 박아 두고 교체를 배치로 처리할 수 있어야 한다.

이 프로젝트에서의 최종 확정(운영 모델 1개, 전환 조건 1개, 호출자용 운영 규칙)은 **§7.6**에 있다. 이 표의 "경량 폴백"은 벤치마크 대안이며, **운영 장애 시 폴백은 모델 교체가 아니라 FTS 키워드 경로**다.

## 1. 평가 기준 (순위 규칙)

브리프가 지정한 우선순위를 그대로 적용했다.

| 순위 | 기준 | 판정 방법 |
| --- | --- | --- |
| 1 | 한국어+영어 검색 품질 | MTEB(kor, v2) Retrieval 9과제 평균 nDCG@10, Kanana Ko-Retrieval 6과제, AutoRAG Top-1, MIRACL ko nDCG@10, MKQA ko Recall@100, Mr. TyDi ko MRR@10 |
| 2 | CPU 실행 가능성·메모리 | 파라미터 수, 가중치 바이트, 최대 입력 길이, GGUF/ONNX 존재 여부 |
| 3 | 라이선스 | 상업적 사용 가능 여부(MIT/Apache-2.0 > Gemma/Qwen Research > CC-BY-NC) |
| 4 | 서빙 단순성 | llama.cpp 서버·TEI 등에서 OpenAI 호환 임베딩 API 노출 가능 여부 |

한국어 품질을 최우선으로 두되, **CPU에서 실제로 돌아가는가**를 사실상의 필터로 썼다. 품질이 다소 높더라도 9B급이면 CPU 전용 환경에서는 후보에서 탈락시켰다.

### 3.9 증거가 약한 후보

- `jinaai/jina-embeddings-v3`: MTEB(kor, v2) 수치는 카드·논문에서 확인하지 못했다. 대신 3.7절의 KURE-v1 카드 집계(한국어 9데이터셋 Top-1 Recall)에서 0.48287로, KURE-v1(0.52640)보다 약 4.4p 낮다. 지표가 달라 3.1절과 직접 비교할 수는 없다.
- `nomic-ai/nomic-embed-text-v1.5`: 영어 전용(카드 language=en). 한국어 증거 없음. 출처: [카드](https://huggingface.co/nomic-ai/nomic-embed-text-v1.5).
- `nomic-ai/nomic-embed-text-v2-moe`: 한국어를 지원 언어로 명시하지만, 카드에 제공된 것은 BEIR/MIRACL **전체 평균**(MIRACL 65.80)뿐이고 한국어 단독 수치는 없다. 또한 최대 512 토큰. 출처: [카드](https://huggingface.co/nomic-ai/nomic-embed-text-v2-moe).
- `BAAI/bge-multilingual-gemma2`: 한국어를 학습 언어로 명시하고 MIRACL SOTA를 주장하지만, 카드의 MIRACL 성과는 **이미지 차트**로만 제공되어 수치를 인용할 수 없다. 3.7절 집계에서 0.47904로 KURE-v1(0.52640)보다 낮다. 출처: [bge-multilingual-gemma2 카드](https://huggingface.co/BAAI/bge-multilingual-gemma2), [KURE-v1 카드](https://huggingface.co/nlpai-lab/KURE-v1).
- `intfloat/e5-mistral-7b-instruct`: MKQA ko 59.4(3.5절)로 mE5-large(68.1)보다 낮다. 파라미터 12배인데 한국어 교차언어 검색은 더 나쁘다.
- `BM-K/KoSimCSE-roberta`, `jhgan/ko-sroberta-multitask`: 공개 수치가 **STS(문장 유사도)** 중심이다(KoSimCSE-RoBERTa 평균 83.65). 검색 과제 성능은 AutoRAG Top-1에서 0.42~0.43 수준으로 낮다. 출처: [KoSimCSE 카드](https://huggingface.co/BM-K/KoSimCSE-roberta), [AutoRAG 벤치마크](https://github.com/Marker-Inc-Korea/AutoRAG-example-korean-embedding-benchmark).
- `DragonKUE`: 개인이 운영하는 한국어 임베딩 모델 모음이다. 대표 모델은 `dragonkue/BGE-m3-ko`(3.1절 0.7547)와 `dragonkue/snowflake-arctic-embed-l-v2.0-ko`(0.7653)이며, ColBERT 계열 `dragonkue/colbert-ko-0.1b`도 있다. 후자는 late-interaction이라 단일 벡터 저장 구조와 호환되지 않는다. 출처: [BGE-m3-ko](https://huggingface.co/dragonkue/BGE-m3-ko), [arctic-ko](https://huggingface.co/dragonkue/snowflake-arctic-embed-l-v2.0-ko), [KURE 리더보드](https://github.com/nlpai-lab/KURE).

출처: 각 모델 카드(BAAI/bge-m3, Qwen3-Embedding-0.6B, multilingual-e5-large, KoE5, KURE-v3, arctic-embed-m-v2.0, nomic-embed-text-v1.5/v2-moe, jina v3/v4/v5-text-small-retrieval, kanana-2-3b-embedding, comsat-embed-ko-8b-preview, e5-mistral-7b-instruct). 링크는 2절 표 하단과 동일하다. KURE-v1의 풀링은 `1_Pooling/config.json`의 `pooling_mode_cls_token: true`로 확인된다. KURE-v3는 `1_Pooling/config.json`이 `pooling_mode: "mean"`이고 차원은 2048이다.

### 5.3 CPU 전용 환경에서의 판단

- **8192 토큰 지원은 CPU에서 곧 비용**이다. bge-m3/KURE-v1의 self-attention 비용은 시퀀스 길이에 제곱으로 늘어나므로, 실제 색인에서는 청크를 512~1024 토큰으로 자르고 `max_length`도 그에 맞춰 낮추는 편이 낫다. 두 모델 모두 `max_length`를 줄여도 가중치·차원은 그대로다.
- **MoE(`nomic-embed-text-v2-moe`)는 CPU에서 유리하지 않다.** active 305M이지만 라우팅 오버헤드와 `trust_remote_code` 의존이 붙는다(카드 Limitation에 명시). 게다가 512 토큰 제한.
- **8B/9B/3B급(`bge-multilingual-gemma2`, `e5-mistral-7b`, `comsat-embed-ko-8b`, `Qwen3-Embedding-4B`, `jina-embeddings-v4`, `kanana-2-3b`)은 CPU 전용 후보로 부적합**하다. 4B도 Q4 양자화 기준 6~9 GB 상주가 필요하고, 토큰당 연산량이 0.6B의 약 7배다. `kanana-2-3b`는 한국어 품질이 가장 좋지만 3.18B(bf16 6.36 GB)라 CPU 상주 RAM이 10 GB를 넘는다.
- **`kanana-2-1.3b-embedding`은 경계선**이다. 1.29B라 fp32 5.16 GB, bf16 2.58 GB다. RAM 16 GB 이상이면 CPU에서도 시도할 만하고, 한국어 6과제 평균 0.7958로 KURE-v1(9과제 0.7616)보다 높다. 다만 지표가 달라 직접 비교는 불가하고, 라이선스가 Kanana Open License다.
- **양자화 리스크**: llama.cpp에서 `Qwen3-Embedding-0.6B` GGUF 출력이 부실하다는 이슈 보고가 있었다(ggml-org/llama.cpp #14234). 출처: [llama.cpp issue 14234](https://github.com/ggml-org/llama.cpp/issues/14234). 양자화 GGUF를 쓸 경우 **원본과 코사인 유사도 분포를 반드시 대조**해야 한다.
- **ONNX 경로**는 PyTorch CPU보다 가볍고 예측 가능하다. `bge-m3`, `multilingual-e5-*`, `nomic-embed-text-v1.5`, `snowflake-arctic-embed-*`, `jina-embeddings-v3` 저장소에 `onnx/` 산출물이 있다. `bge-m3`는 `onnx/model.onnx` + `onnx/model.onnx_data` 형태다. 출처: [BAAI/bge-m3 파일 목록](https://huggingface.co/BAAI/bge-m3/tree/main).

| 차원 | fp32 | fp16 | int8 |

## 6. OpenAI 호환 로컬 서빙 옵션

| 런타임 | OpenAI 호환 임베딩 | 비고 |
| --- | --- | --- |
| **llama.cpp `llama-server`** | `--embedding` 플래그로 `/v1/embeddings` 노출 | GGUF 전용. 서버 README가 "OpenAI API 호환 chat completions, responses, **embeddings** 라우트"를 명시한다. 풀링은 GGUF 메타데이터(`pooling_type`)로 지정되거나 `--pooling` 플래그로 덮어쓴다. KURE-v1 GGUF의 `pooling_type=2`, bge-m3 GGUF의 `pooling_type=2`는 CLS(=BERT 계열) 풀링이다. 출처: [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [KURE-v1 GGUF 메타데이터](https://huggingface.co/mykor/KURE-v1-gguf), [bge-m3 GGUF 메타데이터](https://huggingface.co/gpustack/bge-m3-GGUF) |
| **Hugging Face TEI** | `POST /v1/embeddings` — OpenAPI 스펙에 "OpenAI compatible route"로 등재 | 네이티브 `/embed`도 제공. OpenAI 호환 요청 스키마에 `input`, `model`, `encoding_format`, `user`, 그리고 **`dimensions`(nullable)** 가 포함되어 있어 MRL 절단을 서버에서 처리할 수 있다. 지원 아키텍처: Nomic, BERT, CamemBERT, XLM-RoBERTa, JinaBERT, Mistral, GTE, Qwen2, MPNet, ModernBERT, Qwen3, Gemma3. 출처: [TEI OpenAPI 스펙](https://huggingface.github.io/text-embeddings-inference/openapi.json), [TEI README](https://github.com/huggingface/text-embeddings-inference) |
| **Ollama** | `/v1/embeddings` (OpenAI 호환) | GGUF 기반. 모델 태그만 받아 쓰는 가장 단순한 경로. 다만 템플릿·풀링이 Ollama 쪽 정의에 의존하므로 한국어 특화 모델은 Modelfile 직접 작성이 필요할 수 있다. |
| **vLLM** | OpenAI 호환 임베딩(`runner="pooling"`, `convert="embed"`) | GPU 전제. CPU 전용 환경에서는 사실상 제외. Qwen3·KURE-v3·kanana-2 카드가 vLLM 예시를 제공한다 |
| **OpenAI SDK 직결** | `OpenAI(base_url="http://127.0.0.1:PORT/v1", api_key="dummy")` | 위 런타임 모두 이 형태로 붙는다. 클라이언트 코드는 `embeddings.create(model=..., input=[...])` 한 줄 |

설계상 유의점:

- **모델별 프롬프트 부착 책임**을 클라이언트에 둘지 게이트웨이에 둘지 먼저 정해야 한다. TEI/llama.cpp는 접두사를 자동으로 붙여주지 않는다. e5/nomic/KURE-v3 계열을 쓰려면 게이트웨이에서 `input_type`(query/document)을 받아 접두사를 붙이는 계층이 필요하다. KURE-v3 카드의 자체 API도 `extra_body={"input_type": "query"|"document"}` 방식으로 이 문제를 푼다.
- `dimensions` 파라미터는 **TEI의 OpenAI 호환 라우트에는 있고**(스펙 확인), llama.cpp에는 없다. 절단이 필요하고 llama.cpp를 쓴다면 **애플리케이션 계층에서 자르고 재정규화**하는 편이 이식성이 좋다.

### 7.2 권고: 기본 = `nlpai-lab/KURE-v1`

- **이유**: 한국어 검색 9과제 평균 0.7616으로, 동일 파라미터(568M)의 `bge-m3`(0.7509)보다 높고 CPU 전용 환경에서 감당 가능한 상한선에 있다. MIT 라이선스, 8192 토큰, **프롬프트 불필요**, CLS 풀링이라 클라이언트 규약이 단순하다.
- **정확한 벡터 차원**: **1024** (MRL 없음 → 절단 불가)
- **예상 RAM**: fp32 PyTorch CPU 기준 **3.5~5 GB**(가중치 2.27 GB + 런타임/활성값). q8 GGUF(`Bingsu/KURE-v1-Q8_0-GGUF`, 파일 **634,554,240바이트 ≈ 0.63 GB**, GGUF 메타데이터 `architecture=bert`, `context_length=8192`, `pooling_type=2`)로 내리면 **1.2~2 GB**.
- **색인 비용**: 청크 10만 개 fp32 = 약 0.4 GB, fp16 = 약 0.2 GB.
- **주의**: 커뮤니티 GGUF만 존재하고 공식 양자화는 없다. llama.cpp에서 로드하려면 GGUF의 `pooling_type=2`(CLS)가 원본의 `pooling_mode_cls_token: true`와 일치하는지 확인해야 한다. 둘 다 CLS라 방향은 맞다.
- **영어 품질**: bge-m3 백본이므로 영어 검색은 bge-m3와 동급이다. KURE 저장소의 **RTEB(eng)** 8개 공개 과제 평균 nDCG@10에서 KURE-v1 0.5246, bge-m3 0.5194로 확인된다(둘 다 568M). 참고로 같은 표에서 Qwen3-Embedding-0.6B는 0.5874, KURE-v3는 0.6885다. 출처: [KURE eval/dense/results README](https://github.com/nlpai-lab/KURE/blob/main/eval/dense/results/README.md).
- **영어에서의 상대 약점**: 한국어와 달리 영어에서는 KURE-v1이 Qwen3-0.6B보다 낮다(0.5246 대 0.5874). 한국어·영어 혼합 기록에서 영어 비중이 크다면 이 트레이드오프를 감수해야 한다. KURE-v3(1.14B, 0.6885)가 양쪽을 동시에 만족시키는 대안이다.

### 7.3 경량 폴백: `Qwen/Qwen3-Embedding-0.6B` (512차원 절단)

> 명칭 주의: 여기서 "폴백"은 **품질·메모리 비교용 대안**이라는 뜻이다. 운영 장애 시 실제 폴백은 이 모델이 아니라 FTS 키워드 경로다(§7.6 운영 규칙).

- **이유**: 0.6B로 KURE-v1과 파라미터 규모가 비슷하지만, **공식 GGUF(q8_0)** 와 MRL 절단을 제공해 메모리·지연을 실제로 낮출 수 있다. 32K 컨텍스트, Apache-2.0, llama.cpp/TEI 공식 사용 예시가 있다.
- **정확한 벡터 차원**: 기본 **1024**, **512로 절단 권장**(MRL 32~1024 지원)
- **예상 RAM**: q8_0 GGUF 기준 **1.5~2.5 GB**; 512차원 절단 시 벡터 저장량 절반.
- **대가**: 한국어 검색 품질이 KURE-v1보다 낮다(MTEB(kor,v2) 0.7140 대 0.7616). 또한 질의 측 지시문을 넣지 않으면 1~5% 추가 하락한다. 절단으로 512차원을 쓰면 추가 손실이 있다(정확한 절단 손실폭은 공개 수치 없음).
- **참고(더 낮은 단계가 필요할 때만)**: `intfloat/multilingual-e5-small`(118M, 384차원, 512토큰, MIT, ONNX)은 Mr. TyDi ko MRR@10 54.3으로, RAM 1~1.5 GB에서 동작하는 최후 수단이다. 다만 `query: `·`passage: ` 접두사가 필수이고 512토큰 제한이 있다.

### 7.4 채택하지 않는 이유 요약

- **`bge-multilingual-gemma2`(9.24B)**: CPU 전용 환경에서 RAM 18~37 GB가 필요하다. Gemma 라이선스는 사용 조건이 추가로 붙는다. 무엇보다 카드가 MIRACL 성과를 이미지로만 제시해 **수치로 검증할 수 없다**.
- **`jina-embeddings-v3`**: CC-BY-NC-4.0으로 상업적 사용이 막힌다. 성능이 좋아도 "영구 무료 내부 서비스"외에는 선택할 수 없다.
- **`jina-embeddings-v4`**: 3B 멀티모달 모델로, 텍스트 전용 대화 기록 검색에는 과잉이다. 라이선스도 Qwen Research License로 상업 사용이 제한적이다(카드 License 절이 "cc-by-nc-4.0은 오기, 정정된 라이선스는 Qwen Research License"라고 명시).
- **`e5-mistral-7b-instruct`**: 7.11B인데 MIRACL ko가 mE5-large보다 낮다. 비용 대비 이득이 없다.
- **`sionic-ai/comsat-embed-ko-8b-preview`**: 한국어 9과제 0.7927로 8B급 중 최고지만 7.57B(bf16 15.1 GB)다. 결정적으로 **CC-BY-NC-4.0**이라 상업적 사용이 불가하다.
- **`kanana-2-3b-embedding`**: 한국어 6과제 0.8211로 카드 비교표 1위, 프롬프트 불필요라는 점도 매력적이다. 그러나 3.18B(bf16 6.36 GB)로 CPU 상주 RAM이 10 GB를 넘고, Kanana Open License는 **제3자에게 API·클라우드로 접근을 제공하거나 SI/온프레미스로 재판매할 때 별도 상용 라이선스**를 요구한다(3.1(v)는 "Powered by Kanana" 표시 의무도 부과). 개인·내부용이면 4.2조로 무료지만, 조건이 붙는 라이선스는 기본 후보로 두지 않는다.
- **`jina-embeddings-v5-text-small-retrieval`**: 677M에 한국어 9과제 0.7419, MRL·공식 GGUF까지 갖췄지만 **CC-BY-NC-4.0**이다. 라이선스 제약이 없는 쪽을 우선하므로 MIT인 KURE-v1을 채택한다.
- **`KoSimCSE`/`ko-sroberta-multitask`**: 검색이 아니라 STS로 학습·평가된 모델이고, 카드에 라이선스가 없다.

### 7.5 한국어:영어 비중에 따른 선택 (합성 점수, 방향 참고용)

우리 기록은 한국어와 영어가 섞여 있다. 한국어 9과제(MTEB kor, v2)와 영어 8과제(RTEB eng)를 **단순 가중 평균**하면 아래와 같다. 두 지표는 과제 구성·난이도가 달라 절대 스케일이 같지 않으므로, **순위 방향을 보는 용도로만** 써야 한다.

| 모델 | 한국어(9과제) | 영어(RTEB 8과제) | 70:30 | 50:50 |
| --- | --- | --- | --- | --- |
| `nlpai-lab/KURE-v3` (1.14B) | **0.8027** | **0.6885** | **0.7684** | **0.7456** |
| `Qwen/Qwen3-Embedding-4B` (4.02B) | 0.7737 | 0.6601 | 0.7396 | 0.7169 |
| `jinaai/jina-embeddings-v5-text-small-retrieval` (596M) | 0.7419 | 0.6111 | 0.7027 | 0.6765 |
| `nlpai-lab/KURE-v1` (568M) | 0.7616 | 0.5246 | 0.6905 | 0.6431 |
| `BAAI/bge-m3` (568M) | 0.7509 | 0.5194 | 0.6814 | 0.6351 |
| `Qwen/Qwen3-Embedding-0.6B` (596M) | 0.7140 | 0.5874 | 0.6760 | 0.6507 |
| `google/embeddinggemma-300m` (308M) | 0.7254 | 0.5568 | 0.6748 | 0.6411 |

각 열의 출처: 한국어는 [KURE MTEB(kor,v2) 리더보드](https://github.com/nlpai-lab/KURE/blob/main/eval/dense/results/README.md), 영어는 같은 문서의 [RTEB(eng) 표](https://github.com/nlpai-lab/KURE/blob/main/eval/dense/results/README.md). 70:30·50:50 열은 위 두 값을 가중 평균해 이 문서에서 계산한 값이다.

해석과 결정 규칙:

- **한국어 비중이 약 57%를 넘으면** `KURE-v1`이 `Qwen3-Embedding-0.6B`보다 낫다. 교차점은 0.7616x + 0.5246(1−x) = 0.7140x + 0.5874(1−x)를 풀면 x ≈ 0.5688이다. 우리 대화 기록은 한국어 우세이므로 기본안을 `KURE-v1`로 둔다.
- 반대로 **영어 비중이 43%를 넘는 영어 위주 색인**이라면 Qwen3-0.6B 쪽이 낫다. 다만 그 경우에도 KURE-v3(영어 0.6885)가 더 높으므로, "가볍게 가느냐"와 "영어까지 최고로 가느냐"의 선택이다.
- **jina v5-text-small(596M)이 70:30에서 KURE-v1보다 높다는 점**은 라이선스(CC-BY-NC-4.0)만 해결되면 매력적인 지점이다. 현재는 상업 사용이 막혀 후보에서 뺐다.

### 7.6 이 프로젝트 확정: `nlpai-lab/KURE-v1` 단일 채택

**1) 코퍼스 가정(측정값 아님).** 우리 검색 대상은 ① 한국어 설계문서, ② 한국어·영어 소스코드 주석, ③ 한국어 대화 기록, ④ 조사 중 인용하는 영어 기술문서다. 이 네 갈래의 토큰 비중을 **한국어 8 : 영어 2로 가정**한다. 이것은 실측이 아니라 이 프로젝트의 문서 성격에서 끌어낸 **가정**이며, 색인 대상 청크의 언어 비율을 세기 전까지는 가정으로만 취급한다. 재현 방법: 색인 배치마다 청크의 한글 음절 수와 라틴 문자 수를 함께 기록해 분포를 남긴다.

이 가정은 §7.5의 교차점(한국어 56.88% 초과 시 KURE-v1 우위)을 여유 있게 넘는다. 같은 방식(한국어 9과제 · 영어 RTEB 8과제 단순 가중 평균)으로 8:2를 계산하면 **KURE-v1 0.7142, Qwen3-Embedding-0.6B 0.6887, KURE-v3 0.7799**다. 계산 근거는 §7.5와 동일한 [KURE 결과 README](https://github.com/nlpai-lab/KURE/blob/main/eval/dense/results/README.md)이며, 절대 스케일이 다른 두 지표를 섞은 값이므로 순위 방향으로만 쓴다.

**2) CPU 비용 비교(세 finalist).** 이 프로토타입에는 쓸 만한 GPU가 없다는 전제이므로 CPU 실행 가능성에 가중치를 둔다. 아래 값은 모두 이 문서가 이미 인용한 수치(§5.1, §5.2, §2)이며, 새로 측정한 것이 없다.

| 모델 | 파라미터 | fp32 가중치 | 양자화 산출물 | 예상 상주 RAM | 차원 | 최대 입력 |
| --- | --- | --- | --- | --- | --- | --- |
| `nlpai-lab/KURE-v1` | 567,754,752 (568M) | 2.27 GB | [Q8_0 GGUF 634,554,240바이트](https://huggingface.co/Bingsu/KURE-v1-Q8_0-GGUF) | fp32 3.5~5 GB / Q8 1.2~2 GB | 1024 (MRL 없음) | 8192 |
| `Qwen/Qwen3-Embedding-0.6B` | 596M | 2.38 GB | [공식 q8_0 ≈0.65 GB](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B-GGUF) | 1.5~2.5 GB | 1024 (MRL 32~1024) | 32768 |
| `nlpai-lab/KURE-v3` | 1.14B | 4.56 GB | [커뮤니티 GGUF 2.29 GB](https://huggingface.co/mradermacher/KURE-v3-GGUF) | 4~6 GB (bf16) | 2048 (MRL 2048/1024/512/256) | 8192 |

**CPU 지연·처리량은 세 모델 모두 공개 수치가 없어 미검증이다.** 초당 문서 수나 질의 1건 지연을 근거로 세 모델을 줄 세울 수 없으므로(§9 항목 2), 위 비교는 파라미터 수·가중치 바이트·추정 상주 RAM이라는 간접 지표에 머문다. 확정된 것은 "KURE-v3는 연산량이 약 2배"(§7.1)라는 사실과, 가중치 크기 순서가 KURE-v1 < Qwen3-0.6B < KURE-v3라는 점뿐이다.

**3) 결정.** 운영 모델은 **`nlpai-lab/KURE-v1` 하나로 고정**한다. Qwen3-Embedding-0.6B는 벤치마크 대안으로만 남기고 운영 기본값·폴백 기본값으로 쓰지 않는다.

- 한국어 우세 8:2에서 품질이 더 높고(0.7142 대 0.6887), 프롬프트 규약이 없어 호출 경로가 단순하다.
- CPU에서 가장 가볍게 끝난다. Q8 GGUF 0.63 GB · 상주 1.2~2 GB로, 같은 1024차원을 쓰는 Qwen3-0.6B의 1.5~2.5 GB보다 낮다.
- Qwen3-0.6B를 택하지 않는 이유는 "RAM이 아까워서"가 아니다. 두 모델의 차원이 1024로 같아 교체해도 저장 구조 이득이 없고, 한국어 품질만 낮아지며, 질의 지시문을 클라이언트가 지켜야 하는 규약 부담이 새로 생긴다. 그 비용을 치를 근거가 우리 코퍼스에는 없다.
- KURE-v3(0.8027 / 0.6885, 2048차원)는 품질이 가장 좋지만 1.14B · 연산 약 2배 · 상주 4~6 GB(bf16)로, GPU 없는 프로토타입이라는 제약을 정면으로 위반한다. 지금 단계의 선택지가 아니다.

**확정 사양**: `model_id = nlpai-lab/KURE-v1`, **벡터 차원 1024 고정**(MRL 없음 → 절단 불가. 축소가 필요하면 모델 교체·재색인이다), **예상 상주 RAM 3.5~5 GB(fp32) / 1.2~2 GB(Q8 GGUF)**. 가중치 567,754,752 파라미터, fp32 2.27 GB. 참고로 양자화 산출물은 커뮤니티판뿐이므로 최초 로드 시 원본 fp32와 코사인 유사도 분포를 대조한다(§5.3).

**전환 조건은 하나다.** 이 개발기가 **8 GB 이상 VRAM의 GPU**를 확보하는 순간 `nlpai-lab/KURE-v3`(2048차원, MRL 2048/1024/512/256, bf16 2.28 GB)로 교체하고 전체 재색인한다. `8 GB`는 인용된 사양이 아니라 이 프로젝트가 정한 문턱값이다(KURE-v3 bf16 가중치 2.28 GB + 활성값이 8 GB 카드에 들어가는 선). 그 전에는 한국어 0.7616 → 0.8027이라는 품질 차이만으로는 교체하지 않는다.

**4) 운영 규칙 (호출자가 그대로 구현)**

| 항목 | 확정값 | 구현 지침 |
| --- | --- | --- |
| 모델 id | `nlpai-lab/KURE-v1` | 색인 스키마에 `model_id`·`dim=1024`를 필수 컬럼으로 저장. 조회 시 값이 다르면 그 색인은 사용하지 않고 재색인 대상으로 표시 |
| 질의 접두사 | **없음(불필요)** | 질의·문서 모두 원문 텍스트를 그대로 인코딩한다. `query:` / `passage:` / `Instruct:` 를 붙이지 않는다. KURE-v1은 `config_sentence_transformers.json`의 `prompts`가 빈 객체이고 CLS 풀링이다([KURE-v1 카드](https://huggingface.co/nlpai-lab/KURE-v1), [pooling config](https://huggingface.co/nlpai-lab/KURE-v1/blob/main/1_Pooling/config.json)). 접두사를 붙이는 코드 경로 자체를 만들지 않는다 |
| 입력 토큰 상한 | **1024 토큰 하드 캡** | 토크나이저 기준으로 절단한다(문자 수 절단 금지). 모델 상한은 8192지만 CPU에서 self-attention 비용이 길이에 제곱으로 늘어 실운영은 1024로 고정하고, 청크는 512~1024 토큰으로 자른다(§5.3) |
| 로드 실패 시 | **FTS 키워드 경로로 degrade** | 모델 로드 실패·임베딩 서버 헬스체크 실패·차원 불일치 시 **원격 임베딩 API로 폴백하지 않는다.** SQLite FTS5/BM25 키워드 검색으로 응답하고, 응답 메타데이터에 `retrieval=fts_fallback`을 남긴다. 목적이 "API 비용 0원"이므로 원격 호출은 설정으로도 활성화되지 않게 기본 차단한다 |

전환 비용: 두 모델 모두 1024/512차원으로 맞출 수 있으나 **벡터 공간이 서로 호환되지 않는다.** 폴백으로 바꾸면 전체 재색인이 필요하다. 따라서 색인 스키마에 `model_id`와 `dim`을 필수 컬럼으로 두고, 모델 교체 시 재색인 작업을 배치로 돌릴 수 있게 설계해야 한다.

이 프로젝트의 확정 사양은 §7.6을 따른다: 운영 모델 `nlpai-lab/KURE-v1` **단일 채택**, 1024차원, 접두사 없음, 1024 토큰 캡, 로드 실패 시 원격 API가 아닌 FTS 키워드 경로. 위 표의 "폴백"은 품질 비교용 대안이고, 여기서 말하는 재색인은 **GPU 확보 시 KURE-v3로 올리는 전환**에 해당한다.

## 9. 검증하지 못한 것 (실행 없이는 확정 불가)

1. **우리 대화 기록에서의 실제 검색 품질.** 공개 벤치마크(위키·PDF·ODQA)와 우리 데이터(한국어/영어 혼합 대화, 코드 스니펫, 결정 로그)는 분포가 다르다. 100~300개 질의로 자체 평가셋을 만들어 Recall@5와 nDCG@10을 재야 한다.
2. **CPU 실측 처리량과 지연.** 위 RAM 표는 파라미터 수에서 계산한 추정치다. 초당 처리 문서 수, 질의 1건 지연, 8코어에서의 스레드 효율은 이 기기에서 측정해야 한다.
3. **양자화 손실.** q8/Q4 GGUF가 원본 fp32 대비 한국어 검색을 얼마나 떨어뜨리는지 공개 수치가 없다. 특히 `Qwen3-Embedding-0.6B` GGUF의 출력 이상 이슈(#14234)가 현재 버전에서 해결됐는지 확인되지 않았다.
4. **`KURE-v3`의 GGUF 경로 실행 가능성.** 커뮤니티 `mradermacher/KURE-v3-GGUF`가 존재하고 GGUF 메타데이터상 아키텍처는 `mistral3`, 풀링은 `pooling_type=1`(mean), 파일 2.29 GB로 확인된다. 다만 이 변환이 실제로 llama.cpp에서 로드되고 KURE-v3가 기대하는 `query: `·`passage: ` 프롬프트와 mean pooling을 그대로 재현하는지는 **실행해 보지 않고는 확정할 수 없다.** 원본 카드의 `1_Pooling/config.json`도 mean pooling이라 방향은 맞다.
5. **`bge-m3`·`KURE-v1`의 한국어 파인튜닝 이득이 우리 도메인에서도 유지되는지.** 벤치마크에서는 +1~2p 차이인데, 이 차이가 실사용에서 체감되는 수준인지 알 수 없다.
6. **`BAAI/bge-multilingual-gemma2`의 한국어 수치.** 카드가 이미지 차트로만 제공해 인용 가능한 숫자가 없다.
7. **`kanana-2-*` 계열의 MTEB(kor, v2) 9과제 수치.** 카드는 자체 6과제 Ko-Retrieval과 nano-BEIR만 공개해, KURE 계열의 9과제 평균과 **같은 자로 비교할 수 없다.** 두 지표를 섞어 순위를 매기면 안 된다.
8. **Modu 계열 벤치마크 접근성.** 공개 검색으로는 임베딩 검색 평가용 "Modu 벤치마킹 스위트"의 공개 리더보드를 확인하지 못했다. 국립국어원 모두의 말뭉치는 말뭉치 배포처로 확인되지만 임베딩 검색 평가 리더보드로는 확인되지 않았다. 확인된 한국어 임베딩 리더보드는 MTEB(kor, v2), KURE 리더보드, AutoRAG 예제 벤치마크, ko-embedding-leaderboard(평가 코드 업로드 예정 상태)다.
9. **`dragonkue/*` 모델의 GGUF/ONNX 존재 여부.** 카드와 허브 검색에서 공식·커뮤니티 변환을 확인하지 못했다. 따라서 이 계열은 ONNX/TEI 또는 transformers 경로로만 쓸 수 있다.
10. **`BM-K/KoSimCSE-*`와 `jhgan/ko-sroberta-multitask`의 라이선스.** 카드에 라이선스 필드가 없어 상업적 사용 가능 여부를 확정할 수 없다.
11. **`jina-embeddings-v3`·`v5`의 한국어 검색 순위.** v5-text-small은 KURE 리더보드에 0.7419로 등장하지만, v3는 MTEB(kor, v2) 수치가 확인되지 않아 동일 지표로 비교할 수 없다.
12. **`sionic-ai/comsat-embed-ko-8b-preview`의 프롬프트 규약과 GGUF.** 카드 태그상 Qwen3-Embedding-8B 파인튜닝이지만, 질의 지시문 필요 여부와 양자화 산출물은 확인하지 못했다.
13. **`bge-m3` sparse/multi-vector 출력의 실사용 이득.** 카드가 hybrid retrieval을 권장하지만, 우리 색인은 dense 단일 벡터를 전제한다. sparse 가중치(`sparse_linear.pt`)를 함께 저장할 때의 저장·질의 비용은 측정하지 않았다.
14. **우리 코퍼스의 한국어:영어 비중.** §7.6의 8:2는 문서 성격에서 끌어낸 **가정**이며 실측이 아니다. 청크의 한글 음절 수·라틴 문자 수를 색인 배치마다 기록하면 확정된다. 이 비율이 한국어 56.88% 아래로 떨어지면 §7.5의 교차점 규칙에 따라 기본안 판단을 다시 해야 한다.
