### 0.4 기준선이 이미 말해 주는 것

`engine/hardware_profiler.py`의 현재 판정은 다음 네 줄이다(코드 그대로).

```
Tier 3: ram_gb >= 32.0 AND vram_gb >= 12.0
Tier 2: ram_gb >= 16.0 OR  vram_gb >= 6.0
Tier 1: ram_gb >= 8.0  OR  vram_gb >= 2.0
Tier 0: 그 외
```

이 규칙은 **태도**는 옳지만 **입력이 부족**하다. 다음 다섯 가지가 없다.

1. `vram_gb`는 `memory.total`만 읽는다. 여유 VRAM이 없다(`nvidia-smi --query-gpu=name,memory.total`).
2. GPU 벤더가 NVIDIA 하나뿐이다. AMD/Intel iGPU는 "GPU 없음"과 구분되지 않는다.
3. 데스크톱이 dGPU에 물려 있는지 모른다. 이 PC는 iGPU(AMD Radeon 760M)가 화면을 구동하므로 dGPU가 프레임버퍼를 들고 있지 않다 — 이 사실이 헤드룸 계산을 바꾼다.
4. 디스크·런타임·가중치 존재를 모른다. 그래서 "Tier 2"라는 능력이 "실행 가능"으로 오독된다(인벤토리 §0.2가 이미 지적).
5. `OR` 조건 때문에 RAM 측정 실패(`0.0`)가 VRAM 6GB 게이트를 통과해 Tier 2가 될 수 있다(인벤토리 §0.3의 미해결 결함).

이 문서의 측정 계층은 그 다섯을 닫는다.

## 1. 측정 계층

### 1.1 측정의 목적은 "티어"가 아니라 "예산"이다

티어는 표시용 요약이다. 선택을 실제로 결정하는 것은 다음 네 예산이다.

| 예산 | 산식 | 쓰는 곳 |
| --- | --- | --- |
| `vram_budget_gib` | `vram_total_gib − os_reserved_gib − P_VRAM_SAFETY`(`display_attached`에 따라 `P_VRAM_SAFETY_ON_DGPU` 또는 `P_VRAM_SAFETY_OFF_DGPU`) | 가중치 + KV + 런타임 오버헤드의 상한 |
| `ram_budget_gib` | `ram_total_gib − P_RAM_RESERVE_GIB` | CPU 경로, mmap 페이지 캐시, 부분 오프로드의 상한 |
| `disk_budget_gib` | `disk_free_gib − P_DISK_RESERVE_GIB` | 다운로드 가능 여부 |
| `compute_budget` | `cpu_physical_cores`, `P_MAX_THREADS` | 스레드 수, 부분 오프로드의 하한 판정 |

`vram_total_gib`는 8188 MiB = 7.996 GiB **[측정]**, `os_reserved_gib`는 유휴 시 232 MiB = 0.227 GiB **[측정]**이므로 `usable_vram_gib = 7.77` **[측정, 인용]**. 여기서 안전 여유를 한 번 더 빼는 이유는 §1.4에 적는다.

### 1.3 측정값의 자료형: 3상태

측정 필드는 `float` 하나가 아니라 **3상태**다.

```
Measured[T] = Measured(value) | Unknown(reason) | NotApplicable(reason)
```

- `Unknown`은 `0.0`이 아니다. `0.0`은 "측정했더니 0이었다"이고 `Unknown`은 "측정하지 못했다"이다. 현행 `_detect_ram_gb()`는 둘을 `0.0`으로 합치고, `OR` 판정 때문에 그 값이 상위 티어를 통과할 수 있다(인벤토리 §0.3의 결함).
- `NotApplicable`은 "이 기기에 그 개념이 없다"이다. 예: iGPU에 전용 VRAM 없음, TCC 모드에 WDDM 헤드룸 없음.
- 선택 규칙은 `Unknown`을 만나면 **그 예산을 쓰는 경로를 비활성**하고, `NotApplicable`을 만나면 **다른 경로로 대체**한다. 두 처리가 다르다.

### 1.4 WDDM 공유 메모리: 예산의 일부가 아니라 금지 사유다

이 PC의 드라이버 모델은 WDDM이고, WDDM에서 VRAM 초과는 **실패가 아니라 조용한 시스템 RAM 스필**이다 **[측정, 인용]**. 이것은 두 가지를 뜻한다.

1. **오버커밋을 용량으로 쓸 수 없다.** "8 GB 카드에서 9 GB 모델이 돌아간다"는 관측은 성립할 수 있지만, 그것은 예산을 넘긴 것이고 처리량이 떨어진 상태다. 이 설계는 스필을 **적재 실패로 취급**한다. 즉 `fit` 판정은 `resident_cost ≤ vram_budget_gib`이고, 스필은 그 판정을 통과한 뒤에도 일어날 수 있는 사고이지 통과 수단이 아니다.
2. **안전 여유는 0이 될 수 없다.** 안전 여유는 `display_attached`에 따라 `P_VRAM_SAFETY_OFF_DGPU` 또는 `P_VRAM_SAFETY_ON_DGPU`를 쓰는 릴리스 파라미터다.

| 파라미터 | 값(제안) | 근거 |
| --- | --- | --- |
| `P_VRAM_SAFETY_OFF_DGPU` | 0.5 GiB | 데스크톱이 dGPU를 쓰지 않아도 다른 프로세스와 드라이버가 VRAM을 잡는다. 이 PC의 실측 여유를 매번 재지 않고도 스필을 피하기 위한 완충 **[파라미터]** |
| `P_VRAM_SAFETY_ON_DGPU` | 1.0 GiB | 프레임버퍼·합성기·브라우저 GPU 프로세스가 같은 카드에 있다 **[파라미터]** |
| `P_RUNTIME_OVERHEAD_GIB` | 0.45 GiB | 런타임의 컴퓨트 그래프·스크래치 버퍼. 모델·컨텍스트와 무관한 고정분 **[파라미터]** |
| `P_CO_RESIDENT_MARGIN_GIB` | 0.5 GiB | 두 모델을 동시에 올릴 때 남겨야 하는 최소 여유. 이 PC에서 7B+3B 조합의 잔여가 0.5 GiB 미만일 때 WDDM에서 열화가 관측되었다는 사실 **[측정]** 에 대응하는 값 **[파라미터]** |
| `P_RAM_RESERVE_GIB` | 6.0 GiB | OS·브라우저·IDE를 위해 남기는 RAM **[파라미터]** |
| `P_DISK_RESERVE_GIB` | 5.0 GiB | 다운로드 중 임시 파일과 로그 **[파라미터]** |

이 PC에서 계산하면 `vram_budget_gib = 7.77 − 0.5 = 7.27` **[유도]** 이다. 0.5를 쓰는 이유는 `display_attached=false` **[측정]** 이므로 `P_VRAM_SAFETY_OFF_DGPU`가 적용되기 때문이며, 같은 기기에서 외부 모니터를 dGPU에 직결하면 `display_attached=true`가 되어 `P_VRAM_SAFETY_ON_DGPU`(1.0)가 적용되고 예산이 6.77 GiB로 줄어든다. **같은 노트북이 케이블 하나로 다른 선택을 받는다** — 이것이 측정을 캐시하지 않고 재결정마다 다시 하는 이유다.

### 1.5 최초 실행과 재결정의 측정 집합

| 시점 | 측정 항목 | 이유 |
| --- | --- | --- |
| 최초 실행(S4) | M-01, M-03, M-04, M-06, M-07, M-08, M-09, M-12, M-13, M-14, M-15 | 지문(fingerprint) 생성. 한 번 비싸도 된다 |
| 작업 시작 전 | M-02, M-05, M-10, M-11, M-14, M-15, M-16 | 여유·디스플레이 구성·준비도는 언제든 바뀐다 |
| 적재 직전 | M-02, M-05, M-12 | 마지막 순간의 여유로 `fit`을 재확인 |
| 재결정(T-01) | 지문 필드 전부 | GPU 교체·RAM 증설·드라이버 업데이트 |

**지문(fingerprint)** 은 안정 필드만 해시한다: `gpu_vendor`, `gpu_name`, `vram_total`, `ram_total`, `cpu_physical_cores`, `driver_major`, `driver_model`(WDDM/TCC), `vulkan_device_type`. 여유 VRAM·디스크 여유·엔드포인트 상태는 지문에 넣지 않는다 — 그것들은 매 순간 변하므로 넣으면 재결정이 끝없이 발화한다. 인벤토리 T-01의 "하드웨어 지문 불일치"는 이 필드 집합을 뜻한다.

### 1.6 측정 계층이 하지 않는 일

- **GPU 이름으로 VRAM을 추정하지 않는다.** `"RTX 4060 Laptop"`이라는 문자열에서 8 GB를 유도하지 않는다. M-01이 실패하면 그 카드의 VRAM은 unknown이다.
- **iGPU에서 `AdapterRAM`을 신뢰하지 않는다.** Windows `Win32_VideoController.AdapterRAM`은 32비트 필드로 알려져 있고, 공유 메모리 iGPU에서는 실제 상한을 표현하지 못한다. iGPU는 "전용 VRAM 없음"으로 기록하고 RAM 경로로 보낸다.
- **측정 실패를 저사양으로 표시하지 않는다.** 화면 문구는 "측정 실패"와 "8 GB 미만"을 구분한다(인벤토리 E-HW-02의 요구).
- **측정값을 영수증에 출처와 함께 남긴다.** 인벤토리 §6.3의 영수증 각 줄은 `측정`/`유도`/`파라미터`/`unknown` 중 하나로 표시된다.

## 2. 선택 규칙

### 2.1 선택의 단위는 티어가 아니라 튜플이다

선택 결과는 하나의 값이 아니라 다음 튜플이다.

```
SelectionDecision = {
  status,                    # §4의 상태 어휘
  fore_model_id,             # 카탈로그 ID 또는 null
  bg_model_id,               # 카탈로그 ID 또는 null (포그라운드와 달라야 한다)
  ctx_tokens,                # 포그라운드 컨텍스트
  bg_ctx_tokens,             # 백그라운드 컨텍스트
  quant_label,               # 선택된 카탈로그 항목의 양자화 라벨 (독립 변수 아님)
  gpu_layers,                # 정수 또는 "all"
  kv_type,                   # f16 (P_KV_TYPE)
  threads,                   # CPU 스레드
  residency,                 # co_resident | swap | background_off
  reasons[]                  # 각 단계의 결정 사유 (기계 판독 가능한 코드 + 사람 문장)
}
```

**양자화는 선택의 결과이지 입력이 아니다.** 카탈로그의 각 항목은 하나의 양자화 라벨을 갖는다(`Q4_K_M`, `PQ2_0` 등). 선택기는 "Q4로 7B"를 고르는 것이 아니라 "이 항목이 예산에 들어가는가"를 본다. 이렇게 하면 "존재하지 않는 양자화 조합"이 선택될 수 없다.

### 2.2 적재 비용 산식

모델 하나를 컨텍스트 `ctx`로 올릴 때의 비용은 다음 세 항이다.

```
resident_cost(model, ctx) =
    weights_gib(model)                     # 카탈로그 weights_bytes (실제 파일 크기)
  + kv_gib(model, ctx)                     # 아래 산식
  + P_RUNTIME_OVERHEAD_GIB                 # [파라미터]
```

```
kv_bytes_per_token(model) = 2 * n_layer * n_kv_head * head_dim * bytes_per_element
kv_gib(model, ctx)        = kv_bytes_per_token * ctx / 2^30
```

- `n_layer`, `n_kv_head`, `head_dim`는 GGUF 메타데이터에서 읽는다. **추정하지 않는다.** 이 셋이 없는 모델은 KV를 계산할 수 없으므로 선택 불가다(§7).
- `bytes_per_element`는 `P_KV_TYPE = f16`이면 2다 **[파라미터]**. KV 양자화(q8_0 등)는 `P_KV_TYPE` 값을 바꾸는 릴리스 결정이지 측정값이 아니다.
- `2`는 K와 V 두 텐서를 뜻한다.

이 산식은 **가중치 파일 크기와 KV를 분리**한다. 현행 코드가 `LOCAL_TIER_QUANTIZATION`에 "VRAM 6.7GB"라고 적으면서 티어 게이트는 12 GB인 혼동(인벤토리 §0.3)은 이 분리로 사라진다. 게이트는 총 적재 예산이고, 27B의 가중치 크기는 레지스트리의 `weights_bytes`에 있다(가장 작은 항목인 PTQ1_0이 5,946,648,928 B ≈ 5.54 GiB, PQ2_0가 7,206,168,928 B ≈ 6.71 GiB). 이 문서의 이전 개정이 인용한 7.98 GiB는 어느 항목과도 맞지 않으므로 사용하지 않는다.

### 2.3 결정론적 선택 절차

선택은 다음 8단계를 **순서대로** 수행한다. 각 단계는 앞 단계의 출력만 입력으로 쓴다. 같은 측정·같은 카탈로그·같은 파라미터는 항상 같은 튜플을 낸다.

```
1. 예산 계산
   vram_budget_gib = vram_total − os_reserved
                     − (display_attached ? P_VRAM_SAFETY_ON_DGPU : P_VRAM_SAFETY_OFF_DGPU)
   ram_budget_gib  = ram_total − P_RAM_RESERVE_GIB
   accelerator     = discrete_gpu | integrated_gpu | none
   load_budget_gib = (accelerator == discrete_gpu) ? vram_budget_gib : ram_budget_gib
   # iGPU와 가속 없음은 RAM 예산으로만 판정한다(§2.4 주의 3)

2. 후보 필터 (하드 제약)
   - 카탈로그에 있고 vendor_status == confirmed
   - weights_bytes, n_layer, n_kv_head, head_dim, license 가 모두 존재
   - license 동의가 원장에 있음 (M-07)
   - weights 파일이 실재하고 SHA-256 일치
   - 역할 선언이 요구 역할을 덮음
   → 하나라도 불충족이면 후보에서 제외하고 reason 코드를 남긴다

3. 컨텍스트 상한 계산 (모델별)
   ctx_fit = floor((load_budget_gib − weights_gib − P_RUNTIME_OVERHEAD_GIB) / kv_gib_per_token)
   ctx_sel = clamp(ctx_fit, P_CTX_FLOOR, min(ctx_catalogue, P_CTX_CEIL_FG))
   ctx_fit < P_CTX_FLOOR 이면 그 모델은 부적격
   # 부분 오프로드로 ctx_sel을 늘리지 않는다. CPU로 내려간 레이어의 KV가
   # 어디에 놓이는지는 런타임 구현에 달려 있고 [대기], 그 값에 기대어
   # 컨텍스트를 키우면 예산 계산이 런타임 버전에 의존하게 된다.

4. 포그라운드 선택
   적격 후보를 (size_class 내림차순, ctx_sel 내림차순, model_id 오름차순)으로 정렬해 첫 항목
   (size_class는 카탈로그의 선언값이며 성능 순위가 아니다)

5. 백그라운드 선택 (역할 기반, §5)
   적격 후보 중 fore_model_id != bg_model_id 이고 bg_approved == true 인 것
   정렬 키: (상주 가능, size_class 내림차순, model_id 오름차순)
     상주 가능 = resident_cost(fore) + resident_cost(candidate, P_CTX_CEIL_BG)
                 + P_CO_RESIDENT_MARGIN_GIB <= vram_budget_gib
   상주 가능한 후보가 없고 swap이 허용되면(P_BG_SWAP_ALLOWED) 상주 불가 후보 중 첫 항목을 고른다.
   후보가 없으면 bg_model_id = null, residency = background_off

6. 상주 판정 (§3)
   accelerator == discrete_gpu 일 때만 상주를 논한다
   5단계에서 고른 bg가 상주 가능이면 co_resident, 아니면 swap
   accelerator != discrete_gpu 이면 항상 swap

7. 오프로드 계산
   전량 적재 가능 → gpu_layers = "all"
   부분만 가능 → gpu_layers = floor((load_budget_gib − kv_gib − P_RUNTIME_OVERHEAD_GIB) / bytes_per_layer)
                여기서 bytes_per_layer = weights_gib / n_layer
   부분 비율 < P_MIN_GPU_FRACTION 이면 그 모델은 CPU 경로로 보낸다

8. 최종 재확인
   적재 직전 M-02/M-05를 다시 읽어 7단계 결과가 여전히 성립하는지 확인
   성립하지 않으면 4단계로 돌아가 **한 단계 작은** 후보로 내려간다 (최대 P_FIT_RETRIES회)
```

`size_class`는 카탈로그가 선언하는 등급(예: `small`, `medium`, `large`)이며, **성능 순위가 아니다**. 이 문서는 "큰 모델이 더 좋다"고 주장하지 않는다. 정렬 키로 쓰는 이유는 결정론과 사용자 기대(더 큰 모델을 원한다)뿐이며, 품질 판단은 인벤토리 T-12(사용자 피드백)와 ECPS가 소유한다.

### 2.4 연속 구간 표

아래 표는 **하드 제약의 결과**를 구간별로 보여준다. 구간 경계는 `vram_budget_gib` 기준이며, 경계값 자체는 파라미터다. "포그라운드 등급"은 그 예산에 들어가는 **카탈로그 항목 중 가장 큰 것**이고, 실제 ID는 카탈로그가 정한다.

| 하드웨어 프로필 | `vram_budget_gib` | 포그라운드 | 백그라운드 | 컨텍스트(설계 목표 **[파라미터]**) | 상주 | 상태 |
| --- | --- | --- | --- | --- | --- | --- |
| GPU 없음(가속 디바이스 0) | 0 | RAM 경로: 예산 내 최대 등급 | RAM 경로: 1.5B급 또는 없음 | `P_CTX_CEIL_CPU` 이하 | swap 고정 | `READY_LOCAL_SLOW` |
| iGPU만(전용 VRAM 없음) | 0(공유) | RAM 경로와 동일 | 동일 | 동일 | swap 고정 | `READY_LOCAL_SLOW` |
| 4 GB dGPU | ≈ 3.27 **[유도]** | 1.5B급. 3B급은 KV 확보 여부가 모델 메타데이터에 달림 **[대기]** | 없음 또는 swap | 4K~8K | swap | `READY_LOCAL` |
| 6 GB dGPU | ≈ 5.27 **[유도]** | 1.5B~3B급. 7B급은 가중치 4.36 GiB **[측정]** 를 빼면 KV에 0.46 GiB만 남아 `P_CTX_FLOOR` 확보 여부가 모델 KV에 달림 | 없음 또는 swap | 4K~8K | swap | `READY_LOCAL` |
| 8 GB dGPU(이 PC) | **7.27** **[유도]** (7.77 − 0.5) | 7B급 | 1.5B급 상주 가능 / 3B급은 swap | 16K~32K | 조건부 co_resident | `READY_LOCAL` |
| 12 GB dGPU | ≈ 11.27 **[유도]** | 27B PQ2_0급이 처음 후보가 된다(가중치 6.71 GiB + 런타임 버퍼 1.21 GiB + KV) | 1.5B급(상주 여부는 KV 계산 결과에 따름) | 8K~32K | 조건부 | `READY_LOCAL` |
| 16 GB dGPU | ≈ 15.27 **[유도]** | 27B급 + 여유 KV | 3B~7B급 | 32K 이상 | co_resident 가능 | `READY_LOCAL` |
| 24 GB 이상 dGPU | ≥ 23.27 **[유도]** | 카탈로그 최대 등급 | 7B급 상주 | 카탈로그 상한까지 | co_resident | `READY_LOCAL` |
| RAM만(가속 없음, RAM 충분) | 0 | RAM 예산 내 최대 등급 | 없음 | `P_CTX_CEIL_CPU` | swap | `READY_LOCAL_SLOW` |
| 어떤 조합도 불가 | — | null | null | — | — | `LOCAL_NO_FIT` |

**컨텍스트 열은 측정값이 아니라 설계 목표다.** 실제 값은 §2.3 3단계의 `ctx_fit`이 GGUF 메타데이터(`n_layer`, `n_kv_head`, `head_dim`)로 계산한다. 이 열을 근거로 `ctx_tokens`를 하드코딩하지 않는다 — 같은 8 GB 카드에서도 모델마다 KV/token이 다르고, 그 값이 이 표의 범위를 벗어날 수 있다.

**`vram_budget_gib` 열의 유도 가정:** 8 GB 행은 이 PC의 실측(8188 MiB − 232 MiB = 7.77 GiB **[측정]**)에서 0.5를 뺀 값이다. 나머지 dGPU 행은 "총 VRAM − 232 MiB − 0.5 GiB"라는 **같은 가정**을 적용한 것이며, 그 기기의 실측이 아니다. 다른 기기에서 `os_reserved`가 다르면 그 행의 값도 달라진다.

주의할 점 넷.

1. **8 GB의 7B는 "들어간다"가 아니라 "들어가도록 컨텍스트를 줄인다"이다.** 7B Q4_K_M 가중치가 4.36 GiB **[측정]** 이므로, 7.27 예산에서 오버헤드 0.45를 빼면 KV에 2.46 GiB가 남는다. KV/token을 알면 `ctx_fit`이 정해지고, 그 값이 카탈로그 상한보다 작으면 **컨텍스트가 줄어든 것이지 모델이 안 들어간 것이 아니다.** 이 구분이 영수증에 표시되어야 한다.
2. **12 GB에서 27B가 "처음 후보"가 되는 것은 게이트이지 적재 보증이 아니다.** 가장 작은 27B 항목(PTQ1_0 5.54 GiB)에 런타임 버퍼 1.21 GiB를 더한 6.75 GiB는 이 카드의 총 사용 가능 VRAM(7.77 GiB **[측정]**)보다 작지만 KV 몫이 0.02 GiB만 남아 4,096토큰 하한에 미달하므로, 이 조건에서 27B는 **선택되지 않는다**. 12 GB에서는 KV 예산이 확보되지만, KV 크기는 그 모델의 GGUF 메타데이터로만 계산된다. 현행 `BACKGROUND_MIN_VRAM_GB = 12.0`은 필요조건이고 충분조건이 아니다.
3. **iGPU 구간은 VRAM 예산이 0이다.** 공유 메모리를 "전용 VRAM"으로 부르지 않는다. 이 구간의 판정은 `ram_budget_gib`로만 한다.
4. **표의 등급 이름은 카탈로그 항목을 가리키는 자리표시자다.** 어떤 ID가 선택되는지는 §7의 필드가 채워진 뒤에만 확정된다.

### 2.5 오프로드 결정

| 조건 | `gpu_layers` | 표시 |
| --- | --- | --- |
| `resident_cost ≤ budget` | `"all"` | "전량 GPU" |
| 일부만 적재 | `floor((load_budget_gib − kv_gib − P_RUNTIME_OVERHEAD_GIB) / bytes_per_layer)`, `bytes_per_layer = weights_gib / n_layer` | "부분 오프로드 n/N 레이어" |
| 부분 비율 < `P_MIN_GPU_FRACTION` | `0` (CPU 전용) | "GPU 이점 없음 — CPU 경로" |
| RAM 예산도 초과 | 선택 불가 | `LOCAL_NO_FIT` |

`P_MIN_GPU_FRACTION = 0.6` **[파라미터]** 은 "레이어의 60% 미만만 GPU에 올릴 구성은 GPU 경로로 부르지 않는다"는 뜻이다. 이 값은 성능 주장이 아니라 **경로 이름의 정직성**을 위한 것이다. 절반이 CPU에 있는 구성을 "GPU 가속"이라고 표시하지 않기 위해서다.

부분 오프로드는 **가중치 전체가 RAM에 있어야 한다**. 따라서 `weights_gib ≤ ram_budget_gib`도 함께 확인한다. GPU에 60%가 올라가도 파일 전체는 mmap되어야 하기 때문이다.

## 3. 동시성 정책

### 3.1 문제 정의

포그라운드(사용자 요청)와 백그라운드(압축·제목·증류·트리아지)는 동시에 요청될 수 있다. 8 GB 카드에서 둘을 동시에 올릴 수 있는지 없는지가 이 절의 전부다. 판정은 **산술로만** 한다.

### 3.2 상주 판정 산술

```
co_resident_ok =
    accelerator == discrete_gpu
    AND resident_cost(fore, ctx_fg) + resident_cost(bg, ctx_bg) + P_CO_RESIDENT_MARGIN
        <= vram_budget_gib
```

`accelerator != discrete_gpu`(iGPU·가속 없음)이면 `co_resident_ok`는 **항상 false**다. 공유 메모리에는 "상주"라는 개념이 없다 — 두 모델이 같은 RAM 예산을 나눠 쓰고, 그 예산은 이미 `ram_budget_gib` 하나로 계산되었다.

이 PC의 측정 앵커 두 개 **[측정, 인용]** 로 검산한다. 아래 조합 값은 해당 조합을 실제로 적재했을 때의 점유량이다.

| 조합 | 측정 점유 | 예산 7.27 대비 잔여 | 마진 0.5 대비 | 판정 |
| --- | --- | --- | --- | --- |
| 7B + 1.5B | 6.4 GiB **[측정]** | 0.87 GiB | 통과 | **co_resident** |
| 7B + 3B | 7.2–7.4 GiB **[측정]** | 0.07 ~ −0.13 GiB | 미달 | **swap** |

두 번째 줄이 이 설계의 핵심이다. 7B+3B는 "돌아가기는 한다" — WDDM이 초과분을 조용히 시스템 RAM으로 넘기기 때문이다 **[측정, 인용]**. 그러나 잔여가 0.5 GiB 미만이면 열화가 관측되었으므로 **[측정, 인용]**, 이 설계는 그 조합을 **상주 허용으로 부르지 않는다**. 대신 swap으로 내린다. 사용자는 "백그라운드가 잠시 대기한다"를 경험하고, "포그라운드가 느려졌다"는 경험을 하지 않는다.

즉 **상주 판정의 목적은 throughput 최대화가 아니라 예측 가능성**이다. 조용한 스필은 오류를 만들지 않고 지연만 만들기 때문에, 사용자가 원인을 알 수 없는 종류의 나쁜 경험이다.

### 3.3 상주 모드(co_resident)의 동작

- 두 모델은 각각 하나의 **슬롯**을 갖는다. 슬롯은 `llama.cpp` 서버 인스턴스 하나에 대응한다.
- 포그라운드 슬롯은 `P_FG_CONCURRENCY = 1`(동시 요청 1개), 백그라운드 슬롯도 1이다. 낮은 VRAM에서 병렬 요청은 KV를 두 배로 만들기 때문이다 **[파라미터]**.
- 백그라운드 요청은 **토큰 경계에서만** 중단된다. 문장 중간에서 자르고 다른 모델 출력을 붙이지 않는다(인벤토리 §3.3의 "부분 산출물 이어붙이기 금지").
- 포그라운드 요청이 도착하면 백그라운드 슬롯에 취소 신호를 보낸다. 취소된 작업은 **폐기**되고, 그때까지의 출력은 저장되지 않는다. 이어붙이지 않는다.

### 3.4 교체 모드(swap)의 동작

- **VRAM 리스(lease)** 는 하나뿐이다. 리스 소유자만 모델을 적재할 수 있다.
- 백그라운드 작업은 리스가 비어 있을 때만 적재를 시작한다. 적재 자체가 예산을 넘으면 시작하지 않는다(§2.3 8단계).
- 포그라운드 요청이 리스 대기 중이면:
  1. 진행 중인 백그라운드 작업에 취소를 보내고, 최대 `P_FG_LEASE_WAIT_MAX_MS`(3000ms)까지 기다린다.
  2. 백그라운드 모델을 unload하고, 최대 `P_UNLOAD_VERIFY_MS`(2000ms)까지 `memory.free`가 회복되기를 확인한다.
  3. 회복이 확인되면 포그라운드를 적재한다.
  4. 회복이 확인되지 않으면 **swap을 신뢰할 수 없는 상태**로 표시하고, 이후 `residency = background_off`로 내린다. WDDM에서 unload가 VRAM을 즉시 돌려주지 않는 경우가 있기 때문이다. 이때 사용자는 "백그라운드 요청을 처리할 수 없음"을 보게 되고, 포그라운드는 정상 동작한다.
- 재적재는 **콜드 스타트**다. 이전 대화의 KV를 복원하지 않는다. 복원하려면 컨텍스트를 다시 프리필해야 하고, 그 비용은 재적재와 같거나 크다. KV 재사용은 이 설계의 범위 밖이다 **[대기]**.

### 3.5 큐와 만료

- 백그라운드 큐 깊이는 `P_BG_QUEUE_DEPTH = 2` **[파라미터]** 다. 그 이상은 **병합**한다. 압축 요청 3개는 "가장 최근 컨텍스트에 대한 압축 1개"로 접는다 — 압축은 최신 상태에 대해서만 의미가 있다.
- 각 백그라운드 작업은 `P_BG_DEADLINE_MS`(120000ms)를 갖는다. 초과하면 **중단하고 `expired`로 기록**한다. 조용히 버리지 않는다.
- 만료된 작업의 결과는 부분 출력도 남기지 않는다. 사용자에게는 "백그라운드 요약이 시간 내에 끝나지 않아 규칙 기반 축약을 사용했습니다"라고 표시한다.

### 3.6 사용자 체감 지연의 상한

포그라운드 요청이 백그라운드 때문에 기다리는 시간의 상한은 다음과 같다.

```
T_visible_max = P_FG_LEASE_WAIT_MAX_MS + P_UNLOAD_VERIFY_MS + T_reload(model, ctx)
```

- `T_reload`는 **모델·컨텍스트별로 최초 1회 측정해 저장한다**. 측정 전에는 값을 주장하지 않는다. 영수증에는 "재적재 시간: 측정 전"으로 표시하고, UI는 진행 표시와 취소 버튼을 제공한다.
- `T_reload`가 측정된 뒤에도 이것을 **SLA로 약속하지 않는다**. 느린 디스크·콜드 페이지 캐시·드라이버 상태에 따라 달라지기 때문이다. 상한은 "앱이 스스로 정한 대기 한도"이고, 그 한도를 넘으면 앱은 기다리는 대신 백그라운드를 포기한다.
- 백그라운드가 포그라운드를 기다리게 하는 시간은 **0**이다. 우선순위는 항상 포그라운드다.

### 3.7 예산을 넘는 요청의 처리

| 상황 | 처리 |
| --- | --- |
| 포그라운드 모델이 예산에 안 들어감 | §4의 `LOCAL_NO_FIT`. 더 작은 모델을 **자동으로 고르지 않는다** — §4.3 |
| 포그라운드는 들어가고 백그라운드가 안 들어감 | `residency = background_off`, `bg_model_id = null`. 포그라운드는 정상 |
| 둘 다 들어가지만 마진 미달 | `swap`. 상주시키지 않는다 |
| 적재 직전 여유가 줄어 있음 | §2.3 8단계. 한 등급 내리고 재확인, 그래도 안 되면 `LOCAL_NO_FIT` |
| 상주 중 다른 앱이 VRAM을 잡아 스필 발생 | 어댑터의 스필 신호(§6.2.1: 적재 후 `memory.free` 감소가 예상과 다름)가 감지되면 **백그라운드를 먼저 unload**한다. 포그라운드는 유지. 사용자에게 "다른 앱이 그래픽 메모리를 사용 중" 고지(인벤토리 E-LOC-03) |

**WDDM 스필을 예산의 여유로 계산하지 않는다.** 이 한 줄이 §3 전체의 요약이다.

## 4. 거부와 강등

### 4.1 상태 어휘 (이 문서가 추가하는 것)

인벤토리 §3.1의 어휘를 그대로 쓰고, 로컬 선택에 필요한 일곱 개를 추가한다.

| 상태 | 의미 | 되는 것 | 안 되는 것 | 다음 행동 |
| --- | --- | --- | --- | --- |
| `READY_LOCAL` | 선택된 튜플이 예산 안에 있고 준비 완료 | 포그라운드 로컬 호출 | 예산 밖 모델 | 없음 |
| `READY_LOCAL_SLOW` | CPU/RAM 경로로만 가능 | 로컬 호출(느림을 고지) | GPU 가속 주장 | 없음 |
| `LOCAL_UNPROVISIONED` | 런타임 또는 가중치 없음 | 상태 표시, 다운로드 안내 | 로컬 호출 | 설치·다운로드(사용자 선택) |
| `LOCAL_NO_FIT` | 어떤 카탈로그 항목도 예산에 안 들어감 | 상태 표시, 산식 표시 | 로컬 호출, 자동 축소 대체 | 더 작은 모델을 **사용자가** 고르거나 클라우드 opt-in |

`LOCAL_NO_FIT`과 `LOCAL_FIT_PARTIAL`을 나누는 이유: 전자는 "이 카드로는 안 된다", 후자는 "이 모델로는 이 컨텍스트에서 안 된다"이다. 사용자가 취할 행동이 다르다.

| 금지 | 왜 |

| **조용한 클라우드 폴백** | 로컬이 안 되면 클라우드로 보내는 것은 반출이다. 반출은 M-01 동의 없이는 일어나지 않는다(인벤토리 R-CRED-04 3번) |
| **조용한 소형 모델 대체** | "7B가 안 들어가니 1.5B로"는 사용자가 요청한 것과 다른 모델이다. 인벤토리 §3.3이 금지한 `silent substitution`이다. 사용자가 선택지에서 고를 수는 있지만, 앱이 대신 고르지 않는다 |
| **기능이 동작하는 척** | 백그라운드가 없으면 "요약했다"가 아니라 "규칙 기반으로 축약했다, 모델 호출은 없었다"고 말한다 |
| **WDDM 스필을 성공으로 표시** | 초과 적재가 "돌아가는" 것은 성공이 아니다. 예산 초과는 `LOCAL_NO_FIT`이다 |
| **부분 오프로드를 "GPU 가속"으로 표시** | 레이어 60% 미만이면 GPU 경로라고 부르지 않는다(§2.5) |
| **측정 실패를 저사양으로 표시** | "측정 실패"와 "8 GB 미만"은 다른 문구다(인벤토리 E-HW-02) |
| **모델 크기 추정으로 선택** | 카탈로그에 `weights_bytes`가 없으면 선택 불가다(§7). 파일 크기를 "비슷한 모델에서 유추"하지 않는다 |

### 4.4 강등의 순서

예산이 줄어드는 사건(다른 앱 실행, 도킹, 드라이버 업데이트)에서 강등은 다음 순서로만 일어난다.

```
1. 백그라운드 상주 해제 (포그라운드 유지)
2. 백그라운드 컨텍스트 축소 (P_CTX_CEIL_BG 이하로)
3. 포그라운드 컨텍스트 축소 (P_CTX_FLOOR까지)
4. 포그라운드 모델 등급 하향 — **사용자에게 고지하고 승인받은 경우에만**
5. LOCAL_NO_FIT
```

4번이 자동이 아닌 이유는 §4.3의 두 번째 금지와 같다. 진행 중인 작업의 모델을 바꾸면 부분 산출물이 섞인다(인벤토리 §3.3 세 번째 금지). 작업 경계에서만, 사용자 고지 후에 한다.

## 5. 백그라운드 모델 규칙의 정직한 재정의

### 5.1 현재 규칙과 그 귀결

이 절이 제안한 역할 규칙(R-BG2-01..03)은 **현재 코드에 반영되어 있다.** `engine/registry.py`의 `select_background_model()`은 이름이 아니라 승인 목록(`bg_approved` + 백그라운드 역할 선언)과 `vram_budget.select()`의 적재 산술로 후보를 고르고, 후보가 없으면 `status="unavailable"`, `model_id=""`, `entry=None`을 돌려주며 `require_entry()`가 `BackgroundModelUnavailableError`를 던진다. 승인 목록은 레지스트리의 `local/*` 15개 중 12개다: 27B 세 양자화(PTQ1_0·PQ2_0·Q2_0), 9B 세, 4B 두, 2B 두, 그리고 Qwen 1.5B·7B GGUF다. 빠지는 셋은 `local/qwen2.5-coder-14b-gguf`(백그라운드 역할 선언 없음)와 aux 두 항목이다. 따라서 "항상 27B"라는 서술은 더 이상 코드와 맞지 않는다.

남아 있는 정리 대상은 다음 세 가지다.

1. `BACKGROUND_MODEL_ID = "local/bonsai-2-27b-pq2"` 상수는 **레거시 진단용 이름**으로만 남아 있다(선택 근거가 아니다). 문서에서 이 상수를 요구 조건으로 인용하지 않는다.
2. `BACKGROUND_REQUIRED_TIER = ADVANCED_LOCAL`과 `BACKGROUND_MIN_RAM_GB`/`BACKGROUND_MIN_VRAM_GB`는 **필요조건**이며, 최종 판정은 적재 산술이 한다. 티어가 높다는 사실이 적재 가능을 뜻하지 않는다.
3. 카탈로그의 27B 가중치 크기는 배포 파일 목록 기준 **PTQ1_0 5,946,648,928 bytes(≈5.54 GiB), PQ2_0 7,206,168,928 bytes(≈6.71 GiB), Q2_0 7,626,008,928 bytes(≈7.10 GiB)** 이고 계열 런타임 버퍼는 1.21 GiB **[파라미터]** 다. 이 문서가 앞서 인용한 7.98 GiB는 IQ3_S 계열 파일 크기(12,040,883,904 bytes ≈ 11.21 GiB)와도, 위 세 값과도 맞지 않으므로 27B 최소값으로 쓰지 않는다.

이 카드의 산술 **[유도]**: 표시장치가 dGPU에 붙어 있다고 보수적으로 가정하면 예산은 7.77 − 1.0 = 6.77 GiB이고, 가장 작은 27B 항목(5.54 GiB)에 버퍼 1.21 GiB를 더하면 6.75 GiB가 되어 KV에 0.02 GiB만 남습니다. 이는 4,096토큰 하한(P_CTX_FLOOR × 65,536 bytes/token ≈ 0.25 GiB)에 미달하므로 이 조건에서 27B는 선택되지 않습니다. 표시장치가 dGPU에 없다고 측정되면 예산이 7.27 GiB가 되어 PTQ1_0이 8K 내외 컨텍스트로 산술에 들어오지만, 그 양자화는 `prism_fork` 런타임을 요구하므로 런타임 종류·빌드·백엔드 검사를 통과해야 합니다. 어느 경우든 **측정된 적재·실행 기록은 없습니다.**

### 5.2 재정의: 이름이 아니라 역할

규칙을 다음으로 바꾼다.

> **R-BG2-01 (역할 규칙).** 모든 백그라운드 인지 작업(세션 압축, 제목·커밋 메시지, 메모리 인덱싱·증류, 리랭크, 트리아지, 루프 가드 진단)은 **승인 목록(approved list)에 속한, 포그라운드 모델과 다른 하나의 전담 로컬 모델**로 실행한다. 이 모델은 카탈로그에서 백그라운드 역할을 선언해야 하고, §2의 예산 규칙을 통과해야 하며, 포그라운드 모델 ID와 같아서는 안 된다.

> **R-BG2-02 (대체 금지).** 승인 목록에 적합한 모델이 없으면 `BG_UNAVAILABLE`과 사유를 반환한다. Qwen·클라우드·포그라운드 모델로 조용히 대체하지 않는다. 사용자가 명시적으로 승인 목록을 바꾸는 것은 대체가 아니다.

> **R-BG2-03 (승인 목록).** 승인 목록은 릴리스가 카탈로그에 고정한다. 항목은 `bg_approved: true`와 백그라운드 역할 선언을 가져야 한다. 선택 순서는 §2.3 5단계를 따른다 — 상주 가능한 후보를 먼저, 그 안에서 `size_class` 내림차순, `model_id` 오름차순. 상주 가능한 후보가 없고 `P_BG_SWAP_ALLOWED`가 true이면 swap으로라도 하나를 고른다. 목록에 27B가 있으면 12 GB 이상에서 선택되고, 8 GB에서는 선택되지 않는다 — **그것이 정상 동작이다.**

### 5.3 등급별 귀결 (산술)

| 프로필 | 백그라운드 전담 모델 | 근거 |
| --- | --- | --- |
| 8 GB(이 PC) | 1.5B급. 상주 가능(7B+1.5B = 6.4 GiB **[측정]**) | 3B급은 7.2–7.4 GiB **[측정]** 로 마진 미달 |
| 6 GB | 1.5B급, swap 전용 | 상주 여유 없음. `P_BG_SWAP_ALLOWED`가 false면 없음 |
| 4 GB | 없음(`background_off`) 또는 더 작은 등급 **[대기 — 카탈로그에 해당 항목 없음]** | 1.5B급도 포그라운드와 함께 못 올림 |
| 12 GB | 1.5B~3B급(상주 여부는 27B의 KV 계산 결과에 따름), 7B급은 swap | 27B 가중치 6.71 GiB(PQ2_0)·버퍼 1.21 GiB가 예산 11.27의 대부분을 쓴다 |
| 16 GB | 3B~7B급(상주 여부는 KV 계산 결과에 따름) | 27B + 7B는 마진이 작다 **[유도]** |
| 24 GB 이상 | 7B급 상주, 27B급도 후보 | 카탈로그 승인 목록에 있을 때만 |
| CPU/RAM만 | 1.5B급(느림 고지) 또는 없음 | `ram_budget_gib`에 따름 |

**"8 GB에서는 작고, 12 GB 이상에서는 커진다"가 규칙의 의도된 결과다.** 작은 것이 타협이 아니라 예산의 사실이다.

### 5.4 현재 코드와의 충돌 (수정 대상)

이 재정의는 다음 네 곳에서 현행 코드와 어긋나며, 구현 시 정리해야 한다.

1. **`BACKGROUND_MODEL_ID`가 상수다.** 역할 규칙으로 바꾸려면 `select_background_model()`이 후보 목록을 받아 §5.2의 순서로 고르게 해야 한다. `BackgroundModelSelection.model_id`는 "항상 요구 모델"이 아니라 "선택된 모델"이 된다.
2. **게이트가 티어다.** `BACKGROUND_REQUIRED_TIER = ADVANCED_LOCAL`은 "RAM ≥ 32 AND VRAM ≥ 12"라는 **간접 지표**다. 실제 조건은 "이 모델이 예산에 들어가는가"다. 12 GB 카드에서 27B가 KV를 확보하지 못할 수 있으므로, 티어 게이트는 필요조건으로만 남기고 `fit` 계산이 최종 판정을 해야 한다.
3. **카탈로그의 역할 선언이 모순이다.** `local/qwen2.5-coder-1.5b-gguf`와 `local/qwen2.5-coder-7b-gguf`는 `background_worker`, `memory_distiller`, `compactor` 역할을 **선언하고 있다**(`catalog.json`). 그러나 `rank_models()`는 `BACKGROUND_ROLES`에 속한 역할을 받으면 `BackgroundModelUnavailableError`를 던진다. 즉 두 모델은 "백그라운드를 맡을 수 있다"고 선언되어 있으면서 "백그라운드 역할로는 절대 선택되지 않는다". 이 모순은 새 규칙에서 해소된다 — 그 역할 선언이 바로 승인 목록의 근거가 된다.
4. **가중치 크기 표기가 레지스트리와 어긋난다.** `LOCAL_TIER_QUANTIZATION`은 27B 항목을 "PQ2_0 (Ternary 2.13 bpw, VRAM 6.7GB)"로 적지만, 같은 양자화의 레지스트리 `weights_bytes`는 7,206,168,928 B ≈ 6.71 GiB다. 즉 `LOCAL_TIER_QUANTIZATION`의 "VRAM 6.7GB"는 가중치 크기와 사실상 같은 값을 GB로 적은 것이고, 적재 예산(가중치 + 런타임 버퍼 1.21 GiB + KV)과는 다른 것을 잰다. 이 문서는 레지스트리 값을 쓰고, "VRAM 6.7GB" 표기는 적재 예산으로 인용하지 않는다.

### 5.5 사용자에게 보이는 문장

- 8 GB: "백그라운드 요약은 `{bg_model}`(1.5B급)으로 실행됩니다. 이 PC의 예산에서 3B급은 포그라운드와 함께 올릴 수 없습니다."
- 12 GB: "백그라운드 요약은 `{bg_model}`으로 실행됩니다."
- 불가: "백그라운드 요약은 이 PC에서 실행되지 않습니다: `{사유}`. 대신 규칙 기반 축약을 사용하며, 모델 호출은 없습니다."

어느 경우에도 "Bonsai가 없어서"라고 말하지 않는다. 사용자는 모델 이름을 몰라도 되고, 알아서도 안 된다.

#### 6.2.1 가짜 런타임 어댑터

규칙층 테스트는 `llama.cpp` 없이 돌아야 한다. 이를 위해 런타임을 다음 네 동작만 가진 인터페이스로 좁힌다.

```
RuntimeAdapter = {
  load(model_id, ctx, gpu_layers) -> handle | LoadError,
  unload(handle) -> None,
  measure_occupancy(handle) -> bytes,
  free_vram() -> bytes
}
```

- **가짜 어댑터**는 `measure_occupancy`에 픽스처 점유량(예: 7B+1.5B = 6.4 GiB **[측정]**)을 돌려주고, `free_vram`을 스크립트대로 움직인다. 이로써 V-05·V-06·V-17을 GPU 없이 재현한다.
- **스필 감지**는 어댑터의 계약이다. 실제 런타임에서는 "적재 후 `memory.free`가 예산 안에서 예상대로 줄었는가"로 판정한다. 예상보다 덜 줄었거나 적재 후 지연이 급증하면 스필로 기록한다. 가짜 어댑터는 `spilled=true`를 직접 돌려준다. 이 플래그가 **테스트에서 스필을 관찰 가능한 사건으로 만든다** — 그렇지 않으면 "스필이 없었다"를 주장할 방법이 없다.
- 이 인터페이스는 `[대기]`다. 현행 코드에는 런타임 추상화가 없다(인벤토리 P-03, P-09).

| --- | --- | --- | --- | --- | --- |

### 6.4 이 PC에서 오늘 실행 가능한 범위

**오늘 실행 가능(코드 작성 후 즉시):**

- M-01~M-16 프로브를 실제로 실행해 `SP-04`에 해당하는 측정값을 얻는 것. 단 M-09(Vulkan)는 런타임이 없어 `vulkaninfo`도 없으므로 `Unknown`이 정상 결과다.
- V-01, V-02, V-03, V-05~V-08, V-09~V-15: 전부 주입 프로필 또는 실제 측정으로 검증 가능. GPU를 사지 않아도 된다.
- V-11: 이 PC는 실제로 "런타임 없음, 가중치 없음"이므로 **실측으로** 확인된다. 인벤토리 §0.2가 이미 이 상태를 기록했다.
- V-14: 현행 `select_background_model()`이 `unavailable`을 반환하는 것을 실제로 관찰할 수 있다(`test_this_machine_reports_background_bonsai_unavailable`가 이미 이 주장을 고정하고 있다).

**설치 후 가능(디스크 182.6 GB 여유 **[측정]** 로 충분):**

- V-19, V-20. 필요한 것은 llama.cpp Vulkan 프리빌드 35.92 MB **[측정]** 와 7B Q4_K_M 약 4.36 GiB **[측정]** 다. 둘 다 이 PC에 **아직 없다**.
- V-23. 외부 모니터를 dGPU 출력에 직결하면 `display_attached=true` 분기를 실측할 수 있다.

**이 PC에서 불가능:**

- V-04, V-16~V-18, V-21, V-22. 12/16/24 GB 카드, iGPU 전용 기기, 다른 드라이버의 WDDM 동작이 필요하다.
- 어떤 모델의 처리량·품질. 이 문서는 그 값을 검증 대상으로 삼지 않는다.

### 6.5 골든 튜플

릴리스는 `SP-00`~`SP-14` 각각에 대해 기대 튜플을 고정한다. 테스트는 "튜플이 골든과 같다"를 확인한다. 골든은 파라미터가 바뀌면 함께 갱신되어야 하며, 갱신 없이 파라미터만 바꾸면 테스트가 실패한다. 이 규칙이 없으면 파라미터 변경이 조용히 선택을 바꾼다.

골든 튜플은 **성능 기대가 아니다**. "이 측정값에는 이 구성이 선택된다"는 계약이다.

### 6.6 픽스처 카탈로그

§7.3이 밝힌 대로 실제 카탈로그에는 요구량 필드가 없다. 규칙층 테스트는 **픽스처 카탈로그**를 쓴다.

- 픽스처는 `SP-*` 프로필과 짝을 이루는 최소 항목 집합이다: 1.5B급 하나, 3B급 하나, 7B급 하나, 27B급 하나, 그리고 필드가 일부 빠진 항목 하나.
- 각 항목의 `weights_bytes`는 가능하면 레지스트리 값을 쓰고(7B 4,681,514,353 B ≈ 4.36 GiB, 27B 계열 5.54~7.10 GiB), 나머지는 테스트가 자체 정의한 **가상 값**임을 필드 이름에 표시한다(예: `weights_bytes_fixture`). 가상 값이 측정값처럼 보이면 안 된다.
- 픽스처 카탈로그는 릴리스 카탈로그로 **대체되지 않는다**. 실제 카탈로그가 채워지면 같은 테스트가 실제 값으로 다시 돌아야 하고, 그때 골든 튜플이 바뀌는 것이 정상이다. 바뀌지 않으면 픽스처가 현실을 반영하지 못한 것이다.

## 7. 모델 카탈로그 바인딩

### 7.1 카탈로그가 기록해야 하는 것

현행 `catalog.json`은 `id`, `display_name`, `provider`, `roles`, `context_window`, `zero_data_retention`만 갖는다. 이 문서의 선택기는 다음 필드를 **필수**로 요구한다.

| 필드 | 단위 | 출처 | 없으면 |
| --- | --- | --- | --- |
| `weights_bytes` | bytes | 릴리스 매니페스트의 **실제 파일 크기** | 선택 불가(`E-SEL-06`) |
| `weights_sha256` | hex | 매니페스트 | 무결성 검사 불가 → 선택 불가 |
| `quant_label` | 문자열 | 릴리스 | 선택 불가 |
| `n_layer` | 개 | GGUF 메타데이터 | KV 계산 불가 → 선택 불가 |
| `n_kv_head` | 개 | GGUF 메타데이터 | 동일 |
| `head_dim` | 개 | GGUF 메타데이터 | 동일 |
| `size_class` | `small`/`medium`/`large` | 릴리스 선언(성능 순위 아님) | 정렬 불가 → 선택 불가 |
| `min_vram_bytes` | bytes | **유도값**: `weights_bytes + kv(P_CTX_FLOOR) + P_RUNTIME_OVERHEAD_GIB` | 카탈로그 생성 실패 |
| `license` | 문자열 + 버전 | 릴리스 | 다운로드 불가(M-07) |
| `runtime_min_version` | 문자열 | 릴리스 | 선택 불가 |
| `bg_approved` | bool | 릴리스 | 백그라운드 후보 아님 |
| `vendor_status` | `confirmed` / `pending_confirmation` | 릴리스 | `pending_confirmation`은 선택 불가 |
| `download_url` + 크기 | URL + bytes | 릴리스 | 다운로드 불가 |

**`min_vram_bytes`는 저장값이 아니라 생성값이다.** `scripts/verify_customization.ps1`이 이미 `catalog.json`의 드리프트를 검사하므로, 이 필드도 같은 생성 경로에서 계산되어 드리프트 검사에 포함되어야 한다. 손으로 적은 `min_vram_bytes`는 측정값처럼 보이지만 실제로는 추정이다.

### 7.2 선택 시점의 세 가지 거부

```
R-CAT-01 (부재 거부)
  model_id 가 카탈로그에 없으면 선택 불가.
  "비슷한 항목"으로 대체하지 않는다.

R-CAT-02 (실파일 크기 거부)
  선택 시점에 weights_bytes(또는 디스크의 실제 크기)와 예산을 비교한다.
  weights_bytes + kv(P_CTX_FLOOR) + P_RUNTIME_OVERHEAD_GIB > vram_budget_gib 이면
  그 모델은 후보에서 제외하고, 사유에 실제 크기와 예산을 함께 표시한다.
  파일을 잘라 적재하지 않는다. "거의 들어간다"로 진행하지 않는다.

R-CAT-03 (무결성 거부)
  매니페스트 크기·해시와 실파일이 다르면 사용하지 않는다(E-LOC-02).
  크기가 더 크면 예산 계산이 틀린 것이므로, 선택을 중단하고 카탈로그 갱신을 요구한다.
```

R-CAT-02가 "선택 시점"인 이유는 다운로드 시점만으로는 부족하기 때문이다. 사용자가 다른 앱을 실행해 여유 VRAM이 줄면, 어제 들어가던 모델이 오늘 안 들어간다. 판정은 **매번** 한다.

### 7.3 벤더·항목별 확인 대기

**기준일(2026-11-04) 현재 이 저장소에는 모델 요구량 인벤토리 파일이 없다.** `40_AI보고서/` 아래에서 `weights_bytes`·`n_kv_head`·`kv_per_token`를 가진 파일은 이 문서와 `무설정_자동화_설계.md`(부재를 지적하는 문장)뿐이다. 따라서 로컬 항목의 요구량은 **전부** 릴리스 매니페스트 확인 대기이며, 이 문서는 어떤 항목도 `vendor_status = confirmed`로 두지 않는다.

다음은 확인되지 않았으므로 `vendor_status = pending_confirmation`으로 두고, 확인 전에는 선택 후보가 되지 않는다.

| 항목 | 왜 대기인가 |
| --- | --- |
| `local/bonsai-2-27b-pq2`의 `n_layer`/`n_kv_head`/`head_dim` | 레지스트리에 없다. 가중치 크기는 레지스트리의 `weights_bytes`에 있다(27B 계열: PTQ1_0 5,946,648,928 B ≈ 5.54 GiB, PQ2_0 7,206,168,928 B ≈ 6.71 GiB, Q2_0 7,626,008,928 B ≈ 7.10 GiB). 생성물 `catalog.json`에는 `weights_bytes`가 실리지 않으며, KV 계산에 필요한 위 세 필드는 어디에도 없다 |
| `local/qwen2.5-coder-*-gguf`의 `weights_bytes` | 7B 항목은 레지스트리에 `weights_bytes=4,681,514,353`(≈4.36 GiB)·`kv_bytes_per_token=57,344`가 있으나, 1.5B·14B 항목은 `weights_bytes=None`·`pending_confirmation=True`다. 생성물 `catalog.json`에는 어느 쪽도 실리지 않는다 |
| `local/qwen2.5-coder-3b-gguf` | 카탈로그에 **없다**. §2.4가 "3B급"이라고 쓴 것은 등급 서술이고, 실제 선택에는 카탈로그 항목이 필요하다 |
| 0.5B급 이하 항목 | 카탈로그에 없다(§5.3의 4 GB 행) |
| 각 항목의 `license` | 카탈로그에 없다 |
| 런타임 배포물의 라이선스·버전 | 이 문서는 llama.cpp Vulkan 프리빌드를 "가장 작은 실행 경로"로 인용하지만 **[측정: 크기 35.92 MB]**, 그 배포물의 라이선스 표기는 릴리스 게이트에서 확인해야 한다 |

즉 **§2.4의 표는 구조이고, 실제 ID는 카탈로그가 채워진 뒤에 확정된다.** 이 문서는 빈 칸을 추정으로 채우지 않는다.

### 7.4 카탈로그와 선택기의 계약

```
catalog(모델) ──► fit(model, ctx, budget) ──► SelectionDecision
        ▲                                          │
        └──────── verify_customization.ps1 ◄────────┘
                  (드리프트 검사, min_vram_bytes 재계산)
```

- 선택기는 카탈로그 밖의 모델을 **이름으로** 요청받아도 거부한다(`R-CAT-01`).
- 카탈로그는 선택기의 계산을 **포함하지 않는다**. `min_vram_bytes`는 검증용 사본이고, 실제 판정은 매번 `fit()`이 한다.
- `engine/registry.py`의 클라우드 카탈로그와 이 로컬 요구량 카탈로그는 **같은 릴리스 버전**(`CURATED_APP_RELEASE_VERSION = "2026.11.1"`)을 공유한다. 두 파일이 다른 버전을 가리키면 릴리스 게이트가 실패해야 한다.

## 부록 B. 용어

| 용어 | 뜻 |
| --- | --- |
| 예산(budget) | 안전 여유를 뺀 뒤 실제로 쓸 수 있는 GiB. 측정값이 아니라 유도값이다 |
| 적재 비용(resident cost) | 가중치 + KV + 런타임 오버헤드. 모델과 컨텍스트의 함수다 |
| 상주(co_resident) | 두 모델이 동시에 VRAM에 있는 상태. 마진 조건을 통과해야 한다 |
| 교체(swap) | 한 번에 하나만 VRAM에 있는 상태. 리스로 직렬화한다 |
| 리스(lease) | VRAM 적재 권한. 소유자는 하나뿐이다 |
| 승인 목록(approved list) | 백그라운드 역할을 맡을 수 있다고 릴리스가 고정한 카탈로그 항목 집합 |
| 스필(spill) | WDDM이 VRAM 초과분을 시스템 RAM으로 넘기는 동작. 실패가 아니라 조용한 열화다 |
| 골든 튜플 | 프로필별로 고정된 기대 선택. 성능 기대가 아니라 계약이다 |
