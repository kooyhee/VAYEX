> 본 문서는 초기 2평면(로컬 하네스 + 독립 루프백 SSH 서버 게이트웨이: Ubuntu 24.04 RTX 5090 31.36 GiB, 포트 8000/8787/4318) 설계안을 담고 있었으나, 해당 원격 서버 게이트웨이 분리안은 **완전히 폐기/중단(abandoned)**되었습니다. 현재 시스템의 실행 단위는 **두 개**입니다: **Node 호스트**(UI + bridge + 인프로세스 게이트웨이 라이브러리)와, 그 호스트가 `spawn`으로 실행하는 **에이전트 자식 프로세스**(`omp` 18.16.0, Bun stdio JSON)입니다. 폐기된 것은 게이트웨이가 **별도 서버 프로세스**로 서 있던 구성이며, 시스템 전체가 하나의 OS 프로세스라는 서술은 성립하지 않습니다.
> 1. **두 실행 단위 런타임 및 인프로세스 추론 서피스**: `app/lib/inference.mjs`가 게이트웨이 라이브러리 모듈을 복사 없이 인프로세스로 직접 임포트합니다. Node 호스트는 자체 루프백 리스너(기본 4317)에 `/v1/chat/completions`, `/v1/models`, `/v1/selection`, `/healthz`를 마운트하고, baseUrl이 호스트 자체 포트인 앱 소유 `models.yml`(권한 0o600)을 생성하여 `omp` 18.16.0 런타임을 **자식 프로세스로 spawn**합니다. 자식은 그 `/v1`을 루프백 HTTP로 호출하고, 업스트림으로 나가는 요청은 **호스트**가 수행합니다. 과거의 원격 분리 게이트웨이 포트로의 묵시적 폴백은 완전히 제거되었으며, inference 블록이나 엔드포인트 누락 시 `launch_failed`로 기동이 즉시 중단(fail-closed)됩니다.
> 2. **OMP 프로바이더 주입**: OMP 18.16.0은 `--config` 오버레이로 프로바이더를 정의할 수 없으므로(exit 1, "No default model selected" 확인), 앱 소유 에이전트 디렉터리를 `PI_CODING_AGENT_DIR`로 주입합니다. 전역 사용자 모델 설정은 일체 수정하지 않으며 상속된 프로필 환경변수는 제거됩니다.
> 3. **보존 및 검증된 핵심 정책**: 라우트 어휘 체계와 거절 규약, 대화별 독립 명시 동의(위조된 동의 헤더 무시 → `403 consent_required`), 미확인 사용량을 0으로 위조하지 않는 쿼터 예약/정산, 임의 대체를 무력화하는 기본 자격증명 리댁터 최우선 적용, 기동 시 프롬프트 본문 로그 기록 원천 금지, 번들 설정 파싱 불가·추론 블록 누락·오버레이 파싱 불가·coreArgs의 프로바이더/모델 플래그 재정의 시 즉시 실패(fail-closed) 처리가 철저히 보존·검증되었습니다.
> 4. **폐기/중단된 서버 GPU 계획**: 요청 경로 내 Ubuntu GPU 호스트, SSH 터널, 8000/8787/4318 포트 분리, 서버 측 모델 배포(27B/FLUX), GPU 상주(residency) 및 중재(arbitration), 서버 VRAM 기반 티어 강등, GPU 임대(leasing) 계획은 모두 **폐기/중단**되었습니다. 업스트림 프로바이더는 설정 가능하며 **호스트가** 직접 아웃바운드로 연결합니다. 과거 2평면 서버 게이트웨이를 묘사한 다이어그램과 서술은 모두 대체(superseded)되었습니다.
> 5. **선택 라벨 계약 (Selection-Label Contract)**: `GET /v1/selection`은 신원(identity)+경로(route)당 마지막 결정을 프로세스 메모리에만 보관합니다(용량 16, 재기동 시 리셋, 프롬프트 텍스트/키/헤더 미포함, `no-store`). 결정 이전에는 `{"selection":null}`, 신원 누락 시 `401 identity_required`, 미등록 경로는 `400 invalid_route`를 반환합니다. UI는 결정 전까지 `자동`을 표시하고, 결정 후에는 구체 모델 id와 `추론 <등급> · 생각 토큰 <budget>`을 표시합니다. 제한 단위는 메시지별이 아니라 신원+경로별입니다.
> 6. **라이브 검증 및 테스트 수치**: `/healthz`는 `mode: local-harness`, `compatible_endpoint: http://127.0.0.1:4317/v1`을 반환하며, `/v1/models`는 루프백 데모 스텁을 나열하고, UI 라벨은 `자동` → `demo-chat`(`추론 높음 · 생각 토큰 8192`) → `자동` 전환이 확인되었습니다. 폐기된 원격 게이트웨이 포트에는 아무것도 리스닝하지 않습니다. 테스트 통과 현황: 앱 저자 스위트 **154/154 통과**, 게이트웨이 저자 스위트 **148/148 통과**, 브라우저 회귀 테스트 **51/51 통과**, 엔진 과거 기준선 **319개 통과**(신규 재실행 없음).
> 7. **잔여 한계**: 스탠드얼론 게이트웨이 어댑터(`gateway/server.mjs`, `start.sh`)가 저장소에 남아 있으나 앱 내 어떤 코드도 이를 실행하지 않습니다. 레거시 분리 엔드포인트 헬퍼는 mock/no-inference 구성에서만 접근 가능하며, 번들 설정은 기본적으로 루프백 데모 스텁을 가리킵니다.

## 1. 개요 및 설계 철학

### 1.1 플랫폼 핵심 정의
본 플랫폼은 개발자의 자연어 요청으로부터 소프트웨어 개발 라이프사이클(코드 탐색, 설계, 구현, 단위 테스트, 리팩터링, 보안 검토)을 자율 수행하는 **적응형 멀티에이전트 오케스트레이션 및 동적 모델 지능 라우팅 기반 하이브리드 코딩 플랫폼**입니다.

### 1.2 핵심 설계 원칙 (Core Architectural Principles)
1. **Single Distributable Application & Embedded Gateway (단일 배포 애플리케이션 및 내장 게이트웨이):**
   - 로컬 파일 시스템 수정, 터미널 샌드박스 명령 실행, 컴파일 및 테스트 검증 권한은 **DeepSeek Harness**가 독점합니다.
   - 중앙 서버를 외부 독립 서버로 분리해 유지보수 부하를 유발하는 대신, 게이트웨이 라이브러리를 애플리케이션 내부에서 직접 인프로세스(`app/lib/inference.mjs`)로 구동하여 별도 게이트웨이 서버 프로세스 없이 실행합니다. 에이전트 런타임은 이 호스트가 `spawn`하는 자식 프로세스이므로, 하네스의 실행 단위는 **호스트와 자식 두 개**입니다.
   - **(폐기/중단된 과거 2평면 계획 및 진화 사실)** 과거 한때 검토되었던 "로컬 하네스 + 분리된 외부 Ubuntu GPU 서버 게이트웨이(SSH 터널/8000/8787/4318 포트 분리/RTX 5090 기반 27B·FLUX 배포/GPU 임대)" 계획은 **전면 폐기/중단**되었습니다. 현재 아키텍처는 Node 호스트 + 에이전트 자식의 두 실행 단위이며, 호스트가 자체 루프백 리스너(기본 4317)에서 OpenAI 호환 추론 서피스를 호스팅하고 `omp` 에이전트가 루프백 HTTP로 이를 소비합니다. 아래 3.1·3.2절의 초기 기록 및 과거 2평면 서술은 역사적 설계 기록 또는 대체된 내용으로 관리됩니다.
2. **Curated Release Preset over Live Web Scraping (개발자 검증 프리셋 기반 신뢰성):**
   - 런타임에 외부 벤치마크 사이트나 커뮤니티를 무분별하게 실시간 스크래핑/크롤링하거나 복잡한 이기종 서브에이전트를 임의 자동 배치하는 대신, **개발자가 사전에 벤치마크와 비용 효율성을 실측 검증한 카탈로그(`CURATED_APP_RELEASE`)를 번들링하여 주기적 앱 업데이트(`periodic_developer_release`)로 공급**합니다.
   - 의사결정 및 정밀 계획(Planning) 단계는 Benchmark Heaven JevBench(Capability Score) 결과로 개발자가 고정한 결정 모델 프리셋 5종을 활용합니다. 주 결정·계획 모델은 Baseten 경유 `baseten/mammoth-1`(27B, Score 85.2, 결정 단가 USD 0.027 per 1k decisions)이며, 보조 결정은 OpenRouter 경유 `openrouter/drex-max`(84.2, USD 0.031), `openrouter/subq-snap-1.1`(81.9, USD 0.020), `openrouter/d1-ultra`(80.5, USD 0.018), `openrouter/elephant-9b`(70.2, USD 0.012)입니다.
   - 워커 및 구현 단계는 초저비용·초저지연의 `deepseek/deepseek-v4.1-flash-1017`을 주력 코드 생성 모델(Primary Code Generator)로 배치합니다.
   - 승격은 역할만 올리고 모델은 ECPS가 다시 고릅니다(`registry.escalation_role` → `select_model(..., mode="quality")`). 이 저장소의 엔진으로 확인한 결과 `worker → heavy_worker` 승격은 `openrouter/drex-max`, `reviewer → security_reviewer` 승격은 `anthropic/claude-sonnet-4.5`로 귀결됩니다. 따라서 "승격 = 항상 `claude-sonnet-4.5`"로 쓰지 않으며, 플래그십 승격은 리뷰 계열 역할에서만 성립합니다.
3. **Deterministic Orchestration over Stochastic Execution (결정론적 실행 통제):**
   - LLM은 작업 분해 전략과 코드 작성을 담당하되, 실행 제어권(동시성, 타임아웃, 예산 한도, 체크포인트, 롤백, 프라이버시 필터링)은 로컬의 결정론적 오케스트레이터(Deterministic DAG Orchestrator)가 강력하게 통제합니다.
4. **Zero Data Retention Default (프라이버시 우선 라우팅):**
   - 기본 설정에서 데이터 학습 비동의(No-Log, Zero Data Retention) 검증 경로만 허용하며, 사용자 명시적 동의가 있을 때에만 초저비용 프록시 경로로 후보군을 확장합니다.
5. **Hardware-Adaptive Tiered Local Execution Architecture & Zero-Config UX (하드웨어 적응형 4-Tier 로컬 실행):**
   - 사용자 PC 하드웨어 사양(CPU 코어, 가용 RAM, GPU/VRAM)을 프로파일링해 4개 로컬 실행 티어(`Tier 0` 규칙/클라우드 → `Tier 1` 1.5B GGUF → `Tier 2` 7B GGUF → `Tier 3` 고용량 로컬) 중 하나를 결정론적으로 확정합니다. 이 로직은 `engine/hardware_profiler.py`에 구현되어 있으나 **`omp` 대화 경로에는 아직 배선되어 있지 않습니다.**
   - 일반 노트북(RAM < 8GB, Tier 0)은 로컬 LLM이 없는 티어입니다. 규칙 처리와 SQLite FTS5 검색은 로컬에서 수행할 수 있지만 RAM 사용량이 0이라는 뜻은 아닙니다. 모델 추론에 클라우드를 쓰려면 대화별 명시적 동의와 적격 경로가 필요하며, 동의 없이는 `local_only`를 유지하고 실행 불가로 멈춥니다. 보급형~고성능 PC(Tier 1~3)에서는 양자화 GGUF Q4_K_M 모델 및 3진수 양자화 모델 `Prism ML Bonsai 2 27B`를 **백그라운드 전담 후보**로 둡니다. 카탈로그(`engine/registry.py`의 `_bonsai_entries()`)가 이 계열에 부여하는 역할은 `background_worker`·`memory_distiller`·`compactor` 세 개뿐이고 provider는 `local`이며, 포그라운드 코더 역할은 Qwen GGUF 계열이 맡습니다. 벤더가 공개한 처리량·품질 수치는 본 프로젝트가 측정한 값이 아니므로 이 문서는 인용하지 않습니다. 복잡한 파라미터 설정을 요구하지 않는 Zero-Config UX를 기본 보장합니다.

## 2. 전체 시스템 아키텍처 (현행 두 실행 단위 아키텍처: Node 호스트 + 에이전트 자식)

> **[아키텍처 다이어그램 대체(Superseded) 고지]**
> 아래 다이어그램은 과거 2평면(별도 서버 게이트웨이 호스트)을 묘사했던 구 다이어그램을 대체하여, 현재 실제 구현·검증된 **두 실행 단위(Node 호스트 + 그 호스트가 spawn한 에이전트 자식 프로세스)** 흐름을 나타냅니다. 외부 Ubuntu GPU 서버 호스트, SSH 터널링, 8000/8787/4318 포트 분할은 완전히 폐기되었으며, 모든 요청은 호스트 내부의 인프로세스 정책·선택·쿼터·리댁션 파이프라인을 거쳐 **호스트가** 설정된 업스트림으로 직접 전달합니다. 브라우저는 두 실행 단위 밖의 클라이언트입니다.

### 2.1 아키텍처 블록 다이어그램

```

                                              |   HTTP / WebSocket
                                              v
+=============================================v=====================================================+
| [실행 단위 1] Node 호스트 `app/server.mjs` - UI + bridge + gateway 라이브러리(인프로세스)         |
| 루프백 리스너 http://127.0.0.1:4317   요구사항 node >= 26 (측정된 런타임 값 아님)                 |
|                                                                                                   |
| +-----------------------------+   +-------------------------------------------------------------+ |
| | UI (app/public)             |   | bridge (HTTP + WebSocket)                                   | |
| | - 단일 작업공간 화면        |   | - spawn(bin, args, ...) -> 실행 단위 2                      | |
| | - 대화별 동의 카드          |   | - 자식과는 stdio(JSON) 스트림으로 대화                      | |
| | - 라벨: 자동 -> 모델 id     |   | - 들어온 /v1/* 는 인프로세스 핸들러로 라우팅                | |
| +-----------------------------+   +-------------------------------------------------------------+ |
|                                                                                                   |
| +-----------------------------------------------------------------------------------------------+ |
| | 인프로세스 추론 엔드포인트  `app/lib/inference.mjs` -> `createGatewayHandler`                 | |
| | - POST /v1/chat/completions : 경로 정책, 쿼터 예약/정산, SSE 중계                             | |
| | - GET  /v1/models           : 허용 모델 목록 (기본: 루프백 데모 스텁)                         | |
| | - GET  /v1/selection        : identity+route당 마지막 결정 16건, no-store                     | |
| | - GET  /healthz             : mode: local-harness, compatible_endpoint                        | |
| +-----------------------------------------------------------------------------------------------+ |
|                                                                                                   |
```

## 3. 계층별 상세 기능 및 컴포넌트 명세

### 3.1 단일 배포 앱 및 오케스트레이션 계층 (초기 설계 — DeepSeek Harness, 현행 구조 아님)
로컬 런타임은 DeepSeek Harness의 Everything-is-a-Plugin 아키텍처를 기반으로 핵심 코어 플러그인을 맞춤형으로 구현·탑재하며, 내장 OpenCodex 게이트웨이를 인프로세스 라이브러리로 결합합니다(현행 구현에서는 게이트웨이 라이브러리가 Node 호스트 안에 있고, 에이전트 런타임은 그 호스트가 spawn한 자식 프로세스입니다).

#### 1) Desktop GUI & 설정 인터페이스
- **모드 선택기 (Mode Selector):**
  - **간편 모드 (Zero-Config Default):** 사용자는 개발할 목표와 대상 디렉터리만 선택합니다. 별도의 설정 없이 Decision Engine이 프롬프트 의도와 복잡도를 정밀 감지하여 2대 실행 트랙 중 최적 경로로 즉각 자율 실행합니다.
  - **고급 모드 (Advanced Settings):** 
    - 최적화 목표 설정: `품질 우선(Quality)`, `균형(Balanced, 기본값)`, `비용 우선(Cost)`, `속도 우선(Speed)`.
    - 하드웨어 및 실행 제약: 작업 최대 허용 시간(초), 최대 예산(USD), 서브에이전트 최대 동시 실행 수(코드 상한 `MAX_PARALLEL_WORKERS = 4`이며 그 이상은 `V-06`으로 거부), 실시간 웹 검색 허용 여부.
    - 개인정보 보호: 데이터 학습 동의 토글(`학습 비동의[기본] / 학습 동의`).
- **실시간 대시보드 (Live Telemetry):**
  - 현재 하드웨어 실행 티어(`Tier 0`~`Tier 3`), 감지된 CPU 코어/가용 RAM/전용 VRAM 및 로컬 메모리 점유 상태.
  - 활성화된 서브에이전트 목록 및 DAG 실행 노드 상태(Pending, Running, Succeeded, Failed).
  - 현재 모델별 누적 토큰(로컬 GGUF Q4_K_M vs 클라우드 입력/출력/캐시 적중률 %) 및 실시간 발생 비용(USD, 로컬 처리 구간 USD 0 반영).
  - 로컬 오케스트레이터의 롤백 및 복구 이벤트 로그.

#### 2) 의사결정 및 계획 모듈 (Intelligence Planner - 2-Track 파이프라인 & Zero-Config 자동화)
- **Zero-Config Mode Inferencer (`auto_infer_mode`):**
  - 사용자가 최적화 모드(Quality/Cost/Speed/Balanced)를 수동 설정할 필요 없이, 프롬프트 의도와 코드베이스 복잡도를 정밀 감지하여 최적의 실행 구성을 결정론적으로 자동 할당합니다.
- **프롬프트 특성 기반 2대 자율 실행 트랙 (`classify_execution_track`):**
  - **트랙 1. 간단/명확한 작업 (Direct Execute Track):**
    - 대상 파일이 명시적이거나 단순 버그 수정/함수 추가/오타/린트 등 지시가 명확한 작업.
    - 불필요한 사전 조사나 기획 비용(USD 0)을 생략하고, 로컬 티어(Tier 1~3 GGUF Q4_K_M) 또는 주력 코드 생성 모델(`deepseek/deepseek-v4.1-flash-1017`)을 통해 **즉시 작업/구현 및 단위 테스트 검증**을 수행합니다. (Fast-Path 단일 노드 또는 최소 2노드 직행)
  - **트랙 2. 복잡/불명확한 작업 (Survey & Plan Track):**
    - 아키텍처 재설계, 다중 파일 리팩터링, 원인 미상의 결함, "어떻게 구현할지 조사/분석" 등 탐색적 요구사항.
    - **1단계: 심층 사전 조사 노드(`researcher` / `planner`)**를 선행 배치하여 코드베이스 영향도와 요구사항 명세를 먼저 도출한 후, **2단계: JevBench 기반 고정 결정 모델 프리셋 5종(`baseten/mammoth-1` 주 결정 외 4종)**을 통해 정밀 구현 DAG 계획을 수립하여 계층별 병렬 실행합니다.
- **Decision Engine (Benchmark Heaven JevBench 기반 고정 결정 모델 프리셋 5종 + 주력 코드 생성 + 플래그십 승격):**
  - 의사결정 및 정밀 계획(Planning) 단계는 Benchmark Heaven JevBench(Capability Score) 결과로 검증된 **개발자 고정 결정 프리셋 5종**이 전담합니다:
    1. `baseten/mammoth-1` (27B, Capability Score 85.2, 입력 USD 0.10 per 1M tokens, USD 0.027 per 1k decisions, 전 세계 #3 / 오픈웨이트 #1) - 주 결정·계획 모델 (Primary Decision / Planning Model)
    2. `openrouter/drex-max` (Score 84.2, USD 0.031 per 1k decisions) - 복합 컨텍스트 아키텍처 결정 (Complex Context Architecture Decision)
    3. `openrouter/subq-snap-1.1` (Score 81.9, USD 0.020 per 1k decisions) - 고속 서브태스크 질의 및 분해 (High-speed Subtask Query & Decomposition)
    4. `openrouter/d1-ultra` (Score 80.5, USD 0.018 per 1k decisions) - 고신뢰 추론 라우팅 (High-reliability Reasoning Routing)
    5. `openrouter/elephant-9b` (Score 70.2, USD 0.012 per 1k decisions) - 초경량 1차 필터 (Ultra-lightweight 1st-stage Filter)
  - **주력 코드 생성기 (Primary Code Generator):** `deepseek/deepseek-v4.1-flash-1017` (입력 USD 0.06 per 1M tokens, 출력 USD 0.12 per 1M tokens, 평균 지연 ~450ms)을 대다수 구현 워커 노드의 주력으로 배치합니다.
  - **승격 (Escalation):** 3차 시도에서 역할을 상위 역할로 올리고 `mode="quality"`로 모델을 다시 고릅니다. 구현 워커(`worker → heavy_worker`)는 `openrouter/drex-max`, 리뷰(`reviewer → security_reviewer`)는 `anthropic/claude-sonnet-4.5`로 귀결됩니다(엔진 실행 확인). 즉 플래그십 승격은 리뷰 계열에만 해당합니다.
  - 내장 게이트웨이의 `Curated Built-in Preset Registry` 메타데이터를 기반으로 작업의 요구 지능 수준(1~10)을 산정합니다.
  - 단일/멀티에이전트 여부, 필요한 서브에이전트 수 및 역할(Role) 배분, 모델 및 추론 강도(Low, Medium, High)를 원샷 결정합니다.
- **Planning Engine:**
  - 복합 작업에 대해 선행-후행 의존 관계를 정의한 유향 비순환 그래프(DAG)를 JSON 스키마 형태로 생성합니다.

#### 3) 로컬 결정론적 오케스트레이터 (Deterministic Local DAG Orchestrator)
- **Plan Validator:** Planning Engine이 생성한 DAG 노드가 실제 존재하는 도구인지, 순환 참조가 없는지, 지정된 예산 상한선 내에 들어오는지 정적 검증합니다. (`dag_orchestrator.validate_plan`에 구현)
- **DAG Scheduler & 병렬 실행 (Parallel DAG Execution):**
  - 의존성이 해소된 노드를 탐색하여 동시성 제약 내에서 위상 정렬 기반 계층별 병렬 실행 큐에 디스패치합니다. **동시성 기본값은 `max_parallelism = 4`, 서브에이전트 상한은 `MAX_PARALLEL_WORKERS = 4`이며, 8까지 확장하는 설정은 코드에 없습니다.**
  - 선후 관계가 없는 독립 태스크를 병렬로 동시 수행합니다. **"Wall-clock 대폭 단축"은 측정값이 없으므로 성과로 쓰지 않습니다.**
- **Budget & Rate Controller:** 계획 추정치가 `max_budget_usd`를 넘으면 **실행 전에 거부**합니다(`validate_plan`). 실행 후 원장은 실제 비용과 `unknown`을 구분해 기록합니다. **비용 초과 시 사용자 승인을 요청하는 분기와 토큰 버킷 기반 호출률 제어는 아직 구현되어 있지 않습니다**(`V-07`은 거부만 합니다).
- **Workspace Manager:** 병렬 실행되는 노드 간 파일 쓰기 충돌을 막기 위해 경로별 락과 파일 스냅샷·복원(`FileIsolationWorkspace`)을 사용합니다. Git 워크트리 격리는 설계 항목이며 구현되지 않았습니다.
- **State Checkpoint:** 노드 실행 전 파일 스냅샷을 남기고 실패 시 해당 노드의 스냅샷을 복원하며, 계획이 완료되지 못하면 `finally`에서 계획 전체를 되돌립니다(복원 충돌 시 `overall_status="rollback_conflict"`). **"0.1초 내 무손실 롤백"은 측정값이 아니므로 보장으로 쓰지 않습니다.**
- **Verification Engine & Serving-Path Parity Verifier:**
  - 단위 테스트(pytest, jest, vitest 등) 및 린터를 자동 실행합니다.
  - **AST 기반 심볼 슬라이싱(AST-based Symbol Slicing):** 파일 전체를 프롬프트에 주입하는 대신 Language AST 파서로 호출 관계에 있는 함수, 클래스, 타입 시그니처만 정밀 발췌하여 검증 컨텍스트를 구성합니다. 구현은 `engine/`의 슬라이서에 있고 단위 시험이 존재하지만, **"토큰 70~85% 절감"은 측정값이 아니라 설계 목표다.** 이 저장소에는 그 절감률을 실측한 기록이 없으므로 성과로 인용하지 않습니다.
  - **서빙 경로 일치 검증기(Serving-Path Parity Verifier):** 로컬 하네스 테스트를 통과한 결과물이 프로덕션 서빙 경로(API/스키마 계약, 런타임 의존성, 보안 규격)와 일치하는지 커밋 직전 확인하는 것을 목표로 하는 **설계 항목**입니다. "100% 일치를 자동 검증한다"고 주장하지 않습니다.
  - 실패 시 에러 로그를 분석하여 동일 모델로 1·2차 재시도 → 3차에서 역할 승격(모델은 ECPS가 재선택: 구현 워커는 `openrouter/drex-max`, 리뷰는 `anthropic/claude-sonnet-4.5`) → 국소 재계획의 3단계 자율 복구를 설계로 둡니다. 재시도·승격·롤백은 `dag_orchestrator`에 구현되어 있으나, 실제 모델 호출은 러너 콜백으로 주입되어야 합니다.

#### 4) 하이브리드 컨텍스트 & 메모리 엔진
- **AST 파서 기반 심볼 슬라이싱:** 파일 전체를 컨텍스트에 밀어 넣지 않고, TypeScript/Python AST를 분석하여 호출 관계에 있는 함수·인터페이스 시그니처만 발췌 슬라이싱합니다.
- **경험 기반 비용 제어 및 도구 가지치기 (TokenEconomizer 연계):**
  - **마이크로 스킬(Micro-Skills) 레지스트리:** 저장소 내 반복되는 환경 정보, 테스트 커맨드, 빌드 스크립트 성공 이력을 FTS5와 함께 영속화하여 에이전트가 탐색 없이 즉시 실행하도록 지원합니다.
  - **동적 도구 가지치기(Tool Pruning):** 실행 대상 태스크에서 불필요한 도구의 정의를 시스템 프롬프트에서 제거하는 것을 목표로 합니다. **"매 턴 300~800 토큰 절감"은 측정값이 아니라 설계 추정입니다.**
  - **루프 가드(Loop Guard):** 동일 에러 반복 발생 시 조기에 판단하여 방향 전환(Redirect)을 지시함으로써 무한 루프로 인한 토큰 낭비를 차단합니다.
- **SQLite + FTS5 전문 검색 (FTS5 Sanitized Search & 무임베딩 고속 메모리):**
  - 별도의 무거운 로컬 벡터 임베딩 모델 없이도 프로젝트 규칙과 이전 턴 결정 사항을 SQLite FTS5(Full-Text Search 5) 인덱싱으로 조회합니다. **"5ms 이내"는 이 저장소에서 측정한 값이 아니므로 지연 보장으로 쓰지 않습니다.**
  - 사용자 입력 쿼리 및 소스코드 검색어에 포함된 특수문자, 따옴표, 불리언 예약어를 사전에 이스케이프/정제하는 새니타이즈(Sanitization) 처리를 적용하여 FTS5 문법 에러 및 SQL 인젝션을 원천 차단하고 BM25 랭킹 검색의 안정성을 보장합니다.
- **계층 압축 (설계):** 컨텍스트가 임계치를 초과하면 원본 대화·도구 출력을 로컬에 아카이빙하고 [목표, 완료된 수정, 핵심 결정, 미완료 과제] 블록만 유지하는 방식을 목표로 합니다. 구현된 것은 `engine/aux_tasks.py`의 구조적 압축(모델 호출 없이 최신 턴만 남기는 경로)과 예산 내 요약 경로이며, **"100만 토큰급 무손실 압축"은 측정된 사실이 아닙니다.**

### 3.2 내장 게이트웨이 계층 (초기 설계 — Embedded OpenCodex Gateway Core, 현행 구조 아님)
DeepSeek Harness 앱 프로세스 내에 직접 통합(In-Process)된 초경량, 고동시성 API 프록시 및 프리셋 레지스트리 모듈입니다.

#### 1) In-Process API Proxy & Streaming Engine
- **보안 및 키 보호:** 실제 LLM 공급자(OpenRouter, Anthropic, OpenAI, A6API 등)의 API 키는 로컬 환경변수 또는 보안 볼트에만 암호화 보관되며 클라이언트 코드 로직에 직접 하드코딩되지 않습니다.
- **양방향 스트리밍 중계:** SSE(Server-Sent Events) 파이프라인으로 생성 토큰을 UI와 오케스트레이터에 순차 중계하는 구조를 목표로 합니다. 브리지는 실제 `omp` 세션의 스트리밍 이벤트를 WebSocket 프레임으로 전달하는 것까지 시험했으나(`app/` `npm test`), **"10ms 이하 지연"은 측정값이 아니므로 성능 근거로 쓰지 않습니다.**
- **정밀 과금 원장:** 공급자 응답의 실제 usage 토큰(입력, 출력, 캐시 적중 토큰)을 파싱하여 세션별 정확한 비용을 계산하고 로컬 감사 로그에 영구 기록합니다.

#### 2) Strict Privacy Policy Enforcement Engine
- 요청의 `X-Privacy-Consent` 상태를 게이트웨이 단에서 강제 검증합니다.
  - `false` (학습 비동의, 기본값): 데이터 비학습 및 Zero Data Retention이 공식 계약된 OpenRouter의 No-Log 엔드포인트로만 라우팅합니다. 기타 프록시 경유 요청은 403 Forbidden으로 원천 차단합니다.

#### 4) 지능형 모델 라우팅 수학적 공식 (Expected Cost-per-Success, ECPS)
단순한 1회성 토큰 단가나 벤치마크 점수만을 기준으로 모델을 선택하면, 실패 후 재시도로 인한 누적 비용 폭증이나 지나친 오버스펙 모델 사용에 따른 낭비가 발생합니다. 본 플랫폼은 성공 작업당 기대 비용을 수학적으로 모델링하여 최적의 모델 후보를 결정론적으로 라우팅합니다.

##### (1) ECPS 기본 목적함수
각 서브에이전트 역할(role)과 후보 모델 m에 대해 성공 작업당 기대 비용 ECPS(Expected Cost-per-Success)는 다음과 같이 정의됩니다.

ECPS(m) = E[Cost(m)] / E[P_success(m)]

여기서:
- E[Cost(m)]: 해당 태스크 1회 실행 시 발생하는 기대 API 호출 비용 (USD, 온디바이스 로컬 처리 노드는 USD 0)
- E[P_success(m)]: 해당 모델이 해당 성격의 작업을 1회에 성공(테스트 및 린트 통과)시킬 사후 기대 확률 (0 < P_success ≤ 1)

##### (2) 프롬프트 캐시 적중률(α)을 반영한 비용 모델
Prefix Caching Alignment에 따라 정적 시스템 프롬프트 및 FTS5 지식이 공급자 캐시에 보존되는 비율을 프롬프트 캐시 적중률 α (0 ≤ α ≤ 1)로 정의할 때, 기대 비용 E[Cost(m)]은 다음과 같이 계산됩니다.

E[Cost(m)] = C_input(m, α) · N_in + C_output(m) · N_out

여기서 유효 입력 토큰 단가 C_input(m, α)는:
C_input(m, α) = (1 - α) · C_in_miss(m) + α · C_cache_read(m)

- C_in_miss(m): 기본 프롬프트 입력 단가 (USD per 1M tokens)
- C_cache_read(m): 캐시 적중(Cache Read) 입력 단가 (USD per 1M tokens, 통상 기본 단가의 10~25%)
- C_output(m): 생성 토큰 단가 (USD per 1M tokens)
- N_in, N_out: 해당 서브에이전트 노드의 예상 입력 및 출력 토큰 수 (M tokens 단위)

캐시 적중률 α가 0.8 수준에 도달하면 입력 비용이 최대 75%까지 절감되어, 플래그십 모델이라도 특정 반복 작업에서 경량 모델보다 더 낮은 ECPS를 가질 수 있습니다.

##### (3) Beta-Bernoulli 온라인 성공률 갱신 (Bayesian Online Updates)
정적 벤치마크는 실제 사용자 코드베이스의 특수성을 완벽히 반영하지 못하므로, 각 모델의 성공 확률 P_success(m)은 런타임 실행 결과에 따라 베이지안 방식으로 실시간 업데이트됩니다.

1. 사전 분포 (Prior Distribution):
   P_success(m) ~ Beta(a_0, b_0)
   - a_0, b_0는 개발자 검증 카탈로그의 초기 성공률 및 콜드스타트 가중치로부터 도출됩니다.
   - 예: 초기 성공률 기대치가 96%인 경우 a_0 = 7.68, b_0 = 0.32 로 설정.

2. 관측 및 사후 갱신 (Posterior Update):
   - 해당 모델의 최근 n회 시도 중 k회 성공(1), n - k회 실패(0)가 관측되었을 때:
   - 사후 분포: Beta(a_n, b_n) = Beta(a_0 + k, b_0 + n - k)
   - 사후 기대 성공률 (Posterior Mean):
     E[P_success(m)] = (a_0 + k) / (a_0 + b_0 + n)

3. 런타임 장애 자동 회피 메커니즘:
   - 특정 모델이 문법 파싱 에러나 환각으로 연속 실패할 경우, b_n이 급격히 증가하여 E[P_success(m)]가 즉시 감소합니다.
   - 이에 따라 ECPS(m)의 분모가 작아져 비용 지수가 커지고, 이후 선택 순위에서 그 모델이 밀려납니다. 실제로 구현된 것은 `record_outcome()`이 성공·실패를 Beta 사후분포에 반영하고 `expected_cost_per_success()`가 다음 선택에서 그 값을 쓰는 것까지이며, **실행 중인 요청을 다른 모델로 자동 전환(failover)하는 경로는 없습니다.** 실행 중 교체에 해당하는 것은 3차 시도에서 역할을 승격하는 `select_escalation_model`뿐입니다.

##### (4) 최적화 모드별 라우팅 선택 규칙
적격 후보군 M_compliant(프라이버시 및 역할 충족 모델 집합) 내에서 최종 모델 m*은 선택 모드에 따라 결정됩니다.

- 비용 우선 (Cost Mode):
  m* = argmin_{m ∈ M_compliant} ECPS(m)
- 균형 모드 (Balanced Mode, 기본값):
  가성비 지수 = Intelligence_Index(m) / (ECPS(m)^0.35)
  m* = argmax_{m ∈ M_compliant} [가성비 지수]
- 품질 우선 (Quality Mode):
  m* = argmax_{m ∈ M_compliant} Intelligence_Index(m)  (동점 시 min ECPS)
- 속도 우선 (Speed Mode):
  m* = argmin_{m ∈ M_compliant} E[Latency_ms(m)]  (단, ECPS(m) ≤ Budget_threshold)

- **결정 파이프라인 순서:** ① `elephant-9b` 1차 필터·사전 분류 → ② `subq-snap-1.1` 서브태스크 분해 → ③ `mammoth-1` 주 계획 확정 → ④ 필요 시 `drex-max`(대형 컨텍스트) / `d1-ultra`(신뢰성 재검증) 보조 투입. 이 순서는 프리셋에 고정되어 런타임 변동이 없습니다.

### 3.3 하드웨어 적응형 4-Tier 로컬 실행 계층 (Hardware-Adaptive Tiered Local Execution)
단일 배포 앱이 저사양 사무용 노트북부터 고성능 워크스테이션까지 동일한 기능 집합을 제공하기 위해, 로컬 실행은 다음 **4단계 티어(Tier 0 순수 규칙/클라우드 → Tier 1 1.5B GGUF → Tier 2 7B GGUF → Tier 3 고용량 로컬)**로 구분됩니다. `engine/hardware_profiler.py`의 `LOCAL_TIER_MODEL_IDS`는 Tier 1 = `local/qwen2.5-coder-1.5b-gguf`, Tier 2 = `local/qwen2.5-coder-7b-gguf`, Tier 3 = `local/bonsai-2-27b-pq2`를 가리키고, `LOCAL_TIER_QUANTIZATION`은 Tier 1·2를 Q4_K_M, Tier 3를 PQ2_0(삼진 2.13 bpw)로 둡니다. 다만 **Tier 3가 가리키는 Bonsai 2 27B는 백그라운드 3역할만 선언**하므로 포그라운드 노드로는 실행되지 않고, 카탈로그에 32B 항목은 없습니다. 실제 포그라운드 로컬 상한은 7B GGUF이며, 14B 항목은 카탈로그에 있으나 가중치가 미확인(`pending_confirmation=True`)이라 적재 판정을 통과하지 못합니다.

#### 1) 티어별 명세 (Tier Specification)
| 티어 | 명칭 | 하드웨어 기준 | 로컬 엔진 / 모델 | 로컬 담당 역할 | 비용·프라이버시 효과 |
|---|---|---|---|---|---|
| **Tier 0** | Pure Rules / Cloud | RAM < 8GB, CPU-only | 로컬 LLM 0개 · AST 파서 · Regex · SQLite FTS5 | 정적 구문 분석, 심볼 슬라이싱, 규칙 기반 포맷팅·로그 정제 | LLM 가중치 적재 없음(앱·검색의 RAM 점유까지 0이라는 뜻은 아님). 클라우드 추론은 대화별 명시 동의 후에만 가능하며, 미동의 시 `local_only`를 유지하고 모델 실행은 중단 |
| **Tier 1** | Lightweight Local SLM | RAM 8~16GB 또는 VRAM 2~4GB | 코드가 고정한 프리셋: `local/qwen2.5-coder-1.5b-gguf` (Q4_K_M). 레지스트리에서 `weights_bytes=None`·`pending_confirmation=True`이므로 적재 판정을 통과하지 못한다. 문서의 초기 후보였던 3B 항목은 카탈로그에 없다 | AST 심볼 트리아지, 변경 파일 분류, 마이크로 함수 생성, 단순 수정 (가중치 확인 전에는 실행 불가) | 로컬 처리 노드는 카탈로그 단가 USD 0 (지연 수치는 측정값이 없어 적지 않는다) |
| **Tier 2** | Standard Local LLM | RAM >= 16GB 또는 VRAM >= 6GB | 코드가 고정한 프리셋: `local/qwen2.5-coder-7b-gguf` (Q4_K_M, 레지스트리에 가중치 바이트 4,681,514,353 기록). 8B 항목은 카탈로그에 없다 | Track 1 구현, 1차 코드베이스 조사, 단위 테스트 스캐폴딩 | 로컬 단가 USD 0. **"클라우드 호출량 60~75% 절감"은 측정값이 아니라 설계 목표이므로 성과로 인용하지 않는다** |
| **Tier 3** | Large Local (27B급) | RAM >= 32GB, VRAM >= 12~24GB | 카탈로그 기준: Bonsai-2 27B 세 양자화(PTQ1_0/PQ2_0/Q2_0, 262K 컨텍스트)는 **백그라운드 전담**이며 포그라운드 역할이 없다. 포그라운드 로컬 상한은 `local/qwen2.5-coder-7b-gguf`, `planner` 계열은 `local/qwen2.5-coder-14b-gguf`(가중치 미확인·`pending_confirmation=True`). **32B 항목은 카탈로그에 없다** | 백그라운드 압축·증류·제목 생성(승인 목록에서 적재 산술로 선택). 포그라운드 전 구간 로컬 완결은 현재 코드로 성립하지 않는다 | 로컬 단가 USD 0, 클라우드 경로를 쓰지 않으므로 반출 없음. **Bonsai 27B의 VRAM 점유·처리량은 이 프로젝트가 측정한 값이 아니다**(아래 2항의 경계 고지 참조) |

#### 2) Tier 3 로컬 후보 명세: Prism ML Bonsai 2 27B — 현재 상태와 경계
이 절은 **후보와 카탈로그 사실**을 적습니다. 아래 수치는 이 프로젝트가 해당 가중치를 적재해 측정한 값이 아니며, 측정값으로 인용하지 않습니다.

1. **`engine/registry.py`에 기록된 사실 (`_bonsai_entries()`):**
   - 27B 계열 세 양자화의 가중치 바이트와 262,144 토큰 컨텍스트가 레지스트리에 적혀 있습니다. 예: `local/bonsai-2-27b-pq2` = 7,206,168,928 bytes(≈6.71 GiB), KV 65,536 bytes/token, `runtime_kind` = PrismML 포크(ggml type 142/143). Q2_0는 stock llama.cpp b11556 이상이 필요합니다.
   - **주의: 생성물 `packaging/customization/catalog.json`에는 이 필드들이 없습니다.** 카탈로그 항목은 `id`·`display_name`·`provider`·`roles`·`context_window`·`zero_data_retention`만 담습니다(생성기 `packaging/customization/generate_catalog.py`). 가중치 크기·KV·런타임 조건은 레지스트리에만 있습니다.
   - 이 계열 10개 항목은 모두 provider `local`, `bg_approved=True`, 역할은 `background_worker`·`memory_distiller`·`compactor` **셋뿐**입니다. 포그라운드 코더 역할이 없습니다.
   - 2B/4B/9B 항목은 벤더가 벤치마크 수치를 공개하지 않아 `benchmark_note="model card publishes no benchmark numbers; quality is unquantified"`로 기록되어 있습니다.
2. **미측정 사실 (측정으로 승격하지 말 것):**
   - 이 저장소의 어떤 시험도 Bonsai 가중치를 적재해 처리량·지연·품질을 측정하지 않았습니다. 따라서 생성 속도(tok/s)·프리필 속도·TTFT·벤치마크 점수·FP16 대비 보존율을 본 문서의 성능 근거로 쓸 수 없습니다.
   - "6.7 GiB 상주 → KV 캐시 16 GiB 확보"는 **산술적 여유 계산**이며 적재 후 실제 점유 측정이 아닙니다. 적재 산술의 판정 자체는 `vram_budget.select()`에 구현되어 있고, 런타임 부재·가중치 미확인·미적재 시 후보를 실행 가능으로 승격하지 않습니다.
3. **운용 설계:** Tier 3에서는 이 계열을 백그라운드 인지 작업(압축·제목·증류·트리아지)의 후보로만 두고, 포그라운드 계획·구현·리뷰는 역할을 선언한 Qwen GGUF 계열이 맡습니다. 백그라운드 후보 선택은 고정 이름이 아니라 `select_background_model()`의 적재 산술이 정합니다.
4. **상호 보완(설계 의도, 미검증):** 로컬 의사결정용 모델과 백그라운드 전담 모델을 한 GPU에 함께 두는 구성은 **설계 목표**이며, 이 저장소에서 동시 상주·핫스왑을 실행해 확인한 기록은 없습니다.

#### 3) HardwareProfiler 및 결정론적 티어 확정
- 앱 기동 시 0.2초 이내에 다음 항목을 자동 측정합니다: CPU 물리 코어/논리 스레드/SIMD 지원(AVX2, AVX-512, ARM NEON), 전체·가용 물리 RAM, DirectML/CUDA 가용 디바이스와 전용 VRAM, 모델 가중치 캐시용 여유 디스크.
- 측정 결과는 결정론적 판정 함수 `determine_local_tier(spec, override_tier=...)`(내부 분류는 `_classify_hardware`)로 전달되어 Tier 0~3 중 하나로 확정됩니다. 엔진은 티어 정보를 `LocalExecutionTierInfo`(`registry_model_id`, `capability_tier`, `uses_local_llm`)로 넘겨 모델 후보를 제한합니다. `n_gpu_layers`·스레드 수 같은 로컬 런타임 플래그를 실제로 계산해 주는 배선은 이 저장소에 없습니다(로컬 추론은 외부 OpenAI 호환 서버가 담당).
- 확정된 티어는 UI 상태 표시의 입력으로 쓰입니다. 아래 Tier 3 예시 문자열은 **초기 화면 설계안**이며, 카탈로그의 Bonsai 27B는 포그라운드 역할을 선언하지 않으므로 현재 코드가 만들 수 있는 표시가 아닙니다: `[Tier 3: Prism-ML-Bonsai-2-27B | VRAM 6.7GB/24.0GB | KV Cache: 16.2GB Free]`(설계 예시).

#### 4) 다층 강등 및 클라우드 승격 사다리 (Graceful Degradation — 설계)
**이 절의 사다리는 설계이며, 엔진에 자동 강등 루프가 구현되어 있지 않습니다.** `determine_local_tier`는 하드웨어로 티어를 한 번 정하고 `override_tier`가 있으면 그 값을 쓰되 `capability_tier`에 실측 가능 티어를 함께 남기는 데까지이며, 토큰/초 하한이나 OOM 징후를 감시해 티어를 내리는 런타임 루프는 없습니다. 로컬 서빙 불가·가중치 미확인·적재 불가(no-fit)는 강등이 아니라 **대체 없는 비실행 상태**입니다.
1. **컨텍스트 축소:** 로컬 추론 중 Out-of-Memory 징후가 관측되면 AST 파서로 컨텍스트를 핵심 심볼 단위까지 줄이는 것을 목표로 합니다.
2. **티어 강등:** 메모리 부족이 지속되거나 생성 속도가 허용 하한(예: < 5 tokens/s, 이 값 역시 측정된 임계가 아니라 설계 파라미터)에 미달하면 하위 티어로 내리는 규칙을 둡니다. **이 강등 루프는 아직 구현되지 않았습니다.**
3. **클라우드 승격(구현됨, 엔진 평면):** 오케스트레이터는 3차 시도에서 역할만 상위로 올리고(`select_escalation_model`) `mode="quality"`로 모델을 다시 고릅니다. 확인된 귀결은 `worker → heavy_worker` = `openrouter/drex-max`, `reviewer → security_reviewer` = `anthropic/claude-sonnet-4.5`입니다. 이 승격은 Python 엔진 경로이며 `omp` 대화 런타임에 배선되어 있지 않습니다.

## 4. 데이터 흐름 및 시퀀스 다이어그램

> **[시퀀스 다이어그램 현행화 고지]**
> 아래 시퀀스는 **Node 호스트 + 에이전트 자식** 두 실행 단위 체제에서의 요청 수명주기를 나타냅니다. 과거 별도 서버 호스트로의 SSH 포워딩 다이어그램은 완전히 대체(superseded)되었습니다. UI는 호스트가 서빙하고, `omp` 런타임은 그 호스트가 spawn한 자식 프로세스로서 호스트에 마운트된 엔드포인트를 루프백 HTTP로 호출하며, 인프로세스 정책·선택·쿼터 통제 후 **호스트가** 설정된 업스트림으로 직접 아웃바운드 통신합니다.

게이트웨이 모듈이 인프로세스에서 고른 모델·추론 강도를 로컬 하네스와 UI가 되읽는 유일한 경로입니다.


- 로컬 브라우저/UI는 턴 완료 시 루프백 엔드포인트에서 이 결정을 되읽어, 결정 이전에는 `자동`을 표시하다가 결정 후에는 구체 모델 id와 `추론 <등급> · 생각 토큰 <budget>`으로 표시합니다.

## 6. 보안, 장애 복구 및 성능 최적화 설계

### 6.1 프라이버시 및 보안 강제 메커니즘
1. **API 키 완전 격리:** 사용자 로컬 환경이나 프론트엔드 번들에는 일체의 상용 API 키가 평문 노출되지 않으며, 단일 배포 앱의 내장 볼트 또는 로컬 환경변수를 통해 안전하게 중계됩니다.
2. **Strict Gateway Enforcement:** `X-Privacy-Consent: false` 요청에 대해 내장 게이트웨이는 라우팅 후보군에서 데이터 저장/학습 가능성이 있는 공급자를 물리적으로 제외합니다. 적격 공급자가 고갈될 경우 즉시 `503 Service Unavailable (No Compliant Zero-Retention Route)` 오류를 반환하여 데이터 유출을 차단합니다.
3. **로컬 파일시스템 샌드박싱:** 로컬 클라이언트에서 에이전트가 실행하는 명령은 프로젝트 루트 디렉터리 내로 엄격히 바운딩되며, 시스템 루트(`/`, `C:\Windows`) 접근 시도를 사전 차단합니다.

### 6.2 3단계 장애 복구 정책 및 검증 엔진 (Recovery & Verification Protocol)
1. **1차 복구 (Local Retry & AST Symbol Slicing):**
   - 단위 테스트 실패 시, 실패 스택트레이스에서 호출 경로 상의 심볼 경계만 AST 파서로 정밀 슬라이싱하여 동일 모델에 컨텍스트로 주입합니다.
   - 전체 파일 대신 필요한 인터페이스 및 에러 유발 심볼만 제공하므로 토큰 소비를 최소화하고 1회 국소 수정을 시도합니다.
2. **2차 복구 (Model Escalation & Serving-Path Parity Verifier):**
   - 동일 모델 재시도 실패 시, Beta-Bernoulli 사후 성공률과 ECPS 평가에 기반하여 상위 플래그십 모델(`anthropic/claude-sonnet-4.5`)로 해당 서브에이전트를 동적 승격합니다.
   - 승격 모델이 생성한 코드는 **Serving-Path Parity Verifier**를 거쳐 프로덕션 API 스키마, 런타임 종속성 규격, 보안 취약점 여부를 엄격히 대조 검증합니다.
3. **3차 복구 (Local Replanning):**
   - 승격 모델에서도 통과하지 못할 경우, 로컬 오케스트레이터가 해당 노드 및 의존 노드에 대해 Planning Engine에 국소 재계획(Sub-DAG Replanning)을 요청하여 노드를 더 세부적인 작업 단위로 재분해합니다.
4. **최종 안전망 (스냅샷 롤백):**
   - 연속 실패가 한도를 넘으면 체크포인트 스냅샷으로 원본 파일을 복원하고 사용자에게 상세 원인을 보고합니다. 복원 자체는 `FileIsolationWorkspace`의 파일 스냅샷 복사로 수행하며, **복원에 걸리는 시간(0.1초 등)은 측정값이 아닙니다.** 3차 복구(승격 모델 재시도)와 4차 롤백의 연속 실패 한도는 설계 기준이며, 실제 승격 실행은 아직 연결되지 않았습니다.

### 6.3 Prompt Cache Alignment 및 저사양 최적화 (철회 및 경계)
1. **Prefix Caching Alignment 및 게이트웨이 `prompt_cache_key` 상태:**
   - 공급자(Anthropic, DeepSeek, OpenAI)의 프롬프트 캐시 적중률 설계를 위해 시스템 프롬프트 -> 프로젝트 지식(FTS5) -> 최근 히스토리 순으로 정적 프리픽스를 배치하는 정렬 원칙은 설계안으로 유효합니다.
   - 외부 툴체인 및 벤치마크 설계 아이디어(Claude Code의 프리픽스 정제, Codex의 바운디드 도구 출력, OpenCode의 컴팩션 리저브, Aider의 컨텍스트 선택/경량 요약)의 1차 비교 조사는 유효하며, 앱 스코프의 제네릭 출력 예산 오버레이는 실제 OMP 명령에 저장 및 선택되었으나, 실측된 토큰 절감량이나 완전한 네이티브 복구는 검증되지 않았습니다. 실험적 바운디드 도구 결과 확장은 **철회 상태로 유지**되며(`config.json`은 `--config omp-overlay.yml`만 전달하고 `--extension` 항목을 넣지 않음을 시험이 고정), 정정된 측정에서 네이티브 아티팩트는 두 변형 모두 원본을 보존했고 확장이 추가한 것은 350–521바이트의 고지 텍스트뿐이었습니다.
   - **게이트웨이 `prompt_cache_key` 철회 고지**: 게이트웨이 모델 역량 게이팅(`supports_prompt_cache_key: true`, OMP 내부 모델 호환성 `supportsPromptCacheKey`와 구별) 기반의 `prompt_cache_key` 연동은 반복된 독립 보안 재검토에서 결함(리댁션 순서 및 에러 분기 우회 위험)이 발견되어 **철회 및 미인도(withdrawn/not delivered)** 처리되었습니다. 추가 수정은 중단되었으며, 해당 기능 활성화 권장은 전부 제거되었습니다. 따라서 사용자 요구사항 2(캐시 최적화)는 부분적(partial) 상태로 귀결됩니다.
2. **SQLite WAL 모드 적용:** 쓰기 작업과 검색 작업이 상호 블로킹되지 않도록 SQLite를 Write-Ahead Logging(WAL) 모드로 구동하여 디스크 I/O 병목을 해소합니다.
